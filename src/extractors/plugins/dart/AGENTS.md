# Dart plugin

Reads `.dart` (Flutter and plain Dart) through a regex `RegexLangSpec` ([index.ts](index.ts)) with a tree-sitter front end (`meta.treeSitter`, [tree-sitter.ts](tree-sitter.ts); `parsing` stays `"regex"`, feature `tree-sitter`, off with `no-tree-sitter:dart`) supplying functions and calls. The language stays on the regex path despite a grammar existing (no grammar compiled cleanly for a tree-sitter-first plugin); the grammar build is described in [parsers/AGENTS.md](../../../parsers/AGENTS.md). A file with syntax errors keeps the regex reading. Callee names through a path carry every name back to the head (`club.league.relegate`).

## Imports, packages and scope

- `importedFile` rule: `package:league/x.dart` resolves to that pubspec package's `lib/x.dart`, other URIs beside the importer; the SDK and downloaded packages are none. `part` files are joined to their library by name ([imports.ts](imports.ts): a directive's start `import`/`export`/`part`, never `part of`). Imports and `part`s that put members in scope by bare name are `ImportInfo.inScope`; a barrel file declaring nothing hands on what it exports, three deep; a `show` list narrows a name.
- Module bindings: [module-bindings.ts](module-bindings.ts) types top-level variables and getters (`GarageGateway get garageGateway => …`) by bare name (`extractModuleBindings`).
- Dead code ([reachability.ts](reachability.ts)): imports name files; types and functions are also reached by name (which joins a `part` file to its library); entries `main`, `bin/`, `web/`. A package that is not an app (no `lib/main.dart`) publishes `lib/*.dart` — everything outside `lib/src/` is public API, not judged.
- Tools: `pubspec.yaml` ([package-manifests.ts](package-manifests.ts), [frameworks.ts](frameworks.ts)); `testCommand`/`projectCommands` ([test-command.ts](test-command.ts)): `flutter test` / `dart test` with `--plain-name` for one marked test.

## Types, getters, setters and extensions

- **Getters.** A getter of a class, mixin or extension is a method of its own in both front ends (`FlagService get flags { _flags ??= FlagService(dio); … }`, `Club get club => Club(id)` — its calls and constructions are its own); a function declared `get` carries `FunctionInfo.getter`; a setter and an operator are none. A getter is read like a field, so [getter-reads.ts](getter-reads.ts) (run from `extractValueFlow`, so both front ends state the same) records each bare name, `this.x` and `receiver.x` read the body makes — never a call, an assignment target, a named argument, a name the function declares itself or a field of its class — as `CallInfo.read: "getter"`. The linker (`resolveReadName`) keeps one only where it resolves, by the reading class and its bases or the receiver's declared type, to a function marked `getter` (a `calls` edge): a getter declared in another file, `this.getter` and `club.badge` join the getter's own calls; a namesake getter of another class, a field or a method handed on draws no edge.
- **Setters** (`set best(Club v) { v.save(); }`, a class's or top-level) are functions named as Dart spells it, `best=`, so they never meet a getter `best`: the tree-sitter reader names the span `best=` (`functionName` + `setter_signature`) and the regex spec has a setter pattern with `rename`. Parameters are typed as any function's; a call on `best` as a field is no call row. A constructor (named or factory) states no field writes — it initializes.
- **Extensions**: [extensions.ts](extensions.ts) gives each instance member the extended type as its receiver (`isReceiver`); the rest of the rules are in that file.
- **Awaited results.** `asyncResultTypes: ["Future", "FutureOr"]`: a local bound to `await repo.find(1)` takes the type inside the `Future<Club>` the callee declares, as C# reads `Task<T>` and JS/TS `Promise<T>`; a `Future` nothing awaits, and a `Future<List<Club>>`, type nothing.
- **Locals.** A local from a bare call states `from: "name()"`, typed by the declared return of the enclosing class's own method, else — through `importedFunctionLink`, which reads a bare call an import puts in scope as a cross-file call unless the caller's own class or file declares the name — the imported function's. A loop variable that another declaration of the function shares (`for (final c in players) { c.save(); } … final c = Boat(); c.save();`) is handled in [element-types.ts](element-types.ts) (`addLoopBinderCalls`): the call extractor keeps one call per name, so each call on the name takes the type of the binding in scope at its line (the loop's element inside the loop, the construction the declaration states after it) and the missing ones are added with that `receiverType`; a declaration stating no type (`final c = harbour();`), two declarations disagreeing or a parameter of that name leaves the name as it was. A `from` may be a call chain. Aliases `final c = club;` / `final c = maybeClub!;` state `LocalType.aliasOf` on both front ends ([di.ts](di.ts)); a name assigned again gets none.
- A Dart untyped (or `dynamic`/`var`/`final`) closure parameter named like a typed formal marks its calls `boundLocally` (`markShadowedClosureParams`, both front ends), so no stale type reaches it.
- `classScopeOf` reads a field's value as the children after its name in that one list (a typed primitive without an initializer stays a plain value, so no constructor-parameter copy flows into it); a constructor's signature is visited like a plain function's, so a default value's `const Pause(1)` is a construction row of the function. The class pass keeps the signature of a constructor's return type when `adoptParsedMembers` adopts a parsed function ([members.ts](members.ts): a redirecting factory's target after its parameters, `factory Event.select({…}) = _Select;`).
- `fieldWrites` and thrown types are stated; ORM conventions share the loose `singularize`/`pluralize` of the plugins' `inflection.ts`.

## Value flow ([value-flow.ts](value-flow.ts), [closure-flow.ts](closure-flow.ts))

- Tear-offs and single-call closures are seeds; locals, fields and `widget.x` are cells; a Flutter widget's named constructor argument is an `arg` with `name` meeting the field its constructor copies (a named argument binds the formal of that name); a member read through a property of the enclosing class (`widget.onSave`, a State's widget) keys on that property's declared type; `x!()` / `x?.call()` / `x?()` / `table['k']!()` / `for h in list { h() }` are invokes. An invoke is stated only for a name the file proves holds a function (a function-typed parameter or field, a closure or tear-off initializer, a local from a call) — never for a callable object (`GetIt`) or a name whose type nothing says is a function.
- **Widget-event closures.** A closure handed to a widget event is a pseudo-function (`<onTap@14>`, `<onPressed@218>`) holding its calls. One that calls a callback the widget is handed (`onSave(club)`, `widget.onSelect?.call(club)`, `onLongPress!(club)`, also the one-call forwarder `() => onRename(club)` when `onRename` is a function-typed field or parameter of the file) keeps its own function so the click has a handler: the parser's `invoke` facts of the method around it are copied onto it at the closure's own call line and the closure carries `FunctionInfo.enclosingClass`, so value flow reads `this.x` / `widget.x` in it as that class's receiver (and still its locals as the method's) and links the invoke to what the parent passes — never to a same-named top-level function elsewhere. The tree-sitter reader returns `ParsedFunctionSpan.valueFlow` / `ParsedStructure.moduleValueFlow`; the regex fallback states none for it.
- A `typedef` of a function type is a `FileAnalysis.functionTypeAliases` entry: a value typed by a name the file cannot judge states its `invoke` with `ifFnType`, kept only when the nearest declaring scope has a function-type alias and no class of that name. Calls through a field another class declares callable are derived by core (`fieldInvokes`).
- Navigation helpers: `FileAnalysis.navigationHelpers` records a function that pushes the widget it is handed; core's screen-navigation pass adds the helper-call's widget (`openPage(context, ClubPage())`) as navigation.

## Routes, clients and data

- go_router ([go-router.ts](go-router.ts)): `GoRoute(path: '/home', …)` is a screen at a literal path; the common form names a constant of the screen (`path: MobileHomeScreen.routeName` with `static const routeName = '/home'`), recorded as a per-file fact (class, field, widget the route builds) whose field value is read off the class the name resolves to. A `ShellRoute`/`StatefulShellRoute` builder widget is a shell node and start; a `tab` route (a branch's first) gets an edge from it. Named routes: [named-routes test](named-routes.test.ts).
- Request wrappers ([request-wrappers.ts](request-wrappers.ts)): a project method handing its path parameter to a client and picking the verb from another (`ApiConnection().request(RequestType.POST, '/x')`) is joined by core's `expandRequestFactories` from each call site's `pathArgCalls` — literals, the class it is called on, the verb its enum argument names; a `static const apiBasePath = "mobile"` it interpolates is a `fieldValues` entry of its class. The wrapper's dio rows carry `${url}` (`dartUrlArg`).
- Request bodies ([request-body.ts](request-body.ts)): package:http `body: jsonEncode({...})` and Dio `data: {...}` — a map literal or a local the function assigned one to earlier; values typed by their literal, a spread leaves the object open, null when not stated. Schema reading: [request-schema.ts](request-schema.ts).
- ORM entities ([entities.ts](entities.ts)): Drift (`class X extends Table`, `.references(...)` many-to-one), Isar (`@collection`, `IsarLink` many-to-one, `IsarLinks` one-to-many), Floor (`@entity`, `@ForeignKey`), Hive (`@HiveType`/`@HiveField`). Drift named queries ([drift-queries.ts](drift-queries.ts)): a `.drift` file declaring `mergedBucket: SELECT …` generates a `mergedAssetDrift` accessor (camel-cased base name + `Drift`) on the database; `_db.mergedAssetDrift.mergedBucket(…)` links to the named query of the `.drift` file (read by the SQL plugin); a file name shared by two `.drift` files names neither.
- Dependency injection ([di.ts](di.ts)): get_it (also kiwi, GetX) registrations and lookups, injectable annotations and generated `gh.*` calls, provider `Provider<I>(create: …)`, Riverpod providers and overrides, as facts. The line-based DI readers are shared with Swift and Scala.
- Client bases: `String.fromEnvironment` and similar are runtime-chosen, so Dart states no `serviceConfig` base yet.
- Cross-language bridges: flutter_rust_bridge's generated Dart is joined to Rust by core's foreign-bindings pass (rules stated by the Rust plugin, see [../rust/AGENTS.md](../rust/AGENTS.md)); a generated event class `<Enum><Variant>` is joined to the Rust handler registered for the enum variant.

## Tooling

`blockingCalls`: `sleep`, `File.…Sync`, `Process.runSync` inside an `isAsync` function (a project class's `f.readAsStringSync()` is not listed). Control flow is the approximate regex tier (`meta.regexControlFlow`).

## How core passes read it

- Symbol linker: a call through a static-member path (`PlayerService.instance.add()`) is called on what `instance` holds; a class head vetoes only a call on the class itself.
- A local initialised by a bare call (`final w = topClub();`, `final x = pick();`, `await fetch()`) states `localTypes[].from` as `name()`; the linker types it by the enclosing class's own method return type, else the imported function's (`importedFunctionLink`, which also reads a bare call an import puts in scope, `ImportInfo.inScope`).
