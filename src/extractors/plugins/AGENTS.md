# src/extractors/plugins — Per-language implementations

Each language gets one folder. Two patterns are used depending on whether the language has a working tree-sitter grammar:

## Tree-sitter plugins (AST-based)

Folders: `javascript/`, `python/`, `java-kotlin/`, `csharp/`, `pascal/`

Contents (varies slightly per language):
```
<lang>/
├── manifest.ts               LanguagePluginManifest — STATIC tier (extensions, grammar, patterns, framework rules), eagerly aggregated
├── meta.ts                   LanguagePluginMeta — LAZY tier (spreads the manifest + hooks/extractors), loaded via registry LOADERS
├── frameworks.ts             FrameworkRule[] — manifest-level framework detection for the ecosystem (optional)
├── functions-classes.ts      extends FunctionClassExtractor
├── imports-exports.ts        extends ImportExportExtractor
├── data-sources.ts           extends DataSourceExtractor (optional)
├── data-mutations.ts         extends DataMutationExtractor (optional)
└── routes/                   framework-specific route extractors (optional)
```

Each extractor class implements `abstract collectFunctions(node, results)` / `collectClasses` / `collectImports` / etc. using tree-sitter AST walking. Instances are carried on the plugin's meta (`meta.functionsClasses`, `meta.importsExports`, `meta.routes`, `meta.dataSources`, `meta.dataMutations`, `meta.entities`, `meta.dispatchResolvers`, `meta.routeResolvers`) — the domain `src/extractors/<category>/index.ts` files dispatch via `pluginFor(language)` and import no plugin code. Family plugins share ONE instance across member metas (instance identity = run-once in project-level passes like `reconcileProjectEntities`); dispatch resolvers carry a `priority` that fixes cross-plugin link order.

**Registration by scan** — a handler a framework finds by scanning has no call site, so a dispatch resolver gives it an edge from the registering file. C#: `csharp/assembly-scan.ts` states each `AddMediatR(…RegisterServicesFromAssembly(typeof(X).Assembly))` / `AddMediator()` / MassTransit `AddConsumers…` / `new EndpointConfiguration(…)` as a `cs:assembly-scan` route fact (markers = the `typeof`/generic types named; none = the registering project), and `CSharpAssemblyScanResolver` links the registering function (else `<setup>`) to the `Handle`/`Consume` of every class implementing the family's handler interface in the project that declares the marker (the registering project's namesake first; `Program` with top-level statements is the registering project; a marker nothing declares scans nothing). Android: springxml now admits an `AndroidManifest.xml` (`shared/android-manifest.ts`: an `android-manifest` fact plus a `<manifest>` function), and `java-kotlin/android-manifest-components.ts` links it to each `<activity|service|receiver|provider|application>` class it names, resolved against the manifest `package` (or, for a Gradle `namespace` manifest, the package ending with the written path), within the manifest's own module and only when exactly one class matches. Dead-code verdicts were already correct for both (entry base types, `configMentions`); the edge is what removes the "no callers" answer.

**Advice on its join points** — an AspectJ/Spring AOP advice method has no call site, so `java-kotlin/aop-advice.ts` (a dispatch resolver, `dispatch:aop-advice`, no per-file fact) reads each `@Aspect` class's `@Before`/`@After`/`@AfterReturning`/`@AfterThrowing`/`@Around` pointcut from the decorator text (a string, `"a" + "b"`, a Java text block, `value=`/`pointcut=`) and draws an INFERRED edge from every project method it matches to the advice, so a route's reach lists it. Read: `execution`, `within` (also `within(@pkg.Anno *)`), `@annotation` (a literal type or an advice parameter bound by name), `@within`, `&&`, `||`, `!`, parentheses and a named `@Pointcut` (the aspect's own, else one unique aspect's). Evaluation is three-valued — any other designator, an unresolved name or a modifier other than `public` is unknown, and an edge needs the whole expression certainly true. `..` is zero or more whole segments in a dynamic program over segments (a long pattern cannot backtrack); an interface named by `execution` also reaches the project classes implementing it; test files and the aspects themselves are no join points.

## Regex plugins (source text–based)

Folders: `go/`, `rust/`, `ruby/`, `php/`, `swift/`, `lua/`, `scala/`, `dart/`

Contents:
```
<lang>/
├── meta.ts     LanguagePluginMeta — builtins, extensions (from the spec), parsing: "regex"
└── index.ts    exports a RegexLangSpec
```

The `RegexLangSpec` declares:
- `functionPatterns` — regex + isExported/isAsync predicates
- `classPatterns` — regex + extends extractor
- `importPatterns` — regex + source/specifier extractors
- `indentBased` — true for Ruby/Lua, false for brace languages
- `lineCommentPrefixes` — `["//"]`, `["#"]`, `["--"]`, etc.
- `extractRoutes` (optional) — custom route extraction for frameworks like Rails controllers, Go muxers, Laravel attributes

The shared framework in [shared/regex-base.ts](shared/regex-base.ts) handles:
- Walking lines, matching patterns
- Finding end-of-block (braces or indentation)
- Extracting params, properties, calls from bodies

Specs are loaded by [../../core/regex-extractor.ts](../../core/regex-extractor.ts).

## shared/

[shared/regex-base.ts](shared/regex-base.ts) — the `RegexLangSpec` type and the generic `extractFunctionsWithSpec` / `extractClassesWithSpec` / `extractImportsWithSpec` / `extractCallsFromBody` helpers used by all regex plugins.

[shared/brace-code.ts](shared/brace-code.ts) — a brace language's literal forms (`BraceLexicon`: comments, strings, raw strings, character literals) and the spec hooks built from them (`braceCodeHooks`): `blockEnds` counts braces over code only, `callSourceLines` blanks raw strings and block comments for the call scan, `commentFreeLines` is what a route scan reads, `startsInCode` keeps a function pattern out of comments and code templates. Go, Rust, C, C++, Scala and Swift use it (Scala with blocks that end by braces or indentation, `scala/blocks.ts`; C and C++ through [shared/c-family-code.ts](shared/c-family-code.ts), which also says when a signature is a definition); [shared/call-chains.ts](shared/call-chains.ts) names a method called on a call's result as the chain (`Club.new().register`). Swift's regex call patterns ([swift/code.ts](swift/code.ts) `CONSTRUCTION_CHAIN_CALL`) also name a method on a fresh construction — `Club().sign(`, `try await Club(id: 7).squad(` — as `Club.sign` with `receiverType: Club`, matching the tree-sitter reader; the baseline skips the member after `).` and would otherwise leave it unlinked.

[shared/project-info-queries.ts](shared/project-info-queries.ts) — `hasDep` / `hasGoMod` / `hasCsprojPackage` / … predicate helpers over `ProjectInfo` for `frameworks.ts` rules.

[shared/handler-taint.ts](shared/handler-taint.ts) — request input followed through ONE request handler to a sink (SQL text, command, file path, outbound URL, redirect, eval), the plugin's `ast.taint` hook. The algorithm is here; a plugin supplies a `TaintSpec` (what a handler is, the request-input regex, assignment/call shapes, sanitizers, propagators — the calls whose RESULT carries their arguments' taint; any other function's result is not followed — and sinks with the argument that carries the danger). Python (`python/taint.ts`) and JS/TS (`javascript/taint.ts`) have one. Go and Ruby are read by ANTLR and regex, so they have no `ast.taint` hook: their meta states `regexTaint` (`{ grammar, gate, taint }`) and `file-analyzer.ts` parses a file whose source matches `gate` once more with the tree-sitter grammar the manifest registers (`tree-sitter-go`, `tree-sitter-ruby`; the `taint` feature switches it off) and runs the same `handlerTaint` walk — never on a test or generated file or a tree with syntax errors. `go/taint.ts` builds its spec per file: source reads are looked for only on the context/request parameter names the file declares (`c.Query(…)`, `r.URL.Query()`), SQL sinks only on a receiver that names a database handle (`db`, `tx`, `conn`, `gorm`…), never `repo.Query`; `ruby/taint.ts` takes every method of a controller (superclass or `app/controllers/`) and `get "/x" do` blocks as handlers, drops keyword arguments (`where(name: params[:x])`) and treats a method that assigns its own `params` as having none. Two rules both specs lean on: a value led by something the request does not control (`base + r.URL.Path`, `"#{root}…"`, `leadingOperand`) keeps its host and is no open redirect or SSRF, and a condition that checks a request read (`sourceReads`) clears that read for the rest of the handler. A guard (`startsWith`, `safe…(`, `valid…(` on the value in an `if`) counts as a check. Measured on five real repositories: zero findings, after 16 false ones drove the propagator, guard and free-text-parameter rules — precision first, every finding is an accusation.

[shared/security-context.ts](shared/security-context.ts) — `CREDENTIAL_CONTEXT`, the lookahead that keeps an MD5/SHA-1 rule to lines about a credential.

## Framework detection (frameworks.ts)

Manifest-level framework rules live with the plugin that owns the ecosystem —
`plugins/<lang>/frameworks.ts` exports `FrameworkRule[]`, wired via
`meta.frameworkRules` and aggregated by the registry into `FRAMEWORK_RULES`
(duplicate ids throw at registry build). `core/framework-detector.ts` only
gathers `ProjectInfo` and runs the rules; it knows no framework names, exactly
like `knownPackages`. Notes:

- Rule `check` predicates compose the helpers in
  [shared/project-info-queries.ts](shared/project-info-queries.ts).
- Detections are sorted by id in the detector, so output never depends on
  plugin registration order.
- Family plugins (javascript, java-kotlin, pascal) attach rules to ONE member
  meta only (typescript/java/pascal) so the registry sees each rule once.
- Cross-cutting rules live with the plugin that owns the file format:
  `qt` → cpp, `qt-quick` → qml, `sql` → sql, `jsp` → jsp,
  `spring-webflow` → springxml, `prisma` → prisma.
- Vendored frameworks with no manifest entry (CodeIgniter 2/3) declare
  `meta.markerCandidates` — well-known relative paths collected into
  `ProjectInfo.markerFiles` for rules to match on.

## Adding a new language

### Tree-sitter path (preferred when grammar is available)

1. `npm install tree-sitter-<lang>` (or verify WASM is in a deps package)
2. Add to `Language` type in [../../types/analysis.ts](../../types/analysis.ts)
3. Create `src/extractors/plugins/<lang>/` with per-category extractors
4. Wire each extractor instance onto the meta (`functionsClasses`, `importsExports`, `routes`, `dataSources`, `dataMutations`, `entities`, `dispatchResolvers`, `routeResolvers`)
5. Create `manifest.ts` (the STATIC tier: `language`, `family` — the import-resolution family, shared by languages that resolve each other's bare names (`jvm`, `dotnet`, `cfam`, `script`), else the language's own — `parsing`, extensions (one owner each: the registry throws on a second claim), `grammar` — package + wasm location, with optional per-file variant selection like tsx — test patterns, prefixes/roots, framework hints, `activationFiles`) and `meta.ts` (spreads the manifest, then adds builtins, complexity tables, security rules, ast hooks, and `calls` — at minimum `callNodeTypes`, plus name-resolution/scope hooks as needed; see `call-hooks.ts` in existing plugins). Register the manifest in `ALL_MANIFESTS` and the meta in `LOADERS` in [../registry.ts](../registry.ts) — extensions, discovery, grammar loading, complexity, call extraction, and the rest flow from there
6. If the ecosystem has detectable frameworks, add `frameworks.ts` (`FrameworkRule[]`) and wire `manifest.frameworkRules` (see "Framework detection" above)

### Regex path (languages without reliable grammar)

1. Add to `Language` type in [../../types/analysis.ts](../../types/analysis.ts)
2. Create `src/extractors/plugins/<lang>/index.ts` exporting a `RegexLangSpec`
3. Create `manifest.ts` (`parsing: "regex"`, `family`, `extensions` — the same list as the spec's) and `meta.ts` (spreads the manifest, `regexSpec: <spec>`, builtins), and register both in [../registry.ts](../registry.ts)
4. A script language whose files run their own statements sets the spec's `topLevelCalls` (`true`, or a path RegExp — VB sets it for `.vbs` only): calls outside every function/class become the `<setup>` pseudo-function. A top-level block that only REGISTERS code to run later (`get "/x" do … end`, `before_all do`) is listed by `deferredBlocks` so `<setup>` skips its body; the route carries the body's calls itself (Crystal `get "/x" do`, CoffeeScript `app.get '/x', (req, res) ->` — also a one-line body `-> res.send 'ok'`, a continuation-line handler (`app.get '/x',` then indented `(req, res) ->`), and inside a `module.exports = (app) ->` or named registrar; `callSourceLines` blanks those bodies so a named function that registers the route does not count them again; `app.use` mounts and handlers named at the line's end have no body). Python's SQLAlchemy reader never gives a statement builder (`select(…)`, `func.count(…)`, `sa.select(…)`) a row of its own that names no model: `select(…).filter_by(…)` takes the model its `select` names (a parameter's stays with the session call's row), a bare `func.…` yields none — core would otherwise back-fill the import's module name (`sqlalchemy`) as the table. On a `select(…)` chain, each `.join(Y, …)` whose first argument names a class (`Player`, `models.Player`) or a loop variable of such classes is another read of that table; a string's `"-".join(…)` and a project function named `join` never are. An Alembic revision's `op.create_table(…, schema="league")` (and `drop_table` / `rename_table` / `add_column` / `drop_column` in `upgrade` only) yields a schema-qualified table (`league.clubs`) plus `schemaOps` so the data model joins what code names under that schema — a same-named decoy without `schema=` or under another schema stays a different table; the revision's model copies are still not entities. A model's `__table_args__ = {"schema": "league"}` prefixes its `__tablename__` the same way. A SQLModel `class Club(SQLModel, table=True)` with `league: Optional["League"] = Relationship(…)` (serializer-style nested fields) is an entity relation; a non-`table` SQLModel schema with the same nested shape (`league: Optional[LeagueRead] = None`) is not an entity and yields no relation. A `@declared_attr` (or `@orm.declared_attr`) method whose body is `return relationship(…)` / `return orm.relationship(…)` is the same relation as a field assignment; a `@declared_attr` that returns anything else is not.

### Container formats (e.g. Vue SFC, Delphi .dfm)

- A format that embeds another language (Vue) declares `preprocess` on the host
  language's meta — swap in the embedded source/language before parsing, and
  optionally merge container data back via `postExtract`.
- A Vue template's expressions are parsed in place (`javascript/markup-expressions.ts`): `{{ … }}`, bound attributes
  and a handler that sends a request in one statement (`@click="axios.post(`/api/clubs/${club.id}/archive`)"` —
  `sendsRequest`: `fetch(…)` or a client verb called with a URL, no top-level `;`) become `<setup>` statements, so the
  data-source reader reads the api-call at the handler's line. A loop variable (`v-for="m in matches"`) is
  `FileAnalysis.templateLoops` with the collection's script-stated type, which types a hole reading a member of it, in
  the lines of the element carrying the `v-for` only (`templateScopes` records each loop's extent); the same name outside
  it is the script's own. The script's type is read at its top level only (`const x: T =`, `ref<T>()`, a top-level member of
  `defineProps<{…}>`) with balanced brackets (`Record<string, Club>` whole); a type the reader cannot read cleanly gives none.
- A format with its own parser (.dfm) declares `parsing: "custom"` + `customParse`.
- A parser front end may state each call's arguments (`PatternCallName.args` → `CallInfo.argCount`/`argKinds`/`templateArgs`; C++ `cpp/antlr.ts`): `callRecorder` then keeps one row per distinct (name, count, kinds, template arguments) in a function instead of one per name, so `g(1); g(1.0);` are two calls. The manifest's `calls.overloadTypeKey` folds declared types (`cpp/arg-kinds.ts`), `calls.conversionRanks` makes core rank exact > promotion > conversion (`argFit`'s `ranked` scale), and `calls.explicitSpecializations` has `convert<int>(x)` choose the definition whose `FunctionInfo.specializedOn` names those arguments. Core's `pickOverloads` reads a call's site from the link's own file only. An argument naming a variable is `@name` — also `*name` (a dereferenced pointer) and `this->name` (a field); core types it from the parameters, typed locals, `auto c = Club(3)` (a local whose one initializer is a construction of a class the project declares) and the class's fields.
- An extension several languages share (`.h`) has one owner, but how it is READ can depend on its sub-project: the
  owner's manifest `readingVariant(relativePath, mix)` gets the project's file counts by extension and names a
  variant (the C++ plugin: `c-first` for a `.h` in a project with `.c` and no C++ source) that its `meta.antlr` reader
  receives as a second argument. The analyzer counts the mix once, passes the variant in `FileTask.reading` (workers
  never see the mix) and folds it into the file's manifest `resolver` stamp, so a project whose mix flips re-reads
  its headers although no byte changed. `FileAnalysis.frontEnd.variant` records it.

## Conventions

- **One folder per language.** Even tiny regex specs (24 lines) get their own folder for consistency.
- **Visibility defaults matter.** Java/C# methods default to package-private (isExported=false unless explicitly `public`). Kotlin/TS default to public.
- **Decorators keep their arguments.** `decorators: string[]` holds the attribute/annotation text with its argument list (`Authorize(Policy = nameof(X))`, `ApiVersion("2", Deprecated = true)`), whitespace collapsed — that is where routing, auth and serialization semantics live. Consumers match with a regex or `includes`, never equality on a bare name. (Java's `extractAnnotations` still keeps the name only — a known gap.)
- **Route metadata is language-agnostic.** A route extractor that can see guards, API versions or parameter bindings fills `RouteInfo.middleware` (readable guard strings), `auth`, `versions`/`deprecatedVersions` and `params` — the same fields whatever the framework spells them as — through `shared/route-metadata.ts` (`GuardAttr`, `applyRouteMeta`, `inferredParam`). `csharp/routes/aspnet.ts` and `java-kotlin/routes/meta-annotations.ts` are the references: class-level attributes are inherited by every action, an anonymous marker waives, `[MapToApiVersion]` narrows, and a binding derived from framework defaults is marked `inferred: true`. ASP.NET `Name =` on a verb attribute or the `[Route]` beside it is `RouteInfo.name` (what `CreatedAtRoute` / `Url.RouteUrl` name); `[controller]` / `[action]` tokens expand for the controller that serves the action — on an action inherited from a base, the subclass's token, from the raw `name` on the `cs:controller` action fact (`aspnet-resolver.ts`), never the declaring base's — and a `Name =` alone is never the path.
- **OCaml route paths in another module's constant.** A Dream/Opium path that is a module value (`Dream.get Paths.clubs handler`, or a nested `module Paths = struct let garages = "/api/garages" end`) is `RouteInfo.pathTemplate` `${Paths.clubs}`; string `let`s are `FileAnalysis.moduleValues` (bare and, after the file module is renamed to its stem, `Paths.clubs`) and `ClassInfo.fieldValues` on that module. Core's `resolveRouteTemplates` fills the hole; a same-named `let clubs` in another module never substitutes.
- **Enum-constant bodies and C++ operators.** A Java enum constant's override of a method the enum declares (`ATTACK { void play() { coach.shout(); } }`) hands its calls to the enum's own method of that name (same parameter count; an abstract declaration is the usual host); a method the enum lacks is still added. An anonymous class's calls stay with the enclosing function, but a bare one inside `new Base() { … }` carries `withSubjects` (the anonymous class, then `Base`), so it resolves on the base's member before the enclosing class's or a namesake's ([java-kotlin/java-anonymous.ts](cli/src/extractors/plugins/java-kotlin/java-anonymous.ts)); a local initialized by an anonymous class is typed as a synthetic class of the file (`Runnable$5_23`: `extends` the base, synthetic call-less methods), so `handler.run()` reaches its `run`. Kotlin constructor delegation is a construction like Java's `this(…)`/`super(…)`: a primary `class A(…) : Base(x)` gives the primary constructor (a synthetic parameterless one when none is written) a `new Base` call, a secondary `: this(…)` / `: super(…)` a `new A` / `new <superclass>` call, linked to the constructor its arguments choose ([java-kotlin/kotlin-delegation.ts](cli/src/extractors/plugins/java-kotlin/kotlin-delegation.ts)); a secondary constructor's statements are read as its body. In C++ (`cpp/antlr.ts`), `a + b` / `a == b` / `a < b` / `a << b` (first operator of a flat chain only) and `a[i]` are calls named `a.operator+` … when `a` is a parameter or local declared as a class-typed value — never a pointer, array, primitive or `auto`. The left operand may also be a field of the function's own class (`kit + o`, `this->kit + o`; an out-of-line `Club::f` reads `Club`'s members, collected per class by `collectFields`) or the pointee of a smart pointer, iterator or `this` (`*owner`, `*it`, `*this`), named `Club.operator+` with `receiverType`. A free `operator+(const Club&, …)` defined in the same file also gets a bare `operator+` call when its first parameter's type is the operand's: the file's only free definition of the name links on the left type alone, an overload set only when the right operand's type (a typed local, parameter, field, pointee or literal kind) equals the second parameter of exactly one overload — the call then carries both kinds as `argKinds`, so the linker's overload choice agrees. `it->m()` over a container iterator (`std::vector<Club>::iterator`, `auto it = squad.begin()`) and `*it` / `*owner` as an argument (`record(*it)`) read the element class off the container's or smart pointer's declared type, never a container of pointers. `(*it).m()`, `std::next(it)->m()` and a chain from `it->` read as the element's (`Boot.club().sign`); a method defined in a `.cpp` whose class a header declares names `kit + other` / `this->kit + other` as `kit.operator+` / `this.kit.operator+`, a member the linker types from the class's fields (a primitive field links nothing). An iterator over a field only the header declares (`auto it = boots.begin()`, `cbegin`, `find`, `lower_bound`) is a `localTypes` entry `element: true` from the field name (never when the body declares a local of that name), so `it->m()` and `(*it).m()` are named `it.m` and the linker types the element; `(*it)->m()` reads through a pointer or smart-pointer element (`vector<Boot*>`, `vector<unique_ptr<Boot>>`, `cppCollectionElementOf`), and a value element never takes `->` nor a pointer element `.`. A map's `it->first` / `it->second` are named `it$first.m` / `it$second.m` (types the file spells: the key or value class of `cppMapTypes`) with synthetic `localTypes` at `fromIndex` 0/1 read through `tupleElementsOf`, which also reads a map's key and value, only when the body uses them. A range-for over a map (`for (auto& p : clubs) p.second.m()`, `for (auto& [id, club] : clubs) club.m()`) reads the same way: a local `p` over a name the function does not declare (a field a header declares) names `p.second.m` `p$second.m` with `localTypes` `p$second` at `fromIndex` 1, only when the body uses it, a structured binding is typed at its position from the field's (or a local map's) key and value; the container a free function does not declare is a global no linker types, so its calls keep the plain name. A structured binding `auto [a, b] = f()` over a project struct (manifest `bindsStructFields`) types each name by the struct's data member at its position — the linker reads `ClassInfo.properties` in declaration order, nothing for a class with a base.
- **Tables named by an environment variable (DynamoDB).** A DocumentClient call (`docClient.get({ TableName })`, v2) or a v3 command (`new GetCommand({ TableName })`, `…ItemCommand`) in a file naming DynamoDB / `aws-sdk` is a `database` row ([javascript/dynamodb.ts](javascript/dynamodb.ts)): `TableName` a literal, a same-file constant, or `process.env.X` (directly, through `const T = process.env.X`, or `const { X } = process.env`; a request held in a local object is read too). An env name is `DataSourceInfo.envRef` with no target; the serverless plugin reads each descriptor's `environment` (`provider.environment`, a function's own, SAM `Globals.Function.Environment.Variables` and the function's) into `lambda-env` route facts ([serverless/environment.ts](serverless/environment.ts): literals, `${self:…}` read from the same file, `Ref` to a DynamoDB table resource → its `TableName`, else its logical id; `${opt:…}`, `${ssm:…}`, `!Sub` pseudo parameters and parameters `Ref`s leave the variable out), and its route resolver (`route-anchor.ts` `applyEnvironment`) gives the row the value: provider-wide for any code file below the descriptor's directory, a function's own for the module its handler names (which wins); a variable another service's descriptor sets, or two descriptors / functions of one module set differently, stays unset. Core then drops every row still carrying `envRef` — never a guessed table. Terraform: an `aws_lambda_function`'s `environment { variables }` (a literal, or `aws_dynamodb_table.x.name|id` of a table whose `name` is a literal) goes the same way through the terraform plugin's route resolver, on the module its handler names only (no provider-wide scope); a variable-built name stays unset.
- **A POST form with no action posts to its own page.** The HTML reader marks such a `<form>` (and its submit controls) `InteractiveElementInfo.ownViewPost` (no `action`, or `action=""`; a template expression in the attribute is a URL and never marks it; GET never); core's [own-view-posts.ts](../../core/own-view-posts.ts) gives it `POST <path>` when every route rendering the screen (`ScreenInfo.renderedBy`) is at one path, and the api-call joins the route linker like a written-out action. A template served at two paths says nothing. Rails ERB: a `form_with`/`form_tag` with keyword options only (no `url:`/`model:`/positional/splat, POST) and a native `<form method="post">` are marked the same way; `erb/own-view.ts` (`rails-own-view` route resolver) gives every Rails view's screen `renderedBy` = the ONE GET route of its `Ctl#action` when the action renders implicitly (no `rails-action-exits` fact — the Ruby plugin's per-action `render`/`redirect_to`/`head`/`send_*`/`respond_to` scan — and no such call), else nothing — which is what lets a link to the page draw an edge on the screen map; a `before_action` that halts is not seen there. ERB `link_to`/`button_to`/form helpers name a route helper as `route:<helper>` (`route:club_players` for `club_players_path`) in `request.target` and `ScreenInfo.navigatesTo`; the screen flow and the navigation pass resolve it through `RouteInfo.name` (an `as:`) and else `RouteInfo.derivedName`, so `link_to "Squad", club_players_path(@club)` reaches the screen of that route and a helper a rename replaced (`fixture_path` after `as: :games`) reaches nothing. A plain `.php` page outside `views/` is a screen when the markup around its PHP tags holds a form, link or inline script, and a route at its own path when it reads `$_POST`/`$_GET`/`$_REQUEST`/`$_FILES`/`php://input` ([php/plain-pages.ts](php/plain-pages.ts): document-root directories such as `public/` stripped; class or namespace files, library and framework directories, partials and front controllers excluded), so a self-posting form there links to its own route; relative `.php` targets resolve against the page's directory. Blade and CodeIgniter views go through the HTML reader and `render` links as before.
- **A Next.js `middleware.ts` / `proxy.ts` is a guard** only when its code checks the caller (a caller-check default-export name, a library wrapper, or a session/token read plus a redirect/401): `javascript/routes/next-middleware.ts` emits a `next-middleware` route fact with its `config.matcher` (none = all; an unreadable or `has`/`missing`-conditioned matcher guards nothing) and a resolver gives the matching Next routes of the same sub-project an inherited guard. A header-only middleware guards nothing.

- **Alias of a typed local (`LocalType.aliasOf`).** A name assigned from another plain name — `const q = p`, Go `q := p` / `&p`, PHP `$q = $p`, C++ `auto& q = p` / `= *p`, Rust `let q = p` / `&p`, Python `q = p` and `(q := p)` — is a `localTypes` entry with `type: ""` and `aliasOf: "p"` (no `from`); core types it through `scopedName(aliasOf, depth + 1)` under the same `MAX_INITIALIZER_DEPTH` cap as initializer calls. The plugin emits it only when the name is bound ONCE, from ONE head, and never reassigned, rebound by a loop/`catch`/`foreach`/destructuring or shadowing a parameter (each plugin checks its own language's forms); everything else stays untyped, so an alias of an untyped name links nothing and a namesake method on another class is never reached. Never an alias: `undefined`, `true`/`false`, `nil`/`nullptr`, `self`/`this`. A Python parameter-typed alias is read by the fact table already; `aliasOf` is for a head typed by a call (`p = make(); q = p`). The Python local-type gate skips an alias-only body unless a parameter is annotated. Flow order: the TS/JS scan keeps a timeline of each name's declarations and `=` assignments, and an alias of a head bound or assigned more than once is typed by the nearest binding BEFORE the alias (a concrete `localTypes` entry, only when that binding states a type); a binding in a nested block before it, an untyped one, a loop around the alias or a head bound by something the timeline does not see leaves it untyped. The same order is read in Python (the fact table keeps each name's latest binding and its block; a loop around the alias matters only when the head is bound again LATER in that loop body — the back edge brings both bindings — and then the alias is typed only if that binding states the same type) and PHP (writes in text order, blocks by enclosing statement; a parameter is the head's first write, typed by its declaration, so `$a = $c; $c = new Player();` keeps the declared type and an alias after the reassignment takes the new one; the same loop rule), Rust and the C family ([plugins/shared/alias-flow.ts](shared/alias-flow.ts): open braces, a binding per name, a loop or closure around the alias leaves it untyped when its head is bound more than once); a binding in a block that closed before the alias, or an untyped one, leaves it untyped. ## Thrift (`thrift/`)

A contract plugin like protobuf: `POST /<java namespace>.<Service>/<method>` rows with `contract`, `routeFacts` + a route resolver for `extends`, argument structs as `<Service>_<method>_args` classes. Stub and `Iface` names live in `shared/thrift-stubs.ts`, composed into each language's existing `grpcStubService`/`grpcServiceOf`; certain only when the file imports the Thrift runtime, else only for a declared service. String literals are blanked before fields and methods are read (a default `"2: i32 fake"` is no field; a lone quote never swallows the file). A Go stub TYPE (`ClubServiceClient`) counts only in a file importing the Thrift runtime or a package the project generated from a `.thrift` (a `gen-go/` path, or a package declaring `XClient` beside `XProcessor` — `core/grpc-clients.ts` hands the stub hook every analyzed file as a third argument, and `firstStub` prefers a certain answer). Handlers the generated code does not name — Go `NewClubServiceProcessor(&clubHandler{})`, Python `ClubService.Processor(handler)`, Node `thrift.createServer(ClubService, handler)` — are `thrift-handler` route facts ([shared/thrift-handlers.ts](shared/thrift-handlers.ts)) that the `thrift-handlers` resolver joins with the declared service's rpcs and the one class of the handler's type: each rpc it has a method for becomes a contract row ON that method (the grpc-js `addService` shape), which the `.thrift` row's spec join finds; a handler held in a variable is read from its one literal/constructor assignment, an object-literal handler (`createServer(ClubService, { getClub() {…}, listClubs: async () => … })`, or a variable assigned one) serves the rpcs it has a member for — a held one on its `<holder>.<method>` functions, a literal written in the call on rows named `createServer.<method>`; only in a file naming `thrift`. A handler object written in the call — thrift `createServer(ClubService, {…})` and grpc-js `server.addService(X.service, {…})` — is read from the parse ([javascript/contract-handlers.ts](javascript/contract-handlers.ts)): each member is a function of its own, `createServer.<key>` / `addService.<key>` (a held function's style; the contract row sits on it, so its body's calls are attributed to it); a member that names a function (`getClub: someFn`, `getClub: clubs.getClub`, shorthand, `.bind(this)`) is that pseudo-function holding one `passed: "argument"` call of the name, which `resolvePassedName` resolves without guessing — a namesake in an unrelated file is never the handler; a call-result value (`getClub: makeHandler()`), a spread or an accessor is no handler. A second call in one file reusing a key gets `@<line>` appended. A Node client `thrift.createClient(ClubService, conn)` names its service in an argument: `grpc-clients.ts` asks the stub hook again with `createClient(ClubService)` when the bare spelling answers nothing; an awaited receiver (`(await connect()).createClient(ClubService)`) is read past.

Node handler objects ([javascript/contract-handlers.ts](javascript/contract-handlers.ts): `createServer(Service, {…})`, `addService(X.service, {…})`) read a member's value through parentheses, `as`/`<T>`/`satisfies` assertions and `!`, a `this.x.bind(this)` member as the method `x` of the class the object is written in (the call names `Class.x`, so the linker resolves it on that class, never a namesake), and an object first held in a file's one `const|let|var name = {…}` as `<name>.<key>` functions (a member already a function of that name is not made twice); a name declared twice, or an object defined in another file, is not read.

## AsyncAPI (inside `openapi/`)

An extension has one owning plugin, and `.yml`/`.yaml`/`.json` are OpenAPI's, so AsyncAPI is a branch of its `preprocess` (an `asyncapi:` root key, checked after the OpenAPI sniff) handing the file to `openapi/asyncapi.ts`, not a second plugin. **Convex imported builders.** A module that exports `customQuery(query, …)` (imported from `convex-helpers/server/customFunctions`) emits a `convex-builder` route fact; a functions-directory module calling an imported builder emits `convex-use`, and `convexBuilderResolver` (`routes/convex.ts`) places the route when the import graph reaches a defining file, looking the builder up by the name the defining module exports (`import { authedQuery as q }` finds `authedQuery`; `convex-use` carries `exported`). `http.route` reads a same-file string constant for `path`/`method`.

Every seed and copy a held lambda states carries the same `lambda` id (its `line:col`): state every name its body calls (a plugin bounds that only to keep output small) — core counts the project functions they resolve to and drops the group above four, so a library's name never uses up the cap. Python ([python/value-flow.ts](python/value-flow.ts)): assignments, loop targets, `x.append(f)`, list/tuple/set/dict literals (a container is ONE cell with its elements, a dict also keeps a literal key as its member, `self.x[…]` having no second member level), `functools.partial(f, …)` as a seed of `f`, `return`, positional arguments by written index, and `invoke` for a call of a local, a parameter (not a test's or fixture's, which pytest injects), a module name its own statements bind, `self.<field>` the class assigns (never a method) and `table[k](…)`; a `global` assignment goes to `moduleValueFlow`; a keyword argument `schedule(callback=f)` is an `arg` with `name` (index -1) binding the formal of that name, a `**kwargs` formal or an unknown name nothing; a module-level `name = lambda …` is a function of its own; a lambda written inside a function and landing in a cell (local, `self.x`, list/dict element, positional argument, return) has no function of its own and stands for what its body calls — a seed for each project function it names (`save`, `self.save`, `Club.save`), a `copy` for a name that holds a value, nothing for a call on its own parameter or a local or on a name an import of the standard library or a known external package binds (`json.dumps`, `from time import sleep`: none counts toward the four, and an argument handed to such a call states no `arg` fact), and nothing when the project functions it calls come to more than four (at most four project functions, counted by core over the facts sharing the lambda's id; the plugin itself states up to sixteen names). Java/Kotlin ([java-kotlin/value-flow.ts](java-kotlin/value-flow.ts)): method and callable references (`this::save`, `Club::save`, `club::save`, `Club::new`, `::save`) seed locals, fields (initializers ride on the constructor, else the first method), `List.of`/`listOf`/`mapOf` literals and `add`/`put`/index writes (element cells `[]` / key, a field's as `this.<field>[key]`); `run`/`apply`/`accept`/`get`/`call`/`test`/`compare`/`handle`, Kotlin `f()`/`f.invoke()` are `invoke` facts only on a receiver the facts know holds a function (a JDK functional-interface or Kotlin function type, or initialized from a reference) and never one built by `new`/an anonymous class; a lambda or Kotlin lambda literal landing in a cell (local, field, collection element, argument — a trailing lambda is the last one —, return, field initializer) seeds it with each project function its body calls (`save`, `this.save`, `club.save`, `Club.save`; at most four project functions, counted by core, none for a call on the lambda's own parameter or implicit `it`, a chain or a JDK call) and copies the cell of a held function its body runs (`() -> onDone.run()`); it gets no function of its own, so its calls stay the enclosing function's. Go ([go/value-flow.ts](go/value-flow.ts)) and Rust ([rust/value-flow.ts](rust/value-flow.ts)) state them from their ANTLR readings only (the regex fallback states none; `ParsedFunctionSpan.valueFlow` / `ParsedStructure.moduleValueFlow`): Go's locals, pairs, method values, function-typed fields (an `invoke` on `c.onSave()` only where the file declares the field function-typed), `map`/slice literals and `append`, `range`, package variables (module facts) and factory returns; Rust's `let`/tuple patterns, `Some(Box::new(f))` wrappers, fields via `self`, `push`/`vec![…]`/`for … in`, `if let Some(cb)`, paren-called fields `(self.cb)(x)`, a `Self { cb: … }` literal as the receiver's fields, and a function's tail value. Dart ([dart/value-flow.ts](dart/value-flow.ts), [dart/closure-flow.ts](dart/closure-flow.ts)): a getter of a class, mixin or extension is a method of its own in both front ends (`FlagService get flags { _flags ??= FlagService(dio); … }`, `Club get club => Club(id)` — its calls and constructions are its own; a setter and an operator are none; a function declared `get` carries `FunctionInfo.getter`). A closure handed to a widget event is a pseudo-function `<onTap@14>` holding its calls, and one that calls a callback the widget is handed (`onSave(club)`, `widget.onSelect?.call(club)`, `onLongPress!(club)`, also the one-call forwarder `() => onRename(club)` when `onRename` is a function-typed field or parameter of the file) keeps its own function so the click has a handler: the parser's `invoke` facts of the method around it are copied onto it at the closure's own call line and the closure carries `FunctionInfo.enclosingClass`, so value flow reads `this.x` / `widget.x` in it as that class's receiver (and still its locals as the method's) and links the invoke to what the parent passes — never to a same-named top-level function elsewhere.

**C# query helpers.** A method declared to return `IQueryable<T>` (ordered / including forms, `DbSet<T>`, or a task of one) is a read where it is built; a chain that STARTS at a call of one declared in the same class — `ClubsQuery(id).ExecuteDeleteAsync()`, `this.Active().ExecuteUpdateAsync(…)`, `var q = ClubsQuery(id); q.ExecuteDelete()` — is the read or write it names on the set the helper queries (read off its returned expression, else its declared `T`), at the caller (`csharp/data-sources.ts` `queryHelperEntity`). A same-named helper of another class is not followed. A bulk write on a query ANOTHER class's method returns — `_repo.Active().ExecuteUpdateAsync(…)`, through nothing but query composition (`Where`, `AsNoTracking`, `Include`…), the receiver a field, property or parameter of a declared class — is a write row stating `DataSourceInfo.entityProducer` (`{ type: "ClubRepository", method: "Active" }`, no entity); the C# entity extractor's project pass (`producedQueryEntities`) types it by that method's declared `IQueryable<Club>` (or `DbSet`, or a task of one) when every class of that name declaring the method agrees, so a same-named helper of another class, a method returning no query and a type parameter bind nothing.

**Hangfire jobs run by id.** `RecurringJob.TriggerJob(id)` / `IRecurringJobManager.Trigger(id)` names no method: `csharp/hangfire-triggers.ts` states the arguments of the trigger and of the `AddOrUpdate` registration it names (`CallInfo.args`, through `meta.calls.argsOf`) and its dispatch resolver links the triggering function to the method the registration's lambda runs — on the one class implementing the registered interface (two or more refuse, so a decoy is never linked), or the registered class, or the registering class for a bare `() => Sweep()`. An id is a string literal or a `const` the named (else the caller's own, else the one project) class declares in `ClassInfo.fieldValues`; an unreadable id, or one two registrations give different handlers, links nothing. The scheduled-job entry-point reader (`csharp/scheduled-jobs.ts`) accepts the same id shapes on `AddOrUpdate` — a string literal, `nameof(…)`, a bare identifier, or a `Class.Const` — and resolves a same-file `const string Leaf = "…"` to that literal when the file declares it once.

**Express chained routers.** `const api = Router().use(clubs).use(players); export default Router().use("/api", api)`: a path-less `.use(name)` on a chain rooted in `Router()` / `express.Router()` is a mount row (empty path, receiver = the variable the chain is declared into, or none for a chain exported as the module's router; a chain handed to another call is left alone, a name that is no router file adds nothing, and a plain `router.use(name)` stays unread), so the same-file composer gives the rows the prefix of the local mount of that variable, and the project pass joins each named router file under it. Surviving (cross-file) mount rows of a locally mounted receiver now take that receiver's prefix too. The import index asks a language's own resolver (Python, Rust, Ruby) for the name an aliased import was exported as (`from app.api import api as articles` names module `api`; a default import keeps its local name). **FastAPI settings prefix.** `include_router(api, prefix=settings.api_prefix)` leaves the mount `prefixUnresolved: "mount:settings.api_prefix"`; `python/settings-prefix.ts` (route resolver, before mounts compose) types the holder — a local or module `settings = Settings()`, `get_settings()` through that function's declared return, an instance imported from the module that builds it — and takes the class attribute's literal default (`FileAnalysis.moduleValues`, own or a base's). NestJS `@UseGuards(HeaderGuard)` / `AuthGuard('jwt')` on a controller or action states `RouteInfo.middlewareCalls` as `Class.canActivate`, resolved in the controller file; a `@UseGuards` on a base controller lands as `inheritedMiddleware` naming the base file. NestJS app-wide guards are `nest-global-guards` facts: `app.useGlobalGuards(…)` or `{ provide: APP_GUARD, useClass|useExisting|useValue: … }` — every API route of that sub-project gets the guards and `inheritedMiddleware` naming the registering file; a namesake guard the registerer does not import is not a guard. `useGlobalInterceptors` and `{ provide: APP_INTERCEPTOR, useClass: X }` are a `nest-global-interceptors` fact: middleware text on every route, and `inheritedMiddleware` for every project interceptor's `intercept` (framework types contribute middleware text only). ASP.NET `[ServiceFilter(typeof(X))]` / `[TypeFilter(typeof(X))]` on controllers and Razor `PageModel` classes land in `RouteInfo.filters` and name the filter type's pipeline entry in `middlewareCalls` — `OnAuthorizationAsync` / `OnAuthorization` when the type name says Authorization, otherwise action-filter methods — (`csharp/routes/filter-middleware.ts`; class-level filters on a page model reach every handler in `razor-pages.ts`).

**Loops over a constant of classes.** The Python data-source reader reads `for model in MODELS:` / `MODELS.values()` / `.items()` over a module-level `MODELS = {…}` / tuple / list / set a module assigns exactly once as a row per class listed, as it does for a literal written in the loop (a bare dict walks its keys and reads none). Classes a function adds afterward are included too: a `global MODELS` reassignment to a literal, `MODELS["k"] = X`, in-place `MODELS.append(X)` / `extend` / `update` (no `global` needed), or `MODELS += […]` with `global`. A local rebind of the same name without `global` is a decoy and contributes nothing.

**Vuex commits and names built from constants.** `commit(...)` is a dispatch of the mutation table (`javascript/vuex.ts`): the same key (`dispatchKeyOfArgs`) on a call whose receiver is the store's (`STORE_COMMIT`: bare `commit`/`context.commit` of an action, `store.commit`, `this.$store.commit`, `clubStore.commit` — `repo.commit('x')` is any object's and never gets a key), `mapMutations` read like `mapActions` (`this.SET_PAGE()` carries the key prefixed `commit:`), and `VuexDispatchResolver` looks the name up under `mutations.<M>` / `mutations.[CONST]` (a section parameter beside `actions`; links named `commit:<key>`, strategy `dispatch:vuex-action`, a bare commit inside a module joins its own module first). `new Vuex.Store({ mutations })` and computed mutation keys are named as actions are. A name built from an imported constant (`'clubs/' + types.FETCH`, `` `${NS}/load` ``) keeps the unknown part as a `${ref}` hole in the key (`holeOf`; locals, parameters and `this`/`props` never become holes); the resolver fills each hole with `constantValue` and drops the call when one is unknown. A `mutations` table is built like an `actions` one: `...baseMutations` spreads, `Object.assign({}, mutations, extra)` merges and a module a project factory builds (`storeShapes.spreads.mutations`, `factoryActions(…, "mutations")`); a table that one spreads in is followed too, three tables deep (`export const crudMutations = { ...baseMutations, RESET() {} }` — `storeShapes.spreads` keeps the spreads of any object named `…Mutations` / `…Actions`; `spreadMember` and `foreignMutations`), so the commit and the state watchers reach a mutation written two tables away, and only the module whose own table takes it in. Not yet: a name bound by both `mapActions` and `mapMutations` resolves as the action; the root store shared by the commit and state-watch joins (`vuexStores`) is a file registering `modules:` or one that builds a store (`StoreShapes.root`). State a mutation writes and the watchers reading it: see `core/AGENTS.md` (reactive-triggers).

**Store names read from another module, and the store a bound kind picks.** The JS plugin reports a module's plain string constants as `FileAnalysis.stringConstants` ([javascript/string-constants.ts](javascript/string-constants.ts): `export const LOAD = 'clubs/load'`, `ACTIONS.FETCH`, string enum members — no spaces, no holes, 200 a file). A `store.dispatch(ACTIONS.FETCH_CLUBS)` naming its action by a constant the file does not declare carries it as written in `CallInfo.args[0]`, a Vuex action keyed by a constant (`[ACTIONS.FETCH_CLUBS]() {…}`) is a function named `actions.[ACTIONS.FETCH_CLUBS]`, and the Vuex dispatch resolver reads both through the import chain (`constantValue` in [javascript/vuex.ts](javascript/vuex.ts): named, aliased and namespace imports, re-exports; the import picks the file, so a same-named constant elsewhere is never mixed in) — joined by the local name in a namespaced module, or by the whole name in a store that is not. A record of call results indexed by a prop (`stores[props.kind]`; `LocalType.key` per entry, `CallInfo.indexOrigin` / `LocalType.indexOrigin` for the index) is narrowed by the plugin's `recordChoice` ([javascript/record-choice.ts](javascript/record-choice.ts)) to the entries the component's users bind the prop to — a literal (`kind="player"`), an imported enum member or constant (`PropBinding` origin `constant`, `:kind="Kind.Club"`; only a dotted name or an UPPER_SNAKE one), or a prop they hand on — each link kept to its binding sites (`viaUsage`); no binding naming an entry, or an entry key it cannot read, keeps the fan-out over every entry. The IIFE `switch` store picker stays refused. A binding whose value cannot be read does not drop out of that narrowing: the plugin lists it in `FileAnalysis.unreadPropBindings` (`:kind="row.kind"`, `kind={pick(x)}`, a JSX string literal, which `propBindings` keeps none of), and a bound value of another origin (a route parameter) counts the same — `PropLiterals.complete` is then false and `recordChoice` returns null, so the read reaches every entry (never narrower than what one user could pick). A `dispatch(props.fetchKey)` still links only the names read: it has no list of every action to fall back to, so an unread user's action stays unlinked (the one residual gap).

**A store picked by an IIFE `switch`.** `const store = (() => { switch (props.kind) { case "club": return useClubStore(); … } })()` is stated by `switchRecordEntries` ([javascript/dispatch-maps.ts](cli/src/extractors/plugins/javascript/dispatch-maps.ts)) as the record `store[]` — one `localTypes` entry per case literal with its `key` (grouped cases share their return; a `default` that returns a call has no key, so `recordChoice` cannot narrow and the read reaches every entry; a `default` that only throws holds none) — and a local `store` whose `from` is `store[]` with `indexOrigin` the switch's discriminant when it is a plain prop. Core's `recordCall` then narrows exactly as for a record read at a run-time key. The same `switch` in a named helper of the file (`function pickStore(kind) { switch (kind) { … } }` or `const pickStore = (kind) => …`, one plain parameter, nothing else in its body) states the same record for `const store = pickStore(props.kind)`: the discriminant is the helper's parameter and the origin is the prop the call hands it (`localFunction`, `soleSwitch`, `switchArms`). Any other shape (a case returning a non-call, extra statements, a computed or non-literal case, a discriminant that is no plain prop, an IIFE with parameters, a helper another file declares or one handed anything but a plain prop) states nothing; a `dispatch(props.fetchKey)` whose binding cannot be read stays unlinked.

An array a parent hands a child whose loop calls `x.run()` over a prop (`v-for="x in props.extra"` or `extra`, `ScopeEntry.fromProp`) is the function prop `extra.run`: a declared array's callbacks written in place are bound by their held names (`<rows[].run@5>`, `vueArrayFunctionProps` given the file's function names), and an array literal in the template gives one `:extra.run` element per key (`arrayArrows`, one function holding the calls of every object's arrow) — Vue only; React arrays through props are not read.

**CommonJS barrel.** `module.exports = { build, forge: maker }` and `exports.build = build` / `module.exports.build = build` over names the file binds from `require` (`const { build } = require('./thing')`, `const maker = require('./maker')`) state each as a source-less `re-export`, which the linker's `forwardedDefinition` follows through the import like `export { build }`; a name the file declares itself is no barrel entry.

**C# scope from the build (`csharp/package-manifests.ts`).** `projectFileUsings` applies MSBuild items in evaluation order: the SDK's implicit global usings (the Blazor WebAssembly SDK adds only Configuration, DependencyInjection and Logging — per the SDK's props), then `Directory.Build.props` — the nearest one, plus each parent it imports through `GetPathOfFileAbove`, outermost first — then the project body; a `<Using Remove>` takes away what came before it, so a Remove in the props and an Include in the project keeps the namespace (a conditional Remove still counts, a conditional Include does not). `<Using Include Static="true">` is a project-wide `using static` of that type. The linker (`projectStaticScopes`) reads it, and a `global using static` of any file, as a scope every file of the sub-project has for bare calls, as a file-level `using static` is; an implicit import counts as a static only when it names a class of the project. A `using static` source is normalized (no spacing, no `global::`), and the linker names a nested static class through the classes whose lines enclose it before matching it (`League.Outer.Inner`). A file found by the name of its type (`using static Fx.Tools.Parts;` → `Parts.cs`) is the import's only when the namespace it declares is the one the source names (`importPath`, `nestedPackageLookup`): a namesake `Parts` of another namespace is never opened, and a qualified `Parts.Tune()` over classes of several namespaces takes the one the compiler's lookup (`nestedPackageFile`) decides, else no link.

**Scope evidence, PHP and Rust.** A PHP file that opens several namespaces (`namespace A { … } namespace B { … }`, or `namespace A;` then `namespace B;`) records each class's own `ClassInfo.namespace` (a file with one states it once, in `declaredNamespace`); the linker's `filesNamedByEvidence` compares a candidate class on its own namespace and a caller on the namespace of the class around the call (a free function of a later namespace carries its own `FunctionInfo.namespace`, which the namespaced-function lookup reads instead of the file's first). A facade accessor may be `return self::TOKEN;`/`static::TOKEN` (a string or `X::class` constant of the facade) or several returns that all yield the same value. When the constant is not the facade's own, the accessor is `staticProxyOf: { constant }` and a trait's string constants ride its `fieldValues`; a class extending a `*Facade` base records its constants the same way, and core reads the one value the facade's traits and facade bases (up to four `extends` hops) agree on; a facade may extend such a base when it states the accessor itself. The qualified-function index keeps same-named functions of two namespaces of one file apart by line. Rust path calls keep every earlier segment on `receiverType` in all three readers (ANTLR, ANTLR macro, regex); a segment the manifest's `pathCallTypesNeedScope.typeSegment` calls a type (`Shape::Kind::make()`) makes an associated-type path no import or module path binds, so the linker leaves it unlinked — unless the segment names a module file of the project (`mod Util;` in `Util.rs`, `namesModuleFile`), when it is a module and the type binds through it; a written path to a free function of such a module (`crate::Util::tune()`, `capitalizedModuleCall`) is read as the lowercase spelling is — `target` the path, `member` the function, `moduleMember` — when no project type bears the name, and a bare `Util::tune()` stays a type call. A `#[path]` module's import source `./x.rs::inner` resolves `inner` below the file (a path-loaded file holds its children as a `mod.rs` does: a `mod inner;` it declares itself, which no `foo/inner.rs` answers, is `inner.rs` beside it, so its `pub use inner::X;` re-exports are followed). A client verb handed a URL helper the same file declares (`get(club_url(&self.base, id))`, the helper's body one `format!`) takes the helper's template with the arguments in place; a helper another file declares — a function whose whole body is one `format!` carries `FunctionInfo.urlTemplate` (`rust/url-helpers.ts`, parameters as `{name}`) — is called through a `use` of its name (`club_url(id)`) or its module (`urls::club_url(id)`, only a module the file binds by `mod`/`use`): the target is the hole `${club_url(id)}` / `${urls.club_url(id)}`, which core's symbolic-target pass fills from the helper of the file the name stands for, a namesake of another module never; a multi-line `#[wasm_bindgen(…)]` on an `impl` reads like the one-line form.

**C++ template heads, dependent types, scope (E-216).** `templateHeads` closes a head at the `>` that balances its `<`, never one inside parentheses (`template<int N = (A > B), class Player>`). A type written `Ledger<M>::Row`, `M` a parameter of the head, is dependent whatever `Ledger` is: parameters and locals keep it as `Ledger::Row`, so `dependentTypes` reads the pair off the signature/body text and untypes it — except the class's own name with its own parameters (`Squad<K, C>::Slot` inside `Squad<K, C>::first`), which is the class being defined. **One-line class bodies (C++).** `struct Base { First actions; void Work() {} };` and `namespace league { struct Club { void Play() {} }; }` read as their multi-line spelling. Order-check input: `parsers/antlr/order-inputs/one-line-bodies.cpp`.

**C/C++ pointer aliases, pair members and Qt string slots.** A pointer or reference alias (`using ClubRef = Club*;`, `typedef const Club* ClubView;`) is a `typeAliases` entry for what it points at (`pointeeOf` in [shared/c-family-aliases.ts](shared/c-family-aliases.ts): one level of `*`/`&`/`&&` and cv-qualifiers dropped, `Club**` kept as written and so untyped), so `ClubRef c; c->play()` types like `Club* c`. A range-for structured binding takes the members of the `pair`/`tuple` a container holds (`for (auto& [a, b] : rows)` over `std::vector<std::pair<Club, Team>>`; `cppRangeBindings` in [cpp/collection-element.ts](cpp/collection-element.ts), which also reads a map's key and value, the `pairOf` hook of `extractCFamilyLocalTypes` returning one entry per position — a pointer or non-class member stays null); a container a body does not declare (a header's field) is not read this way yet. A type written through a CamelCase namespace (`LeagueCore::Valve`) reads as a nested class path; where no class bears that path but `Valve` is declared in namespace `LeagueCore`, the member type and `declaredTypeName` mean that class, never the file's own anonymous-namespace `Valve`.

**C++ one-segment direct init and field-path calls (regex fallback).** `Club c(3);` is a constructor call of `Club` the same way `Rank::Iterator it(2);` is of `Rank.Iterator` (`DIRECT_INIT_CALL` / `declarationCallPatterns` in [cpp/index.ts](cpp/index.ts): a one-segment capitalized type is the call name, a nested path keeps the owner as the receiver). **Function values through Vue props and mixins ([javascript/dispatch.ts](javascript/dispatch.ts), [prop-bindings.ts](javascript/prop-bindings.ts), [vue-hooks.ts](javascript/vue-hooks.ts)).** A mixin that itself lists `mixins: [base]` puts the base's imports in scope too (`withMixinScope` marks them `inScope` in a plain script; `scopeMember` follows the chain three levels, the nearer definition winning). `components.forEach((c) => Vue.component(c.name, c))` over an array of imported components registers each under the `name` option it declares (`SubComponentInfo.registeredByName`, `FileAnalysis.componentName`; `globalComponentFiles` reads the target's name, none declared is no tag). A parent's `:extra="[{ run: archive }]"` (or a declared literal array) hands `extra.run` down (`vueArrayFunctionProps`), and a child loop `v-for="x in extra"` over a declared prop marks its scope `fromProp`, so `x.run()` links to it. A Vue `<script setup>` template's bare callback prop (`:on-confirm="saveClub"`, the child calling `props.onConfirm()`) also puts a `passed: "attribute"` call of that name on the page's `<setup>` (`vuePassedFunctionProps`), so the page links to `saveClub` as `passes` the way JSX's `onConfirm={saveClub}` does — never a map/array member, an imported map, or a script-mounted dialog (`importSource`); an Options API page's methods already are the page's, so it invents no `<setup>`; the child's prop call stays the prop-callback resolver's, scoped by `viaUsage` to the page that binds it.

**A prop run in a getter (Vue Options API, [javascript/functions-classes.ts](javascript/functions-classes.ts), [javascript/dispatch.ts](javascript/dispatch.ts)).** A `computed` member (its `get`, not a writable `set`) and a `watch` callback of an Options component are marked `FunctionInfo.reactiveGetter` (`computed` / `watch`): the framework runs them on a state change or read, never a person's click. **Go package variables ([go/value-flow.ts](go/value-flow.ts)).** A package variable a function writes is a `ValueCell.module` cell in that function's facts (a parameter or local may flow into it; the file's `<setup>` states the name), and a package variable declared without a value (`var hooks []func()`, a function type or collection of them) is bound by a module self-copy. `m[k]` with an identifier key is read by the grammar as a type instantiation (`typeArgs` on the operand), so a single type argument is an index with an unknown key (its element member `[]`). **Go method sets follow the receiver kind ([go/addressed-types.ts](go/addressed-types.ts)).** `FunctionInfo.pointerReceiver` marks a `func (c *T)` method (both Go front ends read it from the declaration line), and `FileAnalysis.addressedTypes` lists the types a file uses by address — `&T{…}`, `*T` outside a receiver, `new(T)`, `&x` of a local or parameter declared `T` (an `&x` it cannot type adds every value type the file names). **C# names the language resolves before types.** An `extern alias` qualifier is the assembly, not part of the name: `using LeagueV1::Com.Example.League;` imports the namespace after `::`, and `LeagueV1::Com.Example.League.Club.Sign()` names the call without it (two assemblies declaring one namespace stay undistinguished). **Unwrapping calls where there is no `await`.** A manifest's `valueOut` hook (`extractors/shared/value-out.ts` builds it from a plugin's tables: `calls`, `members`, `elementCalls`, `elementOf`, `index`) is the one question "what does this hop take out of a declared type"; its `calls` table names the calls that take the value out of a wrapper and the wrappers each one unwraps — Java and Kotlin: `join` (`CompletableFuture`), `get` (`CompletableFuture`, `Future`, `Optional`), `orElseThrow` (`Optional`), `block` (`Mono`), Kotlin `await` (`Deferred`). Core's chain walk (`walkChain` in `core/symbol-linker.ts`) asks the hook (`takes` before reading any declaration, `at` on the declared type) and goes on from the wrapper's first type argument when the call before one of these DECLARES a listed wrapper — `var c = repo.findAsync(id).join(); c.promote()` and `repo.findMono(id).block().relegate()` reach `Club`; a project class's own `get()` keeps its declared return type, and an unlisted generic's `join()` unwraps nothing. Keys are read as own properties only (`toString` is no unwrapping call).

**Unwrapping a wrapper a field, parameter or method declares.** The hook also fires when the head or a middle segment of the chain DECLARES the wrapper (`private Provider<ClubRepo> provider; provider.get().save()`, `this.provider.get()`, a `Provider<ClubRepo>` parameter), and its `members` table names the members that hold the value — Kotlin `.value` on a `Lazy<T>`, C# `.Value` on a `Lazy<T>` / `IOptions<T>` / `IOptionsSnapshot<T>` (`CurrentValue` on `IOptionsMonitor<T>`), read by `unwrappedDeclared`/`wrappedHead` in `core/symbol-linker.ts` from the written type. `wrapperShadowed` stays per hop kind: the hook returns the head it read and core refuses a project class of that name (a local's type is read only when its plugin keeps the type arguments and one declaration states it). The wrapper must be listed under that member, so `Box<ClubRepo>.value` and a project class with its own `get()`/`Value` unwrap nothing, and a wrapper name the project declares as a class (its own `Lazy<T>`) is never unwrapped. A wrapper is never a `transparentTypeWrappers` entry: `provider.get()` would then link to a `get` of the wrapped class.

**A local holding the unwrapped value.** The hop also works from a local: a Java/Kotlin `var c = repo.find(1); c.get().save()` reads the wrapper off the declared return of the one call the local is initialized from (not awaited, no `choice`), and a C# `var s = _options.Value; s.Reload()` and a Kotlin `val s = lazy.value` state `localTypes[].from = "_options.Value"` with `member: true`, as does EVERY plain member read off names (`var m = club.Boss`; Java `var m = club.manager`, a Kotlin `val t = settings.turf`; never a call, indexer or `?.` in the path) — the plugin never consults the hook's `members` table: the linker takes the value out of a listed wrapper there and else types the local by the member's declared type, untyped where that is no project class.

**Elements of a declared list or map, and map entries.** The hook's `elementCalls` (Java/Kotlin `get`) with `elementOf` (`jvmIndexedElement`: a `List`'s element, a `Map`'s VALUE, one plain type name) let the linker take one element out of what the segment before DECLARES — `repo.all().get(0).promote()`, `club.players.get(0)`, `var l = repo.all(); l.get(0)`, `var c = repo.all()[1]` (Kotlin states the index as written, `repo.all()[1]`: `receiverChain` makes it an `index` segment, kept only where the hook has an `index` member — Kotlin `get` — and then an index no hop takes an element out of calls that member) — in the same `walkChain`/`wrappedHead`/`unwrappedDeclared` hops as the wrappers; a project class's own `get(int)` is no list and keeps its declared return, and a project class named like the collection shadows it (`wrapperShadowed`). The Java/Kotlin plugin types a loop over `m.entrySet()` / Kotlin `m.entries` / a map looped directly as a `kind: "entry"` state of the shared element chain (`ChainRules.entries`/`entryValue`/`entryKey`: `entrySet()` is a collection whose `elemState` is the entry's key and value types, never a `Map.Entry<K, V>` text), so `en.getValue()`, `en.getKey()` and Kotlin's `en.value` type; a name two loops bind to different entries is dropped. Only a TYPED map root (parameter, field, typed local) is read; a call-initialized map (`repo.byName().entrySet()`) stays untyped.

**Operator lambdas take the element of the wrapper.** In Java/Kotlin a lambda handed to `map`, `flatMap`, `flatMapMany`, `concatMap`, `doOnNext`, `doOnSuccess`, `subscribe`, `thenApply`, `thenAccept`, `thenCompose`, `ifPresent`, `forEach` (Kotlin `collect`) on a call's result binds its first parameter as `localTypes[].from` + `element`, and the linker takes the element from the declared return type through the manifest's `collectionElementOf` — here `jvmElementText` ([java-kotlin/wrapper-elements.ts](java-kotlin/wrapper-elements.ts)): the shared collections plus `Mono`, `Flux`, `CompletableFuture`, `CompletionStage`, `Optional`, `Stream` (Kotlin `Deferred`, `Flow`). **A name the nearest binder rebinds keeps no stale type.** A documented formal (PHP `@param`, Ruby YARD/Sorbet `@param`) holds only while the body does not assign the name again (PHP: assignment, `??=`, `foreach … as`, `list`, `&`; Ruby: any `x = …` but the identity-keeping `x = x.reload`/`.dup`/`.clone`/`.itself`/`.freeze`); then the local's own initializer type applies, or nothing. A Dart untyped (or `dynamic`/`var`/`final`) closure parameter named like a typed formal marks its calls `boundLocally` (`markShadowedClosureParams`, both front ends). A Go `type X` declared in a function body hides the package's `X` from that line on (`hideShadowedTypes`, after the struct-literal pass; both front ends). The parameter of a JS function expression assigned to `this.x` — and of a callback nested in it — states no handed argument (`handedArgs`) and no value-flow seed.

**Imports bind only what their path names.** Where `classNamesByEvidence` is set (PHP), a `use` of a namespaced class names the class declared in exactly that namespace (`ClassInfo.namespace` / `declaredNamespace`) wherever its PSR-4 directory sits — in the typed-receiver lookup and the component graph. **Perl calls.** Perl states its own call forms (`replacesBaseline`): `Pkg->m` and `Pkg::f(` are calls on the package (spelled `Pkg.m` with `receiverType`; `nestedTypePaths` keeps `League::Club` apart from `Garage::Club`), `my $x = Pkg->new` types the local (not a chained `Pkg->new->build`), `$x->m(` needs its parentheses, `$self->m(`/`__PACKAGE__->m` resolve on the enclosing package and its `use parent`/`use base` parents (`-norequire`, lists, `qw`; the first parent `extends`, the rest `implements`), builtins are no calls, and a package-less script's statements are its `<setup>`.

**SQL identifiers are Unicode.** Table, view, foreign-key and column names (and the table tokens of inline SQL, `shared/sql-string-sources.ts`) read `[\p{L}\p{M}\p{N}_]` with the `u` flag, so `CREATE TABLE 球员` is an entity and `SELECT * FROM 球员` a table access; keywords stay ASCII. **JS/TS dead code: what loads a file without naming it.** A computed load (`import(`./plugins/${n}`)`, `require("./cars/" + n)`, `path.resolve("configs", `config.${m}.ts`)`) is a path reference over its literal part (`./plugins/**`; a bare `./${n}` only that folder); a Vue `<script src>` is an import and `<template src>`/`<style src>` path references; a CI or Makefile run line is a passive entry (`ciRunEntries` → `ReachabilityInput.passiveEntries`: kept alive with its imports, never reported, anchoring nothing); `bin/` beside a `package.json` with source is re-admitted (`sourceDirs` `directOnly`); folders named `…migrations`, `db/migrate`, `seeds`/`seeders`, `codegen.ts` and a code generator's `generates:` outputs are tool-loaded; a workspace subpath through a tsconfig `outDir`/`declarationDir` resolves to its source.

**Config reads.** A plugin whose code reads configuration keys marks the row `DataSourceInfo.configRead` (`kind: "env"`, `target` the key as written, no default — Java `@Value`/`@ConfigurationProperties` in [java-kotlin/data-sources.ts](java-kotlin/data-sources.ts), and a Terraform `variable` block as `FileAnalysis.configKeyReads` through the spec's `extractConfigKeyReads` — never a data source) and lists the files that set keys in `serviceConfig.sources` (Terraform's [tfvars.ts](terraform/tfvars.ts), `keysOnly`, names only); core joins them (`core/config-keys.ts`). Never resolve a key to a file in the plugin.

**File path reads.** `meta.ast.filePathReads(tree, text)` → `FileAnalysis.filePathReads`: literal path parts only (Java/Kotlin `File`/`Paths.get`/`Path.of` in a file importing `java.io`/`java.nio.file`, Python `open`/`Path`/`os.path.join`, JS/TS `fs.readFileSync` & co. on `fs`, `path.join`/`resolve` in a file using `fs`); a hole, a variable or another receiver states nothing. Core resolves them (`core/config-files.ts`). Spring `Environment.getProperty`/`getRequiredProperty` on a receiver declared `Environment`/`ConfigurableEnvironment`/`PropertyResolver` in a file importing `org.springframework.core.env` is a `configRead: key` row like `@Value`; an untyped receiver, `Properties` or a project class stays a plain read.

**Type-parameter bounds type the parameters written as them.** Java `<U extends Boat>` / `class Garage<T extends Car>`, Kotlin `fun <U : Boat>` / `class G<T : Car>` (also `where U : Boat`) and C# `M<U>(U u) where U : Boat` / class-level `where T : Car` give each parameter and typed local written as that bare letter the bound as its `ParamInfo.type` / `localTypes[].type` ([java-kotlin/type-bounds.ts](java-kotlin/type-bounds.ts), [csharp/type-bounds.ts](csharp/type-bounds.ts)), so `u.sail()` links like any typed receiver — core is untouched. A method's own letter beats an enclosing class's of the same name, innermost class first; an unbounded letter shadows an outer bound and stays untyped. With several bounds the FIRST is taken (`T extends Car & Comparable<T>` → `Car`; Kotlin `where` order; C# `where T : class, Boat` skips `class`/`struct`/`new()`/`notnull`/`unmanaged` and takes `Boat`) — the plugin cannot tell a project class from a library interface, so a project class listed after a library bound is missed. A bound that is itself another letter of the member (`where T : U`) leaves the letter untyped; the Kotlin extension receiver (`fun <T : Boat> T.dock()`) takes the bound; fields and constructor properties written as the letter, and a local class or lambda inside a generic method, are NOT yet covered (open). The letter-to-bound substitution is [shared/type-parameter-bounds.ts](shared/type-parameter-bounds.ts).

**A column on api-call rows.** `DataSourceInfo.column` (0-based UTF-16 code units from the line's start — a JS string index, never a byte count) is stated by every plugin that makes an api-call row, from the node's `startPosition.column` (tree-sitter) or the match index within the line (regex tiers), and by the three core passes that build rows from other facts (`client-proxies.ts` and `grpc-clients.ts` carry the source `CallInfo.column` when it has one; `config-patterns.ts` computes it from the match index). A row whose position is unknown stays column-less, never 0: a reader that cuts text before matching (Pascal's comment stripper, PHP views' rewritten tags) states a column only when the line's text before it is unchanged. The element-request rows (`shared/element-requests.ts`) take it from `InteractiveElementInfo.column` — the tag's offset, stated by the HTML reader only on an element carrying a `request` or `ownViewPost`, and only while the masked line still starts with the given one (a removed comment shifts it); PHP views and Astro re-check it against the source's own line (`keepSourceColumns`), Blade re-checks it the same way (echo bodies are cut from its lines). The Lisp family's rows take the open-paren offset the s-expression reader keeps on a `(`/`[`/`{` `Form.column` (relative to the text read — a body slice's is its own); `extractGqlDocumentCalls` counts the operation keyword's column.

- **TypeScript tuple destructuring.** `const [club, player] = load()` (and `await load()`) states each identifier as a local `from` the call with `fromIndex` (a hole counts, a rest/default/nested element states nothing); the JS/TS manifests' `tupleElementsOf` ([javascript/tuple-elements.ts](javascript/tuple-elements.ts)) reads the declared `[Club, Player]` (`readonly`, labelled members; never an array, a rest or an optional member), through `Promise` when awaited. Go multi-value returns (`c, err := repo.Find(1)`) already type the first result by the declared results.
- **Kotlin, C# and Swift tuple patterns.** The same `fromIndex` locals and a manifest `tupleElementsOf`: Kotlin `val (club, player) = load()` over `Pair`/`Triple` (`java-kotlin/wrapper-elements.ts`) and, with `bindsStructFields`, over a data class's constructor properties in order; C# `var (club, player) = Load()` and `(var club, var player) = Load()` over `(Club, Player)`, `(Club club, Player player)` or `ValueTuple<…>`, awaited through `Task` (`csharp/tuple-elements.ts`; a class with its own `Deconstruct` states nothing); Swift `let (club, player) = load()` over `(Club, Player)` / labelled, or the annotation `let (a, b): (Club, Player) = …` (`swift/tuple-elements.ts`). A discard or nested pattern only takes up a position.
- **Receiver-typed blocking calls.** `blockingOnReceiver` (`{ receiverTypes, members, types }`, C#: `Wait` on `Task`/`ValueTask`) lets core's `findBlockingInAsync` flag `receiver.member()` inside an async function when the receiver's declared type matches — a parameter, a local's stated type, a field of the caller's class, or the declared return of the call it was initialized from (`own()`, `field.method()` through a class the project declares once). An unknown type, a project class named like the type, or a sync method flags nothing; A chained `repo.SaveAsync().Wait()` is typed by the declared return of `repo.SaveAsync()`. `.Result` is a property read no call states: with `readMembers` (C#: `Result`) the plugin states `FunctionInfo.propertyReads` (`csharp/property-reads.ts`: a name, `this.field` or a call chain as receiver, only in an async method, never inside a lambda or local function, never a name the body awaits), and the same receiver-type test judges it.

**A JSX tag through a namespace import** (`import * as UI from "./ui"` + `<UI.ConfirmDialog onConfirm={save} />`) states `SubComponentInfo.namespaceMember` (`{ source, member }`) with `importSource` left null; the JS plugin's dispatch resolvers are wrapped by `seeingNamespaceTags` ([javascript/namespace-tags.ts](javascript/namespace-tags.ts)), which hands each a copy of the analyses whose such tags carry the file the member lives in — the module's own export, a barrel's `export { X } from`, or `export *` when exactly one file defines it, four hops at most; a member no export reaches stays unresolved, never a leaf-name guess — so bindings, emits and the `dispatch:renders` link attach as for a named import. The same view resolves a plain import that names a barrel (`import { ConfirmDialog } from "../ui"`, `import { Referee as W }`, a default re-export `export { default as X } from "./X.vue"` — React, Vue and Svelte alike, since it reads `SubComponentInfo.importSource` and the file's own import for the name asked) to the file the export walk reaches, and a dotted namespace tag goes further: `<UI.Forms.Dialog/>` (`namespaceMember.member` is dotted), a head that is a relative named import of a namespace the module re-exports with `export * as UI` (`namespaceMember.through`), and a CommonJS `const UI = require("./ui")` head. A name two files of an `export *` both define, or one no export reaches, stays unresolved.
