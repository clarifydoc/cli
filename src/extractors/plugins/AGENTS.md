# src/extractors/plugins — Per-language implementations

Each language gets one folder. Two patterns are used depending on whether the language has a working tree-sitter grammar:

## Tree-sitter plugins (AST-based)

Folders: `javascript/`, `python/`, `java-kotlin/`, `csharp/`, `pascal/`

Contents (varies slightly per language):
```
<lang>/
├── manifest.ts               LanguagePluginManifest — STATIC tier (extensions, grammar, patterns, framework rules), eagerly aggregated
├── meta.ts                   LanguagePluginMeta — LAZY tier (spreads the manifest + hooks/extractors), loaded via registry LOADERS
├── frameworks.ts             FrameworkRule[] — manifest-level framework detection for the ecosystem (optional)
├── functions-classes.ts      extends FunctionClassExtractor
├── imports-exports.ts        extends ImportExportExtractor
├── data-sources.ts           extends DataSourceExtractor (optional)
├── data-mutations.ts         extends DataMutationExtractor (optional)
└── routes/                   framework-specific route extractors (optional)
```

Each extractor class implements `abstract collectFunctions(node, results)` / `collectClasses` / `collectImports` / etc. using tree-sitter AST walking. Instances are carried on the plugin's meta (`meta.functionsClasses`, `meta.importsExports`, `meta.routes`, `meta.dataSources`, `meta.dataMutations`, `meta.entities`, `meta.dispatchResolvers`, `meta.routeResolvers`) — the domain `src/extractors/<category>/index.ts` files dispatch via `pluginFor(language)` and import no plugin code. Family plugins share ONE instance across member metas (instance identity = run-once in project-level passes like `reconcileProjectEntities`); dispatch resolvers carry a `priority` that fixes cross-plugin link order.

## Regex plugins (source text–based)

Folders: `go/`, `rust/`, `ruby/`, `php/`, `swift/`, `lua/`, `scala/`, `dart/`

Contents:
```
<lang>/
├── meta.ts     LanguagePluginMeta — builtins, extensions (from the spec), parsing: "regex"
└── index.ts    exports a RegexLangSpec
```

The `RegexLangSpec` declares:
- `functionPatterns` — regex + isExported/isAsync predicates
- `classPatterns` — regex + extends extractor
- `importPatterns` — regex + source/specifier extractors
- `indentBased` — true for Ruby/Lua, false for brace languages
- `lineCommentPrefixes` — `["//"]`, `["#"]`, `["--"]`, etc.
- `extractRoutes` (optional) — custom route extraction for frameworks like Rails controllers, Go muxers, Laravel attributes

The shared framework in [shared/regex-base.ts](shared/regex-base.ts) handles:
- Walking lines, matching patterns
- Finding end-of-block (braces or indentation)
- Extracting params, properties, calls from bodies

Specs are loaded by [../../core/regex-extractor.ts](../../core/regex-extractor.ts).

## shared/

[shared/regex-base.ts](shared/regex-base.ts) — the `RegexLangSpec` type and the generic `extractFunctionsWithSpec` / `extractClassesWithSpec` / `extractImportsWithSpec` / `extractCallsFromBody` helpers used by all regex plugins.

[shared/brace-code.ts](shared/brace-code.ts) — a brace language's literal forms (`BraceLexicon`: comments, strings, raw strings, character literals) and the spec hooks built from them (`braceCodeHooks`): `blockEnds` counts braces over code only, `callSourceLines` blanks raw strings and block comments for the call scan, `commentFreeLines` is what a route scan reads, `startsInCode` keeps a function pattern out of comments and code templates. Go, Rust, C, C++, Scala and Swift use it (Scala with blocks that end by braces or indentation, `scala/blocks.ts`; C and C++ through [shared/c-family-code.ts](shared/c-family-code.ts), which also says when a signature is a definition); [shared/call-chains.ts](shared/call-chains.ts) names a method called on a call's result as the chain (`Club.new().register`).

[shared/project-info-queries.ts](shared/project-info-queries.ts) — `hasDep` / `hasGoMod` / `hasCsprojPackage` / … predicate helpers over `ProjectInfo` for `frameworks.ts` rules.

[shared/handler-taint.ts](shared/handler-taint.ts) — request input followed through ONE request handler to a sink (SQL text, command, file path, outbound URL, redirect, eval), the plugin's `ast.taint` hook. The algorithm is here; a plugin supplies a `TaintSpec` (what a handler is, the request-input regex, assignment/call shapes, sanitizers, propagators — the calls whose RESULT carries their arguments' taint; any other function's result is not followed — and sinks with the argument that carries the danger). Python (`python/taint.ts`) and JS/TS (`javascript/taint.ts`) have one. A guard (`startsWith`, `safe…(`, `valid…(` on the value in an `if`) counts as a check. Measured on five real repositories: zero findings, after 16 false ones drove the propagator, guard and free-text-parameter rules — precision first, every finding is an accusation.

[shared/security-context.ts](shared/security-context.ts) — `CREDENTIAL_CONTEXT`, the lookahead that keeps an MD5/SHA-1 rule to lines about a credential.

## Framework detection (frameworks.ts)

Manifest-level framework rules live with the plugin that owns the ecosystem —
`plugins/<lang>/frameworks.ts` exports `FrameworkRule[]`, wired via
`meta.frameworkRules` and aggregated by the registry into `FRAMEWORK_RULES`
(duplicate ids throw at registry build). `core/framework-detector.ts` only
gathers `ProjectInfo` and runs the rules; it knows no framework names, exactly
like `knownPackages`. Notes:

- Rule `check` predicates compose the helpers in
  [shared/project-info-queries.ts](shared/project-info-queries.ts).
- Detections are sorted by id in the detector, so output never depends on
  plugin registration order.
- Family plugins (javascript, java-kotlin, pascal) attach rules to ONE member
  meta only (typescript/java/pascal) so the registry sees each rule once.
- Cross-cutting rules live with the plugin that owns the file format:
  `qt` → cpp, `qt-quick` → qml, `sql` → sql, `jsp` → jsp,
  `spring-webflow` → springxml, `prisma` → prisma.
- Vendored frameworks with no manifest entry (CodeIgniter 2/3) declare
  `meta.markerCandidates` — well-known relative paths collected into
  `ProjectInfo.markerFiles` for rules to match on.

## Adding a new language

### Tree-sitter path (preferred when grammar is available)

1. `npm install tree-sitter-<lang>` (or verify WASM is in a deps package)
2. Add to `Language` type in [../../types/analysis.ts](../../types/analysis.ts)
3. Create `src/extractors/plugins/<lang>/` with per-category extractors
4. Wire each extractor instance onto the meta (`functionsClasses`, `importsExports`, `routes`, `dataSources`, `dataMutations`, `entities`, `dispatchResolvers`, `routeResolvers`)
5. Create `manifest.ts` (the STATIC tier: `language`, `family` — the import-resolution family, shared by languages that resolve each other's bare names (`jvm`, `dotnet`, `cfam`, `script`), else the language's own — `parsing`, extensions (one owner each: the registry throws on a second claim), `grammar` — package + wasm location, with optional per-file variant selection like tsx — test patterns, prefixes/roots, framework hints, `activationFiles`) and `meta.ts` (spreads the manifest, then adds builtins, complexity tables, security rules, ast hooks, and `calls` — at minimum `callNodeTypes`, plus name-resolution/scope hooks as needed; see `call-hooks.ts` in existing plugins). Register the manifest in `ALL_MANIFESTS` and the meta in `LOADERS` in [../registry.ts](../registry.ts) — extensions, discovery, grammar loading, complexity, call extraction, and the rest flow from there
6. If the ecosystem has detectable frameworks, add `frameworks.ts` (`FrameworkRule[]`) and wire `manifest.frameworkRules` (see "Framework detection" above)

### Regex path (languages without reliable grammar)

1. Add to `Language` type in [../../types/analysis.ts](../../types/analysis.ts)
2. Create `src/extractors/plugins/<lang>/index.ts` exporting a `RegexLangSpec`
3. Create `manifest.ts` (`parsing: "regex"`, `family`, `extensions` — the same list as the spec's) and `meta.ts` (spreads the manifest, `regexSpec: <spec>`, builtins), and register both in [../registry.ts](../registry.ts)
4. A script language whose files run their own statements sets the spec's `topLevelCalls` (`true`, or a path RegExp — VB sets it for `.vbs` only): calls outside every function/class become the `<setup>` pseudo-function. A top-level block that only REGISTERS code to run later (`get "/x" do … end`, `before_all do`) is listed by `deferredBlocks` so `<setup>` skips its body; the route carries the body's calls itself (Crystal `get "/x" do`, CoffeeScript `app.get '/x', (req, res) ->` — also inside a `module.exports = (app) ->` or other callback; `app.use` mounts and handlers named at the line's end have no body). Python's SQLAlchemy reader never gives a statement builder (`select(…)`, `func.count(…)`, `sa.select(…)`) a row of its own that names no model: `select(…).filter_by(…)` takes the model its `select` names (a parameter's stays with the session call's row), a bare `func.…` yields none — core would otherwise back-fill the import's module name (`sqlalchemy`) as the table.

### Container formats (e.g. Vue SFC, Delphi .dfm)

- A format that embeds another language (Vue) declares `preprocess` on the host
  language's meta — swap in the embedded source/language before parsing, and
  optionally merge container data back via `postExtract`.
- A format with its own parser (.dfm) declares `parsing: "custom"` + `customParse`.
- A parser front end may state each call's arguments (`PatternCallName.args` → `CallInfo.argCount`/`argKinds`/`templateArgs`; C++ `cpp/antlr.ts`): `callRecorder` then keeps one row per distinct (name, count, kinds, template arguments) in a function instead of one per name, so `g(1); g(1.0);` are two calls. The manifest's `calls.overloadTypeKey` folds declared types (`cpp/arg-kinds.ts`), `calls.conversionRanks` makes core rank exact > promotion > conversion (`argFit`'s `ranked` scale), and `calls.explicitSpecializations` has `convert<int>(x)` choose the definition whose `FunctionInfo.specializedOn` names those arguments. Core's `pickOverloads` reads a call's site from the link's own file only. An argument naming a variable is `@name` — also `*name` (a dereferenced pointer) and `this->name` (a field); core types it from the parameters, typed locals, `auto c = Club(3)` (a local whose one initializer is a construction of a class the project declares) and the class's fields.
- An extension several languages share (`.h`) has one owner, but how it is READ can depend on its sub-project: the
  owner's manifest `readingVariant(relativePath, mix)` gets the project's file counts by extension and names a
  variant (the C++ plugin: `c-first` for a `.h` in a project with `.c` and no C++ source) that its `meta.antlr` reader
  receives as a second argument. The analyzer counts the mix once, passes the variant in `FileTask.reading` (workers
  never see the mix) and folds it into the file's manifest `resolver` stamp, so a project whose mix flips re-reads
  its headers although no byte changed. `FileAnalysis.frontEnd.variant` records it.

## Conventions

- **One folder per language.** Even tiny regex specs (24 lines) get their own folder for consistency.
- **Visibility defaults matter.** Java/C# methods default to package-private (isExported=false unless explicitly `public`). Kotlin/TS default to public.
- **Decorators keep their arguments.** `decorators: string[]` holds the attribute/annotation text with its argument list (`Authorize(Policy = nameof(X))`, `ApiVersion("2", Deprecated = true)`), whitespace collapsed — that is where routing, auth and serialization semantics live. Consumers match with a regex or `includes`, never equality on a bare name. (Java's `extractAnnotations` still keeps the name only — a known gap.)
- **Route metadata is language-agnostic.** A route extractor that can see guards, API versions or parameter bindings fills `RouteInfo.middleware` (readable guard strings), `auth`, `versions`/`deprecatedVersions` and `params` — the same fields whatever the framework spells them as — through `shared/route-metadata.ts` (`GuardAttr`, `applyRouteMeta`, `inferredParam`). `csharp/routes/aspnet.ts` and `java-kotlin/routes/meta-annotations.ts` are the references: class-level attributes are inherited by every action, an anonymous marker waives, `[MapToApiVersion]` narrows, and a binding derived from framework defaults is marked `inferred: true`.
- **Enum-constant bodies and C++ operators.** A Java enum constant's override of a method the enum declares (`ATTACK { void play() { coach.shout(); } }`) hands its calls to the enum's own method of that name (same parameter count; an abstract declaration is the usual host); a method the enum lacks is still added. An anonymous class's calls stay with the enclosing function, but a bare one inside `new Base() { … }` carries `withSubjects` (the anonymous class, then `Base`), so it resolves on the base's member before the enclosing class's or a namesake's ([java-kotlin/java-anonymous.ts](cli/src/extractors/plugins/java-kotlin/java-anonymous.ts)); a local initialized by an anonymous class is typed as a synthetic class of the file (`Runnable$5_23`: `extends` the base, synthetic call-less methods), so `handler.run()` reaches its `run`. Kotlin constructor delegation is a construction like Java's `this(…)`/`super(…)`: a primary `class A(…) : Base(x)` gives the primary constructor (a synthetic parameterless one when none is written) a `new Base` call, a secondary `: this(…)` / `: super(…)` a `new A` / `new <superclass>` call, linked to the constructor its arguments choose ([java-kotlin/kotlin-delegation.ts](cli/src/extractors/plugins/java-kotlin/kotlin-delegation.ts)); a secondary constructor's statements are read as its body. In C++ (`cpp/antlr.ts`), `a + b` / `a == b` / `a < b` / `a << b` (first operator of a flat chain only) and `a[i]` are calls named `a.operator+` … when `a` is a parameter or local declared as a class-typed value — never a pointer, array, primitive or `auto`. The left operand may also be a field of the function's own class (`kit + o`, `this->kit + o`; an out-of-line `Club::f` reads `Club`'s members, collected per class by `collectFields`) or the pointee of a smart pointer, iterator or `this` (`*owner`, `*it`, `*this`), named `Club.operator+` with `receiverType`. A free `operator+(const Club&, …)` defined in the same file also gets a bare `operator+` call when its first parameter's type is the operand's: the file's only free definition of the name links on the left type alone, an overload set only when the right operand's type (a typed local, parameter, field, pointee or literal kind) equals the second parameter of exactly one overload — the call then carries both kinds as `argKinds`, so the linker's overload choice agrees. `it->m()` over a container iterator (`std::vector<Club>::iterator`, `auto it = squad.begin()`) and `*it` / `*owner` as an argument (`record(*it)`) read the element class off the container's or smart pointer's declared type, never a container of pointers. `(*it).m()`, `std::next(it)->m()` and a chain from `it->` read as the element's (`Boot.club().sign`); a method defined in a `.cpp` whose class a header declares names `kit + other` / `this->kit + other` as `kit.operator+` / `this.kit.operator+`, a member the linker types from the class's fields (a primitive field links nothing). An iterator over a field only the header declares (`auto it = boots.begin()`, `cbegin`, `find`, `lower_bound`) is a `localTypes` entry `element: true` from the field name (never when the body declares a local of that name), so `it->m()` and `(*it).m()` are named `it.m` and the linker types the element; `(*it)->m()` reads through a pointer or smart-pointer element (`vector<Boot*>`, `vector<unique_ptr<Boot>>`, `cppCollectionElementOf`), and a value element never takes `->` nor a pointer element `.`. A map's `it->first` / `it->second` are named `it$first.m` / `it$second.m` (types the file spells: the key or value class of `cppMapTypes`) with synthetic `localTypes` at `fromIndex` 0/1 read through `tupleElementsOf`, which also reads a map's key and value, only when the body uses them. A range-for over a map (`for (auto& p : clubs) p.second.m()`, `for (auto& [id, club] : clubs) club.m()`) reads the same way: a local `p` over a name the function does not declare (a field a header declares) names `p.second.m` `p$second.m` with `localTypes` `p$second` at `fromIndex` 1, only when the body uses it, a structured binding is typed at its position from the field's (or a local map's) key and value; the container a free function does not declare is a global no linker types, so its calls keep the plain name. A structured binding `auto [a, b] = f()` over a project struct (manifest `bindsStructFields`) types each name by the struct's data member at its position — the linker reads `ClassInfo.properties` in declaration order, nothing for a class with a base.
- **Tables named by an environment variable (DynamoDB).** A DocumentClient call (`docClient.get({ TableName })`, v2) or a v3 command (`new GetCommand({ TableName })`, `…ItemCommand`) in a file naming DynamoDB / `aws-sdk` is a `database` row ([javascript/dynamodb.ts](javascript/dynamodb.ts)): `TableName` a literal, a same-file constant, or `process.env.X` (directly, through `const T = process.env.X`, or `const { X } = process.env`; a request held in a local object is read too). An env name is `DataSourceInfo.envRef` with no target; the serverless plugin reads each descriptor's `environment` (`provider.environment`, a function's own, SAM `Globals.Function.Environment.Variables` and the function's) into `lambda-env` route facts ([serverless/environment.ts](serverless/environment.ts): literals, `${self:…}` read from the same file, `Ref` to a DynamoDB table resource → its `TableName`, else its logical id; `${opt:…}`, `${ssm:…}`, `!Sub` pseudo parameters and parameters `Ref`s leave the variable out), and its route resolver (`route-anchor.ts` `applyEnvironment`) gives the row the value: provider-wide for any code file below the descriptor's directory, a function's own for the module its handler names (which wins); a variable another service's descriptor sets, or two descriptors / functions of one module set differently, stays unset. Core then drops every row still carrying `envRef` — never a guessed table.
- **A POST form with no action posts to its own page.** The HTML reader marks such a `<form>` (and its submit controls) `InteractiveElementInfo.ownViewPost` (no `action`, or `action=""`; a template expression in the attribute is a URL and never marks it; GET never); core's [own-view-posts.ts](../../core/own-view-posts.ts) gives it `POST <path>` when every route rendering the screen (`ScreenInfo.renderedBy`) is at one path, and the api-call joins the route linker like a written-out action. A template served at two paths says nothing.
- **A Next.js `middleware.ts` / `proxy.ts` is a guard** only when its code checks the caller (a caller-check default-export name, a library wrapper, or a session/token read plus a redirect/401): `javascript/routes/next-middleware.ts` emits a `next-middleware` route fact with its `config.matcher` (none = all; an unreadable or `has`/`missing`-conditioned matcher guards nothing) and a resolver gives the matching Next routes of the same sub-project an inherited guard. A header-only middleware guards nothing.
- **JS/TS small shapes.** An Angular `httpResource(() => url)` / `httpResource({ url, method })` / `httpResource.text|json|blob|arrayBuffer(…)` is an api-call at that URL (GET unless a method is stated; `javascript/data-sources.ts` `httpResourceCall`), only in a file importing it from `@angular/common/http`; the options object is not read a second time as a request descriptor. A module whose default export is an anonymous async wrapper of a dynamic import (`export default defineAsyncComponent(() => import('./ClubCard.vue'))`, `createAsyncComponent(…)`, `lazy(…)`, `loadable(…)`) binds the imported module under a name derived from it (`ClubCard`) and names it the default's `sourceName`, so a page importing the wrapper resolves to the loaded component (`imports-exports.ts` `lazyBinding`/`lazyDefaultOf`); a loader name must say lazy/loadable or `…Async…Component…`.
- **Handlers declared elsewhere.** Express, Laravel, Rails, Go, Vapor, Phoenix… register a route by naming a handler whose signature the route line never shows. The extractor still sets `handler`; the plugin supplies what the handler READS (`FunctionInfo.requestAccess`, via the regex spec's `extractRequestAccess` or the AST extractor) and, for typed signatures, `meta.requestSchema.bindParam`. `core/request-schemas.ts` (`attachHandlerParams`) resolves the handler by name (same file → same sub-project → project-wide unique) and fills `params` from both. Never look a handler up from a per-file extractor. Name a handler `Class.method` (Play, Grails, Phoenix) when the route names its class: the linker then binds it only to that class's method (a namespaced `MyAppWeb.UserController` counts) and never, by name alone, to a same-named method of another class — an action the class lacks stays unresolved.
- **Request attributes and declared parameter types (Rails).** `Current.league = League.find(…)` (a constant finder, an `@ivar` the class assigns a model, or `Current.league.clubs.find(…)`) is kept per class in `fieldValues` under `Current.<attr>`; `RubyEntityExtractor.reconcileProject` types `Current.<attr>` when all assignments agree (any other assignment, or two models, types nothing) and, with no assignment, by the model the attribute is named after (`DataSourceInfo.entityConfidence: "INFERRED"`). `Current.<attr>.<assoc>.<verb>` then reads `<assoc>` on THAT model, which settles a name two models declare with different targets (only for the four-segment shape; concern- and inherited associations fall back to the global name). An `@x = param.reload` takes the model a YARD `@param` / Sorbet `sig` gives the parameter (every method declaring that name must agree).
- **Gem-supplied controller actions (Rails).** A controller override that calls `super` records a call named `super`; the route anchor (`ruby/route-anchor.ts`) then gives its route the gem action's model access (Administrate CRUD by the controller's name), and a `mount_devise_token_auth_for 'Model'` route carries a `rails-devise-model` route fact (the model and the access its gem action has) that anchors the same way when the mapped model is one class of the project. `devise_for :players` draws the routes of the modules the model's own `devise :…` line enables (on the model or an ancestor; `ruby/devise-routes.ts` joins the router's `rails-devise-for` fact with the model's `rails-devise-modules` one) — nothing for a model whose `devise` line the project does not state. A concern's bare verbs (`update!` in a `module X; extend ActiveSupport::Concern`) carry `DataSourceInfo.mixinSelf`: inside a method core binds them to the model each resolved call runs on (`core/mixin-self.ts` — a route's `model.update_badges` through the controller's typed reader keeps that model as the call's `receiverType`), and an untyped call binds none; in the concern's body (an `included do` callback) the entity pass makes them one row per including model. A concern's `model.member` call through a memoizing reader (`def model; @model ||= @x; end`) becomes the call of the model's member when `@x` is typed where it is assigned (a model constant, a one-target association, through other variables); `ClassInfo.fieldValues` also holds a variable assigned another variable (`@a`). A method whose last statement is a call chain off a class or off the instance's own method (`def build_car; Car.find_by(…); end` — an implicit return) carries it as `returnedFrom` like a memoizing reader, and `@car = build_car` (a bare name that is no local) is a one-step own-method chain core types through it; a last statement of anything else (a branch, a parameter, a literal) states nothing. `self.class.x` in an instance method of a class is named through the class (`Club.x`) whether or not the class declares `self.x`, so the linker walks its bases and extended modules like any class-method call (a library's `self.class.get` links to nothing).
- **Regex-path attributes.** A spec's `attributeLine` turns own-line attributes (`#[serde(rename = "x")]`, `<Required>`, `@Field(key: "x")`) into `decorators` on the function, class or property below them; inline tags (Go `json:"x"`) belong in the property pattern's `build`.
- **Request-schema hooks.** A plugin whose language has typed request models exposes `meta.requestSchema` (`unwrapNullable`, `describeType`, `serializedName`, `isSerialized`, `isRequired`, see `csharp/request-schema.ts`). The core pass in `core/request-schemas.ts` does the class lookup, inheritance flattening and recursion; the hooks only say what one type text means and what one property is called on the wire.
- **Reachability (dead code).** `meta.reachability` opts a language into dead-code judgement: `load()` reads the toolchain config once and returns the model core walks (entries by manifest and by convention, specifier → files, path references, template tags). Gate framework directory conventions (`pages/`) on the framework id so a plain SPA's dead page is still found, keep every other doubt on the "reached" side, and leave the hook unset for languages that find files by namespace/autoload. `javascript/reachability.ts` is the reference; `javascript/path-references.ts` is its per-file half (glob imports, worker URLs, config-file script paths → `FileAnalysis.pathReferences`). `rust/reachability.ts` (module tree; `mod:`/`path:` references via the regex spec's `extractPathReferences`) and `python/reachability.ts` (`__main__`, `module:`/`file:` references) follow the same shape. `pathReferences` is plugin-private dialect: only the plugin's own model reads it. Split conventions into `entryReason` (where the program starts — anchors a project) and `passiveReason` (run by a tool or instantiated by a framework — configs, migrations, scripts, `[ApiController]`s, `@Component`s): a project anchored only by a migration or a DbContext would have every other file reported. Most languages need no bespoke model: `<lang>/reachability.ts` is a `conventionReachability({...})` spec (shared/reachability-kit.ts) — extensions, `importPath`, which names a file declares, entry files / `main` / `@main`-style source patterns, framework attributes and base types (passive), config files whose identifiers name entries, and an `extend` hook for load-time rules (a Go module path, a gem's `lib/` as public API). C, C++ and Objective-C share one instance (shared/c-family-reachability.ts).
- **Dependency injection: report facts, never resolve.** Core (`core/symbol-linker.ts`) decides which implementation an injected receiver reaches; a plugin supplies the declared types (as written), injection-point `qualifier`s, constructor params, `localTypes` (typed locals and container lookups), `CallInfo.receiverType` for a lookup chained into a call (`calls.receiverTypeOf` / regex `callPatterns` `buildName → receiverType`), `kind: "interface"` (+ `structural`), `abstract` on an abstract class and on each bodyless abstract method (core dispatches through them as through interfaces), every implemented interface as its own `implements` entry, and container registrations as `diBindings` (`ast.diBindings` / `RegexLangSpec.extractDiBindings`). A `@Profile` naming a constant (`PROD`, `Profiles.PROD`, inside a list or a concatenation) is a `${…}` hole in `conditional.profiles`, which core's `resolveBindingConditions` (module-values pass) fills; a list with a name nothing states keeps the bare `Profile` condition. Emit every registration the source states, conditional ones included — core refuses to choose between disagreeing ones. Store the array `extractCalls` returns as-is (append in place): it carries the noise-named calls (`repo.find`) the per-file pipeline restores for typed receivers.
- **Doc comments.** `manifest.docComments` (a `DocCommentSpec` — line prefixes, block delimiters, `docstring`, the attribute lines that may sit between, `blockLead` for a block opened by a lead such as Elixir `@doc """`, `pod` for Perl `=head`…`=cut`, `moduleDocInside` for a module doc read from inside its body, `caseInsensitive` for batch `REM`) is all a language supplies — on the manifest, since MCP tools read it with no plugin body loaded; `core/doc-comments.ts` reads the first sentence above each function, method and class (or the docstring opening its body) into `doc`. Shared shapes: `extractors/shared/doc-comment-specs.ts`.
- **Alias of a typed local (`LocalType.aliasOf`).** A name assigned from another plain name — `const q = p`, Go `q := p` / `&p`, PHP `$q = $p`, C++ `auto& q = p` / `= *p`, Rust `let q = p` / `&p`, Python `q = p` and `(q := p)` — is a `localTypes` entry with `type: ""` and `aliasOf: "p"` (no `from`); core types it through `scopedName(aliasOf, depth + 1)` under the same `MAX_INITIALIZER_DEPTH` cap as initializer calls. The plugin emits it only when the name is bound ONCE, from ONE head, and never reassigned, rebound by a loop/`catch`/`foreach`/destructuring or shadowing a parameter (each plugin checks its own language's forms); everything else stays untyped, so an alias of an untyped name links nothing and a namesake method on another class is never reached. Never an alias: `undefined`, `true`/`false`, `nil`/`nullptr`, `self`/`this`. A Python parameter-typed alias is read by the fact table already; `aliasOf` is for a head typed by a call (`p = make(); q = p`). The Python local-type gate skips an alias-only body unless a parameter is annotated. Flow order: the TS/JS scan keeps a timeline of each name's declarations and `=` assignments, and an alias of a head bound or assigned more than once is typed by the nearest binding BEFORE the alias (a concrete `localTypes` entry, only when that binding states a type); a binding in a nested block before it, an untyped one, a loop around the alias or a head bound by something the timeline does not see leaves it untyped. The same order is read in Python (the fact table keeps each name's latest binding and its block; a loop around the alias matters only when the head is bound again LATER in that loop body — the back edge brings both bindings — and then the alias is typed only if that binding states the same type) and PHP (writes in text order, blocks by enclosing statement; a parameter is the head's first write, typed by its declaration, so `$a = $c; $c = new Player();` keeps the declared type and an alias after the reassignment takes the new one; the same loop rule), Rust and the C family ([plugins/shared/alias-flow.ts](shared/alias-flow.ts): open braces, a binding per name, a loop or closure around the alias leaves it untyped when its head is bound more than once); a binding in a block that closed before the alias, or an untyped one, leaves it untyped. Core's receiver chains follow four calls (`MAX_RECEIVER_CHAIN`).
- **Bindings a body states without a declaration.** A loop variable, a lambda parameter, a narrowed name (`instanceof X x`, `is X`, `if let`, a type switch, `isinstance`), a caught exception or an element read (`list.get(0)`, `m[k]`) is reported as a `localTypes` entry whose `from` names what it is drawn from, or as `CallInfo.receiverType` on the call; core resolves it as it resolves any initializer. JVM and .NET share the chain reader in `shared/element-chain.ts`; tuple unpacking from an annotated return uses `localTypes[].fromIndex` with the manifest's `tupleElementsOf`. Two element types for one name leave it untyped. A `from` may be a chain of calls (Go `club.Address().City()`, Swift `garage.car().engine()`; `Type.init(…)` is a construction of `Type`); a destructured member read off a value or a method's result (`const { coach } = club.staff()`, `= club`) is `localTypes[].member` with `from` = `club.staff().coach`, written only where the body calls on the name; a C++ `auto [a, b] = pairOf()` is `fromIndex` entries typed by the manifest's `tupleElementsOf` (`std::pair`/`std::tuple` returns; a struct return stays untyped). Loops over a call chain or a typed collection: Go `range` over a chain of calls and fields (`league.Club(1).Players()`), PHP `foreach` (a call or property chain as `from`/`element`, a parameter or `@var` local typed by `Player[]`/`array<int, Player>` — a native `array` result with a docblock `@return Player[]` keeps the docblock in `declaredReturnType`), C++ range-for with `auto` (a container-typed name takes its element in the plugin; a call or field goes to the linker; `cpp/collection-element.ts`), Rust `for` over a field or call (`rust/collection-element.ts`), Kotlin `for ((club, player) in map)` / `.keys` / `.withIndex()` (`ChainRules.keys`, `ElementState.key`), Python `for i, (a, b) in enumerate(pairs)` / `.items()` over `list[tuple[A, B]]` / `dict[A, B]` (`rowShape`). An element type the source does not state leaves the variable untyped. A type test narrows PER CALL, never the name: `CallInfo.receiverType` is set only on calls inside the region the test guards — TS/JS `instanceof` ([javascript/narrowing.ts](javascript/narrowing.ts): the true branch, the else of a negated test, the rest of the block after an early `return`/`throw` guard, `&&` and `?:`), C# `is` ([csharp/type-tests.ts](csharp/type-tests.ts), also `is not`), Python `match` class patterns (`case Club():`, `as`, `|` alternatives), Kotlin `when (x) { is A -> …; is B -> … }` (each arm its own type) — and a call outside it, a callback body or after the name is reassigned gets none. The linker keeps ONE link per caller and call name, so a second arm calling the same method name adds none. Java and Kotlin state a narrowed receiver's type while the call walk runs (`withCallNarrowing` around `extractCalls`, read by the call hooks' `receiverTypeOf`), because the walk keeps one call per name and receiver type: `is Club -> x.save(); is Player -> x.save()` stays two calls, a Kotlin subject-less `when { x is Club -> … }` narrows too, and a call outside every arm gets no narrowed type. The regex call recorder likewise keeps a stated `receiverType` in its dedupe key unless the name spells that exact type.
- **Smaller hooks.** `calls.isApiCallShape(callName, imports)` marks a call shape that is an api-call whatever its receiver (tRPC `.query`/`.mutate`; Convex functions are routes at `/convex/<module path>.<export>` (JS plugin `routes/convex.ts`: dots, since a colon is a path parameter; the module path comes from the `_generated/server` import depth, else a `convex/` segment), their `ctx.db.*` calls data sources and `defineTable` entities, all gated on the file naming Convex); `calls.withSubjectsOf` names the implicit receivers a bare call may run on (Delphi `with`, Kotlin `with`/`apply`); `PreprocessOutcome.restoreTypedCalls` asks for noise-named calls to be restored again after a `postExtract` that created their class (Lua tables).   `localTypes[{ from, element: true }]`; `nestedTypeSeparator` (`.` or `::`, default `::`) and `nestedTypesScopeBare`
  name nested types by path; `constructorCalls` (`init`, `new`) are sends that construct their receiver class;

  the compile database files at a project root (`-I` order and `-D` macros reach `read(source, macros)`);

  (`SubProject.references`; a reference may name a package — `ProjectReference.package`, npm `workspace:` — resolved to the one sub-project of that ecosystem declaring it); `preprocessStamp(absolutePath, projectRoot)` fingerprints what a `preprocess` reads

- **Line numbers are 1-based** in all output.

## Thrift (`thrift/`)

A contract plugin like protobuf: `POST /<java namespace>.<Service>/<method>` rows with `contract`, `routeFacts` + a route resolver for `extends`, argument structs as `<Service>_<method>_args` classes. Stub and `Iface` names live in `shared/thrift-stubs.ts`, composed into each language's existing `grpcStubService`/`grpcServiceOf`; certain only when the file imports the Thrift runtime, else only for a declared service. String literals are blanked before fields and methods are read (a default `"2: i32 fake"` is no field; a lone quote never swallows the file). A Go stub TYPE (`ClubServiceClient`) counts only in a file importing the Thrift runtime or a package the project generated from a `.thrift` (a `gen-go/` path, or a package declaring `XClient` beside `XProcessor` — `core/grpc-clients.ts` hands the stub hook every analyzed file as a third argument, and `firstStub` prefers a certain answer). Handlers the generated code does not name — Go `NewClubServiceProcessor(&clubHandler{})`, Python `ClubService.Processor(handler)`, Node `thrift.createServer(ClubService, handler)` — are `thrift-handler` route facts ([shared/thrift-handlers.ts](shared/thrift-handlers.ts)) that the `thrift-handlers` resolver joins with the declared service's rpcs and the one class of the handler's type: each rpc it has a method for becomes a contract row ON that method (the grpc-js `addService` shape), which the `.thrift` row's spec join finds; a handler held in a variable is read from its one literal/constructor assignment, an object-literal handler (`createServer(ClubService, { getClub() {…}, listClubs: async () => … })`, or a variable assigned one) serves the rpcs it has a member for — a held one on its `<holder>.<method>` functions, a literal written in the call on rows named `createServer.<method>`; only in a file naming `thrift`. A handler object written in the call — thrift `createServer(ClubService, {…})` and grpc-js `server.addService(X.service, {…})` — is read from the parse ([javascript/contract-handlers.ts](javascript/contract-handlers.ts)): each member is a function of its own, `createServer.<key>` / `addService.<key>` (a held function's style; the contract row sits on it, so its body's calls are attributed to it); a member that names a function (`getClub: someFn`, `getClub: clubs.getClub`, shorthand, `.bind(this)`) is that pseudo-function holding one `passed: "argument"` call of the name, which `resolvePassedName` resolves without guessing — a namesake in an unrelated file is never the handler; a call-result value (`getClub: makeHandler()`), a spread or an accessor is no handler. A second call in one file reusing a key gets `@<line>` appended. A Node client `thrift.createClient(ClubService, conn)` names its service in an argument: `grpc-clients.ts` asks the stub hook again with `createClient(ClubService)` when the bare spelling answers nothing; an awaited receiver (`(await connect()).createClient(ClubService)`) is read past.

## AsyncAPI (inside `openapi/`)

An extension has one owning plugin, and `.yml`/`.yaml`/`.json` are OpenAPI's, so AsyncAPI is a branch of its `preprocess` (an `asyncapi:` root key, checked after the OpenAPI sniff) handing the file to `openapi/asyncapi.ts`, not a second plugin. Operations become queue rows with `DataSourceInfo.fromContract`, kept in `FileAnalysis.busContracts`, never `dataSources` (no code reader may take the document for a publisher or consumer): 2.x `publish` = the application receives (consume), `subscribe` = it sends (publish); 3.x `action: receive|send`. The broker comes from `servers[].protocol` (`brokerOfProtocol`; a channel's `servers` narrows it, several protocols give a row each), the address from the channel name or 3.x `address` (a `{param}` is a hole, `*` — MQTT's `+` — and the queue node's id reads every `${x}` / `{x}` hole as `*`, so the document and the code's templated destination meet on one node). `buildDataAccessGraph` creates the queue node each names and marks it `contract`, and `unimplemented` when no code row meets it — the document draws no edge; `element-registry.ts` carries both flags through the summary. Payloads: `components.schemas` and each message with an inline `payload` become `openapi` classes.

**Convex imported builders.** A module that exports `customQuery(query, …)` (imported from `convex-helpers/server/customFunctions`) emits a `convex-builder` route fact; a functions-directory module calling an imported builder emits `convex-use`, and `convexBuilderResolver` (`routes/convex.ts`) places the route when the import graph reaches a defining file, looking the builder up by the name the defining module exports (`import { authedQuery as q }` finds `authedQuery`; `convex-use` carries `exported`). `http.route` reads a same-file string constant for `path`/`method`.

**Value-flow facts.** To let core follow a function value (`const h = save; run(h)`, `this.onSave = save`, `handlers.push(f)`, `return cb`), emit `ValueFlowFact`s on the function that contains the statement (`FunctionInfo.valueFlow`; module-level code in `FileAnalysis.moduleValueFlow`) and nothing more: the cell names as written (`{ name: "this", member: "onSave" }`, a list element as member `"[]"`, a literal key as that key), the function a `seed` names as written (`save`, `this.save`, `Club::save`, a held pseudo-name), the `call` of an `arg`/`result`/`invoke` as `CallInfo.name` with its line, and the written argument index. Every seed and copy a held lambda states carries the same `lambda` id (its `line:col`): state every name its body calls (a plugin bounds that only to keep output small) — core counts the project functions they resolve to and drops the group above four, so a library's name never uses up the cap. An `invoke` fact keeps the call out of the name tiers when its cell is a parameter or the facts write it, so emit it only for a call that runs a held value, never for a method call the ordinary linker resolves; a struct's or interface's own field names are no locals. Resolution, receiver typing and imports stay in core ([../../core/value-flow.ts](../../core/value-flow.ts)). **JS/TS/Vue/Svelte** ([javascript/value-flow.ts](javascript/value-flow.ts), run from `finishBody` for every function, method and held callback, plus `meta.ast.moduleValueFlow` for the top level): copies and seeds through locals, parameters and `this.x` fields (a field initializer `onSave = this.save.bind(this)` rides the constructor), `a.b` members, list/map elements (`push`/`set`/literals, `for…of`/`forEach` parameters, `m[k]()`: every key is also an element, `this.items[k]` is member `items[]`, `this.a.b` is member `a.b`), factory results/returns (`<return@N>`/`<arg@N>` one-use cells), `.bind`/`.call`/`.apply`, and module `let`s written from a function (`ValueCell.module`). A name is only a seed when the file can bind it to a function (imports, function and class declarations), data-typed parameters and locals nothing binds are left out, a call on a dispatch map the existing pass owns gets no invoke, and a local made by a call that wraps a function (`useCallback(() => …)`) is a function binding, not a value. Python ([python/value-flow.ts](python/value-flow.ts)): assignments, loop targets, `x.append(f)`, list/tuple/set/dict literals (a container is ONE cell with its elements, a dict also keeps a literal key as its member, `self.x[…]` having no second member level), `functools.partial(f, …)` as a seed of `f`, `return`, positional arguments by written index, and `invoke` for a call of a local, a parameter (not a test's or fixture's, which pytest injects), a module name its own statements bind, `self.<field>` the class assigns (never a method) and `table[k](…)`; a `global` assignment goes to `moduleValueFlow`; keyword arguments are not mapped (the schema has only an index); a module-level `name = lambda …` is a function of its own; a lambda written inside a function and landing in a cell (local, `self.x`, list/dict element, positional argument, return) has no function of its own and stands for what its body calls — a seed for each project function it names (`save`, `self.save`, `Club.save`), a `copy` for a name that holds a value, nothing for a call on its own parameter or a local or on a name an import of the standard library or a known external package binds (`json.dumps`, `from time import sleep`: none counts toward the four, and an argument handed to such a call states no `arg` fact), and nothing when the project functions it calls come to more than four (at most four project functions, counted by core over the facts sharing the lambda's id; the plugin itself states up to sixteen names). Java/Kotlin ([java-kotlin/value-flow.ts](java-kotlin/value-flow.ts)): method and callable references (`this::save`, `Club::save`, `club::save`, `Club::new`, `::save`) seed locals, fields (initializers ride on the constructor, else the first method), `List.of`/`listOf`/`mapOf` literals and `add`/`put`/index writes (element cells `[]` / key, a field's as `this.<field>[key]`); `run`/`apply`/`accept`/`get`/`call`/`test`/`compare`/`handle`, Kotlin `f()`/`f.invoke()` are `invoke` facts only on a receiver the facts know holds a function (a JDK functional-interface or Kotlin function type, or initialized from a reference) and never one built by `new`/an anonymous class; a lambda or Kotlin lambda literal landing in a cell (local, field, collection element, argument — a trailing lambda is the last one —, return, field initializer) seeds it with each project function its body calls (`save`, `this.save`, `club.save`, `Club.save`; at most four project functions, counted by core, none for a call on the lambda's own parameter or implicit `it`, a chain or a JDK call) and copies the cell of a held function its body runs (`() -> onDone.run()`); it gets no function of its own, so its calls stay the enclosing function's. A call into a library states no `arg` fact (`isLibraryCall`, over the file's `LibraryContext` — package, imports, declared methods — carried on `ClassFlow.library` and `methodValueFlow`): a bare name the file does not declare as a method or class, brought in from the manifest's `externalModulePrefixes` or outside the file's root package (first two `package` segments) by a Java `import static` of that name, a Java `import static x.*` when no class of the file extends another (an inherited method looks the same), or a Kotlin import of that very name — never a Kotlin wildcard, since a same-package function or class needs no import — (`import static spark.Spark.*`, `import io.ktor.server.routing.post`), or a call on a receiver typed by such an imported class (`Javalin app`, the class itself `Javalin.create(…)`); a method the file declares itself, and a call on an untyped lambda parameter, are not library. C# keeps its arg loop as is (a type has no namespace in the call, so a library receiver cannot be told from a project one). Go ([go/value-flow.ts](go/value-flow.ts)) and Rust ([rust/value-flow.ts](rust/value-flow.ts)) state them from their ANTLR readings only (the regex fallback states none; `ParsedFunctionSpan.valueFlow` / `ParsedStructure.moduleValueFlow`): Go's locals, pairs, method values, function-typed fields (an `invoke` on `c.onSave()` only where the file declares the field function-typed), `map`/slice literals and `append`, `range`, package variables (module facts) and factory returns; Rust's `let`/tuple patterns, `Some(Box::new(f))` wrappers, fields via `self`, `push`/`vec![…]`/`for … in`, `if let Some(cb)`, paren-called fields `(self.cb)(x)`, a `Self { cb: … }` literal as the receiver's fields, and a function's tail value. A collection field's elements are the member `<field>[]`. A package variable (Go) or `static` (Rust, an uppercase name) a function stores into is stated at module scope (`moduleValueFlow`, with a self-`copy` marking the name bound); a Go package variable declared in another file of the package is not seen, and Rust states a `Self { … }` literal as the receiver's fields only in a function taking no `self`. PHP ([php/value-flow.ts](php/value-flow.ts)) reads string callables, `[$this, 'save']` / `[Club::class, 'save']`, first-class callable syntax and `Closure::fromCallable` as seeds, moves them through variables, properties and array elements, and emits invokes for `$f()`, `($this->h)()`, `$m['a']()` and the callback argument of `call_user_func`/`array_map`-style builtins (a closure or arrow function held in a value stands for the project functions its body calls — at most four project functions, counted by core, `save` / `this.save` / `Club.save` — or copies the cell of a held value it runs; it gets no function of its own, and a call on its parameters, a builtin or an untyped receiver states nothing). Ruby ([ruby/value-flow.ts](ruby/value-flow.ts)) reads `method(:save)` the same way (instance variables, hash/array literals, constants through `moduleValueFlow` from the spec's `extractModuleValueFlow`, `each` block variables; a `&x` block argument is not followed, since a written index cannot name the `&blk` formal; a brace lambda or proc held in a value — `-> { save }`, `lambda { Club.close }`, `proc { … }` — and the `do … end` forms `lambda do |x| … end` / `-> do … end`, whose statement runs through the block's `end` — stands for the project functions its body calls, as in PHP (at most four project functions, counted by core); a block handed to a method or a loop's `do` is no value) and invokes `.call` / `.()`, never on a receiver whose type is stated. Both prune through [shared/value-flow-live.ts](shared/value-flow-live.ts), which drops facts no invoke, argument or return can reach. Dart and Swift state them from their tree-sitter readers ([dart/value-flow.ts](dart/value-flow.ts), [swift/value-flow.ts](swift/value-flow.ts); a parser reader returns `ParsedFunctionSpan.valueFlow` / `ParsedStructure.moduleValueFlow`): tear-offs and single-call closures as seeds, locals, fields and `widget.x` as cells, a Flutter widget's named constructor argument as an `arg` with `name` meeting the field its constructor copies, `x!()` / `x?.call()` / `x?()` / `table['k']!()` / `for h in list { h() }` as invokes. C# ([csharp/value-flow.ts](csharp/value-flow.ts)) states them per member: a method group (`Action a = Save`, `new Action(this.Load)`, `Run(Save)`, `club.Count` where the destination is a delegate), a delegate in a local, parameter, field or property, `x()` / `x.Invoke()` / `x?.Invoke()`, an event (`r.Saved += OnSaved` stores into the declaring class's cell; the raise inside it invokes it), a delegate returned by a factory (`Task<…>` unwrapped), and collections of handlers (a literal key is its own cell and `[]` too; a field collection is one cell). A name is a delegate holder by its declared type (BCL delegates and the file's own `delegate` declarations; `x()` on a declared local, parameter or own field is always a delegate call). A field's delegate initializer is stated on the class's first constructor; a lambda or anonymous method in a local, field, property, event `+=`, collection, argument, return or field initializer stands for the project functions its body calls (`Save()`, `this.Save()`, `club.Save()`, `Club.Save()`; at most four project functions, counted by core over the `lambda` id its facts share; none for a call on its own parameter or a chain; a BCL call is filtered by name where it can be, and where a library receiver cannot be told apart per file it no longer matters for the cap, since an unresolved name never counts) and copies the delegate it runs (`onDone()`, `onDone.Invoke()`), having no function of its own; an element call that has no call row (`handlers[key]()`) is the invoke's `handlers[]`. C and C++ ([shared/c-family-value-flow.ts](shared/c-family-value-flow.ts), the spec's `extractValueFlow` run on the finished analysis) read the text statement by statement: function pointers, `std::function` and lambdas/`std::bind` held in locals, fields (set in a method or a constructor's initializer list, run in another), file-scope globals (`<module>` cell), arrays and vectors of handlers (the container is one cell), and struct ops tables — `{ .sign = club_sign }` seeds the struct TYPE's member, so a call through any pointer to that type reaches it, nested tables as a field path (`club_conf.ops`); a lambda held in a value stands for the project functions its body calls — at most four, counted by core; the plugin states every name its body calls (up to 16) under one `lambda` id. Dart ([dart/value-flow.ts](dart/value-flow.ts), [dart/closure-flow.ts](dart/closure-flow.ts)): a getter of a class, mixin or extension is a method of its own in both front ends (`FlagService get flags { _flags ??= FlagService(dio); … }`, `Club get club => Club(id)` — its calls and constructions are its own; a setter and an operator are none). A closure handed to a widget event is a pseudo-function `<onTap@14>` holding its calls, and one that calls a callback the widget is handed (`onSave(club)`, `widget.onSelect?.call(club)`, `onLongPress!(club)`, also the one-call forwarder `() => onRename(club)` when `onRename` is a function-typed field or parameter of the file) keeps its own function so the click has a handler: the parser's `invoke` facts of the method around it are copied onto it at the closure's own call line and the closure carries `FunctionInfo.enclosingClass`, so value flow reads `this.x` / `widget.x` in it as that class's receiver (and still its locals as the method's) and links the invoke to what the parent passes — never to a same-named top-level function elsewhere.

**C# query helpers.** A method declared to return `IQueryable<T>` (ordered / including forms, `DbSet<T>`, or a task of one) is a read where it is built; a chain that STARTS at a call of one declared in the same class — `ClubsQuery(id).ExecuteDeleteAsync()`, `this.Active().ExecuteUpdateAsync(…)`, `var q = ClubsQuery(id); q.ExecuteDelete()` — is the read or write it names on the set the helper queries (read off its returned expression, else its declared `T`), at the caller (`csharp/data-sources.ts` `queryHelperEntity`). A same-named helper of another class, and a call on a receiver (`_repo.Active()` — another class, usually another file), are not followed: the extractor sees one file.

**Vuex commits and names built from constants.** `commit(...)` is a dispatch of the mutation table (`javascript/vuex.ts`): the same key (`dispatchKeyOfArgs`) on a call whose receiver is the store's (`STORE_COMMIT`: bare `commit`/`context.commit` of an action, `store.commit`, `this.$store.commit`, `clubStore.commit` — `repo.commit('x')` is any object's and never gets a key), `mapMutations` read like `mapActions` (`this.SET_PAGE()` carries the key prefixed `commit:`), and `VuexDispatchResolver` looks the name up under `mutations.<M>` / `mutations.[CONST]` (a section parameter beside `actions`; links named `commit:<key>`, strategy `dispatch:vuex-action`, a bare commit inside a module joins its own module first). `new Vuex.Store({ mutations })` and computed mutation keys are named as actions are. A name built from an imported constant (`'clubs/' + types.FETCH`, `` `${NS}/load` ``) keeps the unknown part as a `${ref}` hole in the key (`holeOf`; locals, parameters and `this`/`props` never become holes); the resolver fills each hole with `constantValue` and drops the call when one is unknown. Not yet: mutations spread in (`...baseMutations`), `Object.assign` merges and factory-built modules (actions only), and a name bound by both `mapActions` and `mapMutations` resolves as the action.

**Store names read from another module, and the store a bound kind picks.** The JS plugin reports a module's plain string constants as `FileAnalysis.stringConstants` ([javascript/string-constants.ts](javascript/string-constants.ts): `export const LOAD = 'clubs/load'`, `ACTIONS.FETCH`, string enum members — no spaces, no holes, 200 a file). A `store.dispatch(ACTIONS.FETCH_CLUBS)` naming its action by a constant the file does not declare carries it as written in `CallInfo.args[0]`, a Vuex action keyed by a constant (`[ACTIONS.FETCH_CLUBS]() {…}`) is a function named `actions.[ACTIONS.FETCH_CLUBS]`, and the Vuex dispatch resolver reads both through the import chain (`constantValue` in [javascript/vuex.ts](javascript/vuex.ts): named, aliased and namespace imports, re-exports; the import picks the file, so a same-named constant elsewhere is never mixed in) — joined by the local name in a namespaced module, or by the whole name in a store that is not. A record of call results indexed by a prop (`stores[props.kind]`; `LocalType.key` per entry, `CallInfo.indexOrigin` / `LocalType.indexOrigin` for the index) is narrowed by the plugin's `recordChoice` ([javascript/record-choice.ts](javascript/record-choice.ts)) to the entries the component's users bind the prop to — a literal (`kind="player"`), an imported enum member or constant (`PropBinding` origin `constant`, `:kind="Kind.Club"`; only a dotted name or an UPPER_SNAKE one), or a prop they hand on — each link kept to its binding sites (`viaUsage`); no binding naming an entry, or an entry key it cannot read, keeps the fan-out over every entry. The IIFE `switch` store picker stays refused.

**One-line class bodies (C++).** `struct Base { First actions; void Work() {} };` and `namespace league { struct Club { void Play() {} }; }` read as their multi-line spelling. A spec with `splitHeaderLineMembers` cuts a one-line brace class into member declarations at its top-level `;` and closing `}` (`headerLineSegments`, string literals and comments blanked) before the function and property patterns read them, so a field in front of a method no longer hides it; `extractCppClasses` reads a line without its leading `namespace x {` openers and their `}` (`unwrapOneLineNamespaces`, columns kept) and qualifies the class by those namespaces. `adoptParsedMembers` pairs a parsed function with a class method by line AND name, and the free-function filter drops a function on a member line only when its name is a member (a free function written after a one-line class stays). Order-check input: `parsers/antlr/order-inputs/one-line-bodies.cpp`.

**C# scope from the build (`csharp/package-manifests.ts`).** `projectFileUsings` applies MSBuild items in evaluation order: the SDK's implicit global usings (the Blazor WebAssembly SDK adds only Configuration, DependencyInjection and Logging — per the SDK's props), then `Directory.Build.props` — the nearest one, plus each parent it imports through `GetPathOfFileAbove`, outermost first — then the project body; a `<Using Remove>` takes away what came before it, so a Remove in the props and an Include in the project keeps the namespace (a conditional Remove still counts, a conditional Include does not). `<Using Include Static="true">` is a project-wide `using static` of that type. A `using static` source is normalized (no spacing, no `global::`), and the linker names a nested static class through the classes whose lines enclose it before matching it (`League.Outer.Inner`).

**Scope evidence, PHP and Rust.** A PHP file that opens several namespaces (`namespace A { … } namespace B { … }`, or `namespace A;` then `namespace B;`) records each class's own `ClassInfo.namespace` (a file with one states it once, in `declaredNamespace`); the linker's `filesNamedByEvidence` compares a candidate class on its own namespace and a caller on the namespace of the class around the call (a free function in a later namespace still reads the first). A facade accessor may be `return self::TOKEN;`/`static::TOKEN` (a string or `X::class` constant of the facade) or several returns that all yield the same value. Rust path calls keep every earlier segment on `receiverType` in all three readers (ANTLR, ANTLR macro, regex); a segment the manifest's `pathCallTypesNeedScope.typeSegment` calls a type (`Shape::Kind::make()`) makes an associated-type path no import or module path binds, so the linker leaves it unlinked. A `#[path]` module's import source `./x.rs::inner` resolves `inner` below the file (a path-loaded file holds its children as a `mod.rs` does).

**C++ template heads, dependent types, scope (E-216).** `templateHeads` closes a head at the `>` that balances its `<`, never one inside parentheses (`template<int N = (A > B), class Player>`). A type written `Ledger<M>::Row`, `M` a parameter of the head, is dependent whatever `Ledger` is: parameters and locals keep it as `Ledger::Row`, so `dependentTypes` reads the pair off the signature/body text and untypes it — except the class's own name with its own parameters (`Squad<K, C>::Slot` inside `Squad<K, C>::first`), which is the class being defined. A wrapper name the file declares as its own class (`template<class T> struct queue`) is no std wrapper for the untyping (`namesTemplateParameter`'s `declaresClass`). An explicit specialization (`template<> void Run<Player>(Player& x) {`) is a function on the regex path too. A one-line `namespace { struct Valve {…}; }` marks its classes `fileLocal`; a type written through a namespace (`other::Valve`) is never the file's own anonymous-namespace class (`typeRefFor`'s `declaredInOtherNamespace`, and `fileOf(…, skipOwnLocal)` for fields). A block-local alias used inside a template argument (`using Q = std::unique_ptr<P>` after `using P = Player`) is substituted (`substituteAliases`).

**One-line class bodies (C++).** `struct Base { First actions; void Work() {} };` and `namespace league { struct Club { void Play() {} }; }` read as their multi-line spelling. A spec with `splitHeaderLineMembers` cuts a one-line brace class into member declarations at its top-level `;` and closing `}` (`headerLineSegments`, string literals and comments blanked) before the function and property patterns read them, so a field in front of a method no longer hides it; `extractCppClasses` reads a line without its leading `namespace x {` openers and their `}` (`unwrapOneLineNamespaces`, columns kept) and qualifies the class by those namespaces. `adoptParsedMembers` pairs a parsed function with a class method by line AND name, and the free-function filter drops a function on a member line only when its name is a member (a free function written after a one-line class stays). A parser states the class a member is declared in (`ParsedFunctionSpan.owner`, the C++ reader's `enclosingClass`), and `adoptParsedMembers` adopts by that name even on the class's own line (`struct A { auto f() -> int { return 1; } };` — a signature the class pass cannot read — is `A.f`, never a free function a bare `f()` could bind to); the regex reading also reads a function written after a one-line class's closing `}` (`functionsAfterHeaderLineClass`, read from the tail alone, never taken for a member).
