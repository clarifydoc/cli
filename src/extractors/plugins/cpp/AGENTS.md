# C++ plugin

Reads C++ (`.h`, `.hpp`, `.hxx`, `.hh`, `.cpp`, `.cc`, `.cxx`, CUDA `.cu`/`.cuh`) through a regex spec plus an ANTLR front end (`antlr.ts`, `meta.antlr`); a file with syntax errors keeps the regex reading (`FileAnalysis.frontEnd`). It also owns the facts C, C++ and Objective-C share (the `cfam` family), the QML plugin (`../qml/`) and the Qt Designer plugin (`../qtui/`). The C plugin ([../c/AGENTS.md](../c/AGENTS.md)) and Objective-C plugin ([../objc/AGENTS.md](../objc/AGENTS.md)) link here. Parser internals (decision settling, the `CTypes`/`CppTypes` passes, grammar regeneration, `.h` variant reading) are in [../../../parsers/AGENTS.md](../../../parsers/AGENTS.md) and not repeated.

## Front end and reading

- `--feature no-antlr` switches back to the regex path, which stays; a file ANTLR refuses keeps the regex reading.
- A header whose C++ is only inside `#ifdef __cplusplus` / `#if defined(__cplusplus)` is offered to the C reader (`withoutCppGuards`).
- `.h` is shared between C and C++ and has one owner (C++). The manifest's `readingVariant(relativePath, mix)` gets the project's file counts by extension and names `c-first` for a `.h` in a project with `.c` and no C++ source (C's grammar reads it first, C++'s stays the fallback); the analyzer folds the variant into the file's manifest `resolver` stamp, so a project whose mix flips re-reads its headers although no byte changed; `FileAnalysis.frontEnd.variant` records it. `.mm` is Objective-C++ and counts as a C++ source for the mix.
- A parser states the class a member is declared in (`ParsedFunctionSpan.owner`, the reader's `enclosingClass`); `adoptParsedMembers` adopts by that name even on the class's own line (`struct A { auto f() -> int { return 1; } };` is `A.f`, never a free function a bare `f()` could bind to) when exactly one class of that name covers the span, and pairs parsed functions with methods by line and name. It refuses when several same-named classes share the extent (two one-line `struct Twin`).
- A parser front end may state each call's arguments (`PatternCallName.args` → `CallInfo.argCount`/`argKinds`/`templateArgs`, `cpp/antlr.ts`): `callRecorder` keeps one row per distinct (name, count, kinds, template arguments) instead of one per name, so `g(1); g(1.0);` are two calls.
- `RegexLangSpec.declarationCallPatterns` lists call patterns read over each parsed function's lines (after the grammar's own calls, never the baseline `name(`): `Club c(3);` and `Rank::Iterator it(2);` are declarations to the grammar and constructor calls to the linker (`DIRECT_INIT_CALL` in `index.ts`: a one-segment capitalized type is the call name, a nested path keeps the owner as `receiverType`, `Rank.Iterator`). Without a front end `callPatterns` carries the same pattern. An undeclared-namespace fallback (`league::Table` → bare `Table` when the project declares no `league`) is not built: no corpus showed it. A call through a field path of three or more names (`kit.actions.Go(`, `g->doors.lock(` after the scan spells `->` as `?.`) is named whole (`FIELD_PATH_CALL`), so the baseline does not keep only the last two with `receiverCut` and refuse to type the cut head as a binding of the caller; a same-named decoy method is never taken.
- [../shared/brace-code.ts](../shared/brace-code.ts) (`BraceLexicon`, `braceCodeHooks`) and [../shared/c-family-code.ts](../shared/c-family-code.ts) count braces over code only and say when a signature is a definition; Go, Rust, Scala and Swift use the brace helper too.
- A C-family plugin's control-flow `sourceView` is `firstBranchView` ([../shared/preprocessor-branches.ts](../shared/preprocessor-branches.ts): dead blocks blanked, then only the first live arm of every `#if`/`#else`, the ANTLR readers' choice, since the arms are alternatives of one build).

## Includes, headers and scope

- `importsShareScope` (C/C++ `#include`): a bare call the file does not define resolves to the ONE included file that does (`import-file`). Where the included file is a header (`declarationExtensions`), the files sharing its stem define what it declares; a `static` body (`isExported: false`) never.
- An `#include`'s stem is no binding (`importedBinding`). An import that names a file with its extension (`#include "parser.h"`) resolves to the file of exactly that name: from the project root when written without `./`, then beside the importer, then the one file whose path ends with it, extension included (`uniquePathEnding`, never a body file sharing the header's stem), then the one path suffix that matches; two files spelling it alike stay unresolved.
- A body file with a declaration file of its own stem beside it defines only that file's names, so `#include <league/club.h>` never binds `other/club.c`: an import binds only the bodies of the header it names.
- `compilationDatabase` (`loadCompilationDatabase`: `compile_commands.json`, at a root or `build/`; paths a CI wrote are matched to discovered files by their longest tail): per translation unit its `-iquote`/`-I`/`-isystem` directories and `-D`/`-U` macros ([../../../core/compilation-database.ts](../../../core/compilation-database.ts)). `placeIncludes` rewrites an include to the file the compiler's search order finds first (before the suffix fallback; in memory only; a file compiled twice with different results, and headers, keep the generic rules). `macrosOf` (the macros every unit agrees on) goes to the parser front end with the task, stamped into the incremental `resolver`; `preprocessor-branches.ts` picks the live arm of `#ifdef` / `#if defined()` only for macros whose state is known (the file's own `#define`/`#undef` counting where every conditional around it is known taken). `readWithBranches(text, cplusplus, read)` blanks dead blocks (`#if 0`, `__cplusplus` as the language says); a file that does not parse is read again with each conditional's first branch, the left-out branches' calls counted, a second-branch reading's definitions added.
- Where includes share scope, a member defined out of line in another file (`methodBesideClass`) answers a class its caller's header declares only when that file's own includes do not reach a different declaration of the class without reaching this one: a `.cpp` of a namesake class in a folder the caller never includes defines that namesake's members, never the caller's.
- Two headers declaring one class name are told apart by the caller's own declaration, then the one its include closure reaches, and refused when neither decides (`pickDefinition`). `typeFileFor` prefers the one declaration with a body in the include closure over a forward declaration.
- Inside a method, a bare call is the caller's own class's member, then its bases', never another class's of the same file and never a class member from a free function; C++ keeps such a link as an INFERRED guess (`bareCallsHideReceivers`, since `TEST_F` bodies read as free functions).
- A member defined outside a lowercase class (`void garage::park() {…}`) reads as a free function of namespace `garage`, since a per-file pass cannot tell that qualifier from a namespace; the linker (`outOfLineNamespaceMember`) takes it as the member of the project class of that name when the one file defining it includes the class's header. An out-of-line method reads the declaring class's fields.
- Vendored single-file libraries (SQLite amalgamation, nlohmann/json, stb…) are recognised by the manifest's `vendoredBanners` (`C_FAMILY_LIBRARY_BANNERS`); the C manifest states the same list.

## Classes, namespaces and templates

- A nested class is named by its path (`Outer::Inner`, manifest `nestedTypePaths`); the class id carries the path, so no line-range lookup is needed. Free functions record `FunctionInfo.namespace`, so `league::util::to_hex()` and `using namespace` calls join across files.
- A C++ class path keeps its lowercase namespace on the call's `receiverType` (`league::Table::make()`), which core resolves against `ClassInfo.namespace`, so a namesake in another namespace is never taken.
- A type written through a CamelCase namespace (`LeagueCore::Valve`) reads as a nested class path; where no class bears that path but `Valve` is declared in namespace `LeagueCore`, the member type and `declaredTypeName` mean that class, never the file's own anonymous-namespace `Valve`.
- A class in an anonymous namespace is `ClassInfo.fileLocal`, seen only by its own file and the files including it. A one-line `namespace { … }` (`namespace { struct Valve {…}; }`) marks its classes `fileLocal`; a type written through a namespace (`other::Valve`) is never the file's anonymous-namespace class (`typeRefFor`'s `declaredInOtherNamespace`, and `fileOf(…, skipOwnLocal)` for fields).
- A class written on one line reads as its multi-line spelling (`struct Base { First actions; void Work() {} };`, `namespace league { struct Club { void Play() {} }; }`; `namespace x { struct Y {…}; }`). `splitHeaderLineMembers` cuts a one-line brace class into member declarations at its top-level `;` and closing `}` (`headerLineSegments`, strings and comments blanked) before the function and property patterns read them, so a field in front of a method does not hide it. Each class's members stop at its own closing `}`; a further `class`/`struct` on the same line (`struct Twin { void home(){} }; struct Twin { void away(){} };`) is its own `ClassInfo` (`pushOneLineSiblingClasses`). `unwrapOneLineNamespaces` reads a line without its `namespace x {` openers and their `}` (columns kept) and `extractCppClasses` qualifies the class by those namespaces. `adoptParsedMembers` pairs a parsed function with a class method by line AND name, and the free-function filter drops a function on a member line only when its name is a member: a free function written after every sibling one-line class stays (`functionsAfterHeaderLineClass` skips those siblings before reading the tail). The order-check input is `parsers/antlr/order-inputs/one-line-bodies.cpp`.
- A type written `Ledger<M>::Row`, `M` a parameter of the template head, is dependent whatever `Ledger` is: parameters and locals keep it as `Ledger::Row`, so `dependentTypes` reads the pair off the signature/body text and untypes it, except the class's own name with its own parameters (`Squad<K, C>::Slot` inside `Squad<K, C>::first`), which is the class being defined.
- A template head's type parameters are no classes, judged on a type's HEAD (`namesTemplateParameter`): `T`, `const T&`, `T::x` and the element or pointee a std wrapper exposes (`unique_ptr<T>`, `vector<T>`) are untyped and listed in `untypedLocals` (`untypeTemplateParameters`, and the ANTLR walk's own local typing), so `template<class Player> void Run(Player& x)` never reaches a real `Player`; a project class taking the parameter as an argument (`Topic<T>`, `flat_map<K,V>`) stays that class. A wrapper name the file declares as its own class (`template<class T> struct queue`) is no std wrapper for the untyping (`declaresClass`).
- `templateHeads` closes a head at the `>` that balances its `<`, never one inside parentheses (`template<int N = (A > B), class Player>`). A type written `X<T>::Y` over a head parameter is dependent and untyped. An explicit specialization (`template<> void Run<Player>(Player& x) {`, `template<> void f<P>(…)`) is a function on both front ends. A block-local alias inside a template argument is substituted (`using P = Player; using Q = std::unique_ptr<P>`, `substituteAliases`).
- Overloads: the manifest's `calls.overloadTypeKey` folds declared types (`cpp/arg-kinds.ts`), `calls.conversionRanks` makes core rank exact > promotion > conversion (`argFit`'s `ranked` scale), and `calls.explicitSpecializations` has `convert<int>(x)` choose the definition whose `FunctionInfo.specializedOn` names those arguments. An argument naming a variable is `@name`, also `*name` (a dereferenced pointer) and `this->name` (a field); core types it from the parameters, typed locals, `auto c = Club(3)` (one initializer constructing a project class) and the class's fields. Core's `pickOverloads` reads a call's site from the link's own file only.
- A transparent wrapper (`transparentTypeWrappers`) is a smart pointer (`unique_ptr`, `shared_ptr`): a member call passes straight through.

## Receivers, operators, iterators and bindings

- A call through a pointer (`p->m()`) names its receiver like `x.m()` in C and C++ (`p.m`; after what no name spells, `list[i]->m()`, it stays `m`).
- Operators: `a + b` / `a == b` / `a < b` / `a << b` (first operator of a flat chain only) and `a[i]` are calls named `a.operator+` … when `a` is a parameter or local declared as a class-typed value, never a pointer, array, primitive or `auto`. The left operand may also be a field of the function's own class (`kit + o`, `this->kit + o`; an out-of-line `Club::f` reads `Club`'s members, collected per class by `collectFields`) or the pointee of a smart pointer, iterator or `this` (`*owner`, `*it`, `*this`), named `Club.operator+` with `receiverType`. A method defined in a `.cpp` whose class a header declares names `kit + other` / `this->kit + other` as `kit.operator+` / `this.kit.operator+`, which the linker types from the class's fields (a primitive field links nothing). A free `operator+(const Club&, …)` in the same file also gets a bare `operator+` call when its first parameter's type is the operand's: the file's only free definition links on the left type alone; an overload set only when the right operand's type (typed local, parameter, field, pointee or literal kind) equals the second parameter of exactly one overload, the call then carrying both kinds as `argKinds`.
- Iterators: `it->m()` over a container iterator (`std::vector<Club>::iterator`, `auto it = squad.begin()`) and `*it` / `*owner` as an argument (`record(*it)`) read the element class off the container's or smart pointer's declared type, never a container of pointers. `(*it).m()`, `std::next(it)->m()` and a chain from `it->` read as the element's (`Boot.club().sign`). An iterator over a field only the header declares (`auto it = boots.begin()`, `cbegin`, `find`, `lower_bound`) is a `localTypes` entry `element: true` from the field name (never when the body declares a local of that name), so `it->m()` and `(*it).m()` are named `it.m` and the linker types the element; `(*it)->m()` reads through a pointer or smart-pointer element (`vector<Boot*>`, `vector<unique_ptr<Boot>>`, `cppCollectionElementOf`); a value element never takes `->`, a pointer element never `.`.
- Maps: `it->first` / `it->second` are named `it$first.m` / `it$second.m` (key or value class of `cppMapTypes`) with synthetic `localTypes` at `fromIndex` 0/1 read through `tupleElementsOf`, only when the body uses them. A range-for over a map (`for (auto& p : clubs) p.second.m()`, `for (auto& [id, club] : clubs) club.m()`) reads the same way: a local `p` over a name the function does not declare (a field a header declares) names `p.second.m` / `p$second.m` with `localTypes` `p$second` at `fromIndex` 1; a structured binding is typed at its position from the field's (or a local map's) key and value. A container a free function does not declare is a global no linker types, so its calls keep the plain name. A range-for over a range of `pair`/`tuple` (`for (auto& [a, b] : rows)` over `std::vector<std::pair<Club, Team>>`) takes the members of the pair (`cppRangeBindings` in `collection-element.ts`, which also reads a map's key and value; the `pairOf` hook of `extractCFamilyLocalTypes` returns one entry per position; a pointer or non-class member stays null); a container a body does not declare (a header's field) is not read this way.
- `auto [a, b] = pairOf()` is `fromIndex` entries typed by the manifest's `tupleElementsOf` (`std::pair`/`std::tuple` returns; a struct return stays untyped). A structured binding `auto [a, b] = f()` over a project struct (manifest `bindsStructFields`) types each name by the struct's data member at its position: the linker reads `ClassInfo.properties` in declaration order, nothing for a class with a base.
- Range-for with `auto`: a container-typed name takes its element in the plugin; a call or field goes to the linker (`collection-element.ts`).
- `LocalType.aliasOf`: `auto& q = p` / `= *p` is `type: ""` + `aliasOf: "p"`, emitted only when the name is bound once from one head and never reassigned (never `nullptr`/`this`); flow order for the C family is read by [../shared/alias-flow.ts](../shared/alias-flow.ts): open braces, a binding per name, a loop or closure around the alias leaves it untyped when its head is bound more than once; a binding in a block that closed before the alias leaves it untyped.
- A block-local `using X = T;` / `typedef` types that block's locals.

## Aliases

- A pointer or reference alias (`using ClubRef = Club*;`, `typedef const Club* ClubView;`) is a `typeAliases` entry for what it points at (`pointeeOf` in [../shared/c-family-aliases.ts](../shared/c-family-aliases.ts): one level of `*`/`&`/`&&` and cv-qualifiers dropped, `Club**` kept as written and so untyped), so `ClubRef c; c->play()` types like `Club* c`.
- A namespace alias (`namespace lib = home;`) is the same table: the linker rewrites a qualifier through it before matching `ClassInfo.namespace`. A foreign namespace with no alias (`lib::Twin` beside only `home::Twin`) refuses rather than falling through to a bare namesake; unique-global keeps the written path (`lib::Twin`) on the receiver so it cannot match `Twin` either.
- The alias scanner reads `typedef`s inside `extern "C"`.

## Callable fields and value flow

- Function-typed fields (`std::function<…> f;`, `R (*f)(…);` by the property patterns, a field typed by a function-pointer typedef or alias of the same file by the value-flow reader) are `PropertyInfo.callable`. A call `x.m()` or `this->m()` through one is derived by core (`fieldInvokes`, no plugin fact, no accessor-name list) from the calls the function already holds, when the receiver's class, found by `locateClass` through the caller's include closure then its bases, declares `m` callable: a field in a header named unlike its class (`club/types.h` declaring `Squad`) runs what another file stored, and a namesake outside the includes does not. A positional aggregate initializer `T t{ a, b }` and a typedef declared in another file are not read by this path.
- A struct holding a function pointer is a class whose properties are its fields in declaration order (`ClassInfo.fieldOrder`; a missing function-pointer field is added; only for a struct with a field that is or reads as a function pointer and that the plugin can count — nested braces, bit-fields, `a, b;` declarators, `#if`, methods and unions are refused). A tagless `typedef struct { … } name_t` is the class of its typedef name (the file's only other class-graph growth); a struct has one class, so a tagless typedef with several names is the class of the first.
- A positional initializer (`static struct club_ops ops = { "club", 0, club_scout, club_release };`) seeds the fields it fills (`ValueCell.positional`): each element that is a function of the file is a seed on `{ name: <struct type>, member: "#N", positional: { index, count } }`. Core names the field in `cellOf` from the property at `index` of the class `classOfType` finds (`locateClass` through the include closure, then a typedef alias by `dealias`, then the one declaration with a body), refusing when the class is unknown, ambiguous, not `fieldOrder` or has fewer fields than the initializer has elements. The plugin refuses an initializer that mixes designators or has a bare upper-case name or call the file does not define as one value (a macro may widen), and states only elements that are functions the file defines.
- Value flow is read by [../shared/c-family-value-flow.ts](../shared/c-family-value-flow.ts) (the spec's `extractValueFlow` run on the finished analysis), statement by statement: function pointers, `std::function` and lambdas/`std::bind` held in locals, fields (set in a method or a constructor's initializer list, run in another), file-scope globals (a `module: true` cell), arrays and vectors of handlers (the container is one cell), and struct ops tables: `{ .sign = club_sign }` seeds the struct TYPE's member, so a call through any pointer to that type reaches it; nested tables are a field path (`club_conf.ops`). A lambda held in a value stands for the project functions its body calls (at most four, counted by core); the plugin states every name its body calls (up to 16) under one `lambda` id. Only values that can be callables are stated (a function pointer, `std::function`, `auto` or a typedef named for one, or a name the body calls); a member call is an `invoke` in C always but in C++ only for a member the file stores a callable in.
- A function writing a global it does not declare states it as `{ name: X, module: true }`.
- A cell name that is no binding but a project class names that class's own members (a C struct type's ops table, a static member); a dotted name (`c.ops` + member `sign`) walks property types before the member.
- A name typed by a plain identifier the file cannot judge (a typedef another file declares) states its `invoke` with `ifFnType`; the file lists its own function-type aliases in `functionTypeAliases` (`ParsedStructure.functionTypeAliases`). Core keeps the invoke (through the host's `isFunctionType` question) only when the linker's function-type question reads that name, as seen from the file, as an alias and no class: where includes share scope that is the file's whole include closure and nothing beyond it, one pool of names across `.c` and the `.h` read as C++ (C `typedef R Name(args)` / `typedef R (*Name)(args)` are `functionTypeAliases`), alias only is a function type, class only or both a class, never a name pooled across sub-projects. A dropped invoke neither links nor keeps the name tiers off the call. C-specific emission rules: [../c/AGENTS.md](../c/AGENTS.md).

## Macros

- A function-like `#define` outside a function body → `FileAnalysis.macros`, each with the bare calls its body makes (`MacroInfo.calls`; none when the body stringizes or pastes with `#`/`##`; a parameter, member, scoped or declaring name never counts) — [../shared/c-family-macros.ts](../shared/c-family-macros.ts) (`extractCFamilyMacros`/`macroBodyCalls`).
- The symbol linker's `macroBodyLinks` gives a call that landed on the macro (own file first, else the one definition its includes reach, `macroDefinition`) those calls as the caller's own: INFERRED links carrying `SymbolLink.viaMacro` (summary and payload slot [10]), resolved in the caller's scope, nested macros four deep, never through one already on the way; each `#define` hop keeps its own row. Their line is the macro's use, which does not spell the callee, so the rename plan, caret assertions and the resolved-site sets (`isSpelledCallSite`) refuse or skip them; where a caller's one link to a function has both a macro use and a line that spells the call, both dedupes keep the spelled line.
- `token-calls.ts` (`tokenCalls`/`defineCalls`/`leftOutCalls`) reads calls off a C-family ANTLR lexer's tokens (`TokenKinds`) where a parse reads no expression: macro arguments, a `#define` inside a function, left-out branches.

## Qt

- Qt's string connect `connect(a, SIGNAL(x()), this, SLOT(saveClub(int)))` hands the slot on as `passed: "argument"` like `&Window::saveClub`, never a call: the ANTLR reading takes the macro-call form from the `MacroName` branch and the `SLOT(saveClub())` postfix form through `connectReferences`, whose inner call `inSlotMacro` keeps out of the call list; the regex reading does the same (`markQtSlotPasses` in `qt-slots.ts`: a `SLOT(name(…))` call is marked passed, a `&Owner::slot` argument after the signal is added as `Owner.slot`). `connect-elements.ts` reads connect arguments.
- Framework rules `qt` (C++ manifest) and `qt-quick` (QML manifest) live with the plugin that owns the file format.

### QML (`../qml/`) and Qt Designer (`../qtui/`)

- QML (`.qml`, regex, `importTarget: false`, `frameworkImportHints: { QtQuick: "qt-quick" }`) has a reachability model among the declarative specs built by [../shared/reachability-kit.ts](../shared/reachability-kit.ts). `QmlCppBridgeResolver` (`qml/dispatch.ts`; `dispatchLanguages: ["cpp", "c", "objc"]`) joins QML elements to the C++/C/Objective-C classes that register them, so a Qt project whose C++ registers QML types needs the bridge even before a `.qml` is discovered.
- Qt Designer forms (`.ui` XML, `qtui/index.ts`, the Qt Widgets analog of Delphi's `.dfm`): each file is one screen named by `<class>`, nested `<widget class=… name=…>` elements are its component tree, and `<connections>` wires widget signals to C++ slots (`pushButtonApply.clicked() → DlgPrefEQ.slotApply()`); the interactive elements carry the slot name as handler for the symbol linker to pick up. No functions, classes or imports.

## CUDA

- `.cu`/`.cuh` are read by this plugin like C++ (`cuda.test.ts`).

## Member effects and reachability

- `fieldWrites`/`thrownTypes`: a C++ method written out of line states its bare names for core to keep where the class or a base declares them (`this->x`, `p->x`, `++`/`--` included); C++ states thrown types (`std::runtime_error` binds only through a qualifier the project backs, `qualifierBacksClass`). Implementation: `member-effects.ts`.
- C, C++ and Objective-C share one reachability instance ([../shared/c-family-reachability.ts](../shared/c-family-reachability.ts), a `conventionReachability` spec): a C function behind a header is reached by name (`declaredNames`).
- A CMake root that registers tests gets the test command `ctest --test-dir build` (build + ctest, read by [../shared/cmake-commands.ts](../shared/cmake-commands.ts)); `projectMarkers` makes a `CMakeLists.txt` a `cmake` project root only when it contains a `project()` call (`project-markers.ts`; activation files `CMakeLists.txt`, `conanfile.txt`, `vcpkg.json`).
- Control flow: C and C++ go through `meta.regexControlFlow` (approximate); node roles from the shared C-family table `control-flow-defaults.ts`.
