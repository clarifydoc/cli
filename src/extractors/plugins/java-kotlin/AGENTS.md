# Java and Kotlin plugin

Reads `.java` (`tree-sitter-java`) and `.kt`/`.kts` (`tree-sitter-kotlin`) with tree-sitter; two metas of one folder, both `family: "jvm"`. The plugin states facts; core resolves (see [core](../../../core/AGENTS.md)). Spring, JAX-RS, Ktor, Javalin/Spark, Android, Retrofit/Feign and the build files are read here; Spring XML, MyBatis XML and `AndroidManifest.xml` are read by [springxml](../springxml/AGENTS.md).

## Files, front end and build files

- Visibility: a Java method is package-private (`isExported=false`) unless `public`; Kotlin defaults to public.
- A manifest's `packageRoots` (JVM `src/<set>/java/`) re-admits `target`/`out`/`bin`/`vendor` below it as packages.
- Both languages are in `FLAT_TREE_LANGUAGES` (flat copy of the tree; a Java repository's cold CPU 24.6 s → 17.5 s). A hidden zero-width MISSING token an external scanner inserts (Kotlin's statement end, its automatic semicolon) is never visited by the cursor, so `flattenTree` asks the real nodes for `hasError` when the real root has it and the copy does not (`readErrorFlags`).
- Framework rules (`frameworks.ts`) attach to ONE member meta only (`java`), so the registry sees each rule once.
- A Maven POM whose root is `<m:project xmlns:m="…">` is read through `withoutRootPrefix` ([../shared/xml-scan.ts](../shared/xml-scan.ts)): the root's prefix is stripped from element names before the dependency, property and parent regexes run (packages, the package it publishes, the project commands). Package managers: Maven (`selfName` = the pom's `groupId:artifactId` with the parent's group) and Gradle (`group` + project name; its registry is maven; a Gradle `namespace` manifest is read for Android).
- Test commands: Maven/Gradle by manifest (`test-command.ts`, `project-commands.ts`).
- Control flow: both are exact tree-sitter graphs. The regex control-flow tier is gated against the Java parser at ≥90% same-shape functions.
- Reachability: a declarative spec from `reachability-kit` (`reachability.ts`). Java finds files by namespace, so an import graph cannot prove a file unreachable; framework-instantiated classes (`@Component`…) are passive, not entries.
- LSP: Java uses jdtls (container `network: "bridge"` because it restores packages to type-check — offline it loses most reference answers; `indexDelayMs` 10 s, needs `pom.xml` and a writable mount), Kotlin uses kotlin-language-server.

## Structure

- `extractAnnotations` for Java keeps the annotation name only (known gap); Kotlin decorators carry arguments. Route attribute metadata (`middleware`, `auth`, `versions`, `params`) is filled through `shared/route-metadata.ts`; [routes/meta-annotations.ts](routes/meta-annotations.ts) is a reference implementation: class-level annotations are inherited by every method, an anonymous marker waives, a binding derived from framework defaults is `inferred: true`.
- Enum constants: a constant's override of a method the enum declares (`ATTACK { void play() { coach.shout(); } }`) hands its calls to the enum's own method of that name (same parameter count; an abstract declaration is the usual host); a method the enum lacks is still added.
- Anonymous classes: calls stay with the enclosing function, but a bare one inside `new Base() { … }` carries `withSubjects` (the anonymous class, then `Base`), so it resolves on the base's member before the enclosing class's or a namesake's ([java-anonymous.ts](java-anonymous.ts)); a local initialized by an anonymous class is typed as a synthetic class of the file (`Runnable$5_23`: `extends` the base, synthetic call-less methods), so `handler.run()` reaches its `run`.
- Constructors: Java `this(…)`/`super(…)` are the calls `new <ownClass>` / `new <superclass>` (`explicit_constructor_invocation`), settled by argument kinds like any construction. Kotlin delegation is the same ([kotlin-delegation.ts](kotlin-delegation.ts)): a primary `class A(…) : Base(x)` gives the primary constructor (a synthetic parameterless one when none is written) a `new Base` call, a secondary `: this(…)` / `: super(…)` a `new A` / `new <superclass>` call, linked to the constructor its arguments choose; a secondary constructor's statements are its body.
- `localDeclarationTypes` (Java `local_variable_declaration`): a declarator in a local declaration names a value, not a function, so `Runnable r = () -> club.save();` leaves `club.save` on the enclosing method's row (a field's lambda stays out).
- Generated JVM types are synthesized, marked `synthetic`, and never shadow written members ([synthesized-members.ts](synthesized-members.ts)):
  - an enum (either language) gets `values()` and `valueOf(String)`, so `Position.valueOf(s).label()` types through and a namesake class's `valueOf` never answers; a Kotlin enum states a static `entries` typed `List<X>`;
  - Lombok `@Builder` (on a class, constructor or static method) gets its own builder class and builder method (named by `builderClassName`/`builderMethodName`/`buildMethodName`, else `<Result>Builder`/`builder`/`build`), `@Singular` collection fields the one-element setter (`players` → `player`, or the name it states), `@Data` accessors; Kotlin `copy()` and record accessors are synthesized too;
  - `@AutoValue` gives the `AutoValue_Club` subclass (`AutoValue_X`) (`AutoValue_Outer_Inner` when nested, through class, record and enum owners); Immutables `ImmutableX` classes: `@Value.Immutable` (only the qualified spelling, never one with `@Value.Style`) gives `ImmutableClub` with `builder()`, `copyOf(…)`, `withX(…)`, `of(…)` for `@Value.Parameter` attributes (`@Value.Default` setters included) and its builder `ImmutableClub_Builder` (a unique name, since a class is told apart by file and name); `ClassInfo.nestedPath` = `ImmutableClub.Builder` is the owner path a written type means it by — the Lombok builder states `Club.ClubBuilder` the same way;
  - a generated AutoValue/Immutables class carries `ClassInfo.yieldsTo` (the written sibling it stands for); core's `dropYieldedClasses` ([../../../core/yielded-classes.ts](../../../core/yielded-classes.ts)) drops it where the same sub-project writes a class of that name, so a name is never two classes;
  - MapStruct needs nothing: the mapper interface's own methods already carry the return types a chain continues through.
- Java reaching Kotlin by JVM names ([kotlin-facade.ts](kotlin-facade.ts)): a Kotlin file's top-level `val`/`var` are the facade class's accessors (`ClubsKt.getSeason()`, `setSeason(…)`, `isOpen()` for a Boolean `isOpen`), appended through the `facadeFunctions` hook as `synthetic` functions (no complexity row; a function the file writes under that name stands; a private, `const`, `lateinit` or `@JvmField` property, a property with a receiver and a `.kts` script have none). A NAMED companion (`companion object Factory`) is `ClassInfo.memberHolder`: Java writes `Club.Factory.build()`, which links to `Club.build`, and `Club.Companion.build()` then links nothing, since a class that names its holder is reached through that name alone.
- Type-parameter bounds ([type-bounds.ts](type-bounds.ts); the letter-to-bound substitution is [../shared/type-parameter-bounds.ts](../shared/type-parameter-bounds.ts)): Java `<U extends Boat>` / `class Garage<T extends Car>` and Kotlin `fun <U : Boat>` / `class G<T : Car>` (also `where U : Boat`) give each parameter and typed local written as that bare letter the bound as its `ParamInfo.type` / `localTypes[].type`, so `u.sail()` links like any typed receiver — core is untouched. A method's own letter beats an enclosing class's, innermost class first; an unbounded letter shadows an outer bound and stays untyped. With several bounds the FIRST is taken (`T extends Car & Comparable<T>` → `Car`; Kotlin `where` order) — a project class listed after a library bound is missed. A bound that is another letter of the member (`where T : U`) leaves the letter untyped; the Kotlin extension receiver (`fun <T : Boat> T.dock()`) takes the bound; fields and constructor properties written as the letter, and a local class or lambda inside a generic method, are NOT covered (open).

## Imports and scope

- `ImportInfo.inScope` marks imports that put members in scope by bare name: Java `import static`, Kotlin function and `object`-member imports. `ImportInfo.aliases` carries a Kotlin `import … as`.
- The manifest's `packageScope` (Kotlin, with `directoryScope`) makes the declared `package`, not the folder, the scope: same-package files in any folder of the sub-project share top-level functions, and a bare class name is the one its own package declares. A Kotlin top-level `val` (declared or constructed) is a `moduleBindings` entry.
- `ownerPathTypes` (manifest): `receiverTypeName` keeps a type written through its owner (`Right.Builder`, a package prefix left off; a platform owner such as `Map.Entry` is no project type), and the plugin states a local's type the same way (`Right.Builder b`, `new Right.Builder()`, Kotlin `Right.Builder()`), also for a field, parameter or return type. Classes keep bare names; core resolves the path with `ownerPathIn` ([../../../core/symbol-linker.ts](../../../core/symbol-linker.ts)): the owner's file, then the class inside the owner's lines or a generated class's `nestedPath`, through the owner's bases for an inherited nested type, else the one file declaring both owner and nested class; a path no owner bears out links nowhere, so two nested `Builder`s, a top-level `Builder` or an external owner never meet the written one.

## Linking rules

- Narrowing: Java and Kotlin state a narrowed receiver's type while the call walk runs (`withCallNarrowing` around `extractCalls`, read by the call hooks' `receiverTypeOf`), because the walk keeps one call per name and receiver type: `is Club -> x.save(); is Player -> x.save()` stays two calls, a Kotlin subject-less `when { x is Club -> … }` narrows too, and a call outside every arm gets no narrowed type.
- Kotlin: `calls.withSubjectsOf` names the implicit receivers of `with`/`apply`; `for ((club, player) in map)` / `.keys` / `.withIndex()` are typed through the shared element chain (`ChainRules.keys`, `ElementState.key`; JVM and .NET share the chain reader `extractors/shared/element-chain.ts`); tuple patterns `val (club, player) = load()` over `Pair`/`Triple` ([wrapper-elements.ts](wrapper-elements.ts)) and, with `bindsStructFields`, over a data class's constructor properties in order use `localTypes[].fromIndex` and the manifest's `tupleElementsOf`.
- Wrappers — Java/Kotlin only list a wrapper the hook unwraps. A wrapper whose members are its own (Java `Optional`/`Provider`, Kotlin `Lazy`) is NOT a `transparentTypeWrappers` entry: `opt.get()` would link to a `get` of the wrapped class.
  - `valueOut.calls` (built by `extractors/shared/value-out.ts`): `join` (`CompletableFuture`), `get` (`CompletableFuture`, `Future`, `Optional`), `orElseThrow` (`Optional`), `block` (`Mono`), Kotlin `await` (`Deferred`). Core's `walkChain` asks the hook (`takes` before reading any declaration, `at` on the declared type) and goes on from the wrapper's first type argument when the call before one of these DECLARES a listed wrapper — `var c = repo.findAsync(id).join(); c.promote()` and `repo.findMono(id).block().relegate()` reach `Club`; a project class's own `get()` keeps its declared return type, and an unlisted generic's `join()` unwraps nothing. Keys are read as own properties only (`toString` is no unwrapping call).
  - A wrapper a field, parameter or method DECLARES (`private Provider<ClubRepo> provider; provider.get().save()`, `this.provider.get()`, a `Provider<ClubRepo>` parameter) is read by `unwrappedDeclared`/`wrappedHead` from the written type; the `members` table names Kotlin `.value` on a `Lazy<T>`. `wrapperShadowed`: the hook returns the head it read and core refuses a project class of that name; a wrapper must be listed under that member, so `Box<ClubRepo>.value` or a project class with its own `get()`/`Value` unwraps nothing, and a wrapper name the project declares as a class is never unwrapped.
  - A local holding the unwrapped value: `var c = repo.find(1); c.get().save()` reads the wrapper off the declared return of the one call the local is initialized from (not awaited, no `choice`); a Kotlin `val s = lazy.value` and EVERY plain member read off names (Java `var m = club.manager`, Kotlin `val t = settings.turf`; never a call, indexer or `?.` in the path) state `localTypes[].from` with `member: true` — the plugin never consults `members`: the linker takes the value out of a listed wrapper and else types the local by the member's declared type, untyped where that is no project class.
  - Elements: `elementCalls` (`get`) with `elementOf` (`jvmIndexedElement`: a `List`'s element, a `Map`'s VALUE, one plain type name) take one element out of what the segment before DECLARES — `repo.all().get(0).promote()`, `club.players.get(0)`, `var l = repo.all(); l.get(0)`, Kotlin `var c = repo.all()[1]` (stated as written, never rewritten as a `.get()` call text: `receiverChain`/`receiverChainOf` makes it an `index` segment, kept only where the hook has an `index` member — Kotlin `get`); a project class's own `get(int)` keeps its declared return, and a project class named like the collection shadows it. `valueOut.arrayIndex` (Java) reads `x[i]` over a declared array (`Position.values()[0].label()`): the index step takes `Position` out of `Position[]` and yields nothing for any other type; Kotlin `Array<X>` is indexed, `first`/`last` take an element.
  - Map entries: a loop over `m.entrySet()` / Kotlin `m.entries` / a map looped directly is a `kind: "entry"` state of the shared element chain (`ChainRules.entries`/`entryValue`/`entryKey`: `entrySet()` is a collection whose `elemState` carries the key and value types, never a `Map.Entry<K, V>` text), so `en.getValue()`, `en.getKey()` and Kotlin `en.value` type; a name two loops bind to different entries is dropped. Only a TYPED map root (parameter, field, typed local) is read; a call-initialized map (`repo.byName().entrySet()`) stays untyped.
  - Operator lambdas: a lambda handed to `map` (`repo.findAll().map(club -> club.promote())`), `flatMap`, `flatMapMany`, `concatMap`, `doOnNext`, `doOnSuccess`, `subscribe`, `thenApply`, `thenAccept`, `thenCompose`, `ifPresent`, `forEach` (Kotlin `collect`) on a call's result binds its first parameter as `localTypes[].from` + `element`; the linker takes the element through the manifest's `collectionElementOf` = `jvmElementText` ([wrapper-elements.ts](wrapper-elements.ts)): the shared collections plus `Mono`, `Flux`, `CompletableFuture`, `CompletionStage`, `Optional`, `Stream` (Kotlin `Deferred`, `Flow`). Operators that keep the element (`filter`, `doOnNext`, `peek`, `stream`… — the rules' `keeps`) are peeled off the receiver first; `map` and `flatMap` are not (their result is the lambda's), so the chain stops typed there. A project generic (`Box<Club>.map`) is no listed wrapper and types nothing; a written parameter type wins.
  - An operator's RESULT is typed where declared types state it: `map(c -> c.league())` hands the next lambda what `Club.league()` declares, `flatMap(c -> c.promote())` the element of what that declares (`Mono<Club>` → `Club`), also through `Club::league` (the reference's class must be the element's); Kotlin `let`/`also` hand `it` the receiver's own type (`?.` and `!!` read through, `let { it.league() }.let { l -> … }` follows the value). The plugin spells it as a `from` chain with the segment `@element()` (`ELEMENT_HOP`, [../../shared/collection-element.ts](../../shared/collection-element.ts)) — `repo.findAll().@element().league()` — read by `walkChain` as the element of the type the segment before DECLARES; only a single call on the parameter is a body (a block, a helper call or a different head stops untyped), and a chain whose first segment is the caller's own bare method has no hop.
  - A name bound by several lambdas of one method is scoped per lambda: a call inside one carries `CallInfo.receiverFrom` (the same `from` + `element`), typed for that call alone, so `clubs.forEach(x -> x.promote()); players.forEach(x -> x.retire());` types both `x`; the method-wide `localTypes` entry stays for other readers, and a call carrying the fact is typed by it first (a lambda whose own source cannot be read keeps what the name's other bindings give it).
- `blockingCalls`: Kotlin `runBlocking`, `Thread.sleep`, matched by name inside an `isAsync` function.
- SQL: a plugin reading SQL handed to a call (Java among them, [data-sources.ts](data-sources.ts)) emits its own row for the statement and `joinedTableRows(sql, own, name, line)` for the rest, or `sqlAccessRow` per access. `execute` is not an HTTP method name (JDBC `stmt.execute` is no api-call).

## Value flow ([value-flow.ts](value-flow.ts))

- Method and callable references (`this::save`, `Club::save`, `club::save`, `Club::new`, `::save`) seed locals, fields (initializers ride on the constructor, else the first method), `List.of`/`listOf`/`mapOf` literals and `add`/`put`/index writes (element cells `[]` / key, a field's as `this.<field>[key]`).
- `run`/`apply`/`accept`/`get`/`call`/`test`/`compare`/`handle`, Kotlin `f()`/`f.invoke()` are `invoke` facts only on a receiver the facts know holds a function (a JDK functional-interface or Kotlin function type, or initialized from a reference), never one built by `new`/an anonymous class.
- A lambda or Kotlin lambda literal landing in a cell (local, field, collection element, argument — a trailing lambda is the last one —, return, field initializer) seeds it with each project function its body calls (`save`, `this.save`, `club.save`, `Club.save`; at most four project functions, counted by core; none for a call on the lambda's own parameter or implicit `it`, a chain or a JDK call) and copies the cell of a held function its body runs (`() -> onDone.run()`); it gets no function of its own, so its calls stay the enclosing function's.
- A call into a library states no `arg` fact (`isLibraryCall`, over the file's `LibraryContext` — package, imports, declared methods — carried on `ClassFlow.library` and `methodValueFlow`): a bare name the file does not declare as a method or class, brought in from the manifest's `externalModulePrefixes` or outside the file's root package (first two `package` segments) by a Java `import static` of that name, a Java `import static x.*` when no class of the file extends another (an inherited method looks the same), or a Kotlin import of that very name — never a Kotlin wildcard, since a same-package function or class needs no import — (`import static spark.Spark.*`, `import io.ktor.server.routing.post`), or a call on a receiver typed by such an imported class (`Javalin app`, `Javalin.create(…)`); a method the file declares itself and a call on an untyped lambda parameter are not library.
- A bare JDK functional-interface name (`Consumer`, `Supplier`, …; not `java.lang`'s `Runnable` or Kotlin's `Comparator`) is a function type only where the file imports it (explicitly from a library path, or by any wildcard import from a library path) or writes it qualified — `isFunctionType(text, lib)` over the `LibraryContext` — so a project class of that name in the file's own package is no function and a call on it keeps its ordinary link. Parameters, locals, `for` variables, fields (a Kotlin constructor property too), returns, element collections (array, `List<Consumer>`, `forEach` parameter) and a Kotlin builder's element type (`mutableListOf<Consumer<T>>()`) state their invoke with `ifFnType` instead (`invoke.ifFnType`) (`functionTypeVerdict`: `true`, `false`, or the bare name for core to judge — [function-types.ts](function-types.ts) is the static list on the manifest as `platformFunctionTypes`; `ClassFlow.cond`/`elemCond`/`returnsCond` carry it from a declaration to the call). Core judges it (`judgePlatformFunctionType`): the platform's when `java.lang` brings it in, a single-type import names no project class of that package, or an on-demand import of a package the project does not declare brings it in and no class of the file's own package shadows it; a class the file declares is the project's. The plugin keeps no judging gate.
- A Kotlin named argument (`schedule(callback = ::f)`) is an `arg` with `name`; a positional one after a named one and a trailing lambda after named arguments state none.

## Member effects

- `FunctionInfo.fieldWrites` (`member`, `receiver` as written — `this`, `this.<field>`, a parameter or local name carrying a declared type, "" for a bare field — and line; never from a constructor, never from an untyped receiver, nested non-arrow functions and local classes left out) and `FunctionInfo.throws` (the type as written with its qualifier, the `throw new T` / Kotlin `throw T(…)` site, `declared` for a Java `throws` clause or Kotlin `@Throws`; a rethrown variable states nothing). A qualified name (`java.io.IOException`) binds by its last segment only through a qualifier the project backs (a package the class is declared in, directories on its path). See [member-effects.ts](member-effects.ts).

## Routes and frameworks

- Routes: [routes/spring.ts](routes/spring.ts) (Spring MVC, plus `routes/security-dsl.ts` — Spring Security `authorizeHttpRequests` rules become guards of the routes they match, resolved cross-file), `routes/jaxrs.ts` (+ resolver; JAX-RS routes carry `RouteInfo.contract` for the type that declares them), `routes/ktor.ts` (a Ktor `fun Route.x()` registers routes on the router it is handed: `owner: "fn:<name>"` rows + `router-call` facts, composed by `plugins/shared/router-functions.ts`), `routes/javalin-spark.ts` (Javalin ApiBuilder + `crud`, Spark `path` groups), plus the Android navigation, GraphQL, actuator, gateway and functional-route readers in `routes/` and [gateway-routes.ts](gateway-routes.ts).
- A guard inherited from a Spring base class is joined through `plugins/shared/class-guards.ts`.
- DI: `@Inject(TOKEN)`/`@Qualifier("x")` states `qualifier` on an injection point; Spring autowire-by-name is `DiBinding.matchesMemberName`, `@Profile`/`@Conditional*` is `conditional` (yielding to an unconditional binding), `@ImplementedBy` is `ifAbsent`. Bindings: [di-bindings.ts](di-bindings.ts), [di-annotations.ts](di-annotations.ts).
- Spring AOP — a dispatch resolver, `dispatch:aop-advice`, no per-file fact ([aop-advice.ts](aop-advice.ts), `java-kotlin/aop-advice.ts`): an AspectJ/Spring AOP advice method has no call site, so the resolver reads each `@Aspect` class's `@Before`/`@After`/`@AfterReturning`/`@AfterThrowing`/`@Around` pointcut from the decorator text (a string, `"a" + "b"`, a Java text block, `value=`/`pointcut=`) and draws an INFERRED edge from every project method it matches to the advice, so a route's reach lists it.
  - Read: `execution`, `within` (also `within(@pkg.Anno *)`), `@annotation` (a literal type or an advice parameter bound by name), `@within`, `&&`, `||`, `!`, parentheses and a named `@Pointcut` (the aspect's own, else one unique aspect's). Evaluation is three-valued: any other designator, an unresolved name or a modifier other than `public` is unknown, and an edge needs the whole expression certainly true.
  - `..` is zero or more whole segments in a dynamic program over segments (a long pattern cannot backtrack); an interface named by `execution` also reaches the project classes implementing it; test files and the aspects themselves are no join points.
  - A pointcut's type name resolves through the aspect file's imports (`resolveSimpleName`: the alias a Kotlin `import … as` binds, never a static import's member), else its own package; each `execution(...)` atom is compiled once per run and fails on its name glob first.
- Android: [android-manifest-components.ts](android-manifest-components.ts) links the manifest function springxml admits to each `<activity|service|receiver|provider|application>` class it names, resolved against the manifest `package` (for a Gradle `namespace` manifest, the package ending with the written path), within the manifest's own module and only when exactly one class matches. Dead-code verdicts were already correct (entry base types, `configMentions`); the edge removes the "no callers" answer.
- Calls through a REST client proxy ([client-proxies.ts](client-proxies.ts)): `HttpClientRegistration.proxyOf` from a `RestClient.createClient(X.class, url)`-style call or (with springxml) a Spring XML factory bean makes every call on a receiver of that type an api-call carrying `contract` (`a.b.PersonApi#getPerson`); a Retrofit builder is keyed by the API interface whose verb-annotated methods are the requests (`${IClubApi}/{id}` until the base is known; [retrofit.ts](retrofit.ts)); `@FeignClient(name = "league")` is a `service` base ref resolved through the name a project registers under in service discovery (`spring.application.name`). Routes carry `contract`; a call with a `contract` joins the route declaring the same operation first.
- Service config ([service-config.ts](service-config.ts)): `routeBaseOf` reads `server.servlet.context-path` (profiles never) so core prefixes the complete API routes; `proxySources` read Spring Cloud Gateway / Zuul routes in `application.yml` (`StripPrefix`, `RewritePath`, `PrefixPath`, `lb://name`); `normalizeKey` states the relaxed key spelling.
- Config reads: `@Value`/`@ConfigurationProperties` ([data-sources.ts](data-sources.ts)) mark `DataSourceInfo.configRead` (`kind: "env"`, `target` the key as written, no default); a `@Value("${LEAGUE_TOKEN}")` spelled like an environment variable is also an `envVars` read. `Environment.getProperty`/`getRequiredProperty` on a receiver declared `Environment`/`ConfigurableEnvironment`/`PropertyResolver` in a file importing `org.springframework.core.env` is a `configRead: key` row like `@Value`; an untyped receiver, `Properties` or a project class stays a plain read.
- File path reads ([file-path-reads.ts](file-path-reads.ts)): `File`/`Paths.get`/`Path.of` in a file importing `java.io`/`java.nio.file`, literal path parts only; a hole, a variable or another receiver states nothing.
- Data: Spring Data derived queries and `@Query` placeholders name their columns; Spring AMQP `convertAndSend("x", "y", payload)` is exchange `x` + routing key `y` (`entity`) unless the third argument is a string literal (two overloads fit: unresolved) or a post-processor; Paho/HiveMQ rows carry `topicSyntax: "mqtt"`, a topic constant read as `Type.NAME` is a row with `target: null` + `targetRef` (filled by core from the declaring class), and `new String[]{…}` / Kotlin `arrayOf` give one row per topic; the Dapr Java SDK is read for pub/sub.

## How core passes read it

- Param columns: `@PathVariable("id") Long clubId` binds the handler parameter `clubId` to the route parameter (`RouteParamInfo.variable`).
- Config reads: `@Value("${league.token}")` is a `key` read and `@ConfigurationProperties(prefix = …)` a `prefix` read (`DataSourceInfo.configRead`); a key spelled like an environment variable is also an `envVars` read. A config-file path in code (`new File("config/league.yml")`) joins its file through `filePathReads`, not as a config key.
- Conditional receivers: Kotlin `if (c) a() else b()` and `when (k) { A -> a(); else -> b() }` mark their arms with one `localTypes[].choice` (a `when` needs an `else` entry and one expression per entry).
- `val dao = Factory.getDAO()`: a local initialized by a call that states no type is stated as `localTypes[].from`; core types it through declared return types.
- Conditional initializers (`if` expression, Kotlin `when` with an `else`) are marked with a shared `localTypes[].choice`.
