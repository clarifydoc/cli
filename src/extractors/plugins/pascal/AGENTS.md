# Pascal plugin (Delphi, Free Pascal / Lazarus, `.dfm`)

Reads Pascal units and programs (`.pas`, `.pp`, `.lpr`, `.dpr`, `.dpk`) with tree-sitter (`tree-sitter-pascal`, wasm built by the grammar setup; `.pas` is in `FLAT_TREE_LANGUAGES`), and the form resources `.dfm` / `.lfm` / `.fmx` through a custom recursive-descent parser (a second manifest, `dfm`: `parsing: "custom"` + `customParse`, `designFormat: true`, not an import target; `.lfm` is Lazarus, `.fmx` FireMonkey — same object syntax, always text; only classic `.dfm` can be a binary TPF0 stream). Both manifests are family `pascal`. Cross-language mechanisms: [../AGENTS.md](../AGENTS.md), [../../../core/AGENTS.md](../../../core/AGENTS.md).

## Files and front end

- [manifest.ts](manifest.ts): `caseInsensitiveNames: true` (`_repo.save` calls the declared `Save`), `importsShareScope: true` (`uses WaitForm;` puts the unit's interface routines in scope unqualified: a bare `ShowWaitForm(…)` is the one used unit that declares it), `constructorCalls: ["Create"]` (`TfrmPlayers.Create(AOwner)` runs the constructor, reported as `constructor`), `dispatchLanguages: ["dfm"]` (the DFM → handler UI bridge joins `.dfm` wirings to form methods, so discovering `.dfm` files must load this plugin's resolvers too).
- Project markers: `**/*.dpr`, `**/*.dpk`, `**/*.dproj` (kind `delphi`, priority 10), `**/*.lpi`, `**/*.lpr` (kind `lazarus`, priority 20).
- External units: unit-scope roots (`System.`, `Vcl.`, `FMX.`, `Data.`, `Winapi.`, `FireDAC.`, …), classic RTL/VCL units in canonical casing (`SysUtils`, `Classes`, `Forms`, …), lowercase variants ONLY for names no other ecosystem would use as a bare import (prefixes aggregate globally; lowercase `classes`/`types`/`db` would shadow legitimate bare local imports in TS/JS repositories), and Indy's flat unit names (`IdHTTP`, …).
- Framework rules ([frameworks.ts](frameworks.ts), uses-clause units and project files) attach to the `pascal` meta only, never to the `.dfm` resource meta (family plugins attach rules to one member meta so the registry sees each rule once).
- Auto-import classification strips a Pascal `F` prefix (`classifyAutoImported` / `qualifiedRootCandidates`).
- Conditional compilation ([directives.ts](directives.ts), the meta's `preprocess`): a `{$IFDEF …}` group that wraps nothing but routine directives after a header (`function Size(…): Integer; {$IFDEF SUPPORTS_INLINE}inline;{$ENDIF}`) cannot be placed by the grammar between a header and its body — the rest of the unit would become one parse error and its routines would be lost — so such groups are rewritten before parsing; so are a one-line `{$IFDEF X} A {$ELSE} B {$ENDIF}` inside a declaration or expression (the first branch is kept), a group holding only string literals (a unit that refuses to compile for an unsupported platform: blanked) and a group right after a routine header wrapping its `var`/`const`/`type`/`label` sections (the directives are blanked, the declarations kept).
- A reader that cuts text before matching (Pascal's comment stripper) states a column only when the line's text before it is unchanged.

## Imports, units and scope

- `uses Unit1 in 'src\Unit1.pas'` ([imports-exports.ts](imports-exports.ts)): `.dpr` files name each unit's FILE; tree-sitter-pascal ERRORs on the in-clause (the string never reaches the AST), so the paths are scanned from the source and joined to the walked imports by unit name; only names that ARE imports are rewritten, so an unrelated `for c in 'abc'` match can never invent one.
- Search paths ([search-paths.ts](search-paths.ts), leaf code the manifest imports; consumed by core's `applyModuleSearchPaths`): a bare import two files answer to (`uses Garage` beside `Win/Garage.pas` and `Posix/Garage.pas`) is rewritten to the file the project's build files mean — a file they name for the module (a `.dproj` `DCCReference Include="Win\Garage.pas"`, an `.lpi` project unit's `Filename Value="…"`, a program's `uses X in 'path'` where the manifest's `moduleSearchPaths.pathImportsPin` says so), else the one in the project's own directory, else the first search directory holding one (`DCC_UnitSearchPath` per `PropertyGroup` — the groups every build reads, no condition or the `$(Base)` one, searched in order; those of platform and configuration groups are `conditionalDirs`, deciding only where they leave one candidate — and Lazarus `OtherUnitFiles` per build mode). Entries holding a macro (`$(DCC_UnitSearchPath)`, `$(TargetOS)`) are left out: what they expand to is the IDE's. Read at each sub-project root; the rewrite is in memory only, before the import index.
- Module bindings ([module-bindings.ts](module-bindings.ts)): the typed variables a unit declares outside every routine — `var dmLeague: TdmLeague;` in the interface section is what `dmLeague.SaveClub` in any unit that `uses` it calls through (`FileAnalysis.moduleBindings`, seen through `importsShareScope`); one in the implementation section only the unit's own routines see; a program's or library's own globals are seen by nobody. Only a named type is kept (not `array of`, `^T` or a builtin): a receiver needs a class. Two used units typing one variable differently decide nothing.
- Forms and units: a form and its unit are companions by basename ([companion.ts](companion.ts)): `Main.dfm` (or `.lfm`, `.fmx`) belongs to `Main.pas` (or `.pp`), the stem lower-cased as Windows file systems compare.

## Linking rules

- A name read without parentheses inside an expression (`CallInfo.read`: `N := ACar.Shine`, `if qry.IsEmpty then`, `N + Points`) is linked by `resolveReadName` only when it resolves without guessing to a function or method — `calls` when that returns a value, `passes` when it is a procedure (`OnClick := btnSaveClick`) — or to a construction; a field, variable or class read draws no edge, and `classifyCalls` never makes one a database or API call. A property whose getter is a method (`PropertyInfo.readAccessor`) answers in the symbol index with that method, so `ACar.Points` lands on `TCar.GetPoints`.
- `calls.withSubjectsOf` names the implicit receivers a bare call may run on (Delphi `with`).
- Control-transfer standard procedures (statement-position identifiers) are never call edges ([call-hooks.ts](call-hooks.ts)).
- UI bridge ([ui-bridge.ts](ui-bridge.ts)): a `.dfm` wires events by NAME only (`OnClick = btnCloseClick`); the method lives in the companion unit's form class (`procedure TfrmMain.btnCloseClick(Sender: TObject);`). Nothing in either file is a call, so the resolver emits INFERRED `<dfm file>::<component> → <pas file>::<TForm>.<handler>` links, joined by the form CLASS declared in the `.dfm` root (`object frmMain: TfrmMain`): the companion unit (same path, `.pas`/`.pp`) wins outright, otherwise the longest common path prefix; handlers inherited from a base form are found by climbing `extends` one unit at a time.
- Dependency injection ([di.ts](di.ts), Spring4D style): registrations (`GlobalContainer.RegisterType<TSqlRepo>.Implements<IRepo>`, optionally a name), lookups (`GlobalContainer.Resolve<IRepo>`, `ServiceLocator.GetService<IClock>`), and the locals a routine declares or fills from either. The symbol linker joins them; nothing here decides which implementation an injection point receives. Generic instantiations are `exprTpl` nodes in the tree.

## The `.dfm` parser and forms

- The parser ([../../../parsers/dfm-parser.ts](../../../parsers/dfm-parser.ts)) produces `ScreenInfo` with a nested `ScreenComponentInfo` tree. A caption is a Pascal string literal decoded (`'caf'#233' squad'` → `café squad`, `''` → `'`). A component's `dataBindings` add what it shows or runs to its data links: `Action=`, `DataField=` / `FieldName=` and the DevExpress `DataBinding.` spellings (screen bindings only, never data sources). `origin` is a place stated without a size (an auto-sized control, or a non-visual component's place on the design surface); `constraints` are what the form holds a field to (`MinValue`/`MaxValue`, `MaxLength`, `ReadOnly`, `Required`, `Enabled = False`, formats and masks, on the control or its `Properties.`); an event set on a sub-object (`Properties.OnValidate`) is among the component's `events`, never an interactive element.
- Data model from forms ([dfm-entities.ts](dfm-entities.ts), fed from the object tree `parseDfm` already built — the `.dfm` is parsed once): a Delphi/Firebird codebase keeps no schema in the repository, but the IDE persists enough into every `.dfm` to rebuild the tables the app uses. A dataset's single-table DML (INSERT column list, UPDATE SET list, single-table SELECT) names the table AND its writable columns, and its persistent `TField` children supply each column's TYPE and width (field classes ARE the column types: `integerfield`, `largeintfield`, …). Columns never come from the field list alone — a dataset's `SelectSQL` is usually a join, so its fields are a result-set shape, not a table shape (attributing them to the owning table would invent columns); a dataset whose only SQL is a multi-table SELECT contributes relations but no table. Relations come from join predicates only (`INNER JOIN TEAM T ON T.ID = TL.TEAM_ID` is `TEAM_PLAYER → TEAM` many-to-one), emitted with orm `"ci-query"` (`DFM_ORM = "dfm"` marks the entities for the cross-file merge) so `buildEntityGraph` and `synthesizeReferencedTableEntities` both pick them up.

## Routes and data access

- [routes.ts](routes.ts): Delphi DataSnap REST — the server-method classes a unit declares (under `{$METHODINFO ON}`, or deriving from `TDSServerModule`), each public method an endpoint whose verb comes from its name prefix (`accept` → PUT, `update` → POST, `cancel` → DELETE, the rest GET, the prefix dropped from the path); RAD Server (EMS) endpoint methods by prefix (`GetUsers`, `PostUser`, `PutItem`, `DeleteUser`).
- [data-sources.ts](data-sources.ts): line-scanned from the unit text (captured in `beginFile`, flushed once at the root node), receiver-gated so no AST context is needed, because substring-matching whole call text (`.open` → `Windows.OpenProcessToken`, `http` → `HttpOpenRequest`) floods desktop code with phantom "database" accesses. Raw SQL rides the shared SQL-in-strings scanner after two normalizations (`sqlScannerLines`): Pascal `'…'` literals become C-style `"…"`, and `Query1.SQL.Add('…');` builder lines lose their statement terminator so consecutive `Add` calls concatenate into one statement.
- [data-mutations.ts](data-mutations.ts): write verbs only on dataset/connection-shaped receivers (`Query1`, `tblOrders`, `cdsUsers`, `ADOConnection1`…); bare `.Delete`/`.Insert`/`.Edit` substrings would flag every `TStringList`/`TListItems` call.

## Reachability

[reachability.ts](reachability.ts): a unit can only use another through `uses`, and a unit name is its file name (case-insensitive), so the uses graph from the program files (`.dpr`/`.lpr`) is exact: a unit no chain reaches is not linked into the program. Packages (`.dpk`) publish theirs.

## Control flow and complexity

Pascal has a tree-sitter control-flow builder. Its complexity table names node types its grammar lacks, so every Delphi function reports 1 and `cyclomaticFromCfg` could never disagree with `computeComplexity`; the gate that guards Pascal is therefore `undrawnStructure` (table-independent: every construct in the body has a node in the graph), not the cyclomatic equality.

## Language server

`genericptr/pascal-language-server` — FPC-based `pasls`, built from source against Lazarus trunk CodeTools; handles `.pas/.pp/.dpr/.dpk/.lpr/.inc` in Delphi mode, but RTL-only: Delphi-exclusive namespaces like `VCL.*` / `FMX.*` do not fully resolve. See [../../../lsp/AGENTS.md](../../../lsp/AGENTS.md).
