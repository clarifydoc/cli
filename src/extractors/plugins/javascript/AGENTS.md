# JavaScript / TypeScript plugin

Reads JS/TS (`.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`), the script and template of Vue and Svelte single-file components, Astro pages, Angular components and templates, AngularJS, Alpine, Lightning Web Components, Aura controller JS and the Node/browser frameworks built on them. Front end: tree-sitter (TypeScript, TSX and JavaScript grammars; the `.tsx` variant is chosen per file; the script of a Vue/Svelte component is TypeScript text), read through flat trees (`FLAT_TREE_LANGUAGES` holds JavaScript and TypeScript). The plugin states facts; core resolves them ([core/symbol-linker.ts](../../../core/symbol-linker.ts), [core/value-flow.ts](../../../core/value-flow.ts), [core/route-linker.ts](../../../core/route-linker.ts)). Apex and the Aura/Visualforce markup belong to [../apex/AGENTS.md](../apex/AGENTS.md) and [../sfmarkup/AGENTS.md](../sfmarkup/AGENTS.md).

## Files and front end

- Entry points: [manifest.ts](manifest.ts) (static tier: extensions, markers, framework rules, package managers), [meta.ts](meta.ts) (lazy tier: hooks and extractors), [frameworks.ts](frameworks.ts) (`FrameworkRule[]`), [functions-classes.ts](functions-classes.ts), [imports-exports.ts](imports-exports.ts), [data-sources.ts](data-sources.ts), [data-mutations.ts](data-mutations.ts), [entities.ts](entities.ts), [routes/index.ts](routes/index.ts).
- Container formats: Vue SFCs are split by [../../../parsers/vue-sfc.ts](../../../parsers/vue-sfc.ts) into `<script>`, `<template>` and `<style>` blocks (`script`, `scriptLang`, `template`, `templateComponents`; template components are extracted separately by string matching), Svelte by [../../../parsers/svelte-sfc.ts](../../../parsers/svelte-sfc.ts), Astro by [../../../parsers/astro-sfc.ts](../../../parsers/astro-sfc.ts); the plugin's `preprocess` swaps in the embedded script. A built webpack/Parcel/browserify/esbuild bundle is refused by `preprocess` ([bundles.ts](bundles.ts)).
- A Vue template's expressions are parsed in place ([markup-expressions.ts](markup-expressions.ts)): `{{ … }}`, bound attributes and a handler that sends a request in one statement (`@click="axios.post(`/api/clubs/${club.id}/archive`)"` — `sendsRequest`: `fetch(…)` or a client verb called with a URL, no top-level `;`) become `<setup>` statements. Markup calls are [markup-calls.ts](markup-calls.ts); handler text is cleaned per framework (Svelte `cleanHandler` in `parsers/svelte-sfc.ts`).
- A template statement that writes state (`@click="page = 2"`, `filters.league = x`, `showAll = !showAll`, `count++`, `picked.push(c)`, `v-model="query"`) is left as a comment naming only the cells it writes ([template-targets.ts](template-targets.ts), `withMarkupExpressions`), never the statement's text; a `v-for`/slot variable or an arrow's own parameter is not the component's cell.
- A `v-for` loop variable (`v-for="m in matches"`) is `FileAnalysis.templateLoops` with the collection's script-stated type (`const matches: Match[]`, `ref<Match[]>()`, a `defineProps<{ matches: Match[] }>` member, brackets balanced: `Record<string, Club>` whole; an unreadable type gives none); `templateScopes` records each loop's extent, so the type applies only inside the element carrying the `v-for` ([template-scopes.ts](template-scopes.ts)).
- The script's type for a `v-for` collection is read at the script's top level only (`const x: T =`, `ref<T>()`, a top-level member of `defineProps<{…}>`). A handler that sends a request in one statement becomes a `<setup>` statement, so the data-source reader reads the api-call at the handler's line.
- Markdown pages: the manifest's `pathScopedExtensions` admits `.md`/`.mdx` only under `pages/` and, through `packageJsonMatches`, where the nearest `package.json` names a framework that routes it (Astro, vite-plugin-pages, `@next/mdx` / `@mdx-js/*`), so a README or a docs repo's `pages/` stays unread (discovery applies the gate as `pathScopedAdmitted`; `getLanguageForFile` answers by path alone; [markdown-pages.ts](markdown-pages.ts)).
- Extension-less `#!` scripts whose interpreter the manifest's `shebangInterpreter` names are JS files. `platformSuffixes` (`.native`, `.ios`, `.android`, `.web`) lets `./Button` answer with `Button.ios.tsx` when no plain file exists; dead code keeps every variant alive.
- Import rewriting before call classification (shared, in `extractors/shared/`): tsconfig/jsconfig `paths` + `baseUrl` ([tsconfig-aliases.ts](../../shared/tsconfig-aliases.ts)), literal `resolve.alias` of `vite.config.*`/`webpack.config.*`/`vue.config.*` ([bundler-aliases.ts](../../shared/bundler-aliases.ts)), framework-generated aliases written only into a generated tsconfig (Nuxt `~`/`@`/`~~`/`@@`, SvelteKit `$lib` from `kit.files.lib`, else `src/lib`, and `kit.alias` entries whose bare paths are relative to the project root; one inside `node_modules` is left out), `${configDir}` in `extends`, and workspace packages npm/yarn/pnpm ([workspace-packages.ts](../../shared/workspace-packages.ts)).
- Framework auto-imports ([nuxt-auto-imports.ts](nuxt-auto-imports.ts)): in a sub-project with a `nuxt.config`, a `useX()` nothing imports and the file does not declare (never a framework built-in such as `useRoute`/`useState`) is read like an imported composable, the caller's own app first.
- Project passes: routes a build plugin generates from a page folder (unplugin-vue-router, vite-plugin-pages) and an Angular component's `templateUrl` template ([angular-external-templates.ts](angular-external-templates.ts)); `ast.fileRoutes` gives file-based routes (Next.js, Nuxt, SvelteKit, Astro, Expo Router, flat routes; [routes/file-based.ts](routes/file-based.ts), [routes/file-routes.ts](routes/file-routes.ts)).
- Packages: [package-manifests.ts](package-manifests.ts) is the npm `PackageManagerSpec` (`selfName` = package.json `name`, `workspace:` references resolved to the one sub-project declaring the package, `installedApi` reading `node_modules` declarations on demand, never during analysis — [installed-api.ts](installed-api.ts)); `**/package.json` is the sub-project marker; Node's built-ins ([node-builtins.ts](node-builtins.ts)) and any package a manifest declares never bind a project file by the names they import.
- Complexity and control flow are exact for TS/JS including Vue/Svelte SFCs. `securityInLiteral` drops a non-raw security rule's match that starts inside a quoted string or regex literal (never a template literal's text).
- Calls: noise names (`console.log`, `.map`, `.filter`, …) are filtered once in `NOISE_CALLS` of [../../shared/call-graph.ts](../../shared/call-graph.ts); `extractCalls` skips a childless node whose type it never reads unless the plugin lists the type as `perNodeTypes` (JSX, `return_statement`, `variable_declarator`, `assignment_expression`). A member chain written across lines is named as on one line (`compactCallName`).

## Structure: functions, classes, components

- `heldFunction` extracts a function expression no declarator names as a function of its own, named for where it is held: a dialog output's `subscribe(() => …)` → `<ClubEditDialog@saved@12>`, an `on[A-Z]` option of a component the script opens → `<ConfirmBox:onConfirm@14>`, a member assigned in a function → `<toast.action@17>`, an object of a declared array → `<items[].run@3>`, a watcher/effect callback a write in the file re-runs → `<watch@21>`, `<useEffect@7>`, `<effect@15>` (see `FileAnalysis.reactiveCells`), an option callback a library object runs → `<useVueTable:onPaginationChange@21>`, an arrow handed to a hook that only calls one of the component's props (`useFixtureList((p) => props.fetcher(p))`) → `<useFixtureList:arg0@34>` ([held-functions.ts](held-functions.ts) `hookPropCallback`), an arrow under a JSX prop no `on…` marks that calls no function of the file → `<Tag:prop@line>` (project components only, never a library's). The walk stops there and records the enclosing function handing it on (`passed: "argument"`; module code hands it on from `<setup>`); ordinary inline arrows (`onClick={() => save()}`, a `useEffect` nothing re-runs, `.then`) stay the writer's.
- `collectExtraCalls` states `attribute`, `return` and `property` values (JSX attribute values, a hook's returned object or array, a dispatch map's values `const ACTIONS = { save: saveClub }` with `returnedAs: "ACTIONS.save"`) as `passed` calls the linker turns into `relation: "passes"`; a name the body also invokes stays one call (a map's value excepted). `property` names are read at module top level too (`extractTopLevelCalls`), so a module-level map's values are `<setup>`'s.
- `callbackArgNodeTypes` + `bindingSites` / `bindingPatterns`: an identifier passed as an argument is recorded as a call (`items.map(formatUser)`) unless the function binds that name itself (parameter, declarator, assignment target, loop/catch variable); the binding tables are grammar data of this plugin. `boundAt` answers per call site (`boundLocally`) where the function-wide set is too coarse (`{ const save = cfg.save; save() }` beside a sibling `save()`), and a site's answer is part of the dedup key ([block-scope.ts](block-scope.ts)).
- `statedMember` / `importedMapMember`: a member call whose leaf is a noise name (`map`, `send`, `filter`) is kept when the file states the receiver is a project value (`const ACTIONS = { send: sendClub }`; the top-level binding in scope at the call — a parameter, local, loop or catch variable of that name is another value, `receiverReboundAt`). A local object literal holding the called key owns the call (`const actions = { get() {…} }; actions.get()` links to the member in its own function; two alike link nowhere) and sets `CallInfo.receiverRebound`, so a rebound head never takes a same-file namesake object's member. A name imported from a project file marked `CallInfo.mapMember` is joined only through the exporting file's dispatch map, so an imported array's `.map` links nothing.
- `this` of a nested method or plain function is not the component's; a watcher sharing a `methods`/`computed` name is `<watch@line>`.
- Registry keyed by a constant ([functions-classes.ts](functions-classes.ts) `extractKeyedRegistry`): `export const saveClub = createThunk(SAVE_CLUB)` and a `[SAVE_CLUB]: handler` entry share only the constant, so the entry becomes a function `[SAVE_CLUB]` (an inline handler's body, or a factory call's calls — `createSaveHandler(section, '/config/club')`, whose URL core's request-factory pass fills at that call) and the creator a function calling it. An entry counts in an object handed to a call (`handleThunks({ … })`), or in a table a property holds (`export default { actionHandlers: { … } }`, registered by another file) where a creator in the same file is made with that key; a computed key in an object written for a value (`headers: { [SessionHeader]: token }`) makes nothing.
- ES5 constructors: methods also come from `Ctor['prototype'] = { … }` and `Object.defineProperty(Ctor.prototype, "m", { value: fn })` (and `Ctor['prototype']`), including a `value`/`get` naming a function of the file; a call whose `Object` is a shadowed parameter adds none (`prototypeClasses`).
- A factory's returned object literal is `FunctionInfo.returnedMembers` (kinds `function`, `object`, `value`, `inline`, `outer`, `open`): a call on the factory's result names a stated member or nothing, never the factory. An `open` member (the literal spreads a call or hands on another object's member: `signIn: backend.signIn`) leaves the call to the unstated-factory reading; inside a non-arrow method of a returned local object, `this.x` names its sibling. A `value` member written as a call or construction carries it as `from` (`clubs: useClubApi()`); a function with no declared return type states what each `return` is (`FunctionInfo.returnedFrom`: `new ClubApi()`, `useClubApi()`, a local's name); the linker types both as a local's initializer, in the factory's own scope, so `const { clubs } = useLeague(); clubs.getAll()` lands on `ClubApi.getAll`. A library's object types nothing. `return await x()` states what `return x()` does; `return this` states the bare name `this` (typed as the receiver the method was called on, so `new YouthQuery().withLeague(a).limit(5).fetch()` stays on the subclass inheriting the fluent base method); `return this.sub` states nothing.
- A returned ref or computed derived from a parameter is `FunctionInfo.derivedLocals` (a computed lookup keyed by it, or a ref every assignment of which is a lookup or a function's result for it, a `watch` callback's first parameter being the watched value, a `computed` over a TanStack Query result `query.data.value?.squad` of `useQuery(computed(() => clubQuery(toValue(clubId))))` deriving through the options function); a call site reading the member (`const { club } = useClub(() => props.clubId)`, `club.value.id`) states a `returned` derivation step that `paramOrigins` follows.
- A gateway exported as a factory's result: `const ClubApi = () => ({ closeClub() { return request(…) } }); export default new Proxy(ClubApi(), handler)` (or `export default ClubApi()`, `export const gateway = ClubApi()`) states `ExportInfo.factoryOf` = `ClubApi` ([imports-exports.ts](imports-exports.ts) `factoryResultOf`: a bare name called, possibly handed to `new Proxy`; the plugin never judges whether it is a factory); the factory's members — every one a function — become functions of their own (`ClubApi.closeClub`, `exportedFactoryNames` widening the generated-client rule of `functionObjectReturned`, one member enough), so each request belongs to its member. The linker's factory-member step (`exportedFactoryOf`, a two-segment call `Gateway.closeClub` through the default import or the named export) lands the call on that member, INFERRED `direct`; a member the literal does not state, a literal that spreads or one the plugin did not split links nothing, so a namesake member of another gateway and a sibling member's route are never reached.
- Vue Options API: a `computed` member (its `get`, not a writable `set`) and a `watch` callback are marked `FunctionInfo.reactiveGetter` (`computed` / `watch`), since the framework runs them on a state change or read, never a click. A Composition `computed(() => props.f())` is a call of `<setup>`; one inside a named composable marks that function `computed` when, outside the getters handed to `computed`, it makes no call but reactivity primitives (`ref`, `reactive`, `toRef`, … — `composableGetterOf`); a Composition `watch(…)` callback (the held `<watch@N>`) is marked `watch`. The mark stays on the function (per-file JSON), so a consumer joins a prop-callback link's `sourceFile` + `sourceSymbol` to it; a function that is both has one link of each.
- `data()` members type `this` ([functions-classes.ts](functions-classes.ts) `typeDataMembers`): a `data()` member written as a call or construction (`settings: new Settings(…)`, its `returnedMembers` `value` entry with `from`) is stated on each other member of the component as a `localTypes` entry `this.settings`, so `this.settings.save()` links to `Settings.save` (core's `chainPoint` types a `this.x` head through such an entry wherever no class is the receiver); a literal, `null` or a bare reference states nothing; a function outside a component's options gets no entry.
- A parameter's default that is a callback calling one function (`fetcher = (p) => ClubsApi.list(p)`) is `ParamInfo.defaultCallback` (`=>ClubsApi.list`): with agreeing sites it joins beside them; where they disagree a site passing fewer arguments runs the default as its own instance (a hook called with none states `CallInfo.args` `[]`, else `argCount`).
- `const onSearch = useDebounceFn(applySearch, 300)` is a function calling `applySearch`.
- Doc comments come from [jsdoc.ts](jsdoc.ts) (a JSDoc `@throws {T}` is a `declared` thrown type beside the body's).

## Imports, exports and scope

- A default import's reference row names the default export; a default import under another name, `export { default as x } from`, sourceless re-exports, `export * as ns` and a CommonJS barrel's `module.exports = { a, b }` over required names lead to the definition. CommonJS barrel: `module.exports = { build, forge: maker }` and `exports.build = build` / `module.exports.build = build` over names the file binds from `require` (`const { build } = require('./thing')`, `const maker = require('./maker')`) state each as a source-less `re-export` that the linker's `forwardedDefinition` follows through the import like `export { build }`; a name the file declares itself is no barrel entry.
- A module whose default export is an anonymous async wrapper of a dynamic import (`export default defineAsyncComponent(() => import('./ClubCard.vue'))`, `createAsyncComponent(…)`, `lazy(…)`, `loadable(…)`) binds the imported module under a name derived from it (`ClubCard`) and names it the default's `sourceName` (`lazyBinding`/`lazyDefaultOf`); a loader name must say lazy/loadable or `…Async…Component…`.
- Import renames are `ImportInfo.aliases` (local → exported, `default` for a default import); the import index resolves through `resolveSpecifier`, never the local alias.
- A mixin that lists `mixins: [base]` puts the base's imports in scope too (`withMixinScope` marks them `inScope`; `scopeMember` follows the chain three levels, the nearer definition winning); `ImportInfo.inScope.transitive` (set where a component or mixin file takes its `mixins:`) makes `inScopeMember` follow the chain, each file once, so `this.saveStadium()` in a page whose mixin takes on another links to it, cycles ending.
- A JSX tag through a namespace import (`import * as UI from "./ui"` + `<UI.ConfirmDialog onConfirm={save} />`) states `SubComponentInfo.namespaceMember` (`{ source, member }`) with `importSource` null; the dispatch resolvers are wrapped by `seeingNamespaceTags` ([namespace-tags.ts](namespace-tags.ts)), which hands each a copy of the analyses whose such tags carry the file the member lives in — the module's own export, a barrel's `export { X } from`, or `export *` when exactly one file defines it, four hops at most; a member no export reaches stays unresolved, never a leaf-name guess, so bindings, emits and the `dispatch:renders` link attach as for a named import (`SubComponentInfo.importSource` is read for a plain import); a name two files of an `export *` both define stays unresolved. The same view resolves a plain import that names a barrel (`import { ConfirmDialog } from "../ui"`, `import { Referee as W }`, `export { default as X } from "./X.vue"` — React, Vue and Svelte alike) and a dotted namespace tag (`<UI.Forms.Dialog/>`: `namespaceMember.member` dotted; a head that is a relative named import of a namespace re-exported with `export * as UI`: `namespaceMember.through`; a CommonJS `const UI = require("./ui")` head).
- `import type` edges are `typeOnlyEdges` (cycles are judged without them). Processes JS starts (`fork`, `spawn`) are `executes` imports that share nothing ([../shared/process-spawns.ts](../shared/process-spawns.ts)).
- A function-local `inject()` holder and `provide(Key, useX())` + `inject(Key)` type the injected local by the same key (identifier keys resolved to the declaration; providers that disagree give no type) — [provide-inject.ts](provide-inject.ts).
- Vue global registration: `components.forEach((c) => Vue.component(c.name, c))` over an array of imported components registers each under the `name` option it declares (`SubComponentInfo.registeredByName`, `FileAnalysis.componentName`; `globalComponentFiles` reads the target's name, none declared is no tag) — [global-components.test.ts](global-components.test.ts).

## Linking rules: receivers, typing and dispatch

- Local typing facts: `localTypes` for typed locals, `from` for a local initialized by a call that states no type, `CallInfo.receiverType` for a lookup chained into a call. A destructured member read off a value or call result (`const { coach } = club.staff()`) is `localTypes[].member` with `from` = `club.staff().coach`, written only where the body calls on the name. `const [club, player] = load()` (and `await load()`) states each identifier as a local `from` the call with `fromIndex` (a hole counts; a rest/default/nested element states nothing); the manifest's `tupleElementsOf` ([tuple-elements.ts](tuple-elements.ts)) reads the declared `[Club, Player]` (`readonly`, labelled members; never an array, a rest or an optional member), through `Promise` when awaited.
- Conditional initializers: the plugin marks the arms of a ternary and of `let api; if (x) { api = a() } else { api = b() }` (one if/else-if/else chain or a `switch` with a `default`, directly after the declaration, every arm one plain assignment, the name touched nowhere else before the statement ends or is assigned again) with a shared `localTypes[].choice`, e.g. `const api = slug ? useGuestApi(slug).clubs : useLeagueApi()`; any other reassignment (assignments in separate `if`s, one after a call, a name read before the if/else) leaves the local untyped. Arms are all-or-nothing: the plugin emits every arm and never pre-filters.
- Alias flow ([variable-aliases.ts](variable-aliases.ts), the `ast.variableAliases` hook: `const s = useStore()` then `s.x.y` is cross-file): the scan keeps a timeline of each name's declarations and `=` assignments; an alias of a head bound or assigned more than once is typed by the nearest binding before the alias (a concrete `localTypes` entry, only when that binding states a type); a binding in a nested block before it, an untyped one, a loop around the alias or a head bound by something the timeline does not see leaves it untyped. `LocalType.aliasOf` marks a name assigned from another plain name (`const q = p`).
- Type tests narrow per call, never the name: `CallInfo.receiverType` is set only on calls inside the region an `instanceof` guards ([narrowing.ts](narrowing.ts): the true branch, the else of a negated test, the rest of the block after an early `return`/`throw` guard, `&&`, `?:`); a call outside it, a callback body or after the name is reassigned gets none.
- A name the nearest binder rebinds keeps no stale type: the parameter of a JS `this.x = function (p) {…}` states no handed argument (`handedArgs`) and no value-flow seed.
- Async results: the manifest's `asyncResultTypes` lists `Promise`, so a local bound to `await repo.find(1)` takes the type inside the `Promise<Club>` the callee declares; a loop over an awaited call takes the element of the result it unwraps.
- Calls the syntax hides: `calls.isApiCallShape(callName, imports)` marks tRPC `.query`/`.mutate` as an api-call whatever the receiver.
- Dispatch maps ([dispatch-maps.ts](dispatch-maps.ts)): a module-level map's values are `<setup>`'s; the linker joins `ACTIONS.save()` to that key's function and `ACTIONS[kind]()` (the call name `ACTIONS[]`) to each of the map's, INFERRED (`dispatch:object-map`). A map imported from a project module (relative or `@/`, `~`, `#`) and handed down (`:actions="clubActions"`, `actions={clubActions}`) is a `functionProps` entry (`:actions="ACTIONS"`, `actions={ACTIONS}` give one per held function, `actions.save`; the handler imported when the file imports it: `FunctionPropBinding.handlerImport`, resolved by the prop-callback resolver; a function the callback hands on counts as its writer's calls in the duplicate detector, `withHeldCalls`) carrying `mapImport`, expanded by the prop-callback resolver from the declaring module's `<setup>` (named re-exports and each `export *` followed, four hops), one function prop per key (`actions.save`), the binding site staying the handing page ([dispatch-map-props.ts](dispatch-map-props.ts), [dispatch.ts](dispatch.ts)). A prop binding whose value cannot be read is listed in `FileAnalysis.unreadPropBindings` (`:kind="row.kind"`, `kind={pick(x)}`, a JSX string literal, which `propBindings` keeps none of) and keeps the full fan-out. A record of call results indexed by a prop (`stores[props.kind]`, `LocalType.key` per entry, `CallInfo.indexOrigin`/`LocalType.indexOrigin` for the index) is narrowed by `recordChoice` ([record-choice.ts](record-choice.ts)) to the entries the component's users bind the prop to — a literal (`kind="player"`), an imported enum member or constant (`PropBinding` origin `constant`, `:kind="Kind.Club"`; only a dotted name or an UPPER_SNAKE one), or a prop they hand on — each link kept to its binding sites (`viaUsage`); no binding naming an entry, an unreadable entry key, or a bound value of another origin (a route parameter; `PropLiterals.complete` false, so `recordChoice` returns null) keeps the full fan-out, never narrower than what one user could pick. `dispatch(props.fetchKey)` links only the names read; an unread user's action stays unlinked.
- A store picked by an IIFE `switch` (`const store = (() => { switch (props.kind) { case "club": return useClubStore(); … } })()`) is stated by `switchRecordEntries` ([dispatch-maps.ts](dispatch-maps.ts)) as the record `store[]`: one `localTypes` entry per case literal with its `key` (grouped cases share their return; a `default` that returns a call has no key, so `recordChoice` cannot narrow and the read reaches every entry; a `default` that only throws holds none), and a local `store` whose `from` is `store[]` with `indexOrigin` the switch's discriminant when it is a plain prop; core's `recordCall` then narrows exactly as for a record read at a run-time key. The same `switch` in a named helper of the file (`function pickStore(kind) { switch (kind) { … } }` or `const pickStore = (kind) => …`, one plain parameter, nothing else in its body) states the same record for `const store = pickStore(props.kind)` (`localFunction`, `soleSwitch`, `switchArms`). Any other shape (a case returning a non-call, extra statements, a computed or non-literal case, a discriminant that is no plain prop, an IIFE with parameters, a helper another file declares or one handed anything but a plain prop) states nothing.
- Component props and callbacks (`JsPropCallbackResolver`, `dispatch:prop-callback`; [prop-bindings.ts](prop-bindings.ts), [prop-flows.ts](prop-flows.ts), [vue-hooks.ts](vue-hooks.ts), [callback-props.test.ts](callback-props.test.ts)): a callback prop's handler is, in the parent that binds it, its own function, a mixin's, a function of an imported dispatch map, the parent's own prop handed on (followed up to four components), or a function destructured from a project factory's result (`const { handleRelease } = useSquadActions()`; `onRelease={handleRelease}`: the parent's call of that name names the factory (`CallInfo.via`), its module and the member a renamed local stands for, and the link lands on the function the factory returns under that member — `returnedMembers`, kind `function`, declared inside the factory; a member returned as a value, or a factory no module the call names declares, joins nothing); a component taking `{ n, ...others }` calls the prop `table.nextPage` as `others.table.nextPage()` (`destructuredRest`, the resolver's `restOf`); a destructuring parameter named by its pattern (`{ table, onRemove: remove }`) gives the props it takes and the names it binds ([../../shared/destructuring.ts](../../shared/destructuring.ts): `destructuredProps`, `patternBindings`). A Vue `<script setup>` template's bare callback prop (`:on-confirm="saveClub"`, the child calling `props.onConfirm()`) also puts a `passed: "attribute"` call on the page's `<setup>` (`vuePassedFunctionProps`) so the page links to `saveClub` as `passes` the way JSX's `onConfirm={saveClub}` does — never a map/array member, an imported map or a script-mounted dialog (`importSource`); an Options API page's methods already are the page's, so it invents no `<setup>`; the child's prop call stays the resolver's, scoped by `viaUsage` to the page that binds it.
- Function props through arrays: a parent's `:extra="[{ run: archive }]"` (or a declared literal array) hands `extra.run` down (`vueArrayFunctionProps`), and a child loop `v-for="x in extra"` / `v-for="x in props.extra"` over a declared prop marks its scope `fromProp` (`ScopeEntry.fromProp`), so `x.run()` links to it; declared arrays' callbacks written in place are bound by held names (`<rows[].run@5>`), an array literal in the template gives one `:extra.run` element per key (`arrayArrows`). Vue only; React arrays through props are not read. In JSX, an array or object literal under a non-`on` prop hands its functions down as `actions.run` / `action.onClick`, and `actions.map((a) => a.run())` over a destructured or `props.` collection is the prop's `actions.run` through `FileAnalysis.propElements` (`jsxPropElements`, `propElementsOf`; stated only by a file that renders JSX).

## Value flow

[value-flow.ts](value-flow.ts) (run from `finishBody` for every function, method and held callback, plus `meta.ast.moduleValueFlow` for the top level; [module-values.ts](module-values.ts), [member-values.ts](member-values.ts), [function-values-js-shapes.test.ts](function-values-js-shapes.test.ts)) states neutral `ValueFlowFact`s; resolution stays in [core/value-flow.ts](../../../core/value-flow.ts).

- Copies and seeds through locals, parameters and `this.x` fields (a field initializer `onSave = this.save.bind(this)` rides the constructor), `a.b` members, list/map elements (`push`/`set`/literals, `for…of`/`forEach` parameters, `m[k]()`: every key is also an element, `this.items[k]` is member `items[]`, `this.a.b` is member `a.b`), factory results/returns (`<return@N>`/`<arg@N>` one-use cells), `.bind`/`.call`/`.apply`, and module `let`s written from a function (`ValueCell.module`).
- An object literal handed as an argument, or typed by `useState<T>`/`ref<T>`/`reactive<T>`/`createContext<T>`, sits on a one-use `<arg@L#n>` cell; core joins its function members to the members of the formal's declared class or interface (`memberCell`, located from the formal's own file so a namesake interface stays apart): `toast.action?.onClick()` and `const { onClick } = substitution` reach the handlers written in literals of that type.
- `reactive(…)`, `shallowReactive`, `readonly`, `markRaw`, `createContext(…)` and `Object.freeze(…)` over an object or array literal hold that literal's members (`VALUE_WRAPPERS`); `useContext(Ctx)`/`inject(Ctx)` read what the named context was built with (`CONTEXT_READS`), so `state.onSave()` and `const { onPurge } = useContext(CmdContext)` reach the literal's function; `const ctx = useContext(Ctx); ctx.onPurge()` is an `invoke` of the context's own member (`contextLocals`, `held: "module"`; the alias holds in the block that declares it, and a parameter, local, loop or catch binding of the name between the call and that block ends it).
- A call `x.m()` on a module-level object — the file's own or one a project module (`./`, `../`, `@/`) it imports under a lower-case name — states an `invoke` marked `held: "module"` even when the function stores nothing into it; core keeps the ordinary resolution unless that same object's member is written in the caller's file or the file its import names (a namesake object of another file never counts; core's `valueFlowInvokeSites`).
- `[...base, run]` copies the spread array's elements (the Vue text reader follows `...base` of a declared literal array, two levels); an object member written as an object also writes the element cell, so `kit[kind].run()` reads every member of a nested literal (a `memberCalls` entry with a `column`, which adds the `kit[].run` call row only once the invoke is stated); a computed key one level below a member (`kits.club[k].run()`) reads the element of that member (`placeOf`); an arrow written in place in an array a project component's tag takes under a non-`on` prop (`<ActionBar actions={[{ run: () => award() }]} />`) is a held function `<ActionBar:actions[].run@5>` unless it returns markup (`jsxArrayHolder`), which the child's loop over its prop runs.
- A key held by a function written in place counts as the map's own key even when its name is a noise leaf (`actions.send()` for `{ send: () => post() }`, `dispatchMapMember(…, withInline)`), so the call is kept and links to that function; a markup handler's calls join the same way through `markupCalls`.
- A name is a seed only when the file can bind it to a function (imports, function and class declarations); data-typed parameters and locals nothing binds are left out; a call on a dispatch map the existing pass owns gets no invoke; a local made by a call that wraps a function (`useCallback(() => …)`) is a function binding, not a value.
- The parameter of a JS function expression assigned to `this.x` — and of a callback nested in it — states no handed argument and no value-flow seed.
- A TanStack Query step keeps the id it is keyed by: the plugin marks the helper step a query options object contributes (`ValueStep` `helper` with `query: true`); core keeps the route-parameter origin through it only when the options' fetch hands the parameter on (`argOrigins`), so a query keyed by `id` whose `queryFn` lists everything gives no origin.

- Data-source reader: [data-sources.ts](data-sources.ts), [http-clients.ts](http-clients.ts), [imported-clients.ts](imported-clients.ts), [responses.ts](responses.ts), [response-reads.ts](response-reads.ts), [path-arg-calls.ts](path-arg-calls.ts) (request wrappers: a project method handing its path parameter to a client, joined by core's `expandRequestFactories` from each site's `FileAnalysis.pathArgCalls`).

- A template literal nested inside a `${}` hole (`` `/api/${`clubs/${id}`}` ``) is spliced into the outer URL (`resolveTemplateUrl`, `rebuiltTemplate`, `renderUrlExpr`; [url-expr.ts](url-expr.ts)), so the outer holes stay readable for the route join; a same-named decoy path is not that call's target.
- URL builders ([url-builders.ts](url-builders.ts), `resolveUrlBuilders`, run through the data-source extractor's `resolveProject` hook; core's [wrapper-index.ts](../../../core/wrapper-index.ts) is the import-resolved index shared with request wrappers): a call whose URL is a project helper — free function or service-class method, `configService.APIUrl("x")` — gets the helper's `urlTemplate` substituted with its literal args; a helper whose body returns a different URL per branch carries `urlTemplateAlternatives` and the call `targetAlternatives`; a local the function sets once to a template, handed to a builder, is written in the call, rebuilt from its parts (escapes decoded, whitespace collapsed only inside holes); a destructured parameter's bindings are parameters (`({ id }) => …` gives `{id}`, filled from the call's object literal by key) and its annotation types them (`localTypes`), read through `Readonly`/`Partial`/`Required`/`NonNullable`/`Pick`/`Omit<X>` and a project generic `Props<T>` to X's members ([destructured-params.ts](destructured-params.ts)); a sync `(path) => `${BASE}${path}`` helper gets the template `${BASE}{path}` (a lowercase base only when it is a module-level string `const`); a bare call no import resolves takes the builder of the caller's own sub-project before the project-wide name. A free helper fills a bare call of its name (`club_url(id)`) or a call through a module binding of its file (`import * as url from './util/url'; url.apiPath(…)`, or a stem-named `urls.apiPath`; that module's helper only) — the head must be the module itself (a namespace import, or a binding named like the module's file, or like the directory when the file is its index module — manifest `directoryIndexStems`, JS `index`) and not a named export (`import { api }`, whose `get` is no function of the module); `api.club_url(id)` and `other.club_url(id)` with no such binding keep their own URL, while a class-method helper may still match by bare name through a receiver. `${this.constructor.BASE}` in an instance method is the static the class seen from declares — a subclass's own first, and a concrete base requests its own beside its subclasses; the plugin drops a TypeScript cast around `this.constructor`.
- `FunctionInfo.isStatic` makes `this` in a static method the class's static side: only static properties and methods are its members, and an instance field read there links nothing. A getter edited by `.replace` in a base-class method (`this.url.replace('clubs', 'kits')`) is evaluated against each subclass's own getter (`overridingClasses` reads `GETTER_EDIT_RE` names too, core's `perSubclass` reads them from `getterReads.text`), and a subclass whose URL equals the written one keeps its own row beside the ones that differ. A hole reading `this` in a plain `function` nested in a method (`DataSourceInfo.thisUnbound`: a function expression or declaration, not a method or an arrow, whose `this` the caller binds) is never typed as the enclosing class and stays a wildcard. `core/typed-member-holes.ts` reads a loop element over a call (`for (const c of repo.all())`, `for (const c of clubsNow())`) by the one declared `returnType` of that method or free function (this file's, or the file it is imported from); overloads and awaited results are not read except the awaited-call loop above. A hole reading a member of a typed local (`${item.entityType}`, `item: Favorite`) is expanded the same way when the field's type is a closed set of strings (an enum whose members state string values, or a literal union written on the field or through a `TypeAliasInfo`, read through the plugin's `requestSchema.describeType`), also for an inline object type (`item: { kind: Kind }`), a nested path through declared property types (`${club.sponsor.tier}`), `this.field.kind` through the class's field types, a loop/callback element of a typed collection parameter or field (`for (const c of this.clubs)`; a call's result by its one declared return type), a receiver declared at module level (read from the file's `<setup>` unless the function rebinds the name — the plugin states such a name untyped there), a `const` array of object literals writing the member as plain strings in every element, never spread, pushed to or computed — its own closed set: `const kinds = [{ kind: 'league' }, { kind: 'cup' }]` — and a loop variable of a Vue template (`v-for="m in matches"`; each loop typed only inside the element carrying its `v-for`, a name the script declares outside it is the script's own). A loop over an awaited call (`for (const c of await repo.all())`) takes the element of the result the plugin's `asyncResultTypes` unwraps (`Promise`). A free helper's `bindsModule` rule decides which module binding it is looked up through.
- Generated clients: RTK Query hooks (a generated `useXQuery`/`useXMutation` names its endpoint — `DataSourceInfo.endpoint` — and takes the method and URL of the slice definition it is imported from: [rtk-query.ts](rtk-query.ts)); Kubb (`kubb.config.ts` → `FileAnalysis.generatedClients`: the spec and the output directories of one module per operation, usually gitignored; a call of a function imported from there — `import { getClub } from '@/api/clients/getClub'`, a barrel, a namespace, a `useGetClub` query hook — becomes an api-call at the spec operation's method and path, which joins the spec row and through it the code route: [kubb.ts](kubb.ts), [generated-clients.ts](generated-clients.ts)); hey-api style SDK operations whose descriptor spreads its own parameter state `DataSourceInfo.pathValues`.

- MQTT topics: a topic argument that is a constant of the file (declared once) reads as its value (a template keeps its `${…}` holes and fills ones the file's constants name); a name a project module exports (a JS import) is a row with `target: null` + `targetRef` that core's module-value pass fills; a lowercase variable or parameter names no topic. ## Gotchas

- Plugins keep no module state: one process analyzes many projects.
- Do not add lazily-created cache properties to tree-sitter nodes; keep per-file data in `Map<node.id, value>` memos.
- A decoy is as important as a link: a namesake class, object, guard or constant of another file must never bind (see the "never a leaf-name guess" rules above).
- Bump `EXTRACTOR_VERSION` for any change in output for the same bytes.
