# C# plugin

Reads `.cs` and `.csx` (C# script) with tree-sitter (`tree-sitter-c-sharp`, flat-tree copy of the parse). Family `dotnet`: the VB, Blazor, XAML and F# plugins share its import-resolution family, and this plugin carries the .NET-wide pieces (the UI bridge, `.sln`/`.csproj` projects, NuGet, service config). See also [../vb/AGENTS.md](../vb/AGENTS.md), [../blazor/AGENTS.md](../blazor/AGENTS.md), [../xaml/AGENTS.md](../xaml/AGENTS.md), [../fsharp/AGENTS.md](../fsharp/AGENTS.md); cross-language mechanisms are in [../AGENTS.md](../AGENTS.md) and [../../../core/AGENTS.md](../../../core/AGENTS.md).

Each file's own rules are in its header comment; this page is the map and the rules that span files.

## Rules that span files

- Plugins report facts, core decides: DI, delegates, wrappers and types are stated as `localTypes`, `diBindings`, `ValueFlowFact`s and `CallInfo` fields; the symbol linker (`core/symbol-linker.ts`) and the value-flow solver choose. Never pre-resolve in the plugin.
- Perf: `extractCalls` skips childless nodes no step of its walk reads (`READ_TYPES_BY_LANGUAGE`); a hook acting on some node types gates on them before reading text. C# is in `FLAT_TREE_LANGUAGES`.
- UI bridge: the XAML, Blazor and VB plugins emit markup facts; `CsharpUiBridgeResolver` joins them to code-behind by class name.
- ASP.NET facts flow as `cs:controller`, `cs:attr-def` and `cs:assembly-scan` route facts that resolvers in [routes/](routes/) and [assembly-scan.ts](assembly-scan.ts) compose after per-file extraction.
- A project anchored only by a migration or a `DbContext` would have every other file reported dead, so those are passive in reachability, never entries.
- A bulk write on another class's returned query (`_repo.Active().ExecuteUpdateAsync(…)`) carries `DataSourceInfo.entityProducer`. When the writing class does not declare the receiver, the producer keeps `receiver` with an empty `type`, and `producedQueryEntities` in [entities.ts](entities.ts) looks the member up on the base-class chain, then finds the method on the interface or base chain, binding a generic base interface's type parameter from the `extends`/`implements` arguments (`IClubService : IBaseService<Club>`). A producer no class resolves is dropped.
- A generic repository's EF statement names the class's type parameter, never a table: a chain from `<context>.Set<T>()` through any query operators, a field declared `DbSet<T>`, `Set<T>().AddOrUpdate(…)`, or a set write (`Add`, `Remove`, `RemoveRange`, `Attach`…) on a context-named receiver whose argument is declared `T` or a collection of it, carries `DataSourceInfo.entityTypeParameter` (not `entity`). The data-flow reach closes it over each caller's type argument; an unbound caller ends nothing. Outside a file with signs of EF the receiver must be named like a context; a method's own `<T>` and a cache's `Set<T>()` bind nothing.
- A set write on a context-named receiver (`_db.Add(club)`, `RemoveRange(squad)`) whose first argument is declared a concrete type (a parameter or local, a `var x = new Club()`, a collection's element type) carries `DataSourceInfo.entityType`, as written, and no `entity`. `entityTypedWrites` in [entities.ts](entities.ts) (the project pass, after entity tagging) sets `entity`/`target` only when the type is a class the project declares as an entity, and drops `entityType` either way. A list's, registry's or dictionary's `Add` (receiver not named like a context) states nothing.
- Visibility: C# methods default to package-private (`isExported = false` unless `public`).
- Generated files (`*.Designer.cs`, `*.g.cs`) and test projects are listed in the manifest; keep the globs case-sensitive.
