# src/core — Analysis pipeline & analyzers

The analysis pipeline orchestrator and all cross-file analyzers live here. Pure functions in / out — no tree-sitter parsing happens at this layer (that's delegated to extractors).

**Core is language-agnostic.** Anything per-language — extensions, parse
strategy, builtin types, complexity tables, security rules, framework hints,
external-package prefixes, AST hooks — comes from the plugin registry
([../extractors/registry.ts](../extractors/registry.ts)), which aggregates each
plugin's `meta.ts`. Don't hardcode language names, ORMs, frameworks, or file
conventions here; ask the registry. Even a **cross-file** join that needs
language knowledge stays in the plugin: core calls a generic hook (e.g.
`reconcileProjectEntities` → each entity extractor's `reconcileProject`), it
never names the language. A `schema.rb` parser or a pluralization rule in
`src/core/` is a layering bug, and so is an import of
`extractors/plugins/<language>/` from production code here —
[core-imports.test.ts](core-imports.test.ts) fails on one (`plugins/shared/`
holds language-free helpers and is allowed).

## Entry point

[analyzer.ts](analyzer.ts) exports `analyze(options)` — the full pipeline. It runs:

1. File discovery + framework detection
2. Parallel per-file analysis (tree-sitter + extractors, or regex fallback)
3. Post-analysis: component graph, link graph, symbol links. A package import (`importsNameDirectories` — Go, Rust, Ruby) resolves to the ONE directory the language's `packageDirectory` rule names from the repository's packages (`SubProject.packageName` + `packages`: a Go import is its go.mod module path — or a `replace` to a local directory — plus the directory; the standard library and downloads are no directory), else to the directory whose path ends with the longest run of its segments (a tie is no edge), narrowed to the files declaring a name the importer uses, tests excluded; dead code reads these edges as reachability, so a phantom fan-out hides real gaps in a language's own model. An import of a third-party package a manifest of the repository declares (`declaredPackageImports`, matched as package usage is: `web-tree-sitter` in a package.json) or of the language's standard library (`standardImport`: Python's, Node's built-ins `path`, `fs`, `node:*`) is no project file, and the names it binds are never matched to a project file exporting the same name
4. Optional LSP enhancement. A stage's time (`stageTimings`, `--verbose` `Timings:`) runs from its `progress.step`/`progress.status` line to the next one, so a long span of passes carries `progress.status("…")` sub-steps at group boundaries (graphs and deployment, call targets, screens, route linking, schemas; entity and data-access graphs, trace impact and tests, data flows and findings; in "Analyzing files" the manifest check, the cached/changed reads and cross-file route resolution) — they emit `step` events and leave `STAGE_OF` and the stage ids alone, since consumers of `--progress json` key on those; a new pass goes under the sub-step it belongs to, and a sub-step under about 50 ms is merged into its neighbour.
5. Advanced analysis (complexity, patterns, duplicates, layer violations, blast radius, health, suggestions)
6. Write project summary + optional HTML report

Each step is gated behind the `ProgressReporter` — both verbose and non-verbose modes.

## Per-file analysis & workers

- [file-analyzer.ts](file-analyzer.ts) — `analyzeFile(task)`: read + parse + run all extractors + write the per-file JSON. Pure per-file logic with no pipeline state, so it can run on any thread.
- [analyze-worker.ts](analyze-worker.ts) — worker_threads entry that wraps `analyzeFile`. Built as its own tsdown entry (`dist/analyze-worker.js`).
- [worker-pool.ts](worker-pool.ts) — `AnalysisWorkerPool`: spreads per-file analysis across cores for projects ≥200 files (override with `CLARIFYDOC_WORKERS=<n>`, `0` disables). Falls back to in-process analysis when workers can't start. A worker that dies on a file (out of memory, or killed past the per-file deadline, `CLARIFYDOC_FILE_DEADLINE_MS`, default 180 s, `0` off) costs that file, never the run: it settles as `FailedFile`, lands in `ProjectAnalysis.failedFiles` with the reason, and a fresh worker takes the queue — never re-run in-process, where the same file would end the process. The in-process path (<200 files) has no deadline. The pool is generic over its task: the query-in-loop pass hands it the files whose control-flow graphs it needs ([loop-shape-batch.ts](loop-shape-batch.ts), from 200 files on; fewer are built in-process), which on a first run was the longest step after reading the files. While a pool runs it sets V8's `--heap-growing-percent` (50, `CLARIFYDOC_HEAP_GROWING_PERCENT`, `0` off; left alone when the process was started with one): every worker has its own heap, and V8's throughput headroom — up to 4× what survived — made eight workers on large files hold several times what they used (a mostly-C repository: 10 GB → 6 GB peak, same time). When the files are read the analyzer stops the idle workers beyond the four that write the held output (`shrinkTo`), since the pool otherwise kept eight heaps and their grammars alive through the link passes (peak RSS about −10 % on three large repositories). A run with no pool (under 200 files, `CLARIFYDOC_WORKERS=0`) sets the same bound for the whole analysis (`boundInProcessHeapGrowth`, lifted when `analyzeProject` ends; a pool that ends restores it rather than V8's own): in-process peak RSS −35 % on a 4,000-file Go repository and −20 % on a 3,000-file C# one, at about +10 % user CPU (parallel GC threads) and equal wall time.
- [unread-code.ts](unread-code.ts) — `summarizeUnreadCode(paths)`: code files no plugin reads, by extension. The list is `extractors/shared/known-code-extensions.ts` data minus the registry's claims (`UNCLAIMED_CODE_EXTENSIONS`); discovery matches them in its own walk and returns paths only (`DiscoveryResult.unreadCode`, `.clarifydocignore` applied), vendored roots and minified names are dropped here, nothing is opened. `ProjectAnalysis.unreadCode`, `analyze`'s `Not read:` line, `clarifydoc_status`. An extension that is as often data (`.cbl` reading lists, `.cue`) stays off the list.
- [ignore-suggestions.ts](ignore-suggestions.ts) — `ignoreSuggestions(files, generatedRoots)`: the generated roots (dead-code's barrel roots) and vendored roots (`vendoredRoots`) that still hold analyzed files, with counts, largest first; `analyze --verbose` prints them as `.clarifydocignore` entries and `clarifydoc_status` adds the same lines (at most 3 roots) — nothing when no such root exists. Performance patterns (`query-in-loop`, `blocking-in-async`) are ordered widest reach first by `rankPerformanceByReach` (finding-entries.ts: the routes `PatternInfo.entries` names plus the screens blast radius's `traceImpact` says reach the file — `PatternInfo.reach`); only the performance patterns' slots are permuted, the set never changes.
- [feature-flags.ts](feature-flags.ts) — extraction paths switched by name, each with a default (`KNOWN_FEATURES`), through `CLARIFYDOC_FEATURES` or `analyze --feature` (`no-antlr`, `antlr:go`, `-antlr:lua`; the most specific name wins). What differs from the defaults joins `EXTRACTOR_VERSION` in `extractorStamp()` (manifest.ts), so a run reading files another way never reuses cached JSON. A feature ships beside the path it replaces; `scripts/ab-features.mjs <project> --feature <name>` analyzes one tree with and without it and lists every disagreement with examples. Today: `antlr` and `tree-sitter`, both on by default — a regex language's `meta.antlr` reader (Go, Lua, Rust, C, C++), else its `meta.treeSitter` reader (Swift, Dart, Elixir, Scala, Objective-C, Haskell), supplies its functions and calls (`readWithParser` in file-analyzer.ts → `extractWithRegex(…, parsed)`); a file it parses with syntax errors keeps the regex reading, and `FileAnalysis.frontEnd` says which reading a file got. When the spec builds its own classes, `adoptParsedMembers` (regex-extractor.ts) gives a class method declared on a parsed function's line that function's calls and extent (keeping the class pass's signature: a Dart constructor's return type), and puts a parsed function no class pass found in the innermost class around it — refusing when several same-named classes share that extent (two one-line `struct Twin` on one line) so a parser's owner name cannot attach a member to the wrong class.

## Discovery & IO

- [file-discovery.ts](file-discovery.ts) — a glob walk by extension. The `EXTENSION_MAP` is the source of truth for which extensions are analyzed. **Every walk goes through [glob.ts](glob.ts)** (tinyglobby — fast-glob was dropped for its `braces` advisory, GHSA-vfj7-8cjw-p6xm, which has no fixed release while `--include`/`--exclude` hand it user patterns): it never follows links — a followed link let a scanned repo read outside itself (`leak.py -> /etc/passwd`) and turned one `src/loop -> ..` into every file repeated ~32 levels deep — and keeps `deep: n` meaning "at most n-1 directories below cwd", which every spec was written against. Discovery asks for the links (`LinkedFiles`, a readdir that lists a link as a file and records it) and keeps a linked *file* only when it resolves to a regular file inside the (resolved) root; the rest land in `skippedSymlinks`. Linked directories are never descended. A new walk imports `glob.ts`, never the engine. The walks of one analysis share their directory listings (`shareDirectoryEntries` in [../extractors/shared/dir-listings.ts](../extractors/shared/dir-listings.ts), held from the start of `analyzeProject` to its end): a run walks its tree a dozen times and more, and a walk over listings already read costs a tenth of one that reads them. A listing is kept unfiltered — each walk prunes, ignores and records links for itself — so a file created during a run is not seen by that run's later walks; a walker of its own reads through `listEntries` / `sharedEntries` instead of `readdir`. No walk enters a linked git worktree of a repository below its `cwd` (a directory whose `.git` FILE says `gitdir: …/worktrees/<name>` inside the walked tree — `git worktree add` inside a checkout made every route and symbol a twin); a submodule (`gitdir: …/modules/…`), a worktree of a repository elsewhere and `cwd` itself are read. A walk can also `prune` directories (a predicate on absolute paths, applied to each listing before the engine sees it); discovery, sub-project detection and framework detection prune what `.clarifydocignore` excludes, so an ignored tree costs one check instead of a walk — on one working tree, ignored checkouts holding 1.1M files had taken discovery from 0.3 s to 35 s. A plugin's `namedFiles` may start with `.` (Bash `.bashrc` / `.zshrc` / `.profile` / `.bash_profile`): discovery globs `**/.bashrc` with `dot` still false, so only those basenames are admitted — not every hidden file; `resolveTarget` / `resolveImportSource` match such a path as written before the leading-dot relative-module rewrite (`.graph` → `./graph`). **Extension-less scripts** are admitted by their first line: a regular, unlinked, non-dotfile in the root or a `bin/`, `script/` or `scripts/` directory at any depth (below the default ignores, `bin/` lifted), whose name does not look like a credential and whose `#!` line — looking through `env` and its flags — names an interpreter a manifest's `shebangInterpreter` declares (`getLanguageForShebang`), is a file of that plugin's language (Ruby, Python, JS, Bash, Perl). Only the first bytes are read to decide, a file over 512 KB is skipped, and executability is not required (a checkout without mode bits keeps the script; the `#!` line is the author's word). Only a regular file is read as a script: a linked one in a script place lands in `skippedSymlinks` when it leaves the root or dangles (never opened) or when its target inside the root is a script (`refusedScriptLink`); a linked directory, or an inside link to no script, is no refusal. The reachability models still read such scripts for the names they mention (`findShebangScripts`); they are now analyzed files as well, so the two agree. A caller holding one path asks the same rule without a walk: `isShebangScriptPlace` (where and how it is named, no read) and `shebangScriptAt` (that plus the `#!` line, or a proposed text) — freshness names a new script "added", the working-tree parse of a change (`analyzeWorkingFiles`) reads one, and git history counts a fix in an analyzed script as a fix in code. A manifest's `sourceDirs` entry may add `requiresAnyOf` (paths beside the marker, one of which must exist): Ruby's Gemfile re-admits `bin/` only beside `app/` or `lib/` — a Gemfile kept for tooling alone no longer does. A Gemfile naming `sinatra` or `rack` (`markerMatches`) re-admits `bin/` with neither. A manifest's `pathScopedExtensions` (TypeScript: `.md`/`.mdx` under `pages/`) claims an extension only below a named directory and, through `packageJsonMatches`, only where the nearest `package.json` above the file matches (Astro, vite-plugin-pages, `@next/mdx` / `@mdx-js/*`) — discovery globs it and applies that gate (`pathScopedAdmitted`), `getLanguageForFile` answers by path alone, a README or a docs repo's `pages/` stays unread. The registry refuses two plugins declaring one `shebangInterpreterNames` entry.
- [clarifydoc-ignore.ts](clarifydoc-ignore.ts) — `.clarifydocignore` / `.clarifydoc/ignore` in gitignore syntax, applied by every reader that walks the tree for its own files through `globUnignored` (compose files, Dockerfiles, Kubernetes, Terraform, CloudFormation, GitOps releases, CI pipelines, config and package manifests, Markdown for doc drift), so an ignored folder's stack never becomes a container; inherited up to the nearest project root — except an inherited pattern that covers the scan root itself (a parent's `/checkouts/` while analyzing `checkouts/x` made the scan empty); `loadIgnorePatterns(root, scanRoot)` keeps such patterns for sub-roots inside the scan. Anchoring is decided in `parseIgnorePattern`, not while matching: a pattern with a `/` in it is fixed to the ignore file's directory (`/dist` leaves `src/dist/` alone), a slash-less one matches that name at any depth. Last match wins, and a file CAN be re-included under an excluded parent — a deliberate divergence from git, pinned by a test. `ignoredDirectories` is the walk-time view: a directory is pruned only by a pattern every path below inherits (an anchored prefix, an unanchored name) that no later `!` pattern follows, so pruning never changes which files come out. `fnmatch` here is the only glob engine; `project-config.ts` shares it. `loadIgnorePatterns` is read once per (root, scan root) while an analysis runs (`perRunAnswer` in `extractors/shared/dir-listings.ts`, emptied with the shared directory listings), so a `.clarifydocignore` edited mid-run is seen by the next run only; outside a run it reads every time.
- **Extension methods and scope** — a manifest's `extensionsNeedImport` (C#; needs `importsNamePackages`) makes `extensionMethodFor` in [symbol-linker.ts](symbol-linker.ts) keep an extension method only when its declaring file is in the caller's scope: same file, the global namespace, a `using` of its namespace, its own or an enclosing namespace, a `global using`, an imported project, or `using static` of its class (`extensionInScope`, built on `importsFile`). Languages without the flag link extension functions from anywhere in the type space.
- [framework-detector.ts](framework-detector.ts) — gathers `ProjectInfo` (package.json, pom.xml, build.gradle, …) per project/sub-project root and runs the plugin-contributed rules (`plugins/<lang>/frameworks.ts`, aggregated into the registry's `FRAMEWORK_RULES`). Produces `FrameworkDetection[]`, sorted by id; core knows no framework names.
- [deployment.ts](deployment.ts) — compose-manifest deployment topology (`ProjectAnalysis.deployment`): parses docker-compose/compose files with a built-in YAML-subset parser, classifies services (app vs datastore/queue/cache), matches app services to sub-projects (entrypoint dll / image tail / marker basenames), and derives service→service edges from env evidence (api-key handshake per file, connection strings literal-first, URL/issuer vars, bus/cache attachment). Powers the report's Context (C1) / Deployment (C2) architecture levels.
- Registry modules and broker URLs in the topology: a Terraform `module` whose source is a well-known registry module (`REGISTRY_MODULES` in [deployment-terraform.ts](deployment-terraform.ts): sqs, sns, dynamodb-table, rds, lambda of `terraform-aws-modules`, also its GitHub or `git::` spelling) is the queue, table, database or function its inputs name (`name`, `identifier`, `function_name`/`handler`/`source_path`), and `module.<label>.<output>` in a function's `environment_variables` or `event_source_mapping` is a bus/db edge; another publisher's namesake and an unlisted module build nothing. Registry sources are listed as `terraform` packages (`plugins/terraform/package-manifests.ts`). In `deployment.ts` every URL of any scheme in a compose/k8s env value, and every bare `host:port` item (`addressesOfEnvValue`; accepted only on a port the broker or cache listens on — compose `ports` both sides and `expose`, a k8s `containerPort` and the ports of the Services selecting it (`RawService.servedPorts`, `K8sManifests.servicePorts`), else its image's default client ports `DEFAULT_SERVICE_PORTS` — whatever the key is named), is resolved to the service of exactly that host (compose name, k8s Service alias, `.svc` first label — `clusterServiceLabel`, shared with `resolveHost`) and judged by that service's kind: a queue gets a `bus` edge, a cache a `db` edge, anything else none; the one-queue guess for a service that merely mentions a broker applies only when no such edge was found.
- [read-text-file.ts](read-text-file.ts) — `readTextFile`/`decodeText`: the one reader of package manifests, build files and config files (dependency inventory, config values, framework and project detection, deployment, CI, Dockerfiles): UTF-8 with or without a mark, UTF-16 LE/BE by its mark (surrogates included), else UTF-8 — a `requirements.txt` from Windows PowerShell 5.1's `>` is UTF-16 LE. `readSourceText` is the source reading (file-analyzer.ts, manifest.ts's skip check): UTF-16 by its mark, else exactly `readFile(path, "utf-8")` (a UTF-8 mark stays for `normalizeSource`); a plugin's `sourceEncoding: "latin1"` keeps its own read.
- [manifest.ts](manifest.ts) — `manifest.json`, written by every run that writes (entries sorted, so two runs write the same bytes) and read only by `--incremental`: a plain run seeds it, and the loop-shape cache beside it, so the first incremental run after one reparses only what changed.
- [deploy-rejects.ts](deploy-rejects.ts) — `.deploy-rejects.json` beside the manifest: the candidate files the deployment readers (CloudFormation, Kubernetes, Terraform) opened and turned down by their text alone, kept by size + modification time and the extractor stamp, so a one-file `--incremental` run stats them instead of reading hundreds of YAML/JSON files. Only rejections are kept; a Helm template (its verdict depends on its chart) and any file that yields facts are read every run.
- [output-writer.ts](output-writer.ts) — writes per-file JSONs + `project-summary.json` (+ `lsp-enhancement.json` / `lsp-ground-truth.json` when LSP runs). With a worker pool the per-file JSON is **not written where it is analyzed**: a file being created holds up the reads beside it, and creating files does not scale with threads (measured: eight threads creating 5,450 small files took longer than four, and reads beside them went from 0.15 s to 0.9 s a thread). A task with `deferWrite` hands its JSON back as bytes (`FileResult.json`, moved, not copied); the analyzer holds them until the sources are read (or `CLARIFYDOC_HELD_OUTPUT_MB`, default 256, is held) and then gives them to four of the pool's now idle workers in batches (`OutputWriteTask` → `writeOutputFilesSync`), which write while the project passes run — a worker, because the main thread's event loop is busy in those passes and an async write needs it between every step. The pool ends when the batches are written; the run waits for them before it writes the summary, and a file that could not be written is left out of the manifest so the next run analyzes it again. A file is written first and its directory made only on a miss.
- [element-registry.ts](element-registry.ts) — the disk-I/O codec. `normalizeProject` (write) lifts repeated nodes into two registries — `elements[]` (symbol-level `file::symbol` ids) and `files[]` page_ids (a file's index, used everywhere a path was repeated); `denormalizeProject` (read) reverses it. In-memory shapes are untouched; all readers go through `denormalizeProject`. A round-trip test over every fixture is the regression gate — adding a path-bearing `ProjectAnalysis` field means adding it to `rewritePageRefs`.
- [context-docs.ts](context-docs.ts) — decision records (files under `adr/`, `decisions/`, `rfcs/` …, with their `Status:`), framing documents (ARCHITECTURE, GLOSSARY, DOMAIN …), schema dumps and the documents `.clarifydoc/config.json` `context` declares (kept inside the root); decision markers in comments (`WHY:`, `DECISION:`, `TRADEOFF:`, `RATIONALE:`, `REJECTED:`, `ADR:`); the analyzed files a document names (`governedFiles`) and which were committed after it (`judgeStaleness`, one `git log`). Read on demand by the MCP server, never during `analyze`.
- [stated-reasons.ts](stated-reasons.ts) — the reasons written down without a decision record: whole comment blocks that state a cause or purpose ("because", "so that", "to avoid", `since` only as a clause), in the language's `docComments` syntax, anchored to the function they sit above or in — licence headers, commented-out code and generated files left out; and the body paragraph stating one in each of a file's last 30 commits (`git log --follow`, or `-L` over one function's lines), bots and dependency bumps skipped. Labelled as stated reasons, never decisions. On demand only (`clarifydoc_context_docs file=`).
- [project-config.ts](project-config.ts) — reads `<root>/.clarifydoc/config.json` (optional, never fatal): per-repository `layers` (glob → ArchLayer, first match wins), `exempt` and `generated` globs, `context` documents, and `refactorPressure` thresholds. Owners of a section resolve it (`resolveArchitectureOverrides`, `resolveRefactorPressureConfig`); unknown keys and bad values become progress warnings and defaults are kept. `matchesAnyGlob` is the one glob test (ignore-file dialect; anchoring is read off the pattern, so a slash-less pattern also matches the bare file name and one carrying a `/` does not). The analyzer loads it once, before the generated/unauthored filter, so `generated` globs reach every quality signal.
- [regex-extractor.ts](regex-extractor.ts) — thin dispatcher for regex-only languages. Real logic lives in `src/extractors/plugins/<lang>/`.

## Report

**One renderer, prebuilt.** The report viewer is a React app maintained outside this repository. `report.html` is that viewer built into a single self-contained file (react + d3 + dagre + css inlined, fully offline) with the payload JSON injected. This package carries only the built template; report features are written in the viewer, and rebuilding it refreshes `report-template.html`.

- `html-report.ts` — `generateHtmlReport` loads the prebuilt template from `html-report/viewer-assets/report-template.html` (committed; rebuilt from the viewer; mirrored into `dist/` by the root tsdown `onSuccess` hook) and swaps `__CLARIFYDOC_TITLE__` / `__CLARIFYDOC_PAYLOAD__`. The payload embeds as **gzip+base64** (`encodeReportPayload`; ~10x smaller than inline JSON, no `<` so no HTML-escaping concerns) and `standalone.tsx` inflates it in the browser via the native `DecompressionStream`. Token replace uses a replacer *function* so `$&` can't corrupt. Also writes `report-data.json` (plain JSON, for consumers that serve the payload in slices) alongside `report.html`.
- `report-payload.ts` — `buildReportPayload(summary)` reshapes a (denormalized) `ProjectAnalysis` into the `ReportPayload` the viewer consumes; `loadReportSummary(dir)` / `loadReportPayload(dir)` read it from disk (with the `lsp-enhancement.json` merge). The payload carries `deferredFields` so a consumer that slices it follows the producer's list.
- `smoke.test.ts` renders a minimal report end-to-end and round-trips hostile payload content through the encoder.

## Adding a new analyzer

1. Create `src/core/my-analyzer.ts` exporting a pure function `analyzeMyThing(input): MyResult[]`
2. Add the return type to [../types/analysis.ts](../types/analysis.ts) and add an optional field to `ProjectAnalysis`
3. Wire into `analyzer.ts` post-analysis section (step 4c)
4. Pass data to `suggestions-engine.ts` if it should drive suggestions
5. If the viewer should show it, add it to `report-payload.ts`; the tab itself is written in the viewer, which is then rebuilt into `report-template.html`
6. Add exports to [../index.ts](../index.ts) if public API

## Conventions

- **Pure functions** — no file IO except `output-writer.ts` and `html-report.ts`. Input is `FileAnalysis[]`, output is typed results.
- **Optional fields** — new fields on `ProjectAnalysis` should be optional so old `project-summary.json` files still load.
- **One import contract** — `import-index.ts` turns every import specifier into a file through one helper (`resolveSpecifier`), by the name the module exports (`ImportInfo.aliases[local]`, never the local alias), for both a language's own `resolveImport` and the generic path, and in `localFor` and `fileForSource` alike; an alias named like a sibling module never reaches it.
- **Progress reporting** — use the `ProgressReporter` class in `analyzer.ts`, not `console.log` directly.
- **BFS with index pointer** — never use `Array.shift()` for BFS queues (it's O(n)); use `let qi = 0; while (qi < queue.length) { ... queue[qi++]; ... }`.

- **`changed-symbols.ts` / `impact-diff.ts`** — `parseUnifiedHunks` keeps new-side ranges on the Map (patch coverage) and records match ranges on `old`: deletes/edits as their old-side lines, a pure insertion as the line it follows (plus pure deletions on `deleted`). `symbolsInHunks` matches those against the stored analysis, so a function below a deletion is not judged at a shifted new-side line that lands in the neighbour above; a hand-built Map with no `old`/`deleted` still matches as written.
- **Dependents are charged by the member that changed.** When the diff's lines are known, `computeImpactDiff` cuts `dependents` to the files that NAME what changed ([member-dependents.ts](member-dependents.ts): call and import-by-name links into a changed function; for a type touched outside its methods — `symbolsInHunks`' `classLevel`, compared before and after by `classChanges` — its usage kinds from the blast-radius `typeUsages`: a removed or re-typed member charges every user of the type, an added member of an interface or abstract type only what implements, extends or builds it, never what passes it on) and keeps the importer count as context (`narrowed.importers`, printed "naming what changed (N files import it …)"). The risk rating, tests, screens and routes read the narrowed list. A file with a changed line in neither a function nor a type (`moduleOnly`), without line ranges, or a type whose comparison shows no member change keeps every importer charged. A type with no usage record is named by nobody only where the manifest says type usage is complete (`typeUsageComplete`, Python); elsewhere it keeps every importer charged. A file that hands a charged or changed module on whole (Python `from .x import *`, `export * from`; `starForwarders` in changed-symbols.ts, read from the per-file `exports` `*` rows) is charged with it, up the chain — only when the change takes a name away (a removed, moved or re-typed function, a type member that changed), never for a body edit; the module a star export names is the file the import index resolved it to (`ProjectAnalysis.starReexports`, file → source as written → file, built by `starReexportTargets` through `ImportIndex.fileForModule`), no path-word guess — a source with no recorded target in a summary older than the field (extractor < 1.722.0) is not followed and `StarForwarders.stale` becomes the limitation "re-run the analysis" (`STAR_REEXPORTS_STALE_NOTE`); `narrowed.members[].lost` marks a member whose name is lost (a `signatureChanges` row, a type member that changed), and `clarifydoc_blast_radius` takes `change` (member → removed/renamed/moved/retyped/body) and cascades only for a lost name — unstated is body, so no cascade; the CLI `impact` and the MCP tools both build `symbols` with `symbolsOfChange`; a git diff of pure deletions (no new-side range, only `hunks.old`/`deleted`) narrows like any other; a file the diff deletes (`+++ /dev/null`) is keyed by its old path with every old line on `hunks.old` (never the new-side Map, which patch coverage reads), and a range covering other functions whole names each of them, not only the smallest one it touches; lines directly above a function (a decorator) belong to that function, except inside a type and in a language whose plugin has no `moduleNames` hook. `symbolsOfChange` builds the `symbols` option for the MCP tools and `impactOfContents` (a proposed edit). A removed or re-typed function is `breaking` only for callers the change leaves alone (`signatureChanges` `edited`: a call on a line the diff edits, or the function calling itself, is rewritten with it), so a private helper folded into its one caller rates nothing; an edit inside the import block of a file that re-exports what it imports (`HunkSpans.reexports`, `ImpactDiff` `forwarded`) charges the importers that import a forwarded name (`filesImportingNames`) — the rest of its importers name nothing that changed. A class gaining a field is charged like an interface gaining a member (`ClassChange.addedField`: what builds it); tests are looked for among everything importing the files that name the change, not only those files. A hunk wholly inside the lines of a module-level name (`FileAnalysis.moduleNames`, Python assignments and JS/TS `const`/`let`/`var`: the statement, the comments above it, the blank lines below it) is an edit of that name — `symbolsInHunks` `bound`, judged before the import block, so a constant between two imports is a constant — and `boundReaders` charges the importers (from `componentGraph`) whose imports list the name, take the module whole (a namespace, a default, `import m`, `from p import m`: spelled by the module's own stem) or star-import it, following a re-export, a package `__init__` or an `index` one hop at a time (four deep); an importer with no per-file record stays charged. Which import row reaches the file is not resolved, so a same-named import from another module also charges, and an importer with no row spelling the module (an edge no import states, a package `__init__`) stays; a value derived from the name in another file (`CAP = LIMIT * 2`) hands nothing on, and a line inserted right after a name reads as an edit of it. A hunk no name covers (a decorator added above a function, an `if` block) still keeps every importer charged; a type with no usage record (a controller nothing names) still abandons the whole file's narrowing.

- **`analysis-lint.ts`** — `lintAnalysis(project, files?)`, a pure check of one analysis against itself (links to non-functions, lines past a file's end, two routes with one `dedupeRoutes` key, `apiRouteLinks` to rows the summary lacks, relations to missing entities, exports naming nothing the file defines). `clarifydoc lint <outputDir>` prints it (exit 1); `analysis-lint.test.ts` gates every `test-output/` summary with a commented allow-list. A new rule must be clean on a freshly generated fixture set, or fix the extractor.
- **`caret-assertions.ts`** — assertions beside the source, SCIP-snapshot style: a comment line under a source line, in the language's plain line-comment prefix (`manifest.docComments.line`, last entry — core names no language), whose `^^^` marks a span and names the fact: `def <name>`, `call [-> <file>::<symbol> | -> unresolved]` (`unresolved` fails when any call in the span carries a link; a bare `call` only says a call is there), `route [METHOD] <path>`, `api-call [METHOD] <url> [-> METHOD <routePath>]`, `table <name> [read|write]` (`<-` points at the comment's column and checks no span; consecutive caret lines speak about the nearest source line above). `checkCaretAssertions(project, files)` (pure; `files` = path → source + `FileAnalysis`) judges each `passed` / `failed` (with `found`, the facts on that line instead, or a span that does not name the fact) / `unmatched` (no source line above, unknown kind); `renderCarets` prints a file with a caret line per fact in the same grammar, so a snapshot pasted back checks clean. Matching is by line and by the span's text (extractors state no end column). `caret-testkit.ts` (`expectCarets({path: source})`) analyzes a temp project and throws listing failures — the vitest helper, never imported by the product; CLI: `clarifydoc lint <dir> --carets [file]` (a file renders it, none checks every analyzed file; the existing `lint` command, since it already loads the summary and per-file JSON). `caret-fixture.test.ts` walks the fixture projects named in its `CARET_FIXTURES` (source carrying hand-written carets, namesake decoys, one must-stay-unresolved call). Tooling only: no analysis output changes.

- `entity-graph.ts` `EntityGraphNode.origin`: `"contract"` on a schema an API-contract language (`isApiContractLanguage`) declares, absent on every table and ORM entity (so a repository with no contract is byte-identical; carried through `element-registry.ts`). Such a node is shown apart — the MCP data-model inventory lists tables and entities first, the schemas as their own capped group with a count, and the report viewer groups them the same way. Nothing is dropped, and a contract schema never covers a table of the same name: `synthesizeReferencedTableEntities` seeds its dedup set without them and `nodeKeyIndex` gives their keys last.
- `data-access-graph.ts` queue nodes: `queue::<broker>::<address>` (`DataSourceInfo.broker`, else read from the row's label by `extractors/shared/message-brokers.ts`; a row naming none takes the one broker every other row of its address states, else `?`), so `matches` on Kafka and on RabbitMQ stay two nodes and `synthesizeQueueSymbolLinks` pairs only equal broker + address (`SymbolDataAccess.broker`). A destination no value resolves (`target` null, with `unresolvedReason`) is `queue::<broker>::?<file>:<line>` — one node per site, never paired, never a shared "(unresolved)" node. Spring AMQP `convertAndSend("x", "y", payload)` is exchange `x` + routing key `y` (`entity`) unless the third argument is a string literal (two overloads fit: unresolved) or a post-processor.
- `queue-env-targets.ts`: a queue/consume row whose target is an env var name (`process.env.JOBS_URL`) is retargeted to the queue the deployment gives that variable (a bus edge whose target has `DeployedService.destination`, i.e. a Terraform queue/topic, from a service running the row's own project; disagreeing services refuse). Terraform `module` blocks (`./` sources) are followed by `deployment-terraform.ts`: `var.x` (every caller must agree, else the default), `local.x` and `module.m.out` resolve to the resources they name, so edges cross module directories.

**Values the source chooses between stay AMBIGUOUS.** `DataSourceInfo.targetChoice` marks `targetAlternatives` that are the values one local takes (a ternary or branch over strings, enum members, a typed string union; a request wrapper's site argument — `PathArgCall.argAlternatives`): the route linker links EVERY route a value reaches, AMBIGUOUS (one reached out of several is INFERRED at most), where a helper's `urlTemplateAlternatives` stay first-hit. A hole reading a member of a typed local (`${item.entityType}`, `item: Favorite`) — or of an inline object type (`item: { kind: Kind }`), a nested path through declared property types (`${club.sponsor.tier}`), `this.field.kind` through the class's field types, or a loop/callback element of a typed collection parameter or field (`for (const c of this.clubs)`; a call's result by its one declared return type; a receiver declared at module level is read from the file's `<setup>` unless the function rebinds the name — the JS plugin states such a name untyped there — and a `const` array of object literals writing the member as plain strings in every element, never spread, pushed to or computed, is its own closed set: `const kinds = [{ kind: 'league' }, { kind: 'cup' }]`), or a loop variable of a Vue template (`v-for="m in matches"`, `FileAnalysis.templateLoops`: the collection and the type the script states for it — `const matches: Match[]`, `ref<Match[]>()`, a `defineProps<{ matches: Match[] }>` member —, read in the template's lines; each loop is typed only inside the element carrying its `v-for`, a name the script declares outside it is the script's own) — is expanded the same way by `typed-member-holes.ts` when the field's declared type is a closed set of strings — an enum whose members state string values, or a literal union written on the field or through a `TypeAliasInfo` — read through the plugin's `requestSchema.describeType`. A URL helper called through a module binding (`urls.club_url(id)`, a base route a subclass hands `super(…)`) is looked up in the imported module's file only where the head is the module itself — a namespace import, or a binding named like the module's file, or like the directory when the file is its index module (manifest `directoryIndexStems`: Python `__init__`, Rust `mod`, JS `index` — `from league.utils import routes`), that the module does not export as a member (`mod urls`, `from . import urls`) —, never where it is a named export (`import { api }`, whose `get` is no function of the module). A free JS URL-builder helper fills a bare call of its name (`club_url(id)`) or a call through a module binding of its file (`import * as url from './util/url'; url.apiPath(…)`, or a stem-named `urls.apiPath` — that module's helper only, via the same `bindsModule` rule as symbolic targets); `api.club_url(id)` and `other.club_url(id)` with no such binding keep their own URL rather than taking a project-wide free template; a class-method helper may still match by bare name through a receiver (`configService.APIUrl(…)`). A loop over an awaited call (`for (const c of await repo.all())`) takes the element of the result the plugin's `asyncResultTypes` unwraps (JS/TS list `Promise`); a hole reading `this` in a plain `function` (`DataSourceInfo.thisUnbound`, stated by the JS plugin: a function expression or declaration, not a method or an arrow, whose `this` the caller binds) is never typed as the enclosing class and stays a wildcard. `CallInfo.alternative` marks one of several calls a descriptor key holds (`task.api.subscribe()`): the symbol linker caps every link it yields at AMBIGUOUS, whichever strategy found the definition (not the Python module-level AMBIGUOUS).

- **Construction without a written constructor call.** A struct literal (`CallInfo.construction: "literal"` — Go `Club{…}`, Rust `Club { … }`, added by [plugins/shared/struct-literals.ts](../extractors/plugins/shared/struct-literals.ts) in expression position only; slice/map literals and match patterns are not) links `instantiates` to the struct itself and never to a `New`/`new` function (`constructionLink`, Strategy 5's `literal`). Java `this(…)`/`super(…)` are the calls `new <ownClass>` / `new <superclass>` (the Java plugin's `explicit_constructor_invocation`), settled by argument kinds like any construction. A bare type name in a package-scoped language (`importsDeclaredPackages`) is the class its own package declares before any namesake (`typeFileFor`), so `new Club()` beside a same-named class elsewhere links the right one.

**Wrapper index** ([wrapper-index.ts](wrapper-index.ts)): one import-resolved index behind both wrapper lookups — `expandRequestFactories` (request wrappers) and the JS plugin's `resolveUrlBuilders` (URL builders). A name resolves lexically (the caller's own file), then through the import that binds it (`importedFrom`: renames and re-exports via the import index), then to the ONE top-level declaration of that name in the caller's sub-project (`declarationsInProject` — never a class method); anything else is unknown. A member wrapper (`receiver.callee`) counts only when EVERY same-named definition the receiver can be (`memberDefinitions`: object members and methods of a class of that name) forwards the URL; the URL-builder index likewise goes ambiguous when a same-named class method states no URL.

**Value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass in `buildSymbolLinks`, after `handedParameterLinks`/`handedClientLinks`, before `abstractDispatchLinks`): a function value is followed from where it is named to the call that runs it, through locals, parameters, fields, lists and returns, in every language, from neutral facts a plugin states (`FunctionInfo.valueFlow`, `FileAnalysis.moduleValueFlow`: `seed` / `copy` / `arg` / `result` / `return` / `invoke` over `ValueCell`s — a name and optionally a member; `this`/`self` is the receiver, a list or map element the member `[]`). Core names the cells: a formal when the function's `params` list it, a local when its facts or `localTypes` bind it (an enclosing function's too), the file's module cell when module facts bind it or the exporting file's when it is imported; a member is the class's field (own, then bases that declare it) for `this`/a typed local, the module holder's otherwise, else a function-local cell. Seeds resolve through `resolvePassedName` (never a name guess); the seeds and copies one held lambda states share a `lambda` id, and that lambda stands for at most four project functions plus held values it runs, counted once resolved (a library's name resolves to nothing and never counts), the whole group dropped above four; arguments bind to formals by written index (a leading `self`/`this`/`cls` parameter of a method is skipped) through the callees the ordinary links found at that call site plus what the solver finds itself, iterated to a fixpoint (inclusion-based, flow- and context-insensitive). Every invoke site links to each function its cell holds — `value-flow`, relation `calls`, INFERRED for 1 to 4 targets, AMBIGUOUS for 5 to 32, nothing above 32 (the overflow poisons the cell and everything it feeds), never EXTRACTED, never production to test file, never a function written in place linking to itself (the solver ignores order, so `const old = x.f; x.f = () => old()` would; a named function handing itself on is real recursion and keeps its link); a spent work budget emits nothing. A call a plugin marks with an `invoke` fact is not resolved by the name tiers (`LinkContext.invokeSites`, `valueFlowInvokeSites`) when its cell is a parameter or a seed or copy writes it, so a namesake cannot take it; a plain name only a call's result writes, or nothing (`const reload = debounce(load)`, `useCallback(…)`), keeps a link into its own file only, and a member no seed or copy writes anywhere (`this.model.apply()` on an object field) keeps its ordinary resolution, as does a dotted path rooted at a name the file imports (`kit.Bench.label()`), which the name tiers resolve exactly; a `boundLocally` call counts as an invoke of the cell it names. A cell flagged `module` (`ValueCell.module`) is the file's own module binding even when written from a function that binds no such name; an invoke site whose call carries `CallInfo.via` (a local a project factory made) still runs the name tiers, so its factory link stays beside the value-flow one; an `arg` fact may carry `name` instead of an index (a Dart named argument binds the formal of that name), and a member read through a property of the enclosing class (`widget.onSave`, a State's widget) keys on that property's declared type. A cell name that is no binding but a project class names that class's own members (a C struct type's ops table, a static member); a dotted name (`c.ops` + member `sign`) walks property types before the member; a function writing a global it does not declare states it as `{ name: X, module: true }` in every plugin (C/C++ included), the one way to name a module binding written from a function. An `invoke` fact — and a C `copy` of a parameter into a field (`peer->free_fn = fn`, `fn` typed by a typedef another header may declare) — may carry `ifFnType` (a cell declared with a type name the file itself cannot judge); `scopesOf` drops it unless the host says it runs a function — `ValueFlowHost.isFunctionType(file, type)` for `ifFnType`, and `isCallableMember({ file, symbol, receiver, member })` for `fieldInvokes`; for a type name the linker answers (`functionTypeQuestion`) from `FileAnalysis.functionTypeAliases` (Dart `typedef`, Swift `typealias` of a function type) and the class index through the nearest scope that declares the name: the file itself, the files it imports (through barrels), its own sub-project, the sub-projects it imports as packages — where includes share scope (C/C++) the file's whole include closure and nothing beyond it, one pool of names across `.c` and the `.h` read as C++ (C `typedef R Name(args)` and `typedef R (*Name)(args)` are `functionTypeAliases`); alias only is a function type, class only or both a class (never a function), never a name pooled across sub-projects — so a field typed by another file's alias runs while one typed by a class of that name does not, and a dropped invoke neither links nor keeps the name tiers off the call. A bare JDK functional-interface name (`Consumer`, the manifest's `platformFunctionTypes`) is judged here too (`judgePlatformFunctionType`): the platform's when `java.lang` brings it in, a single-type import names no project class of that package, or an on-demand import of a package the project does not declare brings it in and no class of the file's own package shadows it; a class the file declares is the project's. The Java/Kotlin plugin states that question as `invoke.ifFnType` for a parameter or local declared with the bare name (and for a `for` variable); fields (a Kotlin constructor property too), returns, element collections and a Kotlin builder's element type (`mutableListOf<Consumer<T>>()`) state it the same way (`ClassFlow.cond`/`elemCond`/`returnsCond`); the plugin keeps no judging gate (`LibraryContext` only tells library calls apart). A call `x.m()` through a field another file's class declares callable is no plugin fact: `fieldInvokes` (value-flow.ts) derives the `invoke` from the calls a function already holds — `x.m()` with `x` a local, a parameter or `this`, `m` a name some class declares a `PropertyInfo.callable` member under (`CallableQuestions.callableFieldNames`, built once per run) and no plugin invoke stated at that line — when the host's `isCallableMember` question (`callableMemberQuestion` in the linker) says yes: it types the receiver with the linker's own `receiverDeclaredType` (`this` is the class the scope is written in), finds the class with `locateClass` from the caller's file (own import, sub-project and include closure first), then its bases by `parentClassOf`, three hops, and says yes only for a `PropertyInfo.callable` member — a method of that name, a data field and a namesake class of another sub-project or outside the caller's includes never run a held value and keep the name tiers. So a callback field in a header named unlike its class (`club/types.h` declaring `Squad`) runs what another file stored, at no per-file output cost. A call through a pointer (`p->m()`) names its receiver like `x.m()` in C and C++ alike (after what no name spells, `list[i]->m()`, it stays `m`), so `fieldInvokes` is the one path and no plugin states a fact of its own for it. A cell flagged `package` (a Go bare call of a name the file neither binds nor declares) is left to the name tiers by `valueFlowInvokeSites` (a function of that name keeps its link) and is resolved only where one sibling file binds the name as a variable. Plugins state facts and resolve nothing; the pass costs nothing when no file states any. A struct of function pointers filled by a positional initializer (`static struct club_ops ops = { "club", 0, club_scout, club_release };`) seeds the fields it fills: the C/C++ plugin states each element that is a function of its file as a seed on `{ name: <struct type>, member: "#N", positional: { index, count } }`, and marks the struct's class `ClassInfo.fieldOrder` where it is declared (its `properties` are then every field in declaration order — a missing function-pointer field is added; only for a struct with a field that is or reads as a function pointer, and not one it cannot count — nested braces, bit-fields, `a, b;` declarators, `#if`, methods, a union; a tagless `typedef struct { … } name_t` is a class under its typedef name, the file's only other class-graph growth). Core names the field in `cellOf` from the property at `index` of the class `classOfType` finds (`locateClass` through the include closure, then a typedef alias by `dealias`), refusing when the class is unknown, ambiguous, not `fieldOrder` or has fewer fields than the initializer has elements; the plugin refuses an initializer that mixes designators or has a bare upper-case name or call the file does not define as one value (a macro may widen), and states only elements that are functions the file defines. A struct has one class: a tagless typedef with several names is the class of the first.  **Field writes and thrown types** ([member-effects.ts](member-effects.ts), `ProjectAnalysis.fieldWrites` / `thrownTypes`, S8.2). A TS/JS, Java or Kotlin plugin states per function what it assigns (`FunctionInfo.fieldWrites`: `member`, `receiver` as written — `this`, `this.<field>`, a parameter or local name that carries a declared type, "" for a bare field — and line; never from a constructor, never from an untyped receiver, nested non-arrow functions and local classes left out) and what it throws (`FunctionInfo.throws`: the type as written with its qualifier, the `throw new T` / Kotlin `throw T(…)` site, and `declared` for a Java `throws` clause or Kotlin `@Throws`; a rethrown variable states nothing). Core decides the class from declared types only: `this` and a bare field are the enclosing class — or the base of its `extends` chain that declares the field, so a subclass's write is the base class's — `this.<field>` goes through that field's declared type, a name through its parameter type or its one stated local type (no `choice`, no `soft`); a class name binds only where exactly one class of that name is in reach (own file, else sub-project, else project), so a namesake field of another class is never listed; a bare name must be a declared field of the class chain. Rows hold names and `path:line`, skip tests and generated files, and exist only where something is stated. Reads (`propertyReads`) stay C#-only for the blocking-call rule; a property read edge is not built. Ruby (`@x`, `@@x`, `self.x =` through a writer method, `@club.x`, a typed receiver; `raise T` as the constant written) and Rust (`self.x`, `self.field.x`, a typed parameter or local, a bare `static mut`, or one written through its module path or after a `use`, which core resolves to the declaring file with the language's `resolveImport`; a field behind `borrow_mut()`/`lock().unwrap()` or a `*self.x` deref; `RefCell`/`Mutex`/`RwLock` are transparent type wrappers; no throws) state them too — a language with `typesBeyondDirectory` looks a type up past its directory, the directory's declarations first, and refuses a qualified name or a name with several real declarations none of which the writing file owns. PHP and Go state writes too: PHP names a class through the writing file's `use`/namespace ([class-evidence.ts](class-evidence.ts), the symbol linker's own rule), takes `self::$x`/`static::$x` as `this`, states a type written through a namespace path as `ParamInfo.typePath`/`PropertyInfo.typePath` beside the bare `type` (core reads the path, so a namesake class of the writer's own namespace never answers for `\App\Models\Club $c`) and a static property written from outside (`Club::$count = 0`) as a write with `class` set to the class as written, bound like a thrown type; where a type spans a directory's files (`typesSpanFiles`) its parts are one type (`ClassRef.parts`), a package-qualified type states nothing, and a Go function's bare assignment (`fieldWrites[].package`) becomes a `via: "package"` row only when exactly one file of the package declares that variable (`FileAnalysis.packageVariables`, the Go plugin's `extractPackageVariables`). `clarifydoc_trace direction=writers` lists the writers of `Class.field` (or the throwers of an exception class) and `clarifydoc_explain` of a function shows "Writes and throws" (`mcp/tools/member-effects.ts`).

**Config key → consumer** ([config-keys.ts](config-keys.ts), `ProjectAnalysis.configKeys`, S8.1). A plugin's `serviceConfig.sources` states the keys config files set (every entry, not only addresses — `keysOnly: true` marks a source no call origin may read, Terraform `*.tfvars`); code states a read as an `env` data source with `DataSourceInfo.configRead` (`key`: Spring `@Value("${league.token}")`; `prefix`: `@ConfigurationProperties(prefix = …)`, every key below it; and `FileAnalysis.configKeyReads` `variable`: a Terraform `variable "x"`, no data source). Core joins them per sub-project — a namesake key of another module is another setting — a `variable` read to the `*.tfvars` in its own directory; relaxed binding (`match-day` = `matchDay` = `match_day`) and `envNamesFor` (`LEAGUE_TOKEN`) match a key; a key only a test profile sets (`ConfigEntry.test`) is read by test code only; a profile file's row carries its `profile`. Rows exist only for keys something reads, hold names and locations, never values, and cap at 50 consumers. A `@Value("${LEAGUE_TOKEN}")` spelled like an environment variable is also an `envVars` read, and a dotted key whose `envNamesFor` name a deployed service sets joins that variable's reads (`env-vars.ts`). A config-file path in code (`new File("config/league.yml")`) reaching its file is not built.

**Config file → consumer** ([config-files.ts](config-files.ts), `ProjectAnalysis.configFiles`, S8.1). A plugin's `ast.filePathReads` states the files a call opens by a path of plain literals (`FileAnalysis.filePathReads`: the parts, the line, `anchor: "file"` for `__dirname`); a part that is not a literal states nothing. `joinConfigFiles` resolves each beside the reader, then at the reader's sub-project root, then at the analysis root — the first that exists (an analyzed file, or a regular file on disk that is no link, no credential-looking name and not under `.clarifydocignore`), never by file name alone; a `..` that leaves the root, an absolute, `~` or URL path, a test reader and a target that declares functions or classes (code, not configuration) join nothing. Rows carry the file, its project and the consumers.

**Bare-call locals, star chains, class variables (E-234).** A local initialised by a bare call (Dart `final w = topClub();`, `final x = pick();`, `await fetch()`) states `localTypes[].from` as `name()`; the linker types it by the declared return type of the enclosing class's own method, else — through `importedFunctionLink`, which now also reads a bare call an import puts in scope (`ImportInfo.inScope`) as a cross-file call unless the caller's own class or file declares the name — the imported function's. A bare call through a wildcard import (`from app.hub import *`) whose module declares nothing follows that module's own wildcard imports up to three hops (`starChainDefinition`, Strategy 6b) and links only when exactly one file defines the name. Python states a class-body construction (`car = Car()`) as a typed static property only when a method calls through it (`self.car.x()`), no method assigns it on the instance, and the call is no ORM column or pydantic `Field`.

**Receivers with several candidate types.** A receiver whose type a run-time choice makes — a local initialised by a conditional expression whose arms call different things (`localTypes` entries sharing one `choice` — the JS/TS plugin marks a ternary's arms and the assignments of `let api; if (x) { api = a() } else { api = b() }` — one if / else-if / else chain, or a `switch` with a `default`, directly after the declaration, every arm one plain assignment and the name touched nowhere else before the statement ends or assigned again; Java and C# `c ? a() : b()`, Kotlin `if (c) a() else b()` and `when (k) { A -> a(); else -> b() }` (an `else` entry required, every entry one expression), PHP `$c ? a() : b()`, Python `a() if c else b()` and Ruby `c ? A.new : B.new` / `if … elsif … else … end` (one expression per branch; each arm a `from` chain, a construction written `A.new()` — `chainPoint` goes on from the instance when the class head is followed by one of the manifest's `constructorCalls`) mark their arms too; a Go, Java or C# `var api Api; if … { api = a() } else { api = b() }` needs none — the declared type states the receiver; separate declarations of one name in different blocks or closures carry none and keep the one-method rule), or a parameter or local declared `Club | Player` / `Club & Named` (`receiverTypeCandidates` in `extractors/shared/type-parser.ts`, read where the manifest sets `candidateTypeUnions`) — is typed per candidate: `scopedName` hands the typed candidates to its caller in `branches`, and the call links through each (`resolveCallToDefinition`'s branch loop). A candidate that declares no such member is skipped; candidates that reach one inherited method link once per class as before; candidates reaching different methods link each, `AMBIGUOUS`, with the usual `injection` strategy; a lone declaring candidate stays `INFERRED`. A candidate that is no project class (a library type, a primitive, an unresolved arm) leaves the receiver untyped, and `Club | null` / `Club | undefined` stay `Club` (`receiverTypeName`'s absent types). Any other reassignment (assignments in separate `if`s, one after a call, a name read before the if/else) leaves the local untyped in JS/TS; Java/Kotlin/C#/PHP/Python state no per-assignment entry at all.

**Spec join beside a code twin.** A contract row (OpenAPI, …) whose method and normalized path exactly one production code API route also states joins by its operation id only, never by a name derived from its path (`spec-join`, `codeServes` in [symbol-linker.ts](symbol-linker.ts)): the pairing of the two rows (`pairContractTwins`) is the implementation, and a function that merely shares the derived name (a client wrapper `deleteClubs`) was a false link that also counted the row as implemented. Both deciders count twins by ONE rule, `codeTwinsIndex` ([route-linker.ts](route-linker.ts)): method, normalized path, narrowed by the API version the contract row's path names (`/v1/` beside `/v2/` is one twin, not two). The symbol linker's gate also asks it `loose`: where the exact path finds nothing, the code row under a conventional base the contract row leaves out (or carries), or behind a parameter the contract row spells as a literal (`/migration/{Name}/migrate`, two literal segments agreeing at least). The parameter fill reads only the rows of the contract row's segment count and first named literal segment (buckets in the index), not every same-method row; the index returns the twin row itself, so the symbol linker's twin carries its `filePath` (no identity map). The two deciders build their own index over their own code sets (the gate leaves tests and class-suffix files out) — a shared build would change which rows count. With a twin, even the operation's own id joins only a function in the twin's file — a client's `register` sharing the id is not the handler (the handler-name and contract-type tiers still join the twin's real handler). A row no code serves, or two code rows serve, keeps the full name join.

**Vulnerable-function reach (E-56).** `analyze --osv` reads, where an OSV record states them, the functions an advisory names as vulnerable — Go's `affected[].ecosystem_specific.imports` (`ExternalPackage.advisories[].functions`: an import path and its exported symbols, from the entry naming this module only; ecosystems whose records carry no such data stay package-level and get no `reach`; the reading and the names a call through such an import is written with are the ecosystem's `PackageManagerSpec.advisoryFunctions`, Go's today, so core names no ecosystem). [vuln-reach.ts](vuln-reach.ts) `attachVulnerableReach` then judges each in the post-analysis from facts every file already holds: a call `head.Symbol(…)` whose head is a name the file imports from that exact import path is a hit; the symbol links walked backwards (depth 8, never across an AMBIGUOUS edge) from the calling function to a route handler, an inline route body or an entry point give `reach.status` `reachable` (with `calls[].from` and the shortest `path`), else `called`; no hit is `not-called`, except an advisory that also names a method (`Type.Method`) — a package-qualified call does not name those — which is `not-judged`, never "safe". A route's root is the one function it is declared on — [`routeHandlerKey`](api-route-symbol-links.ts), the rule `computeDataFlows` also uses (never the function that only registers it; a route carrying its own body's calls and no handler is no function), and, for a route registered inside another function, the handler's own name through `handlerKeyByName` (the one match in that file, else the project's one function of that leaf name — a method when the handler names a receiver; `routeHandlerKey`'s `registeredElsewhere`, passed by `computeDataFlows` too, and the same function resolves an entry point's handler) — plus each middleware the route names (`middlewareCalls`, `inheritedMiddleware`) that the route's own file declares by that plain name, as a root every request passes. Test files are skipped. The OSV fetch is injectable (`AnalyzeOptions.osvFetch`), so tests need no network; `clarifydoc_health`'s dependency listing prints the verdict.

## The pipeline, step by step

1. **Discover files** — [file-discovery.ts](file-discovery.ts) (a glob walk by extension through `core/glob.ts`, which never follows links; skips credential-looking files and a linked git worktree inside the root (a `.git` FILE naming `…/worktrees/…`; a submodule stays); a manifest's `packageRoots` (JVM `src/<set>/java/`) re-admits `target`/`out`/`bin`/`vendor`… below it as packages; a generated file past 4 MB is skipped with its reason; a built webpack/Parcel/browserify/esbuild bundle is refused by the JS plugin's `preprocess`; a manifest's `pathScopedExtensions` admits an extension only below a named directory and where the nearest `package.json` names a framework that routes it — `.md`/`.mdx` under `pages/` for Astro or vite-plugin-pages, `.mdx` for `@next/mdx` — so Markdown pages are screens and a README never is; a Gemfile naming `sinatra`/`rack` re-admits a bare `bin/`; two plugins may not declare one `shebangInterpreterNames` entry). A folder `.clarifydocignore` names is out of every reader that walks the tree itself — deployment manifests, CI pipelines, config and package files, Markdown (`globUnignored`) — not only the source walk; `.gitignore` is not read. Files under a vendored root (`third_party/`, `vendored/`, `public/**/plugins|lib`) — or carrying a copied single-file library's banner (SQLite amalgamation, nlohmann/json, stb…: the manifest's `vendoredBanners`, `FileAnalysis.vendoredLibrary`) stay analyzed but contribute no routes, screens, calls or data (`dropVendoredFacts`). **Code no plugin reads** — a known code extension (`extractors/shared/known-code-extensions.ts`: `.sol`, `.elm`, `.tcl`, `.nix`, `.gd`, `.robot`, `.sv`…) minus every extension a plugin claims (`UNCLAIMED_CODE_EXTENSIONS`, so a new plugin removes its own) is matched by the same discovery walk and only counted, never read (`core/unread-code.ts`: outside vendored, ignored and minified paths): `ProjectAnalysis.unreadCode` (10 extensions, 3 example paths each), one `Not read:` line of `analyze` and a `not read:` line of `clarifydoc_status`.
2. **Detect frameworks** — [framework-detector.ts](framework-detector.ts) (package.json, build files). Manifests, build files and config files are read through `readTextFile` ([read-text-file.ts](read-text-file.ts): UTF-8 with or without a mark, UTF-16 LE/BE by its mark — a `requirements.txt` written by Windows PowerShell 5.1 lists its packages), and a source file saved as UTF-16 is read by its mark (`readSourceText`), where it used to extract nothing.
3. **Detect sub-projects** — [project-detector.ts](project-detector.ts); every file gets a `projectId` (innermost enclosing project); the marker files that make a directory a project (`**/package.json`, `*.csproj`, `Cargo.toml`, `build.sbt`, `sfdx-project.json`, …) are each plugin's `projectMarkers` on the static manifest (`ProjectMarkerSpec`: glob, `kind`, `priority` — the lowest wins a directory holding several kinds —, optional `isProjectRoot` predicate: sbt's `project/` meta-build skip, CMake's `project()` check); the registry builds `PROJECT_MARKERS` and `PROJECT_KIND_PRIORITY` (a kind stated with two priorities throws), core keeps only innermost-wins and the pick; `SubProjectKind` is an open string (nothing outside the detector switches on it); a manifest's `declaredProjects` hook makes the directories a build file names sub-projects too — an sbt `lazy val api = (project in file("api"))` — with `dependsOn`/`aggregate` read as `SubProject.references` by val name (a .NET `.sln` adds nothing: each `ProjectReference` is already one).
4. **Per-file analysis** (parallel; worker threads ≥200 files; a worker that dies on a file (out of memory, the `CLARIFYDOC_FILE_DEADLINE_MS` deadline, default 180 s) is respawned and the file listed in `ProjectAnalysis.failedFiles`, never retried in-process; while a pool runs V8's heap growth is bounded (`--heap-growing-percent=50`, `CLARIFYDOC_HEAP_GROWING_PERCENT`) and an ANTLR grammar's prediction cache is emptied past 10,000 states; a parser front end skips a generated file or one past 2 M characters (`frontEnd.fallback`)) — imports/exports, functions/classes, routes, data sources (with ORM `entity`), **ORM entities + relations**, data mutations, events, interactive elements, template tree, type references, complexity, security. When `--incremental`, unchanged files reuse cached JSON.

a code target, a test reader or a path leaving the root joins nothing), **environment variables** ([env-vars.ts](env-vars.ts): each variable read in code and the services of its project that set it, names only), **CI deploys** ([ci-pipelines.ts](ci-pipelines.ts): the deploy steps of GitHub/GitLab/Azure/CircleCI/Bitbucket pipelines with trigger, path and sub-project — a `docker build` only in a job that pushes), **cross-file taint** ([cross-file-taint.ts](cross-file-taint.ts): a handler's request input passed into a function another file declares, joined through the symbol links from each file's `taintFacts`), **dead code** ([dead-code.ts](dead-code.ts) `analyzeReachability`: authored files no entry point reaches + exports nothing imports, judged only for languages whose plugin declares a `reachability` model; a Procfile process or a compose/Dockerfile command is an entry; a CI or Makefile run line is a passive entry (`ReachabilityInput.passiveEntries`); JS/TS reads computed loads (`import(`./plugins/${n}`)`), Vue `<script src>`, `bin/` beside a `package.json`, migration folders, code-generator outputs and workspace subpaths through `outDir` as loading the files they name; each unused export carries `confidence` and `reasons` — `own-file-only`, `re-exported`, INFERRED; `name-referenced`, `unresolved-imports`, AMBIGUOUS — filtered by `analyze --min-confidence` and `clarifydoc_health`'s `minConfidence`; Swagger Codegen / OpenAPI Generator classes and llparse tables are generated, so their calls' links carry `sourceRole: generated`), health, suggestions, **test coverage** (`--coverage` or the usual report paths: lcov, Cobertura, JaCoCo, Clover, Go → `testCoverage` per file and function, matched by path suffix — [test-coverage.ts](test-coverage.ts)), **doc drift** (paths, routes and class members the project's Markdown names that the tree no longer bears out, guarded by git — [doc-drift.ts](doc-drift.ts)), **performance patterns** (`query-in-loop` from the control-flow graph, `blocking-in-async` from each manifest's `blockingCalls` — [query-in-loop.ts](query-in-loop.ts); both ordered widest reach first by `rankPerformanceByReach`, `PatternInfo.reach`; a manifest's `blockingOnReceiver` — C# `Task.Wait()`, and `.Result` through `readMembers` and `FunctionInfo.propertyReads` — flags `x.Wait()` / `x.Result` in an async method only when `x`'s declared type is that type, never a project class's member), **ignore suggestions** (generated and vendored roots that still hold analyzed files, printed by `analyze --verbose` and `clarifydoc_status` as `.clarifydocignore` entries — [ignore-suggestions.ts](ignore-suggestions.ts)), **entry points** that are not routes (MCP tools, editor and CLI commands → `entryPoints` and `command` data flows), **type-only import edges** (`typeOnlyEdges`: cycles are judged without them — [import-kinds.ts](import-kinds.ts)), **named communities** ([community-names.ts](community-names.ts)), external API specs (`--spec`, read as `@spec/<name>`) and the third-party service an external call reaches (`CallOrigin.service`, `externalServices`).
8. **Write output** — per-file JSON + `project-summary.json` + `report-data.json` (viewer payload, written unconditionally) (+ `manifest.json`, + optional `report.html`). The JSON artifacts are streamed in slices ([json-stream.ts](json-stream.ts): the top levels walked, members through native `JSON.stringify` in batches), byte-identical to `JSON.stringify(v, null, 2)` and never one whole-file string (about −0.9 GB peak on a 6,000-file repository), written to `<name>.partial` and renamed; large text such as `report.html` goes out through `writeTextFile` in 8 M-character slices.

## Data structures in detail

- `RouteInfo` — the attribute layer is kept, not just the path: `middleware` (guard strings — Express middleware names, `Authorize(Policy = …)`, `AllowAnonymous`), `auth` (policies/roles/schemes/anonymous, structured), `versions`/`deprecatedVersions` (`[ApiVersion]`), `params` (each handler parameter with its binding: body/query/route/header/form/services, `inferred` when derived from framework defaults). A page route carries `renderMode` (`ssr`/`ssg`/`isr`/`csr`, copied to `ScreenInfo.renderMode` and shown by `clarifydoc_screens`) only where the framework's own settings state it — Next.js data functions and segment config, SvelteKit page options, Nuxt `routeRules`. Field names are language-agnostic; ASP.NET fills them today, Spring/NestJS can fill the same ones. Decorators (`FunctionInfo`/`ClassInfo`/`PropertyInfo.decorators`) carry their **arguments** in every language — never reduce an attribute to its bare name.
- `ProjectAnalysis` — aggregated: `subProjects`/`fileProjects`, `componentGraph`, `linkGraph` (weighted), `symbolLinks` (call→def, `resolvedBy`, `confidence`), `routeMap` (rows carry `filePath` + `projectId`, optional `requestSchema`), `apiCalls`, `apiRouteLinks` (each with its `sourceProject`/`targetProject`), `projectDependencies` (sub-project → sub-project HTTP/bus edges with their endpoints and the deployment edge that agrees — `clarifydoc_services`, the Architecture Containers view), `screens`, `entityGraph`, `dataAccessGraph`, `classGraph`, `migrations`, `externalPackages`, `deployment`, `deadCode` (unreachable files + unused exports, with what was judged and what was skipped), `fieldWrites`/`thrownTypes` (TS/JS, Java, Kotlin, C#, Python, PHP, Go, Ruby, Rust, Dart, Swift, Scala, Objective-C and C++ functions' field assignments, and thrown types in all but Go and Rust, which have none (a C++ method written out of line states its bare names for core to keep where the class or a base declares them, `this->x`, `p->x` and `++`/`--` included; a Dart constructor, named or factory, a Swift `init` and a Scala `def this(…)` state no writes: they initialize; a Scala named argument on its own line (`name = n,` inside `copy(`) is no write, and `@throws[T]` is `declared`; a Swift or Scala member the type's body declares without a type, `var visits = 0`, is stated once as an `init` declaration so core knows it, an `extension` block is `ClassInfo.extension`, a part of the type, and `throw ClubError.closed` or `throw LeagueError.Missing` names the enum while a signature's `throws(ClubError)` is `declared`) — a Ruby `raise T` names the constant, `raise "text"` no type; an Elixir `raise ClubClosed` names the module through the file's `alias` lines, matched whole (the manifest's `wholeTypeNames`: core's lookup never falls back to the last segment, so `File.Error` is never a project module `Error`), and Elixir states no writes; in every other language a qualified name (`java.io.IOException`, `requests.HTTPError`, `Net::ReadTimeout`, `std::runtime_error`, a field receiver typed `std::io::Error`/`*http.Error` — `writtenTypeName` keeps the qualifier `receiverTypeName` drops) binds by its last segment only through a qualifier the project backs (`qualifierBacksClass`): a namespace/package the class is declared in (`ClassInfo.namespace`, `FileAnalysis.packageName`/`declaredNamespace`), directories or a file stem on its path (a Java package, a Python module), a class its own file declares (a nested type, a Ruby module), or a name the writing file imports from that file or namespace (`import * as errors from "./x"`, `using Err = …`); a manifest's `relativeTypeQualifiers` (Rust `crate`/`self`/`super`) name no module, so `crate::Club` stays the project's own; a Go type written through a package qualifier still states nothing, C#, Go and Visual Basic types found only in the writer's directory (`typesSpanFiles` without `typesBeyondDirectory`) are unchanged; a Ruby class declares an instance variable by assigning it, so each method's first `@x` write and each writer method (`attr_writer`, `def x=`) states an `init` declaration beside it, and a Rust `static mut` written bare is a `package` write joined within its own file, while one written through its module (`crate::stats::TOTAL += 1`, `stats::TOTAL = 0` after `use crate::stats;`) or bare after `use crate::stats::TOTAL;` is a `package` write whose `receiver` is the module path — core resolves it with the language's own `resolveImport` to the one file that must declare the variable (`moduleVariableHome`), never a namesake module's; a Rust field written through a shared cell (`self.stats.borrow_mut().goals += 1`, `club.lock().unwrap().name = n`) or a deref (`*self.count += 1`) is a write of that field, `RefCell`/`Mutex`/`RwLock` being transparent wrappers of a declared type; a PHP docblock `@throws` and a JSDoc `@throws {T}` is a `declared` thrown type beside the body's, a Python `__init__` states its `self.x` writes as `init` declarations core never lists as writers — `FunctionInfo.fieldWrites`/`throws` — resolved to project classes by declared types only and only within the writer's language family (a TypeScript `throw new Error` never meets a Go `Error` struct), `core/member-effects.ts`: where a type is looked up beyond its directory (`typesBeyondDirectory`, Ruby and Rust: the directory's declarations lead, a qualified name or several real declarations of a name that the writing file does not own refuse), where classes are looked up by namespace (`classNamesByEvidence`, PHP) a name binds through the writing file's `use`/namespace ([class-evidence.ts](class-evidence.ts), shared with the symbol linker), and where a type spans a directory's files (`typesSpanFiles`, Go) its parts are one type, a package-qualified type states nothing; a Go bare assignment is a candidate package variable (`fieldWrites[].package`) listed only when exactly one file of the package declares it (`FileAnalysis.packageVariables`, `via: "package"`, `class` the package name); a PHP type written through a namespace path states it as `ParamInfo.typePath`/`PropertyInfo.typePath` beside the bare `type`, and a static property written from outside its class (`Club::$count = 0`) is a write with `fieldWrites[].class`, the class as written — core binds both through the writing file's evidence, so a namesake of the writer's own namespace never answers; `clarifydoc_trace direction=writers`, `clarifydoc_explain`'s "Writes and throws"), plus all quality/topology results.

## How to extend the core

- **Teach a plugin a DI container** — plugins only report facts; core resolves. Fill `ParamInfo`/`PropertyInfo.type` (as written — core normalizes with `receiverTypeName`, unwrapping the language's `meta.transparentTypeWrappers` such as Rust `Arc<dyn T>`), `qualifier` for a token/key on an injection point (`@Inject(TOKEN)`, `@Qualifier("x")`, `[FromKeyedServices("k")]`), constructor params (a method named `constructor`/`__init__`/`__construct`/`init`/`new` or the class name), `FunctionInfo.localTypes` for typed locals and container lookups into a local — and, for a local initialized by a call that states no type (`val dao = Factory.getDAO()`, `var u = await repo.FindAsync(id)`), that call as `from` (spelled by `callChainText`, `awaited` when awaited; one entry per distinct initializer, a stated type always wins): core types it through declared return types (`FunctionInfo.returnType`, docblock `@return` included; the manifest's `asyncResultTypes` unwraps `Task<T>`), and only when every initializer agrees — except the arms of one conditional initializer (`const api = slug ? useGuestApi(slug).clubs : useLeagueApi()`, a JS/TS `let api;` assigned on every arm of the if/else or `switch` right after it, and the conditional initializers of Java, C#, Kotlin (`when` with an `else` too), PHP, Python and Ruby (`c ? A.new : B.new`, an `if` expression, read as `from: "A.new()"` chains) — each plugin marks the arms with a shared `localTypes[].choice`; a Go, Java or C# local assigned on each arm is typed by its declared type) and a TypeScript `Club | Player` / `Club & Named` (manifest `candidateTypeUnions`), which link once per candidate that declares the member: AMBIGUOUS when the targets differ, INFERRED when one declares it, untyped when any candidate is no project class; separate declarations of one name in different blocks carry no `choice` and keep the one-method rule; arms are all-or-nothing — one initializer core cannot type leaves the local untyped, so plugins emit every arm and never pre-filter; a type a plugin read off one assignment is `localTypes[].inferred` (PHP), and core drops it when another assignment of the name is a call it cannot type or one typing another class (a construction guarding a null test of the same name, or the last straight-line assignment, keeps it) —, `CallInfo.receiverType` for a lookup chained into a call (`meta.calls.receiverTypeOf`, or a regex `callPatterns` entry), `ClassInfo.kind: "interface"` (+ `structural: true` for Go interfaces / Python `Protocol`), and registrations as `FileAnalysis.diBindings` (`meta.ast.diBindings` / `RegexLangSpec.extractDiBindings`). A `DiBinding` says asking for `service` (type or token) yields `implementation`, with `qualifier`/`keyedOnly` (named and keyed registrations), `primary`, `matchesMemberName` (Spring autowire-by-name), `consumer` (contextual), `ifAbsent` (`TryAdd*`, `@ImplementedBy`), `conditional` (active only under a profile or condition — Spring `@Profile`/`@Conditional*` — and yielding to an unconditional binding, as a default does). Core picks: test containers never apply to production code; contextual beats general; the consumer's own sub-project beats others (which must agree); a default yields to a real registration; then ONE implementation, or one primary, or one named like the member — otherwise it refuses to choose and the call stays on the interface. Never pre-resolve in a plugin.
- **Teach a plugin where services are** — a leaf `plugins/<lang>/service-config.ts` exporting a `ServiceConfigSpec` on the manifest's `serviceConfig`: `sources` (config files at each project root and a parser returning `ConfigEntry`s — mark `profile`/`test`, `env` for variables a profile sets, `listen` for URLs the project binds; core keeps only URL-shaped values), `baseRefOf` (a base expression as written → `env`/`config`/`literal` `CallBaseRef`, with `fallback` for `?? "…"`), `envNamesFor` (config key → the env vars that override it), `routeBaseOf` (every entry of those files → the base the project serves its routes under — Spring `server.servlet.context-path`, profiles never; core's [route-bases.ts](route-bases.ts) prefixes the complete API routes, `RouteInfo.basePath`), and `proxySources` (config files declaring forwarding rules → `ProxyRule`s; [plugins/shared/proxy-kit.ts](../extractors/plugins/shared/proxy-kit.ts) reads prefixes, rewrites and gateway templates; a code file's proxies go through `meta.ast.proxyRules`). Python (`httpx`/`aiohttp` `base_url`) and Go (resty `SetBaseURL`, URL-named fields) state client bases, PHP (`config/*.php`, `env()`, Guzzle `base_uri`) and Ruby (`config/*.yml` ERB, `config.x`, `ENV.fetch`) have a `serviceConfig`, Rust a `baseRefOf` for a base opening with `env::var("X")` (no fallback literal, no build-time `env!`); a config entry carries the variables that override it as `ConfigEntry.envNames` — plugins keep no module state. Clients go through `meta.ast.httpClientRegistrations` / `RegexLangSpec.extractHttpClientRegistrations` (what configures a base, keyed the way a call names the client — a Refit `AddRefitClient<IClubApi>()` / `RestService.For<IClubApi>(…)` or a Retrofit builder is keyed by the API interface whose verb-attributed methods are the requests (`${IClubApi}/{id}` until the base is known); a generated proxy of an API interface sets `proxyOf` to its fully qualified name, and core turns every call on a receiver of that type into a contract call) and the call row's `baseRef: { kind: "client" }` or `client`. Routes declared on a typed API set `RouteInfo.contract`. Never resolve a host in the plugin — core's call-origin pass does. `.env` files are never read (discovery treats them as secrets). Labelled fixture: `test-fixtures/sample-microservices` (C#, TS, Java services, plus Python httpx/aiohttp, Go resty, PHP Guzzle/`config()` and Ruby Faraday/`ENV` callers with one `archive` decoy each) + [cross-project-fixture.test.ts](cross-project-fixture.test.ts).
- **Add a package manager** — a `PackageManagerSpec` in `plugins/<lang>/package-manifests.ts`, listed in that plugin's manifest `packageManagers`: the manifest files to read at each root (exact names or bounded globs, `firstOnly`, `readSibling` for a lockfile beside it) and a parser per format, `selfName` for the package the project itself publishes (package.json `name`, a pom's `groupId:artifactId` with the parent's group, Gradle `group` + project name, a `.csproj`'s `PackageId`/`AssemblyName` — what another repository's dependency joins in a system), `registry` when its names are another ecosystem's (Gradle → maven), plus how an import names a package (`importKey`, `packageKey`, `prefixMatch`, `assertsUnused` only where EVERY import of a package is visible, `installedOwners` for what the manager installed — Composer's autoload map; `installedApi` for an installed package's exported API, read on demand by `clarifydoc_extract package=` — npm's reads `node_modules` declarations, never during analysis). Each language lists the ecosystems it imports from in `packageEcosystems`. It lives on the static manifest because the inventory reads every manifest whether or not the language was discovered. Several plugins may contribute manifests to one ecosystem (sbt → maven, rebar3 → hex); only one may define its matching (the registry throws otherwise). [dependency-inventory.ts](dependency-inventory.ts) only walks the roots, dedupes, classifies and counts — it names no ecosystem but `.gitmodules`.
- **Judge a language for dead code** — give its meta a `reachability` hook ([src/types/language-plugin.ts](../types/language-plugin.ts) `ReachabilityHooks`): `load()` reads the toolchain's entry points and returns a model that says which files START the program (`entryReason` — these anchor a project), which are merely RUN BY A TOOL (`passiveReason`: configs, migrations, scripts — kept alive, never reported, anchor nothing), resolves an import specifier to the files it loads (`resolve`: `[]` = external, `null` = local but unknown) and resolves `pathReferences`/template tags. Set `judgeExports: false` when imports don't name what they use. Languages that reach by NAME (a C# type across its namespace, a PHP class Composer autoloads, a C function behind a header) declare `declaredNames` — core then reaches a file when any reachable file's text mentions one; `configMentions` (manifests, appsettings, `META-INF/services`) anchor what the framework instantiates by name; `unitOf` makes a Go package one unit. Every code language has a model: bespoke for JS/TS/Vue/Svelte ([plugins/javascript/reachability.ts](../extractors/plugins/javascript/reachability.ts) — files and exports; below an `sfdx-project.json`'s `packageDirectories` an LWC `lwc/<n>/<n>.js` and an Aura `aura/<n>/<n>{Controller,Helper,Renderer}.js` are passive — the platform loads them by folder name, they anchor no project, so an SFDX repository with no other JS entry stays unjudged — while a stray file of the folder no import reaches keeps its finding), Rust (`mod` tree) and Python (imports + `__init__` chains, server commands); the rest are declarative specs built by [plugins/shared/reachability-kit.ts](../extractors/plugins/shared/reachability-kit.ts) (C#, VB, Blazor, Java/Kotlin, Scala, Swift, C/C++/Objective-C, Go, PHP, Ruby, Perl, Lua, Dart, Elixir, Erlang, Haskell, Clojure, Delphi, QML, Nim, D, V, Fortran, Apex — with `foldNames` for a language whose names ignore case). Markup and schema formats are never judged but are read as mention sources. Libraries are not judged as dead: a published package's modules (pyproject/gemspec/CPAN/Composer library, Go packages outside `internal/`, Swift `public`, Dart `lib/`) are its API. Extension-less `#!` scripts are read through [plugins/shared/shebang-scripts.ts](../extractors/plugins/shared/shebang-scripts.ts). Only declare it for a language whose imports NAME files — C#/Java/PHP/Rails find files by namespace or autoload, and an import graph cannot prove those unreachable. Measure precision on a real repo before shipping: every finding is an accusation. `test-fixtures/sample-dead-code` + [dead-code-fixture.test.ts](dead-code-fixture.test.ts) are labelled by hand from the source.
- **Explain a complexity number** — `clarifydoc cfg <file> --function <name>` builds a control-flow graph for one function and renders it as Mermaid ([control-flow.ts](control-flow.ts)); `--slice <line>` prints the backward slice at a line instead — the statements that can affect the values used there, by reaching definitions (both arms of an `if`) and control dependence over that graph ([control-flow-slice.ts](control-flow-slice.ts); defs/uses read off node text, so approximate where a language assigns through a call). On demand only: it reads one file, writes nothing, and never reaches `project-summary.json` — a CFG is per-function detail that would multiply the artifact for something almost nobody reads in aggregate. Per-language node roles come from `meta.controlFlow` ([control-flow-defaults.ts](../extractors/shared/control-flow-defaults.ts) is the shared C-family table, and `extendControlFlow` is how a plugin adds its own spellings). Covered exactly: **TypeScript/JavaScript (incl. Vue/Svelte SFCs), C#, Python, PHP, Java, Kotlin, Pascal/Delphi** — every tree-sitter plugin. A language with no grammar gets a second front end rather than a second builder: [control-flow-regex.ts](control-flow-regex.ts) reads the function's text, blanks comments/strings/regex literals, infers nesting from block delimiters and synthesizes nodes carrying the SAME canonical types, which go to the SAME interpreter (`FlowNode` in [types/control-flow.ts](../types/control-flow.ts) is the seam; tree-sitter's `Node` satisfies it unchanged). That covers **Go, Rust, C, C++, Objective-C, Swift, Dart, Perl** via `meta.regexControlFlow`, marked `approximate` on the graph and in every surface that shows one. Keyword-delimited languages (**Ruby, Lua, Elixir, VB**) go through the same scanner with a plugin `blockDelta` hook instead of brace counting: it says what each line opens (`if` at a statement's start, a trailing `do`, `If … Then` with nothing after it) while `blockClose` says what closes (`end`, `End If`, `Next`), which is how a modifier `if` is told from a block — plus `armBlocks` (a Ruby `case`'s `else` is an arm) and `inlineGuard` (`stmt if cond`, `If c Then s`). Ruby is gated against tree-sitter-ruby, a dev dependency whose wasm also ships for the Ruby taint reader (98.9% of one real Rails repository's methods, 98.0% of a second's). The regex tier is gated by measuring it against the parser on the languages that have both: ≥90% of TypeScript and Java functions and ≥85% of C# ones must come out the same shape ([control-flow-regex.test.ts](control-flow-regex.test.ts)). `clarifydoc cfg --capabilities` publishes the list and the VS Code `$(flame) complexity N` CodeLens uses it to fall back to the Complexity report rather than dead-end. Two gates keep the builder honest, both in `control-flow.test.ts`: `cyclomaticFromCfg` must equal `computeComplexity` (sharp, but blind where a complexity table is wrong — Pascal's is), and `undrawnStructure` must find nothing (table-independent: every construct in the body has a node in the graph). Each corpus also asserts which constructs it contains, because a gate that quietly stops exercising a construct is worse than no gate.
- **Tell the impact report how to run tests** — a manifest's `testCommand(tests, ctx)` returns the runner's command for test files and the test functions a change reaches (pytest node ids, `go test -run`, Maven/Gradle by manifest, `dotnet test --filter`, …); `projectCommands(root)` reads how a whole project is built, tested and started from its root files (`ProjectAnalysis.projectCommands`, shown in `clarifydoc_status` and the `install` guidance block); `blockingCalls` names the calls that block inside async code (Swift among them); Scala (`sbt testOnly`), Perl (`prove`) and C/C++ (a CMake root that registers tests: `ctest`, through `plugins/shared/cmake-commands.ts`) state test commands too, and `TestCommandContext.projectTests` hands a plugin the project's own test commands; Go, Ruby and Rust state their `TaintSpec` through `meta.regexTaint` (`{ gate, taint }`; Go also follows a request body bound into a struct by its text fields — `c.ShouldBindJSON(&req)`, a JSON decoder, `TaintSpec.binds` —, Ruby reads heredoc interpolation into SQL sinks, Ruby also reads a heredoc chained into text-keeping calls (`<<~SQL.strip`, `.squish`) as its body, Rust reads axum/actix-web/rocket extractors — an axum `String`/`Bytes` last parameter of an `async` handler beside another extractor, never `HeaderMap`, never a plain helper — with `format!` captures — `stringReads`; the shared walk reads expression values from a spec's `valueParts` table — a comparison is a boolean, an `if`/`match` its arms —, guards through one `condition(ifNode)` text hook, and a redirect or outbound-URL sink, by its category, is one a fixed host does not reach): a file whose source matches the gate is parsed once more with the one tree-sitter grammar variant the manifest registers (`tree-sitter-go`, `tree-sitter-ruby`, `tree-sitter-rust`, shipped in `dist/grammars`; the `taint` feature switches it off) for the shared `handlerTaint` walk — never a test or generated file or a tree with syntax errors; a command needing a stated fact reads it from `TestTarget.suites` (`FileAnalysis.testSuites`: a Go testify suite → its runner, `-testify.m`) or `TestCommandContext.testTargets` (SwiftPM `.testTarget(path:)`), and an Elixir umbrella app's tests run inside the app; `testSetupRuns(root, files)` names the files a test run executes while setting up (Django's migrations and `AppConfig.ready()` under pytest-django), which the test-reach verdict counts as tested (`ProjectAnalysis.testSetupRuns`); a spec suite describing a type the file declares (`describe Club`, with cases, same sub-project, not replaced by a double) is test-verdict basis `described`, since framework wiring (a prepended mixin, callbacks) has no written call; `docComments` is the comment syntax tools read on demand. All live on the static manifest, as leaf code.
- **Draft architecture rules** — `clarifydoc rules init` ([core/rules-init.ts](rules-init.ts)) writes `.clarifydoc/config.json` `rules` from the folder dependency matrix (per folder "stays below its dependents", per cycle group "stays out of its cycle"; never an `allowOnly`), shows the diff, and with `--write` merges by rule name and writes the baseline SARIF `analyze --baseline` takes. `clarifydoc install --remove` ([agents/remove.ts](../agents/remove.ts)) reverses every install writer from the same plan functions, surgically; `mcp --print-config --pin` prints `npx -y clarifydoc@<version>`.

## Performance rules

- **Profiling:** `CLARIFYDOC_WORKERS=0 node --cpu-prof --cpu-prof-dir=<dir> dist/cli.js analyze …` (workers=0 keeps per-file work in the profile), then aggregate the profile per function. Self-time is too flat to act on — aggregate **inclusive** time per function.
- **Thermal-resistant metric:** wall clock swings up to 3× on laptops. Track the nonParse/parse ratio instead — `(inclusive analyzeFile − inclusive parseSource) / parseSource`; parseSource is fixed WASM work, so the ratio isolates extraction efficiency.
- **Correctness gates for any perf change:** (1) byte-identical per-file JSON on a real corpus (diff ignoring `analyzedAt`); (2) regenerate fixtures and diff `test-output/`; (3) vitest.
- **Worker pool:** worker threads kick in at ≥200 files; the cap of 8 is empirically optimal (more workers measured slower). `CLARIFYDOC_WORKERS=<n>` overrides, `=0` forces in-process. Each worker's young generation is capped at 16 MB (`CLARIFYDOC_WORKER_YOUNG_MB`, `0` = V8's default, which scales with machine memory): cold-run peak RSS −20 to −27 % on three 4,000–6,500-file repositories, output identical.
- **V8 hidden-class trap:** `Node.type` is cached on instances via a patched prototype getter (parser-manager.ts). Do **not** add more lazily-created cache properties to nodes — it forks hidden classes and makes all node property access megamorphic (measured 3.5× slowdown in route extraction). Cache per-file data in `Map<node.id, value>` memos instead. `id`/`startIndex`/`startPosition`/`tree` are free fields; `endPosition`/`endIndex`/`text`/`childForFieldName` cross into WASM per call.
- **Walk fusion:** full-tree walks dominate non-parse time; fuse N extractor walks into one traversal with per-extractor buckets (done for JS routes and data-sources/mutations). Caution: stateful extractors keep per-file state — fused walks must call the base-class `beginFile`/`endFile` hooks around the traversal or state silently goes stale. `extractCalls` does not enter a childless node whose type no step of its walk reads (not a scope, binding site or call type) when the plugin states no per-node hook (`readNames`, `collectExtraCalls`, `destructuredFromCall`, `heldFunction`) and no `skip` is given — 60 % of a C# body's nodes (`READ_TYPES_BY_LANGUAGE`, [call-graph.ts](../extractors/shared/call-graph.ts)); a hook that only acts on some node types is gated on them before it reads text (C# Hangfire/`ToTable` arguments, `is`-pattern narrowing), and the per-call cost of the C# argument hooks is what is left of `extractCalls`.
- **Memos per link run:** the linker's per-run caches are the `memos` object of `LinkContext` (`LinkMemos` — `typeFileFor` per (type, file, project), about 13 calls per key on a 4k-file repository; callable members; include closures …), never module-level `WeakMap`s; never spread a context; anything a memo reads from the context must be built before linking starts. A dotted call of an internal name whose last name no file of the run declares (`namesNothingDeclared`, `declaredLeafNames`: every function, method, class, property, event, alias, export, import, mixin rename, returned-member key, constructor name and `constructorCalls` entry, lower-cased; a name with `<` never) is refused after the dispatch-map and record questions and before the receiver is walked — a bare name is not (`super`, a local holding a factory's result resolve by no declared name); `namespaceHeadMember` is memoized per (file, written path), a directory's package files per language family (`packageFilesOf`, the caller's own file cut out per call) and the language families holding any dispatch map (`familyHoldsMaps`: a one-key `x.y` call whose file holds no map of that name, in a family where no file holds one, skips the imported-map lookup).
- **Flat trees (the only path since the `flat-tree` feature, default from 1.731.0, was retired; a leftover `no-flat-tree` is ignored):** byte-identical to the real nodes on all 38 corpus repositories and every fixture; `parseSource` of a language in `FLAT_TREE_LANGUAGES` (C#, Java, JavaScript, Kotlin, PHP, Python, TypeScript — TSX and the Vue/Svelte scripts are TypeScript text — plus F#, Bash, R, Julia, Zig, OCaml and Pascal `.pas`) copies the tree once into typed arrays and returns `FlatNode`s ([parsers/flat-tree.ts](../parsers/flat-tree.ts)) — a 4,000-file C# repository's cold CPU 67.7 s → 43.5 s, output identical; a TypeScript repository's 25.8 s → 19.6 s; a Python repository 22.4 s → 17.6 s, a PHP one 11.7 s → 9.0 s, a Java one 24.6 s → 17.5 s. A hidden zero-width MISSING token an external scanner inserts (Kotlin's statement end) is never visited by the cursor, so a file whose real root says `hasError` while the copy does not reads the flag from the real nodes (`readErrorFlags`). A language joins the set only when its corpus output is byte-identical on the flat copy and the real tree (`--stable-output`); `flat-tree.test.ts` holds every member equal to the real node, quirks included; `descendantForIndex` is not copied (its edge answers differ by grammar), so callers descend through `children`. Plan: E-295.
- **Scaling gate:** `cli/scripts/check-scaling.mjs` (CI `verify` job, about 20 s) analyzes generated TS/Python/Go sub-projects at N and 4N single-threaded and fails when (t(4N) − t(1 project)) / (t(N) − t(1)) / 4 exceeds 2.5 — a quadratic pass shows there, fixtures are too small; it prints both runs' stage timings on failure. Never spread a six-figure array into `splice`/`push`/`Math.max` (stack overflow: the symbol linker's overload pass did on a repository with 120k links) and never scan a file's whole text per call or per name (cache the answer per file, `httpResourceFile`, `mutatesCollection`).
- **Cheap gates:** substring-gate expensive subtree walks (`sourceText.includes("import(")` before walking for dynamic imports); whole-text regex gate before per-line rule loops, and a whole-text gate asked per call site is computed once per file (Python `managerAssigned`); a pattern built from a name is built only after a substring test on that name passes (Ruby `assignmentsOf`); a per-line rule loop over a whole file (Go's `extractGoRoutes`) first tests one alternation of the words every rule names after a `.` and skips the line otherwise, `goAddressedTypes` reads value locals and value types only when an `&x` of a value exists, and `typeBlockLocalCalls` indexes the body's identifiers once instead of testing every declared name against every line. A per-argument walk of the enclosing function (PHP `assignmentsOf`, Python `assignsTo`) is one walk per function building a name table, kept per tree in a `WeakMap`; a text blanker (`stripPythonNonCode`) scans char codes and copies kept stretches by `slice`, never a per-character array.
