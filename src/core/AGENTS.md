# src/core — Analysis pipeline & analyzers

The analysis pipeline orchestrator and all cross-file analyzers live here. Pure functions in / out — no tree-sitter parsing happens at this layer (that's delegated to extractors).

**Core is language-agnostic.** Anything per-language — extensions, parse
strategy, builtin types, complexity tables, security rules, framework hints,
external-package prefixes, AST hooks — comes from the plugin registry
([../extractors/registry.ts](../extractors/registry.ts)), which aggregates each
plugin's `meta.ts`. Don't hardcode language names, ORMs, frameworks, or file
conventions here; ask the registry. Even a **cross-file** join that needs
language knowledge stays in the plugin: core calls a generic hook (e.g.
`reconcileProjectEntities` → each entity extractor's `reconcileProject`), it
never names the language. A `schema.rb` parser or a pluralization rule in
`src/core/` is a layering bug, and so is an import of
`extractors/plugins/<language>/` from production code here —
[core-imports.test.ts](core-imports.test.ts) fails on one (`plugins/shared/`
holds language-free helpers and is allowed).

## Entry point

[analyzer.ts](analyzer.ts) exports `analyze(options)` — the full pipeline (the stages are described in `## The pipeline, step by step`):

1. File discovery + framework detection.
2. Parallel per-file analysis (tree-sitter + extractors, or regex fallback).
3. Post-analysis: component graph, link graph, symbol links.
4. Optional LSP enhancement.
5. Advanced analysis (complexity, patterns, duplicates, layer violations, blast radius, health, suggestions).
6. Write the project summary + optional HTML report.

Every step is gated behind the `ProgressReporter`, in both verbose and non-verbose modes.

- **Import edges of the component graph.** A package import (`importsNameDirectories` — Go, Rust, Ruby) resolves to the ONE directory the language's `packageDirectory` rule names from the repository's packages (`SubProject.packageName` + `packages`; the standard library and downloads are no directory), else to the directory whose path ends with the longest run of its segments (a tie is no edge), narrowed to the files declaring a name the importer uses, tests excluded. Per-language rules: [Go](../extractors/plugins/go/AGENTS.md), [Rust](../extractors/plugins/rust/AGENTS.md), [Ruby](../extractors/plugins/ruby/AGENTS.md). Dead code reads these edges as reachability, so a phantom fan-out hides real gaps in a language's own model.
- **External imports bind nothing.** An import of a third-party package a manifest of the repository declares (`declaredPackageImports`, matched as package usage is) or of the language's standard library (`standardImport`) is no project file (the standard library includes Python's modules and Node's built-ins `path`, `fs`, `node:*`), and the names it binds are never matched to a project file exporting the same name.
- **Stage timings.** A stage's time (`stageTimings`, `--verbose` `Timings:`) runs from its `progress.step`/`progress.status` line to the next one, so a long span of passes carries `progress.status("…")` sub-steps at group boundaries (graphs and deployment, call targets, screens, route linking, schemas; entity and data-access graphs, trace impact and tests, data flows and findings; in "Analyzing files" the manifest check, the cached/changed reads and cross-file route resolution). They emit `step` events and leave `STAGE_OF` and the stage ids alone, since consumers of `--progress json` key on those. A new pass goes under the sub-step it belongs to; a sub-step under about 50 ms is merged into its neighbour.

## Analyzers (post-analysis passes)

All take `FileAnalysis[]` and/or `componentGraph` and return typed results. Each pass below lists its output, its inputs (the facts plugins state) and its rules. Per-language spellings of those facts live in each plugin's own `AGENTS.md` ([../extractors/plugins/](../extractors/plugins/AGENTS.md)).

**Dependency order matters.** Health and suggestions depend on everything else. The analyzer computes the import cycles ONCE (`findCircularDeps` over the runtime graph — type-only edges and edges only a dynamic `import()` states (`dynamicImportEdges`, loaded on demand) dropped — of authored, non-test files) and hands them to refactor pressure, health and suggestions (`cycles`). A cycle group is a set: print it with `cycleChain` (a path the imports really take), never as its members joined by arrows.

### Linking

#### symbol-linker.ts — `SymbolLink[]`

A fallback cascade. Tiers, roughly in order:

- **Direct.**
  - Where functions nest (read from `line`/`endLine`), a bare name is the function declared inside the caller, else the one in the innermost scope enclosing it, before a top-level namesake or an import of that name. Another function's inner helper only when it is the one of that name and the caller is handed it — a parameter of its name, or a call of the function declaring it — INFERRED.
  - Case-folded on the callable's own name where the manifest says `caseInsensitiveNames`/`caseInsensitiveCallables`.
  - A cross-file call whose file only re-exports the name (a barrel's `export * from` / `export { x } from`, a Python package `__init__`'s `from .impl import X`) follows the re-exports to the definition, unique-or-nothing; a named re-export stays the target only when it leads outside the project.
- **Bare `super`** — the base class's same-named method, or its constructor from a constructor; never a `super()` that only receives a member call.
- **Inheritance.**
  - Along the C3 order where the manifest says `multipleInheritance` (Python).
  - `this.foo` — and a bare `foo()` where members need no `this.` — on the enclosing class and its bases first. Another class's member of the file only from a class it encloses and never from a free function, unless the manifest's `bareCallsHideReceivers` says the extractor reads `p->foo()` as `foo`: then a same-file one is an INFERRED guess.
  - Only for calls on the instance itself (`foo()`, `this.foo()`, `super.foo()`); then the ONE mixed-in module/trait/interface that defines it (Ruby `include`, PHP `use`); never a bare name where members need `this.`.
- **Declared-type resolution** (`resolveThroughDeclaredType`) — see below.
- **Deep-qualified** — never matches a chain's leaf alone on a file its head's name chose. **Factory-via** — the factory FUNCTION a library-made receiver came from; a receiver the caller constructed (`const league = new League()`, typed or not) is no factory: a member the class lacks links nothing, never the class.
- **ClassName.method** — a namespace written relative to the caller (`Routes::Fixtures` inside `module League`) falls back to the ONE declared class whose name ends that way. Where the manifest says `classNamesByEvidence` (PHP) the class is bound only through the caller's own evidence — its own file, an import naming it (alias or namespace prefix too), its own `declaredNamespace`, a fully qualified name kept in the call name (`\\App\\Other\\Garage.park`) — never a namesake of another namespace, and a class head that refusal leaves is not found again by the unique-global name guess ([PHP](../extractors/plugins/php/AGENTS.md)). Where the manifest says `valuePathsNameNoType` (Go: `a.b.C.m(` never names a type), a `receiverCut` name is also refused by this guess — a namesake class is no reading of a field's unresolved type ([Go](../extractors/plugins/go/AGENTS.md)).
- **Constructor** (`new X`/bare class) — any link a call naming a class makes to the class itself lands on the constructor that class declares (`__init__`/`constructor`/class-named/a manifest's `constructorNames`, never a base's); a class without one stays the target, a JSX element stays on the class, and a function named `new` is reached only by a call spelled `new X`.
- **Package-qualified import head** (file and dir); **a function by its namespace-qualified name** (`FileAnalysis.declaredNamespace`: `use function`, `\App\fn()`, the caller's namespace then the global one).
- **Bare call into shared scope.**
  - A used unit (`importsShareScope`: Pascal `uses`, PowerShell dot-sourcing, PHP `require`/`include`, a C/C++ `#include`): where the included file is a header (`declarationExtensions`), the files sharing its stem define what it declares, a `static` body (`isExported: false`) never.
  - A wildcard import (`from m import *`, what the module exports).
  - The caller's package directory (`directoryScope`: Go, Kotlin, Swift — the one non-test sibling file declaring it).
  - A module import or dotted call naming a module by its DECLARED name (Elixir `alias`).
- **Unique-global-leaf** (evidenced and import-blind):
  - The files a file imports are named by the language's `resolveImport` or `importedFile` rule first, else by the generic path rules; a file declaring nothing of its own (a barrel of `export` lines) hands on what it imports, three deep.
  - A language whose loader finds files by the constants they define adds those files (`autoloadedFiles`) and is never import-blind.
  - Where imports name packages (`importsNamePackages`: Scala, C# namespaces, Swift), an import is the files whose `FileAnalysis.packageName` it names — narrowed to those declaring the member it names — and a file also sees its own and enclosing packages.
  - A language's `typeNamedByReceiver` (`match_report` → `MatchReport`) is evidence too. For Go, where a package is its directory, the evidence is the files of every package any non-test file of the caller's package imports, and a receiver that is a package no directory holds (`strings.Cut`) is vetoed.
  - Vetoed when the receiver's type — a typed local/param/field, or the call's own `receiverType`, a builtin one included — names another class. On a chain that type is the one the chain resolves to (a library type vetoes, a project type lacking the member does not — a Dart `extension … on` it may serve it; a chain it cannot type keeps the head's), and a class head vetoes only a call on the class itself (`PlayerService.instance.x` is called on what `instance` holds). A receiver's name is evidence only as the segment right before the method (`club.league.relegated?` is called on `league`).
  - For this tier and deep-qualified alike: refused when a head the callable binds (a local typed as written or by its initializer, a parameter, or `this.x`) — or, in a language whose call names spell the receiver from its head (`callPathsFromHead`; a call whose name keeps only the receiver's last names says so, `CallInfo.receiverCut`), a typed field of the caller's class or a module binding — types the receiver through its chain to a project class that, with its ancestors and mixins, lacks the member (`receiverTypeRefuses`; a namesake in another namespace, `Overlay::Club`, excepted — it may be mixed in unseen).
  - A `receiverCut` call (`items[0].league.markTable(` read as `league.markTable`) has no head the caller binds in such a language: Strategy 2, `chainReceiverType`, `receiverTypeRefuses` and the name guess's declared type all leave it alone (`receiverCutName`), so the caller's own `league` field neither types it nor contradicts the one definition of the name.
- **Generic type-argument**, plus the route/spec/fan-out/reference producers in `buildSymbolLinks`.
  - **Abstract dispatch** (`abstractDispatchLinks`): a call landing on an abstract method (`FunctionInfo.abstract`) is re-aimed at the ONE override below the class it dispatches on (the caller's own for `send()`/`this.send()`, else the receiver's); every abstract method fans out to its overrides as an interface method does.
  - **Extensions.** An extension function's receiver parameter named `this` makes its type's fields the body's, and a chain step the type does not declare goes on through the extension of that name (its return type); a `Car.Build()` the class lacks reaches a static extension member. An extension on a builtin collection of one element (`on List<Club>`, a bounded `List<T extends Club>`) names no project class, so a call on a local, parameter or field of the caller's own class declared with that element (`collectionElementOf`) takes the one such extension, the receiver's own collection preferred (`collectionExtensionLink`), never another element's.

**Declared-type resolution** (`resolveThroughDeclaredType`) types a receiver chain through field types AND declared return types (`a.getB().getC().m()`, `new X(…).m()`, `Factory::getInstance()->m()`, a project class's static member `PlayerService.instance.add()`, fluent `$this`/`static`/`Self` returns; a local typed by its initializer call, `localTypes[].from`). The receiver is, in order:

1. a typed local;
2. a parameter;
3. a field of the ENCLOSING class (own ctor params/properties, inherited fields);
4. a typed module-level variable (`FileAnalysis.moduleBindings`): the file's own, or an exported one of a unit `importsShareScope` puts in scope (Pascal `var dmLeague: TdmLeague` seen through `uses`), or of a library an `ImportInfo.inScope` import names, with its `part`s and what its barrel `export`s forward. A `show` list narrows it; two used units typing it differently decide nothing. Where the manifest declares `typesSpanFiles` (partials, extensions, Go methods beside their struct), the other parts of the same type in the directory count;
5. or a member chain through declared field types, or `CallInfo.receiverType`.

Then `linkThroughPoint`:

- a container registration (`di-binding`, decided by `boundImplementation`);
- an interface with ONE implementation and no extending interface implemented (`interface-redirect`);
- an abstract class (`ClassInfo.abstract`) with ONE concrete class below it (`interface-redirect`);
- else the declared type's own or inherited member (`injection`);
- else the ONE interface method the type — or one of its `ClassInfo.extension` parts, which never stands as the type's declaration — implements (a trait's default method).

A redirected/bound call also emits a `reference` link to the interface method so the interface keeps its callers. Name-classified `database`/`api-call` calls resolve ONLY through this tier.

**Module-level and local typing.**

- A module-level binding types a call where the function reads it (Python's manifest sets `moduleLocalsInScope`; per-language detail in [Python](../extractors/plugins/python/AGENTS.md)): a function that rebinds the name lists it in `FunctionInfo.boundNames`, `scopedName` skips the module's `<setup>` local for it, and a name the function binds itself is never read through the file's `moduleBindings`.
- A bare name no local, parameter or field takes reads the file's `moduleBindings` (typed, or `from` an initializer call typed by its callee's declared result), then — where the manifest's `directoryNamesShared` says a directory is one package (Go) — those of its sibling files and its siblings' functions.
- `<setup>` is made for a module that only declares typed variables (`let ticket: SeasonTicket;`).
- A local typed through a module the file imports (`m.Club` after `import league.models as m`) takes the class that module's file declares (`moduleQualifiedType`, from `ImportInfo` specifiers, aliases and source — never the leaf name's namesake).
- A local typed by its initializer call inside a function written in place (a held callback, `<watch@12>`, `<kit.action@4>`) is typed by the call the function around it writes, innermost first, resolved in that function's scope (`importedFunctionLink`).
- A held noise member (`c.Status.String(`) called through a path from a typed head is restored (`restoreTypedReceiverCalls`); front ends that name a path from a local by its whole path let the linker type the local (`localTypes`) and follow the fields ([Go](../extractors/plugins/go/AGENTS.md)).
- Where includes share scope, a member defined out of line in another file (`methodBesideClass`) is scoped by the caller's include closure ([C++](../extractors/plugins/cpp/AGENTS.md)).
- A call the syntax makes (`CallInfo.syntax`: an attribute assignment, operator or index) is linked only through the receiver's declared type or the enclosing class — never by a guess of its name — in `resolveCallToDefinitionBody`, as a `mapMember` call is ([Ruby](../extractors/plugins/ruby/AGENTS.md)).

**Link metadata and special reads.**

- **Every link carries `strategy`** (`SymbolLinkStrategy` in `types/analysis.ts`) naming which tier produced it, and `relation` naming what kind of edge it is; both are set at each construction site and `relationForStrategy` derives the second from the first.
- The final per-caller-and-name dedupe keeps the highest-confidence link at the EARLIEST `sourceLine` either record gave it (two passes list one name in no fixed order); the target never moves.
- **Passed names.** A name handed on rather than invoked (`CallInfo.passed`: a callback argument, a JSX attribute value `onClick={saveClub}`) links as `relation: "passes"` (`resolvePassedName`), only to a function, method, class or a module's default export and never through a name-only guess (`unique-global*`, `type-argument`). A factory's whole result handed on passes the factory; a name destructured from it passes what the factory returns under that key (`CallInfo.returnedAs` on the factory's `passed: "return"` names) or nothing. Reach, screens, trace and impact dependents follow it; sequence diagrams, param-columns/param-origins and arity checks skip it.
- **Reads without parentheses** (`CallInfo.read`: Pascal `N := ACar.Shine`, `if qry.IsEmpty then`) are linked by `resolveReadName` only when they resolve without guessing to a function or method — `calls` when that returns a value, `passes` when it is a procedure (`OnClick := btnSaveClick`) — or to a construction. A field, variable or class read draws no edge, and `classifyCalls` never makes one a database or API call. A property whose getter is a method (`PropertyInfo.readAccessor`) answers in the symbol index with that method, so `ACar.Points` lands on `TCar.GetPoints`.
- **Schema classes.** No strategy lands on a schema's class (`declaresSchemaTypes`: an API contract's schemas and messages, a SQL table, a Prisma model — kept out of the symbol index, its exports and the type catalogs), so a bare `update` never reaches an OpenAPI fragment `update.yml`.
- **Guards of heuristic tiers:** same sub-project only, never into test-fixture paths, the registry's `builtinMembers` stoplist (`set.add`, `s.strip`), and the caller's own language's `untypedReceiverMembers` (`find_by`, `save`, `where` on a receiver nothing types: the framework's, not the one class defining the name).

**Symbol index, class-name tier** (no file of its own):

- A member marked `FunctionInfo.explicitInterface` never takes the class-qualified or bare name a same-named member of the class holds (`SymbolDef.explicitOnly`): a class-typed receiver reaches the public member, an interface-typed one the explicit implementation (`explicitImplementation`) ([C#](../extractors/plugins/csharp/AGENTS.md)).
- A call through a nested type's owner path (`Right.Builder.build`, three or more capitalized segments) resolves in `classNameMember` on the class declared inside the owner's body (class line ranges per candidate file), never a namesake nested elsewhere; a nested type with no such member and no bases refuses the call.
- Where a manifest sets `ownerPathTypes` a TYPE written through its owner resolves the same way, by `ownerPathIn` ([Java/Kotlin](../extractors/plugins/java-kotlin/AGENTS.md)). Both walks ask one lookup, `classesAtOwnerPath` (the non-synthetic owner, then each segment inside the previous one's lines).
- A third, separate mechanism — `nestedTypePaths` / `lexicalConstants` — names the class by its path in the class id/`typePaths`, so it needs no line-range lookup and stays apart until the class id carries a path for every language ([C++](../extractors/plugins/cpp/AGENTS.md), [Ruby](../extractors/plugins/ruby/AGENTS.md), [Perl](../extractors/plugins/perl/AGENTS.md), [Swift](../extractors/plugins/swift/AGENTS.md)).

#### reactive-triggers.ts — `SymbolLink[]`

A write to a reactive cell re-runs the callbacks watching it.

- Input: `FileAnalysis.reactiveCells` — the plugin scopes each cell (`<scope line>:<name>`, plus the member path written or read) to the component or class declaring it.
- Each write links the function writing to every callback on the same cell (a path leading into the other counts) as INFERRED `dispatch`, strategy `dispatch:reactive-trigger`, `callName` what the write spells (`setClubId`, `pickedClubs`). Never across files; a callback writing its own cell draws nothing.
- A trigger marked `immediate` also gets a link from the file's `<setup>` (callName `immediate`), written to or not; a component with no setup of its own gets the pseudo-function through `ReactiveCells.component`.
- A statement a template runs is a write too, by the component's `<setup>` at its line; the reader leaves each as a comment naming only the cells it writes, never the statement's text ([plugins/javascript/template-targets.ts](../extractors/plugins/javascript/template-targets.ts), `withMarkupExpressions`).
- Store-state facts: a watcher's reads are `storeWatch.watchers` on the factory `$vuex` with the path from the root state; `Object.assign(state, p)` or a computed member writes `""`, any member; read keys include `watch: { '$store.state.clubs.list': … }`, `...mapState('clubs', ['list'])` and an Options `computed: { total() { return this.page * this.size } }` (the `this.X` paths it reads).
- Across components and files the plugin states more facts and registers resolvers: props (`dispatch:prop-flow`, `dispatch:param-type`), Subjects (`JsSubjectResolver`, `dispatch:subject`), store state (`JsStoreWatchResolver`, `dispatch:store-watch`), Vuex (`dispatch:vuex-action`, `dispatch:vuex-state-watch`), composables, `toRefs` and computed chains. All of it is the JS plugin's; see [JavaScript](../extractors/plugins/javascript/AGENTS.md) for the rules and facts (`propFlows`, `subjectFlows`, `storeWatch`, `StoreShapes.root`, `foreignMutations`, `getterReads`).

#### Dispatch-side data passes (in memory, before the data-access pass)

- [channel-factories.ts](channel-factories.ts) — adds in-memory `queue-publish`/`queue-consume` rows to callers' `dataSources`. A wrapper whose publish names its own parameter (`DataSourceInfo.channelParameter`: `clientSend(event, room) { server.to(room).emit(event) }`) publishes, at each resolved call handing it a literal there (`CallInfo.args`), on that channel — before the data-access pass and the broker hop.
- [channel-topics.ts](channel-topics.ts) — scopes Phoenix channel events by topic; fills MQTT `${…}` holes; joins MQTT publishes to `+`/`#` filters | `scopeChannelTopics` retargets an event that states more than one topic; `resolveMqttTopicHoles` fills known holes in an MQTT `target` from the file's string constants and the module-value lookup (unresolved holes stay); `joinMqttTopicFilters` repeats a publish at every covering filter — a hole level matches `+`.
- [entity-parameters.ts](entity-parameters.ts) — adds in-memory `database` rows to callers' `dataSources`. A helper whose statement queries the model one of its own parameters holds (`DataSourceInfo.entityParameter`: `def model_count(model): select(func.count(model.id))`) reads, at each call resolved by an EXTRACTED or INFERRED link that hands it a class the project declares as an entity at that position (`CallInfo.args`: `model_count(Club)`, or by keyword — `model_count(model=Club)`, reported as `model=Club` after the positional arguments), that entity — every call of the name in the calling function, since the linker keeps one link per caller and callee. A function that hands its own parameter on to such a helper (`def total(model): return model_count(model)`) is a helper of that parameter too, up to three levels; a non-entity class, a local or a parameter nothing hands on binds nothing. A loop over a literal or a module-level constant of classes is a row per listed class ([Python](../extractors/plugins/python/AGENTS.md)). Runs beside the channel factories, before the data-access pass.
- [mixin-self.ts](mixin-self.ts) — `captureMixinReceivers`, `bindMixinSelfAccess`: adds in-memory `database` rows to callers' `dataSources`. A mixin's access on its own receiver (`DataSourceInfo.mixinSelf`: a bare `update!` in a Rails concern's method) is the table of the class the call runs on. At each call resolved by an EXTRACTED or INFERRED link whose receiver the linker typed (`SymbolLink.viaType`, captured before `moveInheritedCallsToSubclasses` drops it) as a class the project declares an entity, a row of the same access at the call site names it (`handler` = the route for a route's own call). A call on the caller's own instance from a class that is no entity (another method of the mixin) hands the rows on to the caller; an untyped receiver binds nothing — the table is never guessed from the includers.
- [foreign-bindings.ts](foreign-bindings.ts) — `SymbolLink[]`: calls across a generated language bridge.
  - A plugin's `foreignBindings(root, read, files)` reads a generator's configuration at each sub-project root into `ForeignBindingRule`s: the implementing files, the module path each is written to (usually gitignored, so absent), how importers spell it, the naming rule and the generator's attribute.
  - Each call through an import of such a module — its prefix (`as contracts`, `* as w`, a local bound to `await import(…)` or to a module loader's awaited result), a name it brings into scope, or the module a call loaded in place names as its `target` (`(await import("./pkg/club")).listClubs()`, `(await loadClub()).listClubs()`) — links EXTRACTED, strategy `dispatch:foreign-binding`, to the public function the rule binds under that name; the linker's guesses for the same call (a namesake method elsewhere) are dropped.
  - A rule whose `decorator.classes` is set also binds the classes carrying the attribute (with their constructor, `constructorArgument`, and the methods carrying it), and a call joins a method through a receiver the file types (`new (await wasm()).SquadIndex()`, `index.search()` on a typed local or parameter, `this.index.search()` on a typed field, `(await this.index).search()`, `Module.create()`): the class resolves by import, namespace, or the one bound module the file loads, and a same-named class the file declares or imports from elsewhere is never taken. A name two files of one module bind joins neither. Generator specifics: [Rust](../extractors/plugins/rust/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Dart](../extractors/plugins/dart/AGENTS.md).
- [typed-receivers.ts](typed-receivers.ts) — per-file pass, mutates calls. `restoreTypedReceiverCalls` brings back member calls `extractCalls` held back as noise by leaf name (`repo.find`, `notifier.send`) when the receiver has a declared, non-builtin type in scope, or is itself a type: a static call `ClubStore.find(…)` / `Club.new` on a capitalized, non-builtin head no name in scope spells (where imports bind names, only a class the file declares or imports), and a bare `send(…)` (where members need no `this.`) / `this.send(…)` when the enclosing class or a same-file base declares that method. Runs before `classifyCalls`. The linker decides whether the project declares the class, and a name-classified `database`/`api-call` call on a class the project declares resolves through the class-name tier (`project-call-data-sources.ts` then drops the `db-write` it made). Also `declaredSupertypes` (extends/implements minus ORM relation targets, which entity extractors list in `implements`) and `sameTypeSpace`.
- [inheritance-edges.ts](inheritance-edges.ts) — component-graph edges: implementation → interface / subclass → base for supertypes no import names (same namespace/package), resolved unambiguously (own sub-project, closest by directory, else globally unique in the type space; a qualified base — `base.Club`, `models.Car` — through the class index, never a namesake beside the class). An interface's blast radius includes its implementations.
- [client-proxies.ts](client-proxies.ts) — api-call rows for calls through REST client proxies: a receiver (field, constructor/method param, typed local) whose declared type — qualified through the file's imports, or the one registered type of that name — a registration marks `proxyOf` becomes `{ contract: { type, method }, baseRef: client }`. The URL usually lives in a shared API jar the repo does not contain; the route linker joins the call by contract. Inputs: `httpClientRegistrations`, classes/functions, imports.

#### data-flow-reach.ts — `symbolReach`, `dataFlows`

Reverse BFS per (effect, resource) from each direct DB/queue/api-call effect over the symbol links.

- **Type-parameter tables.** A read whose table is a class type parameter (`DataSourceInfo.entityTypeParameter`: `_database.Query<TModel>` in `BasicRepository<TModel>`) is bound first: a call inside the class keeps the parameter; a link's in-memory `typeArgs` (set by the linker from the receiver's written type, a subclass's closed base or a route owner — unified through a base both share when the call lands on an implementation) moves it to the caller's own parameter or ends it at the first caller naming a type, which seeds an ordinary effect at that distance with the hops below it. An unbound caller ends nothing.
- **Usage gate.** A walk back through a dispatch to a component's user (`SymbolLink.viaUsage`: an emit, callback-prop call or dialog close, tagged by the plugin with the parent's binding site) continues only into the files binding it there.
  - A file using the child (importing it, rendering it — a plugin states every tag of a child some tag binds an event on as a `dispatch:renders` `(reference)` link —, calling into it through a template ref, binding any of its events) leads out through its own bindings only — none when it binds that event nowhere.
  - A tag spreading props or listeners into it (`{...props}`, `v-bind="$attrs"`, `v-on="$listeners"`: `dispatch:renders-open`) states no binding and keeps taking every one; a subclass of the child, or a file with no sign of using it, leads out through every binding.
  - `usageGate` in [symbol-graph.ts](symbol-graph.ts) holds one level of context; the MCP trace walk, its `to=` path search, `clarifydoc seq` (the diagram, and the tree `--diff`/`--lock`/`--check` compare) and the screen-spec export use the same gate forward. Per-framework detail: [JavaScript](../extractors/plugins/javascript/AGENTS.md).
  - So a page rendering a shared dialog never reaches another page's handler through it. The dialog's own symbol still reaches every binding (blast radius and the MCP walks are context-insensitive), but a data flow of the dialog's SCREEN lists only what its own code reaches: an effect reached only through a bound emit or callback is `ReachedEffect.viaBinding`, sorted after the symbol's own effects so `EFFECTS_CAP` never drops them, and left out of the screen's flows. Each parent's screen keeps the effects its binding brings in — a handler the parent imports or takes from a hook or composable included, since the tag that binds it is the parent's own link to it, reached with no binding state. The screen-spec export refuses a bound edge on a walk still in its start file and gives a control that hands its work to the parents' handlers no reach of its own.
  - Blast radius and the trace impact stay context-insensitive (an over-approximation is the safe side of "what may this change break"), but a dispatch link is no dependency: the component graph (`enrichGraphFromSymbolLinks`, hence cycles, dependents, communities) and the component launches leave `viaUsage` links out, so a shared dialog neither closes a cycle with nor opens dialogs for every page using it.
- **Routes.** A route's flows are its own symbol's reach — a route symbol that links somewhere and reaches nothing reaches nothing — and a route whose symbol links nowhere falls back to the function around its line only when the route is declared ON it (`declaredOn` in [api-route-symbol-links.ts](api-route-symbol-links.ts): the handler names it, or the route sits on its first line), never the function registering it (a `main` that also migrates and schedules). The cross-tier anchoring uses the same rule.
- **Route identity.** `RouteInfo.registrar` (the function whose body declares a route operation, [Go](../extractors/plugins/go/AGENTS.md)) is part of `routeIdentityKey`, so two registrars declaring one templated path keep two rows, and of the route's symbol (`routeSymbolName` in [route-symbol.ts](route-symbol.ts): `route:GET /items @registerClubs`) — every core site naming a route's symbol goes through it, so two registrars of one file never share a symbol, reach or data-access row. `routeAnchor` (the call-graph symbol of a routeMap row, used by `clarifydoc_explain`, `clarifydoc_sequence`, the role reader and the flow lock) takes the row's `registrar` too: a registrar's row anchors on its own `@registrar` symbol only and any other row on the unsuffixed ones.
- **Middleware reads.** What a router's middleware reads at request time is the route's: a plugin lists the functions its registration names (`RouteInfo.middlewareCalls` — the middleware of the route's own group only), the symbol linker resolves them as it resolves a handler (a link from the route's own symbol), and a flow whose witness leaves the route through one carries `viaMiddleware`.
  - A middleware a function-mounted route inherits from its mount site (`api := r.Group("/api", auth.Required()); clubs.Register(api)`) is `RouteInfo.inheritedMiddleware` — the names with the file each mount is written in, which the linker resolves in THAT file (its imports) and re-anchors on the route's own symbol.
  - A name the file's import binds resolves through that import (`resolveMiddlewareName`), never by a leaf name guessed across the project. A dependency's callable reads what it reads whether or not its name says it checks the caller.
  - Global guards a bootstrap registers (`app.useGlobalGuards(new HeaderGuard())`, the `nest-global-guards` fact) give every API route of that sub-project the guards as middleware/auth, with `inheritedMiddleware` naming the bootstrap file so each guard method resolves through its imports. Sources per framework: [Go](../extractors/plugins/go/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Python](../extractors/plugins/python/AGENTS.md).

#### sequence.ts, sequence-frames.ts, sequence-order.ts — Mermaid `sequenceDiagram`

Served by `clarifydoc seq` and `clarifydoc_sequence`. On demand, never stored.

- Links give what each call reaches; the order and the repeats are read off the function's source (`sequenceReading` → `SequenceOptions.sources`), since the extractors keep one call row per callee and the linker one link per caller and callee.
- `callSitesIn` finishes a call where its parentheses close, so `save(build(make()))` is make, build, save and a chain runs left to right. Every site of a name that has one link is drawn; a name with several links takes the site on its own line; `await` marks the call it introduces; a link no site matches keeps its line.
- Frames come from the CFG (`Cfg.regions` — a `try` with its `catch`/`finally` starts — drawn as `critical` + `option`; `CfgNode.column`/`endColumn` split a one-line `if/else` into `alt`/`else`). A frame uses columns only for a function whose sites were read, else lines.

### Value resolution and service origins

#### module-values.ts — `ModuleValueLookup`, `resolveTargetRefs`, `resolveRouteTemplates`

`ModuleValueLookup` is `ProjectContext.moduleValue`: the string value a name stands for in a file, followed into the module that defines it.

- Plugins report `FileAnalysis.moduleValues` (top-level string values by name) and the reference as written (a `${…}` hole in a URL or route prefix, `DataSourceInfo.targetRef`). The pass resolves it in the file, through an import binding (named, aliased, namespace), through a package import naming a directory (`importsNameDirectories`: the one directory the import path ends with, by `import-directories.ts` — the component graph's rule) or in the caller's own package (`directoryScope`), and a name an import puts in scope without binding it (a static import's type, a package wildcard's files).
- A dotted `Head.member` no import or scope reached (an alias path the resolver cannot follow, as in `@Controller(RouteKey.Club)`) is filled from the ONE module of the caller's sub-project whose value table has that head (`headTable`). A head two modules declare, or only another sub-project does, fills nothing. When an import names that head, its source's last segment may match the owner's file stem case-insensitively (`Paths` → `paths.ml`).
- Family-scoped; test files never feed production code; two values decide nothing.
- Used for api-call URLs (`resolveSymbolicTargets`), queue targets, route paths a plugin writes as `RouteInfo.pathTemplate` (`resolveRouteTemplates`: a value nothing states is never guessed away — unknown leading segments leave the tail under `prefixUnresolved: "constant:…"`, any other unknown hole stays in the path, named in `pathUnresolved`, and the route never joins a call nor counts as uncalled) and, by a plugin's route resolver, route prefixes.

#### call-origins.ts — mutates `apiCalls[].origin`

Also rebases the target and drops `baseExpr` once the base is known. The service a call reaches:

1. **Reference:** absolute/loopback URL → client registration → plugin `baseRefOf` of `baseExpr`. A hole host (`http://${IP}:5000`) is read by its port only, INFERRED.
2. **Values:** the caller's deployment `urlEnv`, then config; the code's fallback only when neither states one.
3. **Host** via the address book.

One project from every value = EXTRACTED; two = AMBIGUOUS, none chosen; no project = `external` — except a base valued only by the code's fallback literal (`CallBaseRef.fallback`) whose host no address, deployment or `listen` URL names and no third party owns, which keeps the unresolved base (INFERRED, the fallback in the evidence; a known third-party host still marks it external).

Then **forwarding**: the project a request arrives at (its origin, or its own project for a same-origin call) applies its longest matching `ProxyRule` (dev proxy, gateway), up to four hops; a rule whose target is no service here changes nothing. Inputs: `httpClientRegistrations`, `deployment`, config values, service addresses, `serviceConfigFor`.

#### config-values.ts

Per sub-project, the address-valued entries of every plugin's `serviceConfig.sources` and the forwarding rules of its `proxySources`.

- For a key a config file says variables override (`ConfigEntry.envNames`), the entry is kept even with no URL value, so call-origins' `envNamesOf` reads the caller project's own names.
- `urlValue` drops non-addresses and strips credentials (a `serviceName` entry — the name the project registers under in discovery — is kept as written); sensitive files are never opened.
- Config values stay in memory; rules persist as `proxyRules`.
- `readRouteBases`: every entry of those files to the plugin's `routeBaseOf`, per sub-project.
- Inputs: `CONFIG_SOURCES`, `ROUTE_BASE_SPECS`, `isSensitive`.

#### service-addresses.ts — `ServiceAddress[]`

`serviceAddresses` + `resolveHost`: compose/k8s service names and aliases, published host ports, `listen` URLs. A loopback host resolves by port only; several projects on one name resolve to none.

#### route-bases.ts

Mutates `analysis.routes` (in memory, after router mounts, before the symbol linker): a project's configured base in front of its complete API routes of the plugin's languages, `RouteInfo.basePath` saying where it is set; a `prefixUnresolved` row keeps its tail. `stateLocalPaths`/`dropUnchangedLocalPaths` bracket the mount and base passes so an API route composed under a mount or base carries `RouteInfo.localPath`, the path its own router wrote (never set by a plugin; the route linker's added-base tier and search's below-base alias read it before the conventional list).

#### module-search-paths.ts

`applyModuleSearchPaths`: a bare import two files of a language answer to (`uses Garage` beside `Win/Garage.pas` and `Posix/Garage.pas`) is rewritten to the file the project's build files mean — a file they name for the module, else the one in the project's own directory, else the first search directory holding one. Read at each sub-project root through the manifest's `moduleSearchPaths` (`pathImportsPin` says where a program's own `uses X in 'path'` pins); before the import index, in memory only. Build-file spellings: [Pascal](../extractors/plugins/pascal/AGENTS.md).

#### compilation-database.ts

`loadCompilationDatabase`: the manifest's `compilationDatabase` (paths a CI wrote are matched to discovered files by their longest tail) → per translation unit its include directories and macros.

- `placeIncludes` rewrites an include to the file the compiler's search order finds first (before the suffix fallback; in memory only). A file compiled twice with different results, and headers, keep the generic rules.
- `macrosOf` (the macros every unit agrees on) goes to the parser front end with the task, stamped into the incremental `resolver`, where `preprocessor-branches.ts` picks the live arm of a conditional — only for macros whose state is known, the file's own `#define`/`#undef` counting where every conditional around it is known taken.
- Format and flags: [C++](../extractors/plugins/cpp/AGENTS.md), [C](../extractors/plugins/c/AGENTS.md).

### Parameters and contracts

#### param-origins.ts — `ParamOrigin[]`

For each `${slot}` that is a whole path segment or query value of an API call's URL — and each `{slot}` of a generated SDK operation whose descriptor spreads its own parameter (`DataSourceInfo.pathValues`: `{ url: '/clubs/{id}', ...options }` takes `options.path.id`) — where its value starts: a screen's route parameter or query value, a literal, or `unknown`.

- **Walk.** Back from the call's enclosing function through its callers' `CallInfo.argOrigins`, by parameter name and, for an object argument, the property (`field: "path.id"`); eight deep, sixteen per slot; a dispatch link ends the walk. A call the symbol linker records twice (in a function and as a hook callback's data source) is one site, the record naming no function of the file left out; a destructured parameter binds its own name, never an outer binding of it.
- **Props.** A component's `prop` origin goes on to the URL value the route rendering it hands that prop (`RouteInfo.propsFromRoute`) and to the value each parent's markup binds it (`FileAnalysis.propBindings`, the tag resolved among the files the parent imports, a barrel's re-exports followed to the file that declares it, `throughBarrels`, three deep).
- **Derivations.** A value the plugin states is derived from a known one (`CallArgOrigin.derivation` / `PropBinding.derivation`) keeps that origin with the steps in `ParamOrigin.derivation`, INFERRED: a property of a record read off a collection the value keys (`clubStore.clubs[props.clubId].id`), what a function returns for it with literals beside (`getSeasonIdFromClubId(props.clubId)`; a function step only when its call links to a project function), or a member of what a composable returns for it (only when the function the call links to states how that member derives from that parameter, `FunctionInfo.derivedLocals`; its own steps, read in its file, follow). A query-library result is one such member (`query.data[.value][.prop]`). A record handed whole — or spread into an object literal (`{ ...club.value, name }`) — stands for the property a mutation callback takes; a record in a URL slot is `unknown`. Framework spellings: [JavaScript](../extractors/plugins/javascript/AGENTS.md).
- Also reports the backend route parameter it binds (segments aligned from the end of the joined route).
- Inputs: `CallInfo.argOrigins` (plugin `calls.argOriginsOf`), `propBindings` (plugin `ast.propBindings`), `symbolLinks`, `apiRouteLinks`, routes, screens, `componentGraph`.

#### param-columns.ts — `ParamColumn[]`

The backend half: each API route parameter (`RouteInfo.params`, binding route/query) followed forward to the entity, field and access of the statement that filters on it.

- **Starting points.** The route's own calls (a request read, `CallInfo.argOrigins` `route-param`/`query-param`); the handler's parameter of that name (`RouteParamInfo.variable` when the handler names it otherwise — `@PathVariable("id") Long clubId`) or its own request read (hop `arg: -1`), including a field of a parameter whose declared type a binder fills (`PropertyInfo.boundFrom`); a callee the framework hands the route's parameters by name (`CallInfo.routeParamsByName`, and the dependencies that one asks for in turn); any other function the route runs reading the request itself (a `before_action` callback); and, for a handler built for a type it binds the request into (`RouteInfo.handlerTypes`), each of that type's methods the route runs, as the field the binder writes the parameter into.
- **Carriers.** A field slot through `receiver-field` / `param-field` origins, the receiver handed on whole (`receiver`, at index -1 for a call made on it) and composite literals' fields (`CallArgOrigin.field`; written in place or a local built from one). An object handed to a generic handler that calls a method on it (`DoUpdate(ctx, obj CObject, a)` → `obj.Update`) goes on through the call site's `interface-redirect` link to that type's method, its field now the receiver's. A `request-param` origin (`params[:id]`, path and query merged) matches either binding.
- **Through calls.** Entities a later project pass settles are filled in after it by `fillParamColumnEntities`, over the symbol links through the calls that hand it on (`argOrigins` `param`). An argument given by name (`CallArgOrigin.param`) lands on the callee's parameter of that name and is the only kind followed through a dispatch link; an extension method's receiver parameter is skipped; of overloads the link's target line picks one and it is followed only when the declared types agree.
- **Statements that filter.** `DataSourceInfo.whereFields` (a column compared to the value: `where: { … }`, `findOneBy({ … })`; named-query `col = :name`; derived queries and `@Query` placeholders; a generic repository's column parameter, `whereFields[].fieldParam`, is the string literal the call just walked through hands that parameter, and a key no call states as a literal gives no row) or `DataSourceInfo.whereObjects` (a filter on a whole object the field slot names: a bean read into, less the fields written first, `except`; the field carried in it is the column, unless a `whereFields` row of the statement already names that value's column). A struct member is settled to its column first — the mapper's tag of the struct, found beside the statement before a same-named one elsewhere, else the mapper convention (`whereFields[].fieldOf` until the entity pass rewrites `field`, `whereObjects[].columns` read here). Detail: [Go](../extractors/plugins/go/AGENTS.md), [Python](../extractors/plugins/python/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [C#](../extractors/plugins/csharp/AGENTS.md), [Java/Kotlin](../extractors/plugins/java-kotlin/AGENTS.md).
- Six calls deep, 32 rows per route; a call the linker did not resolve ends the walk.
- Shown in `clarifydoc_contract` ("parameters filter on") and FLOWS.md ("Parameters filter on").

#### project-dependencies.ts — `ProjectDependency[]`

Sub-project → sub-project runtime edges: `http` (cross-project `apiRouteLinks`) and `bus` (`mq` symbol links), each with its endpoints (capped, most-linked first), confidence counts, and the compose/k8s edge that states the same pair (`links: 0` = deployment only, no call found). Test callers and AMBIGUOUS links never make an edge — the same rule as the trace edges, so this graph and Call Traces agree. Inputs: `apiRouteLinks` (with `sourceProject`/`targetProject`, set by the route linker), `symbolLinks`, `deployment`.

#### contract-check.ts — `ContractFinding[]`

`contractFindings`: on each EXTRACTED `apiRouteLink`, the body the call states against the route.

- `missing-field` / `unknown-field` / `type-mismatch` on `requestBody` vs a closed `requestSchema`.
- `unknown-response-field` when `responseReads` names a field a closed `responseSchema` lacks.
- `missing-expected-response-field` when `expectedResponseFields` (required closed members of the call's expected response type — a typed generic client call, a typed `json()` local) names a field that schema lacks.
- Open schemas (`additionalProperties: true`) and INFERRED links stay quiet.
- Inputs: `apiRouteLinks`, `apiCalls` (`requestBody`, `responseReads`, `expectedResponseFields`), `routeMap` schemas.

### Screens and navigation

#### rendered-views.ts

`ScreenInfo.renderedBy` (+ `routePath` where none): the GET route whose handler (or a function it calls, two deep) renders a template screen by name — a render-named call's first string argument, a `template`/`view`/`page` field, a returned string; only a name that resolves to exactly one other-language screen by path suffix. Data flows then give the page what its route loads. Inputs: `symbolLinks` (route synthetic symbol → handler), raw source of the handler spans. Controller-template conventions come from a plugin's `templatePaths(name, fromFile)` ([Elixir](../extractors/plugins/elixir/AGENTS.md), [PHP](../extractors/plugins/php/AGENTS.md)).

#### screen-navigation.ts

Adds to `ScreenInfo.navigatesTo` the navigation of the components of OTHER files a screen builds, four files deep, never through another screen.

- Each name in a component's `builds` resolves to the one component another file declares under it (the imported one first, then the one of the sub-project; production never into tests). A parameter's default widget (`defaults`) counts only when the builder leaves the parameter out (`passes`).
- What a component hands a navigation helper (`navigatesVia`: `openPage(context, ClubPage())`) is navigation when a file declares that function one (`FileAnalysis.navigationHelpers`: it pushes the widget it is handed) — the imported declaration, else the sub-project's, else the analysis's one ([Dart](../extractors/plugins/dart/AGENTS.md)).
- Languages where every component file is already a screen of its own do not need it; the screen-specs export composes them.
- Inputs: `FileAnalysis.uiComponents`, `navigationHelpers`, the component graph.

#### server-redirects.ts

`RouteInfo.redirectsTo`: the app paths an API route's handler redirects to.

- The literal of a redirect-named call, a `"redirect:/x"` view, or a `Location` header (a concatenated tail `"/x/" + id` reads `/x/{}`).
- Or a name (`url_for`/`reverse`, `RedirectToAction("A", "Ctl")`, `action:`) resolved first to the route registered under that name (`RouteInfo.name`, e.g. `as:`, `.as()`, `->name()`, `Name =`; a framework's path helper only ever by name — a stated one, else the name the framework derives, `RouteInfo.derivedName`; a route-by-name redirect such as `toRoute` or `CreatedAtRoute("…")` reads the same `Name`), else to the one route whose handler has it (same file first, controller beside it).
- Only the handler's own body; a function holding several routes is cut at the next route.
- Per-framework spellings: [Ruby](../extractors/plugins/ruby/AGENTS.md), [PHP](../extractors/plugins/php/AGENTS.md), [C#](../extractors/plugins/csharp/AGENTS.md).
- Inputs: `symbolLinks` + raw source through [route-handlers.ts](route-handlers.ts), shared with rendered-views.

#### screen-flow.ts — `ProjectAnalysis.screenFlow`

The navigation map: page and dialog nodes (+ `path:` nodes for client routes that only redirect), starts (main form, the screen at `/`, a redirect from `/`), edges typed `navigate` / `dialog` / `redirect` / `server-redirect` / `submit`.

- **Edges.** `submit` (a form post — a post to the page's own route is a `submit` self-edge `POST /path`, the one self-edge kept —, or a route's own `leadsTo` (Web Flow transitions, through action/decision states, a subflow to its start view). Screens match a target by its path as written first (flow states carry `#`), then by key.
- **Shells.** What no screen uses but a component rendering the language's router outlet frames (manifest `routerOutlet`, a regex on the UI file's source) hangs off that component as a `shell` node, a start. `linksFromBase` marks languages whose bare links are app-root paths. A route's `shell` (a router's shell-route builder widget, [Dart](../extractors/plugins/dart/AGENTS.md)) is a shell node and start; a `tab` route (a branch's first) gets an edge from it. A component most pages of a sub-project include (`FRAME_PAGES`/`FRAME_SHARE`) is their frame, a `shell` node.
- **A screen is the sum of what makes it up:** components it renders (by import, or by name in its own sub-project or one it uses), its code-behind class, `codeFiles` and the `viewModel` it binds (`addViewCodeNavigation`). A component's links and dialogs count for every page and dialog that imports it, however deep, never through another screen nor through two non-component modules in a row, over the import graph as it was before call edges joined it; a launcher module's own rows are skipped.
- **Scope.** A link target resolves within the screen's sub-project or one related by imports/calls (`related`): two apps' pages are no targets of each other; a shared library component's unresolved link resolves in the app of the page rendering it.
- **Link reading.** Comments are blanked before reading. Every screen's own file is read for links (plugin-authored screens included). Link helpers (`href="@CarLinks.Url(car)"`) are followed into the URL the function builds (`urlTemplate`), else its app-path literals (`resolveLinkHelpers`) — a path table's member (`paths.app.club.getHref(id)`) by its qualified name in the file it is imported from, in `navigate(…)`, `to={…}` or a nav item's `to:`. A base-URL prefix before a link's path (`{{AppSubUrl}}/x`, `${…urlBase}/x`, a context path) is dropped (`BASE_URL_PREFIX`).
- **Named routes.** Links by route name (`route('clubs.show')`, `{% url 'clubs:detail' %}`, `{ name: 'clubs' }`, `ui-sref`, a URL helper like `url('cars.show')`, Ziggy `route()`) are `route:<name>`, resolved through `RouteInfo.name` — for navigation targets and for interactive-element requests, whose GET links are navigation and whose other requests submit. Screen-table rows keep their `name`.
- **Ambiguity.** A link to a path two screens answer opens the page, not the layout rendering the outlet, and not an empty screen (a SPA's mount document). A file routing itself (an HTML page) that a route table also routes is one screen; a template made only of the partials it includes is a page (`includedFile`).
- **Per-framework link spellings** (hash routes, router-link arrays, `goto`, component `to=` attributes, `~p` sigils, helper object members, external-template screens, `componentTags`): [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Elixir](../extractors/plugins/elixir/AGENTS.md), [Blazor](../extractors/plugins/blazor/AGENTS.md), [templates](../extractors/plugins/templates/AGENTS.md), [XAML](../extractors/plugins/xaml/AGENTS.md). MAUI routes (XAML `<ShellContent Route>` under `<TabBar Route>`, C# `Routing.RegisterRoute`) are read there too.
- Navigation targets are read in `extractNavigationTargets` (analyzer.ts): link elements, anchors to app paths, `router.push`/`window.open`/`location` with literals, concatenations (`"/x/" + id` → `/x/{}`), interpolations, a URL variable a navigation call takes, and an item property a link binds (`:to="link.ref"` → the file's `ref:` values).
- A concrete path matches the route with the most literal segments; `route:<name>` targets resolve by `RouteInfo.name`, in the caller's own sub-project first — a name it states, then the name its framework derives (`RouteInfo.derivedName`) — and only then another sub-project's, so another project stating the name never hides the caller's derived one (`canonicalNavigationTargets`, and screen-flow for elements).
- The Screens tab draws it. Inputs: screens, routes (`redirectTo`, `redirectsTo`), `componentLaunches`, interactive element requests, the component graph.

A spec suite describing a type (`TestFunctionRow.subject`, `FunctionInfo.testCase.subject`) in a test file that holds at least one case marks the files declaring a class of exactly that name tested: a mixin the spec prepends onto an anonymous class, or a callback class a framework runs, has no written call. Exact full name only (no leaf or namespace guess), within the spec's own sub-project, never for a file a test replaces with a double; a spec without cases never counts. ### Quality passes

- [blast-radius.ts](blast-radius.ts) — `BlastRadiusInfo[]`: downstream dependents, exported-symbol usage, plus `contextBurden` (the two-hop neighbourhood in BOTH directions with a line/token estimate — what must be read to edit the file safely). Input: reverse graph from componentGraph; `FileAnalysis.lineCount` for sizes.
- [complexity-analyzer.ts](complexity-analyzer.ts) — `FileComplexityInfo[]`: per function cyclomatic, cognitive (branch + nesting penalty, `else if` continuations exempt, callbacks deepen), nesting depth, parameter count. Input: tree-sitter AST (per-file); the plugin `complexity` spec (`branchNodes`, `logicalOps`, `nestingNodes`).
- [control-flow.ts](control-flow.ts) — `Cfg`: one function's control-flow graph, built **on demand** and never written to `project-summary.json` ([control-flow-file.ts](control-flow-file.ts) is the per-file entry point, [control-flow-mermaid.ts](control-flow-mermaid.ts) renders it).
  - Input: the same `findBodyNode` the complexity analyzer uses, plus the plugin `controlFlow` spec (node type → role).
  - Two gates in `control-flow.test.ts`: `cyclomaticFromCfg` must equal `computeComplexity` (sharp, but sees only what the complexity table counts), and `undrawnStructure` must come back empty (table-independent — required because a complexity table can name node types its grammar lacks, so every function reports 1 and the arithmetic can never fail).
  - Tree-sitter languages are built exactly. A language with no grammar goes through [control-flow-regex.ts](control-flow-regex.ts) instead — a line scanner that synthesizes the same node shapes for the same interpreter, gated by measuring it against the parser where both exist.
  - A plugin's `sourceView` may reduce the text first; the C family's is `firstBranchView` (preprocessor-branches.ts: dead blocks blanked, then only the first live arm of every conditional — the ANTLR readers' choice — since the arms are alternatives of one build, never code run in a row; see [C++](../extractors/plugins/cpp/AGENTS.md)).
- [pattern-detector.ts](pattern-detector.ts) — `PatternInfo[]`. Inputs: classes, functions, imports; a file's function counts (the god-object threshold) skip `synthetic` members and functions — generated code is no code the file writes.
- [responsibility-profile.ts](responsibility-profile.ts) — `ResponsibilityProfile[]` per file: boundaries touched (database, http, queue, auth, logging, …), workflow roles, concern count, read/write/publish/serve flags with evidence. Input: imports classified through the plugins' `knownPackages` tables + dataSources/routes/screens; core names no package.
- [security-scanner.ts](security-scanner.ts) — `SecurityIssue[]`. Input: raw source text (regex-based).
  - A non-raw rule's match that starts inside a literal the plugin says is data (`securityInLiteral`) is dropped; a private key header with no key material in the next lines (a form's placeholder) is none; `eval` never matches a method or function declared under that name, nor a test file.
  - A hardcoded-secret finding is its kind and location, its snippet masking every string literal with a fixed `********` (no characters of a value). A value equal to its own name folded for case and separators (`API_KEY = "API_KEY"`) is no secret.
  - `isSecretConstant` is the one predicate (a known key format, or a credential-named constant whose value is no placeholder, endpoint or namespaced identifier); `dropSecretConstants`, run by `analyzeFile`'s `store`, removes such entries from `stringConstants`, `moduleValues` and class `fieldValues` before the per-file JSON is written.
  - A value judged by its name alone that is a letters-only word under 16 characters (`const TOKEN = 'pitch'`, a container key) stays in the JSON.
  - A plugin whose `securityPreprocess` blanks strings states its assignment rule `raw`; a finding whose value is prose or a namespaced name (`isKeyShapedValue`) is dropped as the constant is kept, and a linter's inline suppression comment silences hardcoded-secret only (`suppressionOf`) ([Python](../extractors/plugins/python/AGENTS.md)).
- [duplication-detector.ts](duplication-detector.ts) — `DuplicateGroup[]`: structural fingerprinting; a `synthetic` (generated) function is never compared.
- [layer-analyzer.ts](layer-analyzer.ts) — `ArchLayer` map + violations. Inputs: file paths + componentGraph; `.clarifydoc/config.json` `layers`/`exempt` overrides are consulted before the path heuristics (tests stay exempt first).
  - A file importing its neighbour in the same folder is none; into its own folder's subtree a file sits at the higher of its own and its folder's layer, so `routers/api.py` mounting `routers/clubs/` is the routers folder using its parts; `router/` and `routers/` folders sit with `routes/` at the top.
  - `layerEvidenceAll` (what a file does: API routes, entities, queries, templates — declared facts, never imports) → `fileLayerAlternates` (its other layers) and `fileLayerConflicts` (placed by path or name where a strong fact disagrees).
  - Team `rules` (`detectRuleViolations`): `noCycles` walks the runtime import graph (type-only / lazy `import()` edges dropped).
  - `clarifydoc rules init` ([rules-init.ts](rules-init.ts)) drafts those rules from the folder dependency matrix at `--depth`: per folder "stays below its dependents" (the folders that import it, directly or not) and, for a cycle group, "stays out of its cycle". It prints the diff; `--write` merges by rule name (never overwriting) and writes `.clarifydoc/baseline.sarif` for `analyze --baseline`, so only new drift fails.
- [refactor-pressure.ts](refactor-pressure.ts) — `RefactorPressureInfo[]` per file: 0–100 composite of complexity, size, mixed concerns, coupling and churn, band, drivers, fired gates, confidence (= share of signal available). Inputs: complexity, blastRadius, responsibilityProfiles, fileChurn, layerViolations, componentGraph cycles; thresholds from `DEFAULT_REFACTOR_PRESSURE_CONFIG`, overridable in `.clarifydoc/config.json` (`project-config.ts`).
- [dead-code.ts](dead-code.ts) — `analyzeUnusedCode` → `generatedRoots` + `unusedFiles` (codegen/vendored trees nothing outside imports); `analyzeReachability` → `deadCode` (authored files no entry point reaches, exports nothing imports). Inputs: componentGraph + symbolLinks + each language's plugin `reachability` model (entry points, module resolution).
  - A barrel counts as codegen only if it is not a package's public entry and its tree is self-contained (<3 project files outside it).
  - Reachability walks from **anchors**: manifest/convention entries, scripts a page loads, serverless/SAM handlers a descriptor routed onto (`resolvedBy: serverless-handler-anchor` or `entryPoints` with framework `sam`/`serverless`), and a file a deployment runs — a Procfile process (`procfileEntries`, [dockerfiles.ts](dockerfiles.ts)) or a compose/Dockerfile command (`DeployedService.entryFile`) — through `ReachabilityInput.deployEntries`, its reason used only where the language model gives none. Then **passive roots**: tests, fixture/example/bench dirs, ambient `.d.ts`, generated code, tool-run files, other languages' files, unreadable files' directories.
  - A project is anchored PER LANGUAGE MODEL; one no anchor reaches is skipped, not reported whole.
  - Edges: the component graph, the model's import resolution, re-exports, path references, template tags, NAME references (for models with `declaredNames`: every reachable file's text is tokenized once and any identifier a judged file declares reaches it — comments and strings included, so over-matching only keeps code alive) and compilation units (`unitOf`: a Go package is reached whole).
  - An export is judged only when every way into its file names what it uses — namespace/dynamic/glob imports and unexplained edges mark the whole file used — and names are followed through re-export chains.
  - Each unused-export row carries `confidence` and, when any apply, `reasons`: `own-file-only`, `re-exported` (a barrel forwards it and nobody asks the barrel), INFERRED; `name-referenced` (another file uses the bare name with no import that resolved) or `unresolved-imports` (the project has local imports naming nothing analyzed), AMBIGUOUS. `analyze --min-confidence` and `clarifydoc_health`'s `minConfidence` filter dead-code rows by it (`atLeastConfidence`; a row written before it counts as INFERRED).
- [health-scorer.ts](health-scorer.ts) — `HealthScore`, model `rates-v2`: each dimension is a RATE over N = max(50, authored non-test files) (files in cycles, god objects, long files, files with >10 non-test importers, severity-weighted security per distinct file+category, duplicate groups, files with layer violations, files holding a function over complexity 20), deducting `cap · r/(r + rHalf)`. Caps and `rHalf` live in `HEALTH_MODEL`, calibrated on an open-source corpus. Penalty reasons keep the keywords the Health tab routes on. Inputs: all other analyzers + Tarjan SCC for cycles.
- [suggestions-engine.ts](suggestions-engine.ts) — `Suggestion[]` from all other analyzers.

## Per-file analysis & workers

- [file-analyzer.ts](file-analyzer.ts) — `analyzeFile(task)`: read + parse + run all extractors + write the per-file JSON. Pure per-file logic with no pipeline state, so it can run on any thread.
- [analyze-worker.ts](analyze-worker.ts) — worker_threads entry that wraps `analyzeFile`. Built as its own tsdown entry (`dist/analyze-worker.js`).
- [worker-pool.ts](worker-pool.ts) — `AnalysisWorkerPool`, generic over its task.
  - Spreads per-file analysis across cores for projects ≥200 files (override with `CLARIFYDOC_WORKERS=<n>`, `0` disables); falls back to in-process analysis when workers cannot start. The in-process path (<200 files) has no deadline.
  - A worker that dies on a file (out of memory, or killed past the per-file deadline, `CLARIFYDOC_FILE_DEADLINE_MS`, default 180 s, `0` off) costs that file, never the run: it settles as `FailedFile`, lands in `ProjectAnalysis.failedFiles` with the reason, and a fresh worker takes the queue. The file is never re-run in-process, where it would end the process.
  - The query-in-loop pass hands the pool the files whose control-flow graphs it needs ([loop-shape-batch.ts](loop-shape-batch.ts), from 200 files on; fewer are built in-process).
  - **Heap bound.** While a pool runs it sets V8's `--heap-growing-percent` (50, `CLARIFYDOC_HEAP_GROWING_PERCENT`, `0` off; left alone when the process was started with one): every worker has its own heap, and V8's throughput headroom — up to 4× what survived — made eight workers on large files hold several times what they used. A run with no pool (under 200 files, `CLARIFYDOC_WORKERS=0`) sets the same bound for the whole analysis (`boundInProcessHeapGrowth`, lifted when `analyzeProject` ends; a pool that ends restores it rather than V8's own), at a small cost in user CPU (parallel GC threads) and equal wall time.
  - **Shrinking.** When the files are read the analyzer stops the idle workers beyond the four that write the held output (`shrinkTo`); otherwise the pool keeps eight heaps and their grammars alive through the link passes.
- [unread-code.ts](unread-code.ts) — `summarizeUnreadCode(paths)`: code files no plugin reads, by extension. The list is `extractors/shared/known-code-extensions.ts` data minus the registry's claims (`UNCLAIMED_CODE_EXTENSIONS`). Discovery matches them in its own walk and returns paths only (`DiscoveryResult.unreadCode`, `.clarifydocignore` applied); vendored roots and minified names are dropped here; nothing is opened. Surfaces: `ProjectAnalysis.unreadCode`, `analyze`'s `Not read:` line, `clarifydoc_status`. An extension that is as often data (`.cbl` reading lists, `.cue`) stays off the list.
- [ignore-suggestions.ts](ignore-suggestions.ts) — `ignoreSuggestions(files, generatedRoots)`: the generated roots (dead-code's barrel roots) and vendored roots (`vendoredRoots`) that still hold analyzed files, with counts, largest first. `analyze --verbose` prints them as `.clarifydocignore` entries and `clarifydoc_status` adds the same lines (at most 3 roots); nothing when no such root exists.
  - Performance patterns (`query-in-loop`, `blocking-in-async`) are ordered widest reach first by `rankPerformanceByReach` (finding-entries.ts: the routes `PatternInfo.entries` names plus the screens blast radius's `traceImpact` says reach the file — `PatternInfo.reach`); only the performance patterns' slots are permuted, the set never changes.
- [feature-flags.ts](feature-flags.ts) — extraction paths switched by name, each with a default (`KNOWN_FEATURES`), through `CLARIFYDOC_FEATURES` or `analyze --feature` (`no-antlr`, `antlr:go`, `-antlr:lua`; the most specific name wins).
  - What differs from the defaults joins `EXTRACTOR_VERSION` in `extractorStamp()` (manifest.ts), so a run reading files another way never reuses cached JSON. A feature ships beside the path it replaces; `scripts/ab-features.mjs <project> --feature <name>` analyzes one tree with and without it and lists every disagreement with examples.
  - Two features, both on by default: `antlr` and `tree-sitter`. A regex language's `meta.antlr` reader, else its `meta.treeSitter` reader, supplies its functions and calls (`readWithParser` in file-analyzer.ts → `extractWithRegex(…, parsed)`); which languages have which front end is each plugin's own (ANTLR: [Go](../extractors/plugins/go/AGENTS.md), [Rust](../extractors/plugins/rust/AGENTS.md), [C](../extractors/plugins/c/AGENTS.md), [C++](../extractors/plugins/cpp/AGENTS.md), [Lua](../extractors/plugins/lua/AGENTS.md); tree-sitter: [Swift](../extractors/plugins/swift/AGENTS.md), [Dart](../extractors/plugins/dart/AGENTS.md), [Elixir](../extractors/plugins/elixir/AGENTS.md), [Scala](../extractors/plugins/scala/AGENTS.md), [Objective-C](../extractors/plugins/objc/AGENTS.md), [Haskell](../extractors/plugins/haskell/AGENTS.md)). A file the parser reads with syntax errors keeps the regex reading, and `FileAnalysis.frontEnd` says which reading a file got.
  - When the spec builds its own classes, `adoptParsedMembers` (regex-extractor.ts) gives a class method declared on a parsed function's line that function's calls and extent (keeping the class pass's signature), and puts a parsed function no class pass found in the innermost class around it — refusing when several same-named classes share that extent, so a parser's owner name cannot attach a member to the wrong class.

## Discovery & IO

- [file-discovery.ts](file-discovery.ts) — a glob walk by extension.
  - The `EXTENSION_MAP` is the source of truth for which extensions are analyzed.
  - **Every walk goes through [glob.ts](glob.ts)** (tinyglobby; user patterns from `--include`/`--exclude` go through it): it never follows links — a followed link let a scanned repo read outside itself (`leak.py -> /etc/passwd`) and turned one `src/loop -> ..` into every file repeated ~32 levels deep — and keeps `deep: n` meaning "at most n-1 directories below cwd", which every spec was written against.
  - Discovery asks for the links (`LinkedFiles`, a readdir that lists a link as a file and records it) and keeps a linked *file* only when it resolves to a regular file inside the (resolved) root; the rest land in `skippedSymlinks`.
  - Linked directories are never descended.
  - A new walk imports `glob.ts`, never the engine.
  - The walks of one analysis share their directory listings (`shareDirectoryEntries` in [../extractors/shared/dir-listings.ts](../extractors/shared/dir-listings.ts), held from the start of `analyzeProject` to its end): a run walks its tree a dozen times and more, and a walk over listings already read costs a tenth of one that reads them.
  - A listing is kept unfiltered — each walk prunes, ignores and records links for itself — so a file created during a run is not seen by that run's later walks; a walker of its own reads through `listEntries` / `sharedEntries` instead of `readdir`.
  - No walk enters a linked git worktree of a repository below its `cwd` (a directory whose `.git` FILE says `gitdir: …/worktrees/<name>` inside the walked tree — `git worktree add` inside a checkout made every route and symbol a twin); a submodule (`gitdir: …/modules/…`), a worktree of a repository elsewhere and `cwd` itself are read.
  - A walk can also `prune` directories (a predicate on absolute paths, applied to each listing before the engine sees it); discovery, sub-project detection and framework detection prune what `.clarifydocignore` excludes, so an ignored tree costs one check instead of a walk — on one working tree, ignored checkouts holding 1.1M files had taken discovery from 0.3 s to 35 s.
  - A plugin's `namedFiles` may start with `.` (Bash `.bashrc` / `.zshrc` / `.profile` / `.bash_profile`): discovery globs `**/.bashrc` with `dot` still false, so only those basenames are admitted — not every hidden file; `resolveTarget` / `resolveImportSource` match such a path as written before the leading-dot relative-module rewrite (`.graph` → `./graph`).
  - **Extension-less scripts** are admitted by their first line: a regular, unlinked, non-dotfile in the root or a `bin/`, `script/` or `scripts/` directory at any depth (below the default ignores, `bin/` lifted), whose name does not look like a credential and whose `#!` line — looking through `env` and its flags — names an interpreter a manifest's `shebangInterpreter` declares (`getLanguageForShebang`), is a file of that plugin's language (Ruby, Python, JS, Bash, Perl).
  - Only the first bytes are read to decide, a file over 512 KB is skipped, and executability is not required (a checkout without mode bits keeps the script; the `#!` line is the author's word).
  - Only a regular file is read as a script: a linked one in a script place lands in `skippedSymlinks` when it leaves the root or dangles (never opened) or when its target inside the root is a script (`refusedScriptLink`); a linked directory, or an inside link to no script, is no refusal.
  - The reachability models still read such scripts for the names they mention (`findShebangScripts`); they are analyzed files as well, so the two agree.
  - A caller holding one path asks the same rule without a walk: `isShebangScriptPlace` (where and how it is named, no read) and `shebangScriptAt` (that plus the `#!` line, or a proposed text) — freshness names a new script "added", the working-tree parse of a change (`analyzeWorkingFiles`) reads one, and git history counts a fix in an analyzed script as a fix in code.
  - A manifest's `pathScopedExtensions` (TypeScript: `.md`/`.mdx` under `pages/`) claims an extension only below a named directory and, through `packageJsonMatches`, only where the nearest `package.json` above the file matches (Astro, vite-plugin-pages, `@next/mdx` / `@mdx-js/*`) — discovery globs it and applies that gate (`pathScopedAdmitted`), `getLanguageForFile` answers by path alone, a README or a docs repo's `pages/` stays unread.
  - The registry refuses two plugins declaring one `shebangInterpreterNames` entry.
- [clarifydoc-ignore.ts](clarifydoc-ignore.ts) — `.clarifydocignore` / `.clarifydoc/ignore` in gitignore syntax, applied by every reader that walks the tree for its own files through `globUnignored` (compose files, Dockerfiles, Kubernetes, Terraform, CloudFormation, GitOps releases, CI pipelines, config and package manifests, Markdown for doc drift), so an ignored folder's stack never becomes a container; inherited up to the nearest project root — except an inherited pattern that covers the scan root itself (a parent's `/checkouts/` while analyzing `checkouts/x` made the scan empty); `loadIgnorePatterns(root, scanRoot)` keeps such patterns for sub-roots inside the scan.
  - Anchoring is decided in `parseIgnorePattern`, not while matching: a pattern with a `/` in it is fixed to the ignore file's directory (`/dist` leaves `src/dist/` alone), a slash-less one matches that name at any depth.
  - Last match wins, and a file CAN be re-included under an excluded parent — a deliberate divergence from git, pinned by a test.
  - `ignoredDirectories` is the walk-time view: a directory is pruned only by a pattern every path below inherits (an anchored prefix, an unanchored name) that no later `!` pattern follows, so pruning never changes which files come out.
  - `fnmatch` here is the only glob engine; `project-config.ts` shares it.
  - `loadIgnorePatterns` is read once per (root, scan root) while an analysis runs (`perRunAnswer` in `extractors/shared/dir-listings.ts`, emptied with the shared directory listings), so a `.clarifydocignore` edited mid-run is seen by the next run only; outside a run it reads every time.
- **Extension methods and scope** — a manifest's `extensionsNeedImport` (C#; needs `importsNamePackages`) makes `extensionMethodFor` in [symbol-linker.ts](symbol-linker.ts) keep an extension method only when its declaring file is in the caller's scope: same file, the global namespace, a `using` of its namespace, its own or an enclosing namespace, a `global using`, an imported project, or `using static` of its class (`extensionInScope`, built on `importsFile`). Languages without the flag link extension functions from anywhere in the type space.
- [framework-detector.ts](framework-detector.ts) — gathers `ProjectInfo` (package.json, pom.xml, build.gradle, …) per project/sub-project root and runs the plugin-contributed rules (`plugins/<lang>/frameworks.ts`, aggregated into the registry's `FRAMEWORK_RULES`). Produces `FrameworkDetection[]`, sorted by id; core knows no framework names.
- [deployment.ts](deployment.ts) — compose-manifest deployment topology (`ProjectAnalysis.deployment`): parses docker-compose/compose files with a built-in YAML-subset parser, classifies services (app vs datastore/queue/cache), matches app services to sub-projects (entrypoint dll / image tail / marker basenames), and derives service→service edges from env evidence (api-key handshake per file, connection strings literal-first, URL/issuer vars, bus/cache attachment). Powers the report's Context (C1) / Deployment (C2) architecture levels.
- Broker and cache URLs in the topology: in `deployment.ts` every URL of any scheme in a compose/k8s env value, and every bare `host:port` item (`addressesOfEnvValue`; accepted only on a port the broker or cache listens on — compose `ports` both sides and `expose`, a k8s `containerPort` and the ports of the Services selecting it (`RawService.servedPorts`, `K8sManifests.servicePorts`), else its image's default client ports `DEFAULT_SERVICE_PORTS` — whatever the key is named), is resolved to the service of exactly that host (compose name, k8s Service alias, `.svc` first label — `clusterServiceLabel`, shared with `resolveHost`) and judged by that service's kind: a queue gets a `bus` edge, a cache a `db` edge, anything else none; the one-queue guess for a service that merely mentions a broker applies only when no such edge was found.
- [read-text-file.ts](read-text-file.ts) — `readTextFile`/`decodeText`: the one reader of package manifests, build files and config files (dependency inventory, config values, framework and project detection, deployment, CI, Dockerfiles): UTF-8 with or without a mark, UTF-16 LE/BE by its mark (surrogates included), else UTF-8 — a `requirements.txt` from Windows PowerShell 5.1's `>` is UTF-16 LE. `readSourceText` is the source reading (file-analyzer.ts, manifest.ts's skip check): UTF-16 by its mark, else exactly `readFile(path, "utf-8")` (a UTF-8 mark stays for `normalizeSource`); a plugin's `sourceEncoding: "latin1"` keeps its own read.
- [manifest.ts](manifest.ts) — `manifest.json`, written by every run that writes (entries sorted, so two runs write the same bytes) and read only by `--incremental`: a plain run seeds it, and the loop-shape cache beside it, so the first incremental run after one reparses only what changed.
- [deploy-rejects.ts](deploy-rejects.ts) — `.deploy-rejects.json` beside the manifest: the candidate files the deployment readers (CloudFormation, Kubernetes, Terraform) opened and turned down by their text alone, kept by size + modification time and the extractor stamp, so a one-file `--incremental` run stats them instead of reading hundreds of YAML/JSON files. Only rejections are kept; a Helm template (its verdict depends on its chart) and any file that yields facts are read every run.
- [output-writer.ts](output-writer.ts) — writes per-file JSONs + `project-summary.json` (+ `lsp-enhancement.json` / `lsp-ground-truth.json` when LSP runs).
  - With a worker pool the per-file JSON is **not written where it is analyzed**: a file being created holds up the reads beside it, and creating files does not scale with threads (measured: eight threads creating 5,450 small files took longer than four, and reads beside them went from 0.15 s to 0.9 s a thread).
  - A task with `deferWrite` hands its JSON back as bytes (`FileResult.json`, moved, not copied); the analyzer holds them until the sources are read (or `CLARIFYDOC_HELD_OUTPUT_MB`, default 256, is held) and then gives them to four of the pool's now idle workers in batches (`OutputWriteTask` → `writeOutputFilesSync`), which write while the project passes run — a worker, because the main thread's event loop is busy in those passes and an async write needs it between every step.
  - The pool ends when the batches are written; the run waits for them before it writes the summary, and a file that could not be written is left out of the manifest so the next run analyzes it again.
  - A file is written first and its directory made only on a miss.
- [element-registry.ts](element-registry.ts) — the disk-I/O codec. `normalizeProject` (write) lifts repeated nodes into two registries — `elements[]` (symbol-level `file::symbol` ids) and `files[]` page_ids (a file's index, used everywhere a path was repeated); `denormalizeProject` (read) reverses it. In-memory shapes are untouched; all readers go through `denormalizeProject`. A round-trip test over every fixture is the regression gate — adding a path-bearing `ProjectAnalysis` field means adding it to `rewritePageRefs`.
- [context-docs.ts](context-docs.ts) — decision records (files under `adr/`, `decisions/`, `rfcs/` …, with their `Status:`), framing documents (ARCHITECTURE, GLOSSARY, DOMAIN …), schema dumps and the documents `.clarifydoc/config.json` `context` declares (kept inside the root); decision markers in comments (`WHY:`, `DECISION:`, `TRADEOFF:`, `RATIONALE:`, `REJECTED:`, `ADR:`); the analyzed files a document names (`governedFiles`) and which were committed after it (`judgeStaleness`, one `git log`). Read on demand by the MCP server, never during `analyze`.
- [stated-reasons.ts](stated-reasons.ts) — the reasons written down without a decision record: whole comment blocks that state a cause or purpose ("because", "so that", "to avoid", `since` only as a clause), in the language's `docComments` syntax, anchored to the function they sit above or in — licence headers, commented-out code and generated files left out; and the body paragraph stating one in each of a file's last 30 commits (`git log --follow`, or `-L` over one function's lines), bots and dependency bumps skipped. Labelled as stated reasons, never decisions. On demand only (`clarifydoc_context_docs file=`).
- [project-config.ts](project-config.ts) — reads `<root>/.clarifydoc/config.json` (optional, never fatal): per-repository `layers` (glob → ArchLayer, first match wins), `exempt` and `generated` globs, `context` documents, and `refactorPressure` thresholds.
  - Owners of a section resolve it (`resolveArchitectureOverrides`, `resolveRefactorPressureConfig`); unknown keys and bad values become progress warnings and defaults are kept.
  - `matchesAnyGlob` is the one glob test (ignore-file dialect; anchoring is read off the pattern, so a slash-less pattern also matches the bare file name and one carrying a `/` does not).
  - The analyzer loads it once, before the generated/unauthored filter, so `generated` globs reach every quality signal.
- [regex-extractor.ts](regex-extractor.ts) — thin dispatcher for regex-only languages. Real logic lives in `src/extractors/plugins/<lang>/`.

## Report

**One renderer, prebuilt.** The report viewer is a React app maintained outside this repository. `report.html` is that viewer built into a single self-contained file (react + d3 + dagre + css inlined, fully offline) with the payload JSON injected. This package carries only the built template; report features are written in the viewer, and rebuilding it refreshes `report-template.html`.

- `html-report.ts` — `generateHtmlReport` loads the prebuilt template from `html-report/viewer-assets/report-template.html` (committed; rebuilt from the viewer; mirrored into `dist/` by the root tsdown `onSuccess` hook) and swaps `__CLARIFYDOC_TITLE__` / `__CLARIFYDOC_PAYLOAD__`.
  - The payload embeds as **gzip+base64** (`encodeReportPayload`; ~10x smaller than inline JSON, no `<` so no HTML-escaping concerns); `standalone.tsx` inflates it in the browser via the native `DecompressionStream`.
  - Token replace uses a replacer *function* so `$&` cannot corrupt.
  - Also writes `report-data.json` (plain JSON, for consumers that serve the payload in slices) alongside `report.html`.
- `report-payload.ts` — `buildReportPayload(summary)` reshapes a (denormalized) `ProjectAnalysis` into the `ReportPayload` the viewer consumes; `loadReportSummary(dir)` / `loadReportPayload(dir)` read it from disk (with the `lsp-enhancement.json` merge). The payload carries `deferredFields` so a consumer that slices it follows the producer's list.
- `smoke.test.ts` renders a minimal report end-to-end and round-trips hostile payload content through the encoder.

## Adding a new analyzer

1. Create `src/core/my-analyzer.ts` exporting a pure function `analyzeMyThing(input): MyResult[]`.
2. Add the return type to [../types/analysis.ts](../types/analysis.ts) and an optional field to `ProjectAnalysis`.
3. Wire it into the `analyzer.ts` post-analysis section (step 4c).
4. Pass its data to `suggestions-engine.ts` if it should drive suggestions.
5. If the viewer should show it, add it to `report-payload.ts`; the tab itself is written in the viewer, which is then rebuilt into `report-template.html`.
6. Add exports to [../index.ts](../index.ts) if public API.

## Conventions

### Rules for core code

- **Pure functions** — no file IO except `output-writer.ts` and `html-report.ts`. Input is `FileAnalysis[]`, output is typed results.
- **Optional fields** — new fields on `ProjectAnalysis` should be optional so old `project-summary.json` files still load.
- **One import contract** — `import-index.ts` turns every import specifier into a file through one helper (`resolveSpecifier`), by the name the module exports (`ImportInfo.aliases[local]`, never the local alias), for both a language's own `resolveImport` and the generic path, and in `localFor` and `fileForSource` alike; an alias named like a sibling module never reaches it.
- **Progress reporting** — use the `ProgressReporter` class in `analyzer.ts`, not `console.log` directly.
- **BFS with index pointer** — never use `Array.shift()` for BFS queues (it's O(n)); use `let qi = 0; while (qi < queue.length) { ... queue[qi++]; ... }`.

### Impact: changed symbols and dependents

- **`changed-symbols.ts` / `impact-diff.ts`** — `parseUnifiedHunks` keeps new-side ranges on the Map (patch coverage) and records match ranges on `old`: deletes/edits as their old-side lines, a pure insertion as the line it follows (plus pure deletions on `deleted`). `symbolsInHunks` matches those against the stored analysis, so a function below a deletion is not judged at a shifted new-side line that lands in the neighbour above; a hand-built Map with no `old`/`deleted` still matches as written.
- **Dependents are charged by the member that changed.**
  - When the diff's lines are known, `computeImpactDiff` cuts `dependents` to the files that NAME what changed ([member-dependents.ts](member-dependents.ts): call and import-by-name links into a changed function; for a type touched outside its methods — `symbolsInHunks`' `classLevel`, compared before and after by `classChanges` — its usage kinds from the blast-radius `typeUsages`: a removed or re-typed member charges every user of the type, an added member of an interface or abstract type only what implements, extends or builds it, never what passes it on) and keeps the importer count as context (`narrowed.importers`, printed "naming what changed (N files import it …)").
  - The risk rating, tests, screens and routes read the narrowed list.
  - A file with a changed line in neither a function nor a type (`moduleOnly`), without line ranges, or a type whose comparison shows no member change keeps every importer charged.
  -  A file that hands a charged or changed module on whole (Python `from .x import *`, `export * from`; `starForwarders` in changed-symbols.ts, read from the per-file `exports` `*` rows) is charged with it, up the chain — only when the change takes a name away (a removed, moved or re-typed function, a type member that changed), never for a body edit; the module a star export names is the file the import index resolved it to (`ProjectAnalysis.starReexports`, file → source as written → file, built by `starReexportTargets` through `ImportIndex.fileForModule`), no path-word guess — a source with no recorded target in a summary older than the field is not followed and `StarForwarders.stale` becomes the limitation "re-run the analysis" (`STAR_REEXPORTS_STALE_NOTE`); `narrowed.members[].lost` marks a member whose name is lost (a `signatureChanges` row, a type member that changed), and `clarifydoc_blast_radius` takes `change` (member → removed/renamed/moved/retyped/body) and cascades only for a lost name — unstated is body, so no cascade; the CLI `impact` and the MCP tools both build `symbols` with `symbolsOfChange`; a git diff of pure deletions (no new-side range, only `hunks.old`/`deleted`) narrows like any other; a file the diff deletes (`+++ /dev/null`) is keyed by its old path with every old line on `hunks.old` (never the new-side Map, which patch coverage reads), and a range covering other functions whole names each of them, not only the smallest one it touches; lines directly above a function (a decorator) belong to that function, except inside a type and in a language whose plugin has no `moduleNames` hook.
  - `symbolsOfChange` builds the `symbols` option for the MCP tools and `impactOfContents` (a proposed edit).
  - A removed or re-typed function is `breaking` only for callers the change leaves alone (`signatureChanges` `edited`: a call on a line the diff edits, or the function calling itself, is rewritten with it), so a private helper folded into its one caller rates nothing; an edit inside the import block of a file that re-exports what it imports (`HunkSpans.reexports`, `ImpactDiff` `forwarded`) charges the importers that import a forwarded name (`filesImportingNames`) — the rest of its importers name nothing that changed.
  - A class gaining a field is charged like an interface gaining a member (`ClassChange.addedField`: what builds it); tests are looked for among everything importing the files that name the change, not only those files.
  - A hunk wholly inside the lines of a module-level name (`FileAnalysis.moduleNames`, Python assignments and JS/TS `const`/`let`/`var`: the statement, the comments above it, the blank lines below it) is an edit of that name — `symbolsInHunks` `bound`, judged before the import block, so a constant between two imports is a constant — and `boundReaders` charges the importers (from `componentGraph`) whose imports list the name, take the module whole (a namespace, a default, `import m`, `from p import m`: spelled by the module's own stem) or star-import it, following a re-export, a package `__init__` or an `index` one hop at a time (four deep); an importer with no per-file record stays charged.
  - Which import row reaches the file is not resolved, so a same-named import from another module also charges, and an importer with no row spelling the module (an edge no import states, a package `__init__`) stays; a value derived from the name in another file (`CAP = LIMIT * 2`) hands nothing on, and a line inserted right after a name reads as an edit of it.
  - A hunk no name covers (a decorator added above a function, an `if` block) still keeps every importer charged; a type with no usage record (a controller nothing names) still abandons the whole file's narrowing.

### Value flow

- **Value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass in `buildSymbolLinks`, after `handedParameterLinks`/`handedClientLinks`, before `abstractDispatchLinks`): a function value is followed from where it is named to the call that runs it, through locals, parameters, fields, lists and returns, in every language.
  - Facts: neutral and stated by a plugin (`FunctionInfo.valueFlow`, `FileAnalysis.moduleValueFlow`: `seed` / `copy` / `arg` / `result` / `return` / `invoke` over `ValueCell`s — a name and optionally a member; `this`/`self` is the receiver, a list or map element the member `[]`). Stated today by the JS/TS, Python, Java/Kotlin, C#, Go, Rust, C/C++, PHP, Ruby, Dart and Swift plugins; each plugin's own spellings (object literals, closures, blocks, events, struct fields) are in its folder's `AGENTS.md` — [javascript](../extractors/plugins/javascript/AGENTS.md), [python](../extractors/plugins/python/AGENTS.md), [java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md), [csharp](../extractors/plugins/csharp/AGENTS.md), [go](../extractors/plugins/go/AGENTS.md), [rust](../extractors/plugins/rust/AGENTS.md), [c](../extractors/plugins/c/AGENTS.md), [cpp](../extractors/plugins/cpp/AGENTS.md), [php](../extractors/plugins/php/AGENTS.md), [ruby](../extractors/plugins/ruby/AGENTS.md), [dart](../extractors/plugins/dart/AGENTS.md), [swift](../extractors/plugins/swift/AGENTS.md).
  - Core names the cells — a formal when the function's `params` list it, a local when its facts or `localTypes` bind it (an enclosing function's too), the file's module cell when module facts bind it or the exporting file's when it is imported; a member is the class's field (own, then bases that declare it) for `this`/a typed local, the module holder's otherwise, else a function-local cell.
  - Seeds resolve through `resolvePassedName` (never a name guess); the seeds and copies one held lambda states share a `lambda` id, and that lambda stands for at most four project functions plus held values it runs, counted once resolved (a library's name resolves to nothing and never counts), the whole group dropped above four; arguments bind to formals by written index (a leading `self`/`this`/`cls` parameter of a method is skipped) through the callees the ordinary links found at that call site plus what the solver finds itself, iterated to a fixpoint (inclusion-based, flow- and context-insensitive).
  - Every invoke site links to each function its cell holds — `value-flow`, relation `calls`, INFERRED for 1 to 4 targets, AMBIGUOUS for 5 to 32, nothing above 32 (the overflow poisons the cell and everything it feeds), never EXTRACTED, never production to test file, never a function written in place linking to itself (the solver ignores order, so `const old = x.f; x.f = () => old()` would; a named function handing itself on is real recursion and keeps its link); a spent work budget emits nothing.
  - Argument binding: a keyword or named argument is an `arg` with `name` binding the formal whose `ParamInfo.argumentLabel ?? name` it names (Python `callback=f`, C# `callback: F`, Kotlin `callback = ::f`, Swift `callback: f`, Ruby `callback: method(:f)`, PHP 8 `callback: $this->f(...)`, Dart); a `**kwargs` formal or an unknown name binds nothing, never by position.
  - Name tiers: a call a plugin marks with an `invoke` fact is not resolved by the name tiers (`LinkContext.invokeSites`, `valueFlowInvokeSites`) when its cell is a parameter or a seed or copy writes it, so a namesake cannot take it; a plain name only a call's result writes, or nothing (`const reload = debounce(load)`, `useCallback(…)`), keeps a link into its own file only, and a member no seed or copy writes anywhere (`this.model.apply()` on an object field) keeps its ordinary resolution, as does a dotted path rooted at a name the file imports (`kit.Bench.label()`), which the name tiers resolve exactly; a `boundLocally` call counts as an invoke of the cell it names.
  - A cell flagged `module` (`ValueCell.module`) is the file's own module binding even when written from a function that binds no such name; an invoke site whose call carries `CallInfo.via` (a local a project factory made) still runs the name tiers, so its factory link stays beside the value-flow one; an `arg` fact may carry `name` instead of an index (a Dart named argument binds the formal of that name), and a member read through a property of the enclosing class (`widget.onSave`, a State's widget) keys on that property's declared type.
  - A cell name that is no binding but a project class names that class's own members (a C struct type's ops table, a static member); a dotted name (`c.ops` + member `sign`) walks property types before the member; a function writing a global it does not declare states it as `{ name: X, module: true }` in every plugin, the one way to name a module binding written from a function.
  - Two sibling scopes of one member (top-level blocks, blocks of a method) declaring the same local are two cells (`h@<first line of the scope>`, by the line of each fact; two blocks written on one line stay one).
  - A name another file of the package declares is a `ValueCell.package` cell joined to the one sibling that binds it (`ValueFlowHost.sharedModuleFiles`); a function writing a global it does not declare is a `{ name: X, module: true }` cell in every plugin.
  - **`ifFnType`.** An `invoke` fact — and a C `copy` of a parameter into a field (`peer->free_fn = fn`, `fn` typed by a typedef another header may declare) — may carry `ifFnType` (a cell declared with a type name the file itself cannot judge); `scopesOf` drops it unless the host says it runs a function — `ValueFlowHost.isFunctionType(file, type)` for `ifFnType`, and `isCallableMember({ file, symbol, receiver, member })` for `fieldInvokes`; for a type name the linker answers (`functionTypeQuestion`) from `FileAnalysis.functionTypeAliases` (Dart `typedef`, Swift `typealias` of a function type) and the class index through the nearest scope that declares the name: the file itself, the files it imports (through barrels), its own sub-project, the sub-projects it imports as packages — where includes share scope (C/C++) the file's whole include closure and nothing beyond it, one pool of names across `.c` and the `.h` read as C++ (C `typedef R Name(args)` and `typedef R (*Name)(args)` are `functionTypeAliases`); alias only is a function type, class only or both a class (never a function), never a name pooled across sub-projects — so a field typed by another file's alias runs while one typed by a class of that name does not, and a dropped invoke neither links nor keeps the name tiers off the call. The nearest scope is searched in this order: the file, its imports, the packages it imports by name where a package is a directory (a Swift `import LeagueCore` is the SwiftPM target `Sources/LeagueCore/`; a C# namespace is none), its sub-project, the sub-projects it imports, then those its build references (`SubProject.references`, a .NET `ProjectReference`, no import line needed). A tree-sitter plugin states function-type aliases through `ast.functionTypeAliases` (`typedef`, `typealias`, a C# `delegate`). Per language: [c](../extractors/plugins/c/AGENTS.md), [cpp](../extractors/plugins/cpp/AGENTS.md), [csharp](../extractors/plugins/csharp/AGENTS.md), [dart](../extractors/plugins/dart/AGENTS.md), [swift](../extractors/plugins/swift/AGENTS.md), [java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md).
  -   A call `x.m()` through a field another file's class declares callable is no plugin fact: `fieldInvokes` (value-flow.ts) derives the `invoke` from the calls a function already holds — `x.m()` with `x` a local, a parameter or `this`, `m` a name some class declares a `PropertyInfo.callable` member under (`CallableQuestions.callableFieldNames`, built once per run) and no plugin invoke stated at that line — when the host's `isCallableMember` question (`callableMemberQuestion` in the linker) says yes: it types the receiver with the linker's own `receiverDeclaredType` (`this` is the class the scope is written in), finds the class with `locateClass` from the caller's file (own import, sub-project and include closure first), then its bases by `parentClassOf`, three hops, and says yes only for a `PropertyInfo.callable` member — a method of that name, a data field and a namesake class of another sub-project or outside the caller's includes never run a held value and keep the name tiers.
  -  Plugins state facts and resolve nothing; the pass costs nothing when no file states any.

### Field writes and thrown types

- **Field writes and thrown types** ([member-effects.ts](member-effects.ts), `ProjectAnalysis.fieldWrites` / `thrownTypes`): who assigns a field and who throws an exception class, resolved to project classes by declared types only and only within the writer's language family (a TypeScript `throw new Error` never meets a Go `Error` struct).
  - Plugin facts: per function what it assigns (`FunctionInfo.fieldWrites`: `member`, `receiver` as written — `this`, `this.<field>`, a parameter or local name that carries a declared type, "" for a bare field — and line; never from an untyped receiver, nested non-arrow functions and local classes left out) and what it throws (`FunctionInfo.throws`: the type as written with its qualifier, the `throw new T` / `raise T` site, and `declared` for a signature's throws clause or a docblock `@throws`; a rethrown variable states nothing). A constructor (named or factory, `init`, `def this`) initializes and states no writes; a member the type's body declares without writing it is stated once as an `init` declaration so core knows it, and core never lists it as a writer.
  - Languages: writes in TS/JS, Java, Kotlin, C#, Python, PHP, Go, Ruby, Rust (a field behind `borrow_mut()`/`lock().unwrap()` or a `*self.x` deref), Dart, Swift, Scala, Objective-C and C++; thrown types in all of them but Go and Rust, which have none; Elixir states thrown types (`raise ClubClosed`, a module name through the file's `alias` lines) and no writes. Per-language spellings: [java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md), [javascript](../extractors/plugins/javascript/AGENTS.md), [python](../extractors/plugins/python/AGENTS.md), [php](../extractors/plugins/php/AGENTS.md), [go](../extractors/plugins/go/AGENTS.md), [ruby](../extractors/plugins/ruby/AGENTS.md), [rust](../extractors/plugins/rust/AGENTS.md), [cpp](../extractors/plugins/cpp/AGENTS.md), [swift](../extractors/plugins/swift/AGENTS.md), [scala](../extractors/plugins/scala/AGENTS.md), [dart](../extractors/plugins/dart/AGENTS.md), [elixir](../extractors/plugins/elixir/AGENTS.md).
  - Core decides the class from declared types only: `this` and a bare field are the enclosing class — or the base of its `extends` chain that declares the field, so a subclass's write is the base class's —, `this.<field>` goes through that field's declared type, a name through its parameter type or its one stated local type (no `choice`, no `soft`); a class name binds only where exactly one class of that name is in reach (own file, else sub-project, else project), so a namesake field of another class is never listed; a bare name must be a declared field of the class chain.
  - Qualified names (`java.io.IOException`, `requests.HTTPError`, `Net::ReadTimeout`, `std::runtime_error`, a field receiver typed `std::io::Error`/`*http.Error` — `writtenTypeName` keeps the qualifier `receiverTypeName` drops) bind by their last segment only through a qualifier the project backs (`qualifierBacksClass`): a namespace/package the class is declared in (`ClassInfo.namespace`, `FileAnalysis.packageName`/`declaredNamespace`), directories or a file stem on its path, a class its own file declares (a nested type, a Ruby module), or a name the writing file imports from that file or namespace (`import * as errors from "./x"`, `using Err = …`). A manifest's `relativeTypeQualifiers` (`crate`/`self`/`super`) name no module, and its `wholeTypeNames` stops core's lookup from falling back to the last segment (`File.Error` is never a project module `Error`).
  - Where a type is looked up: a language with `typesBeyondDirectory` looks a type up past its directory, the directory's declarations first, and refuses a qualified name or a name with several real declarations none of which the writing file owns; a language with `classNamesByEvidence` binds a name through the writing file's `use`/namespace ([class-evidence.ts](class-evidence.ts), shared with the symbol linker; a type written through a namespace path states `ParamInfo.typePath`/`PropertyInfo.typePath` beside the bare `type`); where a type spans a directory's files (`typesSpanFiles`) its parts are one type (`ClassRef.parts`) and a package-qualified type states nothing; a bare assignment of a package variable (`fieldWrites[].package`) becomes a `via: "package"` row only when exactly one file of the package declares it (`FileAnalysis.packageVariables`, `class` the package name; a module-level variable written through its module path is resolved with the language's own `resolveImport`, `moduleVariableHome`).
  - Rows hold names and `path:line`, skip tests and generated files, and exist only where something is stated. Reads (`propertyReads`) stay C#-only for the blocking-call rule; a property read edge is not built.
  - Surfaces: `clarifydoc_trace direction=writers` lists the writers of `Class.field` (or the throwers of an exception class) and `clarifydoc_explain` of a function shows "Writes and throws" (`mcp/tools/member-effects.ts`).

- **Config file → consumer** ([config-files.ts](config-files.ts), `ProjectAnalysis.configFiles`).
  - A plugin's `ast.filePathReads` states the files a call opens by a path of plain literals (`FileAnalysis.filePathReads`: the parts, the line, `anchor: "file"` for `__dirname`); a part that is not a literal states nothing.
  - `joinConfigFiles` resolves each beside the reader, then at the reader's sub-project root, then at the analysis root — the first that exists (an analyzed file, or a regular file on disk that is no link, no credential-looking name and not under `.clarifydocignore`), never by file name alone; a `..` that leaves the root, an absolute, `~` or URL path, a test reader and a target that declares functions or classes (code, not configuration) join nothing.
  - Rows carry the file, its project and the consumers.
- **Spec join beside a code twin.** A contract row (OpenAPI, …) whose method and normalized path exactly one production code API route also states joins by its operation id only, never by a name derived from its path (`spec-join`, `codeServes` in [symbol-linker.ts](symbol-linker.ts)): the pairing of the two rows (`pairContractTwins`) is the implementation, and a function that merely shares the derived name (a client wrapper `deleteClubs`) is a false link that also counts the row as implemented.
  - Both deciders count twins by ONE rule, `codeTwinsIndex` ([route-linker.ts](route-linker.ts)): method, normalized path, narrowed by the API version the contract row's path names (`/v1/` beside `/v2/` is one twin, not two).
  - The symbol linker's gate also asks it `loose`: where the exact path finds nothing, the code row under a conventional base the contract row leaves out (or carries), or behind a parameter the contract row spells as a literal (`/migration/{Name}/migrate`, two literal segments agreeing at least).
  - The parameter fill reads only the rows of the contract row's segment count and first named literal segment (buckets in the index), not every same-method row; the index returns the twin row itself, so the symbol linker's twin carries its `filePath` (no identity map).
  - The two deciders build their own index over their own code sets (the gate leaves tests and class-suffix files out) — a shared build would change which rows count.
  - With a twin, even the operation's own id joins only a function in the twin's file — a client's `register` sharing the id is not the handler (the handler-name and contract-type tiers still join the twin's real handler).
  - A row no code serves, or two code rows serve, keeps the full name join.
- **Vulnerable-function reach.** `analyze --osv` reads, where an OSV record states them, the functions an advisory names as vulnerable — Go's `affected[].ecosystem_specific.imports` (`ExternalPackage.advisories[].functions`: an import path and its exported symbols, from the entry naming this module only; ecosystems whose records carry no such data stay package-level and get no `reach`; the reading and the names a call through such an import is written with are the ecosystem's `PackageManagerSpec.advisoryFunctions`, Go's today, so core names no ecosystem).
  - [vuln-reach.ts](vuln-reach.ts) `attachVulnerableReach` then judges each in the post-analysis from facts every file already holds: a call `head.Symbol(…)` whose head is a name the file imports from that exact import path is a hit; the symbol links walked backwards (depth 8, never across an AMBIGUOUS edge) from the calling function to a route handler, an inline route body or an entry point give `reach.status` `reachable` (with `calls[].from` and the shortest `path`), else `called`; no hit is `not-called`, except an advisory that also names a method (`Type.Method`) — a package-qualified call does not name those — which is `not-judged`, never "safe".
  - A route's root is the one function it is declared on — [`routeHandlerKey`](api-route-symbol-links.ts), the rule `computeDataFlows` also uses (never the function that only registers it; a route carrying its own body's calls and no handler is no function), and, for a route registered inside another function, the handler's own name through `handlerKeyByName` (the one match in that file, else the project's one function of that leaf name — a method when the handler names a receiver; `routeHandlerKey`'s `registeredElsewhere`, passed by `computeDataFlows` too, and the same function resolves an entry point's handler) — plus each middleware the route names (`middlewareCalls`, `inheritedMiddleware`) that the route's own file declares by that plain name, as a root every request passes.
  - Test files are skipped.
  - The OSV fetch is injectable (`AnalyzeOptions.osvFetch`), so tests need no network; `clarifydoc_health`'s dependency listing prints the verdict.

## The pipeline, step by step

The ordered overview. Each pass has its rules in the section that owns it ("Analyzers (post-analysis passes)", "Discovery & IO", "Conventions"); per-language rules live in the plugin folders' `AGENTS.md` files ([javascript](../extractors/plugins/javascript/AGENTS.md), [python](../extractors/plugins/python/AGENTS.md), [java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md), [csharp](../extractors/plugins/csharp/AGENTS.md), [go](../extractors/plugins/go/AGENTS.md), [rust](../extractors/plugins/rust/AGENTS.md), [ruby](../extractors/plugins/ruby/AGENTS.md), [php](../extractors/plugins/php/AGENTS.md), [c](../extractors/plugins/c/AGENTS.md), [cpp](../extractors/plugins/cpp/AGENTS.md), [swift](../extractors/plugins/swift/AGENTS.md), [dart](../extractors/plugins/dart/AGENTS.md)).

1. **Discover files** — [file-discovery.ts](file-discovery.ts) (rules in "Discovery & IO").
   - A glob walk by extension through `core/glob.ts`, which never follows links; it skips credential-looking files and a linked git worktree inside the root (a `.git` FILE naming `…/worktrees/…`; a submodule stays).
   - A manifest's `packageRoots` (JVM `src/<set>/java/`) re-admits `target`/`out`/`bin`/`vendor`… below it as packages ([java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md)).
   - A generated file past 4 MB is skipped with its reason; a built webpack/Parcel/browserify/esbuild bundle is refused by the JS plugin's `preprocess`.
   - A folder `.clarifydocignore` names is out of every reader that walks the tree itself — deployment manifests, CI pipelines, config and package files, Markdown (`globUnignored`) — not only the source walk; `.gitignore` is not read.
   - Files under a vendored root (`third_party/`, `vendored/`, `public/**/plugins|lib`) — or carrying a copied single-file library's banner (SQLite amalgamation, nlohmann/json, stb…: the manifest's `vendoredBanners`, `FileAnalysis.vendoredLibrary`) stay analyzed but contribute no routes, screens, calls or data (`dropVendoredFacts`).
   - **Code no plugin reads** — a known code extension (`extractors/shared/known-code-extensions.ts`: `.sol`, `.elm`, `.tcl`, `.nix`, `.gd`, `.robot`, `.sv`…) minus every extension a plugin claims (`UNCLAIMED_CODE_EXTENSIONS`, so a new plugin removes its own) is matched by the same discovery walk and only counted, never read (`core/unread-code.ts`: outside vendored, ignored and minified paths): `ProjectAnalysis.unreadCode` (10 extensions, 3 example paths each), one `Not read:` line of `analyze` and a `not read:` line of `clarifydoc_status`.
2. **Detect frameworks** — [framework-detector.ts](framework-detector.ts) (package.json, build files). Manifests, build files and config files are read through `readTextFile` ([read-text-file.ts](read-text-file.ts): UTF-8 with or without a mark, UTF-16 LE/BE by its mark — a `requirements.txt` written by Windows PowerShell 5.1 lists its packages); a source file saved as UTF-16 is read by its mark (`readSourceText`).
3. **Detect sub-projects** — [project-detector.ts](project-detector.ts); every file gets a `projectId` (innermost enclosing project).
   - The marker files that make a directory a project (`**/package.json`, `*.csproj`, `Cargo.toml`, `build.sbt`, `sfdx-project.json`, …) are each plugin's `projectMarkers` on the static manifest (`ProjectMarkerSpec`: glob, `kind`, `priority` — the lowest wins a directory holding several kinds —, optional `isProjectRoot` predicate: sbt's `project/` meta-build skip, CMake's `project()` check).
   - The registry builds `PROJECT_MARKERS` and `PROJECT_KIND_PRIORITY` (a kind stated with two priorities throws); core keeps only innermost-wins and the pick; `SubProjectKind` is an open string (nothing outside the detector switches on it).
   - A manifest's `declaredProjects` hook makes the directories a build file names sub-projects too — an sbt `lazy val api = (project in file("api"))` — with `dependsOn`/`aggregate` read as `SubProject.references` by val name (a .NET `.sln` adds nothing: each `ProjectReference` is already one).
4. **Per-file analysis** — see "Per-file analysis & workers". Parallel; worker threads ≥200 files.
   - A worker that dies on a file (out of memory, the `CLARIFYDOC_FILE_DEADLINE_MS` deadline, default 180 s) is respawned and the file listed in `ProjectAnalysis.failedFiles`, never retried in-process.
   - While a pool runs V8's heap growth is bounded (`--heap-growing-percent=50`, `CLARIFYDOC_HEAP_GROWING_PERCENT`) and an ANTLR grammar's prediction cache is emptied past 10,000 states; a parser front end skips a generated file or one past 2 M characters (`frontEnd.fallback`).
   - Extracted: imports/exports, functions/classes, routes, data sources (with ORM `entity`), **ORM entities + relations**, data mutations, events, interactive elements, template tree, type references, complexity, security. When `--incremental`, unchanged files reuse cached JSON.
5. **Post-analysis** — one bullet per pass; the rules of each pass are in "Analyzers (post-analysis passes)" and "Conventions".
   - **Component graph** — imports, plus implements/extends edges no import states ([inheritance-edges.ts](inheritance-edges.ts)); an import of a package a manifest declares or of the standard library — Node's built-ins included — never binds a project file by the names it imports.
   - **Link graph** (proximity-weighted).
   - **Symbol links** ([symbol-linker.ts](symbol-linker.ts)) — call→def traces, **dependency-injection aware**: a call through an injected/typed receiver resolves on the receiver's declared type and, through `FileAnalysis.diBindings`, to the implementation the container builds (see "Teach a plugin a DI container" in "How to extend the core").
   - **Route resolvers** (plugin-contributed, cross-file route facts), joined before router mounts compose and before the symbol linker anchors routes: urlconf includes, router registrations, routes registered by a function on the router it is handed (`owner: "fn:<name>"` rows + `router-call` facts, composed by [plugins/shared/router-functions.ts](../extractors/plugins/shared/router-functions.ts) with each plugin's rule for which function a callee names), security-configuration rules on the routes they match, a chained `Router().use(a).use(b)` composed under the local mount of its variable, and guards a route inherits from where its router or controller is declared ([plugins/shared/class-guards.ts](../extractors/plugins/shared/class-guards.ts)).
     - A router function's routes take the guards of the site that mounts it: `RouteInfo.inheritedMiddleware`, resolved in the mount's file and joined as `viaMiddleware`. Express states `RouteInfo.middlewareCalls` too — a route's own middleware arguments and what an earlier `router.use(…)` of its receiver names, a name the file imports resolved through that import, never a leaf-name guess.
     - A route a registrar function declares (`RouteInfo.registrar`) is its own symbol `route:GET /items @registerClubs` (`routeSymbolName`), so two registrars of one file never share reach.
     - A filter or dependency is a guard only when its name says it checks the caller ([plugins/shared/guard-words.ts](../extractors/plugins/shared/guard-words.ts)).
     - Per language: [python](../extractors/plugins/python/AGENTS.md), [go](../extractors/plugins/go/AGENTS.md), [java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md), [javascript](../extractors/plugins/javascript/AGENTS.md), [csharp](../extractors/plugins/csharp/AGENTS.md), [ruby](../extractors/plugins/ruby/AGENTS.md) (FastAPI includes and settings prefixes, Go/Ktor router functions, Spring security rules, tRPC and Convex routes, ASP.NET conventional route tables, Rails prepended editions).
   - **Dispatch resolvers** (plugin-contributed): links the text has no call for.
     - A call landing on an abstract method → the one override below the class it dispatches on (`abstractDispatchLinks`; `ClassInfo.abstract`/`FunctionInfo.abstract`, abstract methods fan out like interface methods).
     - Frameworks' own dispatch: a mediator send → its handler, an AOP advice → the methods its pointcut matches (`dispatch:aop-advice`), an assembly scan → the handlers it registers (`cs:assembly-scan` facts, the project declaring the marker type), `AndroidManifest.xml` → each activity/service/receiver/provider it names, a MyBatis mapper method → its statement in the mapper XML ([java-kotlin](../extractors/plugins/java-kotlin/AGENTS.md), [springxml](../extractors/plugins/springxml/AGENTS.md), [csharp](../extractors/plugins/csharp/AGENTS.md)).
     - A Livewire `wire:click` → the component class's method ([php](../extractors/plugins/php/AGENTS.md)); a Ruby attribute assignment, operator or index → the setter or operator method the receiver's declared class gives (`CallInfo.syntax`, [ruby](../extractors/plugins/ruby/AGENTS.md)).
     - Browser-side: a template handler under a component scope → that component's member (`dispatch:scoped-handler`), component-emit → parent-handler (EXTRACTED when the child declares the event, refused when it declares only others), a call through a template ref → the child component's method ([javascript](../extractors/plugins/javascript/AGENTS.md)).
     - A manifest's `foreignImportTarget` (`foreignImportMember`) is the one link that crosses language families, by a type and member another language's files declare — a Lightning Web Component's `@salesforce/apex/Class.method` import → the Apex method; a bare call only, one declaring file only ([javascript](../extractors/plugins/javascript/AGENTS.md), [apex](../extractors/plugins/apex/AGENTS.md)).
   - **Stated local path** (`RouteInfo.localPath`, set by [route-bases.ts](route-bases.ts) around the mount and base passes, never by a plugin, omitted when equal to `path`): the route linker's added-base tier meets a call that leaves the mount out through it first — INFERRED, `base-prefix:<mount>`, only where one sub-project states that path — then the conventional list; `clarifydoc_search`'s below-base alias reads it before the list.
   - **Route identity** (`dedupeRoutes` keys a route on sub-project + method + path + declared API-version set, so the same endpoint in two services, or in a V2 and a V3 controller, stays two rows).
   - **JS/TS client resolution** — gateways exported as a factory's result (`ExportInfo.factoryOf`), RTK Query hooks, Kubb-generated clients, URL-builder resolution (`resolveProject` of the data-source extractor), `this.constructor` statics, a fact map read by own property only (`ownValue`, [extractors/shared/own-value.ts](../extractors/shared/own-value.ts)), named fetch options, Pinia stores, Vuex mutations and state watchers, reactive triggers ([core/reactive-triggers.ts](reactive-triggers.ts): a write of a reactive cell joins the watchers on it; Angular subjects, React props typed from the tags that render them, Nuxt auto-imports) — [javascript](../extractors/plugins/javascript/AGENTS.md).
     - Examples of what is stated there: `export default new Proxy(ClubApi(), …)` with a call `Gateway.closeClub()` reaching `ClubApi.closeClub`; Vuex `commit(…)` joining `mutations.<M>` as dispatch joins `actions.<A>`, and state watchers (`$store.state…`, `useStore().state`, `this.$watch('$store.state…')`, `store.watch(getter, cb)`, `store.getters['ns/name']`) joining the mutations that write that state; a component's write to store state (`store.x =`) as a store write; `toSignal(…pipe(cb))` listening to an Angular subject; a dispatch map imported from a project module and handed down as a prop (`FunctionPropBinding.mapImport`); a store picked by an IIFE `switch` on a prop (`(() => { switch (props.kind) { case 'club': return useClubStore() … } })()`) as a record keyed by the case literals.
   - **Scheme-hole URLs** (`finalizeApiTargets`): leading holes spelling `${protocol}://${host}[:${port}]` are an absolute URL of unknown origin, the path after it the target; a literal host after the scheme hole stays that host.
   - **Request wrappers** — a project method that hands its path parameter to a client and picks the verb from another (`ApiConnection().request(RequestType.POST, '/x')`, `$conn->request(Verb::DELETE, "/x/" . $id)`) is joined by core's `expandRequestFactories` from each call site's `FileAnalysis.pathArgCalls`, which may name the `receiverType` the method is looked up on and the `method` the site selects; regex plugins emit them through `RegexLangSpec.extractPathArgCalls` (the lookup is the "Wrapper index" in "Conventions").
   - **Client-proxy calls** ([client-proxies.ts](client-proxies.ts)) — a call on a receiver whose declared type a registration says is a REST client proxy (`HttpClientRegistration.proxyOf`, from a Spring XML factory bean / `<jaxrs:client>` or a `RestClient.createClient(X.class, url)`-style call) becomes an api-call carrying its `contract`, the interface operation `a.b.PersonApi#getPerson`; JAX-RS routes carry the same `contract` for the type that declares them.
   - **gRPC client stubs** ([grpc-clients.ts](grpc-clients.ts)) — a plugin's `grpcStubService` reads protoc's stub naming (`pb.NewOrderServiceClient(conn)`, `…_pb2_grpc.GreeterStub`, `OrderServiceGrpc.newBlockingStub`, `Greeter.GreeterClient`); a call on such a stub becomes an api-call at the rpc row's own path when the `.proto` is in the analysis, else with its `contract`.
   - **Call origins** ([call-origins.ts](call-origins.ts)) — The service each call reaches, followed through stated facts — an absolute or loopback URL, the client it is made through (`FileAnalysis.httpClientRegistrations`: typed/named .NET clients, `axios.create({ baseURL })`), or a base expression the plugin reads (`serviceConfig.baseRefOf`: `process.env.X`, `_config["A:B"]`).
     - Its values from the caller's deployment env (`DeployedService.urlEnv`) and config files ([config-values.ts](config-values.ts), `serviceConfig.sources`, URL-shaped values only, test profiles and sensitive files never).
     - The host through the address book ([service-addresses.ts](service-addresses.ts): compose/k8s names and aliases, published ports, `listen` URLs, the name a project registers under in service discovery — `ConfigEntry.serviceName`, Spring `spring.application.name` — which a `service` base ref such as `@FeignClient(name = "league")` resolves through, a name no project registers staying a host elsewhere, never a third party).
     - A project is named only when every value agrees, and a base valued only by the code's fallback literal whose host nothing here names and no third party owns keeps its unresolved-base link (INFERRED) instead of becoming an outside service.
     - Then **forwarding** — a request arriving at a project with a matching `ProxyRule` (a same-origin call at its own frontend's dev proxy: Vite/webpack/`setupProxy.js` via `meta.ast.proxyRules`, Angular `proxy.conf.json`/CRA `proxy` via `serviceConfig.proxySources`; a call whose origin is a gateway: YARP `ReverseProxy`, `ocelot.json`, Spring Cloud Gateway / Zuul routes in `application.yml` — `StripPrefix`, `RewritePath`, `PrefixPath`, `lb://name`) goes on to the rule's target, path rewritten, up to four hops → `apiCalls[].origin`, `proxyRules`.
   - **Route linking** ([route-linker.ts](route-linker.ts), `apiRouteLinks`) — Frontend api-call URL ↔ backend route by method + normalized path — the first of `target` + `targetAlternatives` that reaches a route.
     - Candidates are gathered across three tiers (the path as written, a conventional base stripped, one added).
     - An API-contract row (OpenAPI, … — `manifest.apiContract`) yields to the code row implementing it (`pairContractTwins`: same method + path, or the symbol linker's spec join).
     - A contract row exactly one production code route serves joins its handler by operation id only, never by a name derived from its path (see "Spec join beside a code twin" in "Conventions").
     - The twin serving the concrete `/api/v5/` the client names wins (`versions`, or a literal `/v1/` in the route path — `matchedVia: "version-mismatch"`, AMBIGUOUS, when none does).
     - A route serving another method is REFUSED, never a fallback.
     - Then code > contract > prefix-unknown, literal tier first, same sub-project.
     - A call with a `contract` joins the route declaring the same operation first (`matchedVia: "contract"`, no URL needed — the shared API jar states it; two such routes = AMBIGUOUS), falling back to its path.
     - A call whose origin names a project with EXTRACTED confidence joins only the routes that project serves (itself + what it imports, `projectServesClosure`) — a miss is `refused.originMismatch`, never another service's route.
     - An INFERRED origin only ranks them first.
     - Links from tests and generated code carry `sourceRole`.
     - `apiRouteLinkStats` counts links, refusals and unmatched calls.
   - **Handler params + request schemas** ([request-schemas.ts](request-schemas.ts)) — A route whose handler is declared elsewhere gets its `params` from that function's signature (`bindParam` hook) and body reads (`FunctionInfo.requestAccess`).
     - A body-bound parameter's class is then flattened through `extends` and mapped to JSON via the plugin's `requestSchema` hooks → `routeMap[].requestSchema`.
   - **Server redirects + the navigation map** ([server-redirects.ts](server-redirects.ts)) — `RouteInfo.redirectsTo`, the paths a handler redirects to.
     - [screen-flow.ts](screen-flow.ts): `ProjectAnalysis.screenFlow`, screens and dialogs joined by typed edges — navigate, dialog, router redirect, server redirect, form submit (a post to the page's own route is a `submit` self-edge, the one self-edge kept; a Rails view's URL-less POST form posts to the action that renders it implicitly, `erb/own-view.ts`) — from the main form or `/`, which the Screens tab opens on.
   - **Webhook routes** ([webhook-routes.ts](webhook-routes.ts)) — A route that reads a provider's webhook header, calls its verification or is an unauthenticated POST whose path says webhook gets `RouteInfo.webhook` — `provider`, and `verified` when its reach (inline calls, the handler's, followed by unique name three deep, guards and decorators) checks the signature by SDK, HMAC/constant-time compare, a guard named for it or a shared-token header.
     - `verified: false` only when every call in reach is known, and only then the `webhook-unverified` finding (CWE-345).
     - A webhook route is never "no call reaches".
   - **Click→data trace edges** ([api-route-symbol-links.ts](api-route-symbol-links.ts); an api-call joining a route whose handler is an action a mixin defines for several includers — a Rails concern — lands on that includer's own `route:` symbol, the row found by normalized path, so `{id}` and `:id` spellings meet);  and **value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass after `handedClientLinks`): a function value is followed through locals.
   - **Value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass after `handedClientLinks`) — a function value followed through locals, parameters, fields, lists and returns to the call that runs it; the rules are in "Conventions" → "Value flow".
6. **LSP enhancement** (optional) — resolve unresolved calls; writes `lsp-enhancement.json` + `lsp-ground-truth.json`. The Docker probe (`isDockerAvailable`: the endpoint the CLI would use — `DOCKER_HOST`, else the current context's `meta.json`, else the platform sockets — pinged with `GET /_ping` over its socket, so a stopped daemon answers at once; a `tcp://`, `ssh://` or unreadable endpoint gets `docker info` bounded to 1.5 s) starts before cross-file linking and is awaited here; a run where no language has a configured server never probes. Language-server containers run with `--network none` (`LspDockerConfig.network`, default; `dockerRunArgs`) except those whose server restores packages to type-check — Java (jdtls) and C#/VB (Roslyn) say `"bridge"`, as measured offline they lose most reference answers; `cli/SECURITY.md` states it.
7. **Advanced analysis** — one bullet per pass; the rules are in "Analyzers (post-analysis passes)".
   - **Quality and topology** — patterns, duplicates, layer violations, blast radius, communities/topology, **class graph**.
   - **Data-access graph** — message-queue publish/consume nodes and the rest of the data stores.
     - Queue nodes: AMQP, Kafka, pika, BullMQ/Bull, Socket.IO events, Phoenix Channels (`handle_in`/`push`/`broadcast` and the `phoenix` JS client, scoped by the topic both sides join — `core/channel-topics.ts`), Dapr pub/sub (the C#, Go, Python, Java and JS/TS SDKs — a publish and a subscription keyed by topic, each file gated on importing the SDK — and `kind: Subscription` YAML on the route it names), Celery tasks.
   - **Entity (ER) graph** — a schema an API contract declares is `origin: "contract"`, listed apart by `clarifydoc_data_model` and the viewer, and never covers a same-named table.
   - **External-package inventory** — with `--osv`, an advisory whose OSV record names its vulnerable functions (Go's `ecosystem_specific.imports`) carries `functions` and `reach` ([vuln-reach.ts](vuln-reach.ts)).
     - An advisory whose OSV record names its vulnerable functions — Go's `ecosystem_specific.imports` — carries `functions` and `reach`: `reachable` with the route or entry point — rooted at the route's handler by the data-flow pass's own rule, `routeHandlerKey` (a route registered inside another function, and an entry point, through `handlerKeyByName`), plus the middleware it names — and the shortest call path, `called`, `not-called` or `not-judged`,; Terraform registry module sources are `terraform` packages
   - **Deployment topology** from docker-compose, Kubernetes, Dockerfiles, Terraform and CloudFormation ([deployment.ts](deployment.ts)).
     - A candidate file a CloudFormation, Kubernetes or Terraform reader turned down by its text alone is remembered by size, mtime and extractor stamp in `.deploy-rejects.json` and not re-read by `--incremental` — [deploy-rejects.ts](deploy-rejects.ts).
     - A compose `build:` reads its Dockerfile's `CMD`/`ENV`, the build context names the project, `entryFile` is the source file the command starts — [dockerfiles.ts](dockerfiles.ts).
     - CloudFormation/SAM templates, YAML or JSON found by content, give the same nodes and the edges a template states — env `Ref`/`GetAtt`/`Sub`, SAM `Events`, event-source mappings, subscriptions, policy templates.
     - A logical id is local to its stack, a physical name meets the same resource in another template — [deployment-cloudformation.ts](deployment-cloudformation.ts).
     - any URL in a compose/k8s env value whose host is a deployed queue (`bus` edge) or cache (`db` edge) — judged by that service's kind, not a scheme list — and a bare `host:port` only on a port that service serves (compose `ports`/`expose`, k8s container and Service ports, the image's default client ports: `RawService.servedPorts`, `DEFAULT_SERVICE_PORTS`), whatever the key.
     - The `.svc` first-label rule is `clusterServiceLabel`, shared with `resolveHost`.
   - **Config keys** ([config-keys.ts](config-keys.ts), `configKeys`) — A key a config file sets and the code that reads it — Spring `@Value`/`@ConfigurationProperties` rows marked `configRead`, a Terraform `variable` block (`configKeyReads`) against the tfvars beside it.
     - A plugin's `serviceConfig.normalizeKey` states its relaxed spelling.
     - Spring `Environment.getProperty` on a typed receiver joins like `@Value`.
   - **Config files** ([config-files.ts](config-files.ts), `configFiles`) — A file the code opens by a path of plain literals — Java/Kotlin `File`/`Paths.get`/`Path.of`, Python `open`/`Path(…).read_text()`, JS/TS `fs` reads and `path.join(__dirname, …)` as their argument — stated as `FileAnalysis.filePathReads` through `meta.ast.filePathReads`, resolved beside the reader, then at its sub-project root, then at the analysis root, never by file name alone.
     - A code target, a test reader or a path leaving the root joins nothing.
   - **Environment variables** ([env-vars.ts](env-vars.ts)) — Each variable read in code and the services of its project that set it, names only.
   - **CI deploys** ([ci-pipelines.ts](ci-pipelines.ts)) — The deploy steps of GitHub/GitLab/Azure/CircleCI/Bitbucket pipelines with trigger, path and sub-project — a `docker build` only in a job that pushes.
   - **Cross-file taint** ([cross-file-taint.ts](cross-file-taint.ts)) — A handler's request input passed into a function another file declares, joined through the symbol links from each file's `taintFacts`.
   - **Dead code** ([dead-code.ts](dead-code.ts), `analyzeReachability`) — Authored files no entry point reaches + exports nothing imports, judged only for languages whose plugin declares a `reachability` model; a Procfile process or a compose/Dockerfile command is an entry; a CI or Makefile run line is a passive entry (`ReachabilityInput.passiveEntries`); JS/TS reads computed loads (`import(`./plugins/${n}`)`), Vue `<script src>`, `bin/` beside a `package.json`, migration folders, code-generator outputs and workspace subpaths through `outDir` as loading the files they name; each unused export carries `confidence` and `reasons` — `own-file-only`, `re-exported`, INFERRED; `name-referenced`, `unresolved-imports`, AMBIGUOUS — filtered by `analyze --min-confidence` and `clarifydoc_health`'s `minConfidence`; Swagger Codegen / OpenAPI Generator classes and llparse tables are generated, so their calls' links carry `sourceRole: generated`.
   - **Health** and **suggestions**.
   - **Test coverage** — `--coverage` or the usual report paths: lcov, Cobertura, JaCoCo, Clover, Go → `testCoverage` per file and function, matched by path suffix — [test-coverage.ts](test-coverage.ts).
   - **Doc drift** — Paths, routes and class members the project's Markdown names that the tree no longer bears out, guarded by git — [doc-drift.ts](doc-drift.ts).
   - **Performance patterns** — `query-in-loop` from the control-flow graph, `blocking-in-async` from each manifest's `blockingCalls` — [query-in-loop.ts](query-in-loop.ts).
     - Both ordered widest reach first by `rankPerformanceByReach`, `PatternInfo.reach`.
     - A manifest's `blockingOnReceiver` — C# `Task.Wait()`, and `.Result` through `readMembers` and `FunctionInfo.propertyReads` — flags `x.Wait()` / `x.Result` in an async method only when `x`'s declared type is that type, never a project class's member.
   - **Ignore suggestions** — Generated and vendored roots that still hold analyzed files, printed by `analyze --verbose` and `clarifydoc_status` as `.clarifydocignore` entries — [ignore-suggestions.ts](ignore-suggestions.ts).
   - **Type-only import edges** — `typeOnlyEdges`: cycles are judged without them — [import-kinds.ts](import-kinds.ts).
   - **Named communities** — [community-names.ts](community-names.ts).
   - **Entry points** that are not routes (MCP tools, editor and CLI commands → `entryPoints` and `command` data flows).
   - **External API specs** (`--spec`, read as `@spec/<name>`) and the third-party service an external call reaches (`CallOrigin.service`, `externalServices`).
8. **Write output** — per-file JSON + `project-summary.json` + `report-data.json` (viewer payload, written unconditionally) (+ `manifest.json`, + optional `report.html`). The JSON artifacts are streamed in slices ([json-stream.ts](json-stream.ts): the top levels walked, members through native `JSON.stringify` in batches), byte-identical to `JSON.stringify(v, null, 2)` and never one whole-file string (about −0.9 GB peak on a 6,000-file repository), written to `<name>.partial` and renamed; large text such as `report.html` goes out through `writeTextFile` in 8 M-character slices.

## Data structures in detail

- `RouteInfo` — the attribute layer is kept, not just the path: `middleware` (guard strings — Express middleware names, `Authorize(Policy = …)`, `AllowAnonymous`), `auth` (policies/roles/schemes/anonymous, structured), `versions`/`deprecatedVersions` (`[ApiVersion]`), `params` (each handler parameter with its binding: body/query/route/header/form/services, `inferred` when derived from framework defaults).
  - A page route carries `renderMode` (`ssr`/`ssg`/`isr`/`csr`, copied to `ScreenInfo.renderMode` and shown by `clarifydoc_screens`) only where the framework's own settings state it — Next.js data functions and segment config, SvelteKit page options, Nuxt `routeRules`.
  - Field names are language-agnostic; ASP.NET fills them today, Spring/NestJS can fill the same ones.
  - Decorators (`FunctionInfo`/`ClassInfo`/`PropertyInfo.decorators`) carry their **arguments** in every language — never reduce an attribute to its bare name.
- `ProjectAnalysis` — aggregated: `subProjects`/`fileProjects`, `componentGraph`, `linkGraph` (weighted), `symbolLinks` (call→def, `resolvedBy`, `confidence`), `routeMap` (rows carry `filePath` + `projectId`, optional `requestSchema`), `apiCalls`, `apiRouteLinks` (each with its `sourceProject`/`targetProject`), `projectDependencies` (sub-project → sub-project HTTP/bus edges with their endpoints and the deployment edge that agrees — `clarifydoc_services`, the Architecture Containers view), `screens`, `entityGraph`, `dataAccessGraph`, `classGraph`, `migrations`, `externalPackages`, `deployment`, `deadCode` (unreachable files + unused exports, with what was judged and what was skipped), `fieldWrites`/`thrownTypes` (field assignments and thrown types per function, resolved by declared types — rules in "Conventions" → "Field writes and thrown types"; per-language spellings in the plugin folders' `AGENTS.md` files), plus all quality/topology results.

- **Teach a plugin a DI container** — plugins only report facts; core resolves.

  - Labelled fixture: `test-fixtures/sample-microservices` (C#, TS, Java services, plus Python httpx/aiohttp, Go resty, PHP Guzzle/`config()` and Ruby Faraday/`ENV` callers with one `archive` decoy each) + [cross-project-fixture.test.ts](cross-project-fixture.test.ts).

  - It lives on the static manifest because the inventory reads every manifest whether or not the language was discovered.

  - [dependency-inventory.ts](dependency-inventory.ts) only walks the roots, dedupes, classifies and counts — it names no ecosystem but `.gitmodules`.
- **Judge a language for dead code** — give its meta a `reachability` hook ([src/types/language-plugin.ts](../types/language-plugin.ts) `ReachabilityHooks`): `load()` reads the toolchain's entry points and returns a model that says which files START the program (`entryReason` — these anchor a project), which are merely RUN BY A TOOL (`passiveReason`: configs, migrations, scripts — kept alive, never reported, anchor nothing), resolves an import specifier to the files it loads (`resolve`: `[]` = external, `null` = local but unknown) and resolves `pathReferences`/template tags.
  - Set `judgeExports: false` when imports don't name what they use.
  - Languages that reach by NAME (a C# type across its namespace, a PHP class Composer autoloads, a C function behind a header) declare `declaredNames` — core then reaches a file when any reachable file's text mentions one; `configMentions` (manifests, appsettings, `META-INF/services`) anchor what the framework instantiates by name; `unitOf` makes a Go package one unit.
  - Every code language has a model: bespoke for JS/TS/Vue/Svelte ([plugins/javascript/reachability.ts](../extractors/plugins/javascript/reachability.ts) — files and exports; below an `sfdx-project.json`'s `packageDirectories` an LWC `lwc/<n>/<n>.js` and an Aura `aura/<n>/<n>{Controller,Helper,Renderer}.js` are passive — the platform loads them by folder name, they anchor no project, so an SFDX repository with no other JS entry stays unjudged — while a stray file of the folder no import reaches keeps its finding), Rust (`mod` tree) and Python (imports + `__init__` chains, server commands); the rest are declarative specs built by [plugins/shared/reachability-kit.ts](../extractors/plugins/shared/reachability-kit.ts) (C#, VB, Blazor, Java/Kotlin, Scala, Swift, C/C++/Objective-C, Go, PHP, Ruby, Perl, Lua, Dart, Elixir, Erlang, Haskell, Clojure, Delphi, QML, Nim, D, V, Fortran, Apex — with `foldNames` for a language whose names ignore case).
  - Markup and schema formats are never judged but are read as mention sources.
  - Libraries are not judged as dead: a published package's modules (pyproject/gemspec/CPAN/Composer library, Go packages outside `internal/`, Swift `public`, Dart `lib/`) are its API.
  - Extension-less `#!` scripts are read through [plugins/shared/shebang-scripts.ts](../extractors/plugins/shared/shebang-scripts.ts).
  - Only declare it for a language whose imports NAME files — C#/Java/PHP/Rails find files by namespace or autoload, and an import graph cannot prove those unreachable.
  - Measure precision on a real repo before shipping: every finding is an accusation.
  - `test-fixtures/sample-dead-code` + [dead-code-fixture.test.ts](dead-code-fixture.test.ts) are labelled by hand from the source.
- **Explain a complexity number** — `clarifydoc cfg <file> --function <name>` builds a control-flow graph for one function and renders it as Mermaid ([control-flow.ts](control-flow.ts)); `--slice <line>` prints the backward slice at a line instead — the statements that can affect the values used there, by reaching definitions (both arms of an `if`) and control dependence over that graph ([control-flow-slice.ts](control-flow-slice.ts); defs/uses read off node text, so approximate where a language assigns through a call).
  - On demand only: it reads one file, writes nothing, and never reaches `project-summary.json` — a CFG is per-function detail that would multiply the artifact for something almost nobody reads in aggregate.
  - Per-language node roles come from `meta.controlFlow` ([control-flow-defaults.ts](../extractors/shared/control-flow-defaults.ts) is the shared C-family table, and `extendControlFlow` is how a plugin adds its own spellings).
  - Covered exactly: **TypeScript/JavaScript (incl. Vue/Svelte SFCs), C#, Python, PHP, Java, Kotlin, Pascal/Delphi** — every tree-sitter plugin.
  - A language with no grammar gets a second front end rather than a second builder: [control-flow-regex.ts](control-flow-regex.ts) reads the function's text, blanks comments/strings/regex literals, infers nesting from block delimiters and synthesizes nodes carrying the SAME canonical types, which go to the SAME interpreter (`FlowNode` in [types/control-flow.ts](../types/control-flow.ts) is the seam; tree-sitter's `Node` satisfies it unchanged).
  - That covers **Go, Rust, C, C++, Objective-C, Swift, Dart, Perl** via `meta.regexControlFlow`, marked `approximate` on the graph and in every surface that shows one.
  - Keyword-delimited languages (**Ruby, Lua, Elixir, VB**) go through the same scanner with a plugin `blockDelta` hook instead of brace counting: it says what each line opens (`if` at a statement's start, a trailing `do`, `If … Then` with nothing after it) while `blockClose` says what closes (`end`, `End If`, `Next`), which is how a modifier `if` is told from a block — plus `armBlocks` (a Ruby `case`'s `else` is an arm) and `inlineGuard` (`stmt if cond`, `If c Then s`).
  - The regex tier is gated by measuring it against the parser on the languages that have both: ≥90% of TypeScript and Java functions and ≥85% of C# ones must come out the same shape ([control-flow-regex.test.ts](control-flow-regex.test.ts)).
  - `clarifydoc cfg --capabilities` publishes the list and the VS Code `$(flame) complexity N` CodeLens uses it to fall back to the Complexity report rather than dead-end.
  - Two gates keep the builder honest, both in `control-flow.test.ts`: `cyclomaticFromCfg` must equal `computeComplexity` (sharp, but blind where a complexity table is wrong — Pascal's is), and `undrawnStructure` must find nothing (table-independent: every construct in the body has a node in the graph).
  - Each corpus also asserts which constructs it contains, because a gate that quietly stops exercising a construct is worse than no gate.
- **Tell the impact report how to run tests** — a manifest's `testCommand(tests, ctx)` returns the runner's command for test files and the test functions a change reaches (pytest node ids, `go test -run`, Maven/Gradle by manifest, `dotnet test --filter`, …); `projectCommands(root)` reads how a whole project is built, tested and started from its root files (`ProjectAnalysis.projectCommands`, shown in `clarifydoc_status` and the `install` guidance block); `blockingCalls` names the calls that block inside async code (Swift among them); Scala (`sbt testOnly`), Perl (`prove`) and C/C++ (a CMake root that registers tests: `ctest`, through `plugins/shared/cmake-commands.ts`) state test commands too, and `TestCommandContext.projectTests` hands a plugin the project's own test commands; Go, Ruby and Rust state their `TaintSpec` through `meta.regexTaint` (`{ gate, taint }`; Go also follows a request body bound into a struct by its text fields — `c.ShouldBindJSON(&req)`, a JSON decoder, `TaintSpec.binds` —, Ruby reads heredoc interpolation into SQL sinks, Ruby also reads a heredoc chained into text-keeping calls (`<<~SQL.strip`, `.squish`) as its body, Rust reads axum/actix-web/rocket extractors — an axum `String`/`Bytes` last parameter of an `async` handler beside another extractor, never `HeaderMap`, never a plain helper — with `format!` captures — `stringReads`; the shared walk reads expression values from a spec's `valueParts` table — a comparison is a boolean, an `if`/`match` its arms —, guards through one `condition(ifNode)` text hook, and a redirect or outbound-URL sink, by its category, is one a fixed host does not reach): a file whose source matches the gate is parsed once more with the one tree-sitter grammar variant the manifest registers (`tree-sitter-go`, `tree-sitter-ruby`, `tree-sitter-rust`, shipped in `dist/grammars`; the `taint` feature switches it off) for the shared `handlerTaint` walk — never a test or generated file or a tree with syntax errors; a command needing a stated fact reads it from `TestTarget.suites` (`FileAnalysis.testSuites`: a Go testify suite → its runner, `-testify.m`) or `TestCommandContext.testTargets` (SwiftPM `.testTarget(path:)`), and an Elixir umbrella app's tests run inside the app; `testSetupRuns(root, files)` names the files a test run executes while setting up (Django's migrations and `AppConfig.ready()` under pytest-django), which the test-reach verdict counts as tested (`ProjectAnalysis.testSetupRuns`); a spec suite describing a type the file declares (`describe Club`, with cases, same sub-project, not replaced by a double) is test-verdict basis `described`, since framework wiring (a prepended mixin, callbacks) has no written call; `docComments` is the comment syntax tools read on demand. - **Draft architecture rules** — `clarifydoc rules init` ([core/rules-init.ts](rules-init.ts)) writes `.clarifydoc/config.json` `rules` from the folder dependency matrix (per folder "stays below its dependents", per cycle group "stays out of its cycle"; never an `allowOnly`), shows the diff, and with `--write` merges by rule name and writes the baseline SARIF `analyze --baseline` takes. `clarifydoc install --remove` ([agents/remove.ts](../agents/remove.ts)) reverses every install writer from the same plan functions, surgically; `mcp --print-config --pin` prints `npx -y clarifydoc@<version>`.

## Performance rules

- **Profiling:** `CLARIFYDOC_WORKERS=0 node --cpu-prof --cpu-prof-dir=<dir> dist/cli.js analyze …` (workers=0 keeps per-file work in the profile), then aggregate the profile per function. Self-time is too flat to act on — aggregate **inclusive** time per function.
- **Thermal-resistant metric:** wall clock swings up to 3× on laptops. Track the nonParse/parse ratio instead — `(inclusive analyzeFile − inclusive parseSource) / parseSource`; parseSource is fixed WASM work, so the ratio isolates extraction efficiency.
- **Correctness gates for any perf change:** (1) byte-identical per-file JSON on a real corpus (diff ignoring `analyzedAt`); (2) regenerate fixtures and diff `test-output/`; (3) vitest.
- **Worker pool:** worker threads kick in at ≥200 files; the cap of 8 is empirically optimal (more workers measured slower). `CLARIFYDOC_WORKERS=<n>` overrides, `=0` forces in-process. Each worker's young generation is capped at 16 MB (`CLARIFYDOC_WORKER_YOUNG_MB`, `0` = V8's default, which scales with machine memory): cold-run peak RSS −20 to −27 % on three 4,000–6,500-file repositories, output identical.
- **V8 hidden-class trap:** `Node.type` is cached on instances via a patched prototype getter (parser-manager.ts). Do **not** add more lazily-created cache properties to nodes — it forks hidden classes and makes all node property access megamorphic (measured 3.5× slowdown in route extraction). Cache per-file data in `Map<node.id, value>` memos instead. `id`/`startIndex`/`startPosition`/`tree` are free fields; `endPosition`/`endIndex`/`text`/`childForFieldName` cross into WASM per call.
- **Walk fusion:** full-tree walks dominate non-parse time; fuse N extractor walks into one traversal with per-extractor buckets (done for JS routes and data-sources/mutations).
  - Caution: stateful extractors keep per-file state — fused walks must call the base-class `beginFile`/`endFile` hooks around the traversal or state silently goes stale.
  - `extractCalls` does not enter a childless node whose type no step of its walk reads (not a scope, binding site or call type) when the plugin states no per-node hook (`readNames`, `collectExtraCalls`, `destructuredFromCall`, `heldFunction`) and no `skip` is given — 60 % of a C# body's nodes (`READ_TYPES_BY_LANGUAGE`, [call-graph.ts](../extractors/shared/call-graph.ts)); a hook that only acts on some node types is gated on them before it reads text (C# Hangfire/`ToTable` arguments, `is`-pattern narrowing), and the per-call cost of the C# argument hooks is what is left of `extractCalls`.
- **Memos per link run:** the linker's per-run caches are the `memos` object of `LinkContext` (`LinkMemos` — `typeFileFor` per (type, file, project), about 13 calls per key on a 4k-file repository; callable members; include closures …), never module-level `WeakMap`s; never spread a context; anything a memo reads from the context must be built before linking starts. A dotted call of an internal name whose last name no file of the run declares (`namesNothingDeclared`, `declaredLeafNames`: every function, method, class, property, event, alias, export, import, mixin rename, returned-member key, constructor name and `constructorCalls` entry, lower-cased; a name with `<` never) is refused after the dispatch-map and record questions and before the receiver is walked — a bare name is not (`super`, a local holding a factory's result resolve by no declared name); `namespaceHeadMember` is memoized per (file, written path), a directory's package files per language family (`packageFilesOf`, the caller's own file cut out per call) and the language families holding any dispatch map (`familyHoldsMaps`: a one-key `x.y` call whose file holds no map of that name, in a family where no file holds one, skips the imported-map lookup).
- **Flat trees (the only path; a leftover `no-flat-tree` feature is ignored):** byte-identical to the real nodes on all 38 corpus repositories and every fixture; `parseSource` of a language in `FLAT_TREE_LANGUAGES` (C#, Java, JavaScript, Kotlin, PHP, Python, TypeScript — TSX and the Vue/Svelte scripts are TypeScript text — plus F#, Bash, R, Julia, Zig, OCaml and Pascal `.pas`) copies the tree once into typed arrays and returns `FlatNode`s ([parsers/flat-tree.ts](../parsers/flat-tree.ts)) — a 4,000-file C# repository's cold CPU 67.7 s → 43.5 s, output identical; a TypeScript repository's 25.8 s → 19.6 s; a Python repository 22.4 s → 17.6 s, a PHP one 11.7 s → 9.0 s, a Java one 24.6 s → 17.5 s.  A language joins the set only when its corpus output is byte-identical on the flat copy and the real tree (`--stable-output`); `flat-tree.test.ts` holds every member equal to the real node, quirks included; `descendantForIndex` is not copied (its edge answers differ by grammar), so callers descend through `children`.
- **Scaling gate:** `cli/scripts/check-scaling.mjs` (CI `verify` job, about 20 s) analyzes generated TS/Python/Go sub-projects at N and 4N single-threaded and fails when (t(4N) − t(1 project)) / (t(N) − t(1)) / 4 exceeds 2.5 — a quadratic pass shows there, fixtures are too small; it prints both runs' stage timings on failure. Never spread a six-figure array into `splice`/`push`/`Math.max` (stack overflow) and never scan a file's whole text per call or per name (cache the answer per file, `httpResourceFile`, `mutatesCollection`).
- **Cheap gates:** substring-gate expensive subtree walks (`sourceText.includes("import(")` before walking for dynamic imports); whole-text regex gate before per-line rule loops, and a whole-text gate asked per call site is computed once per file (Python `managerAssigned`); a pattern built from a name is built only after a substring test on that name passes (Ruby `assignmentsOf`); a per-line rule loop over a whole file (Go's `extractGoRoutes`) first tests one alternation of the words every rule names after a `.` and skips the line otherwise, `goAddressedTypes` reads value locals and value types only when an `&x` of a value exists, and `typeBlockLocalCalls` indexes the body's identifiers once instead of testing every declared name against every line. A per-argument walk of the enclosing function (PHP `assignmentsOf`, Python `assignsTo`) is one walk per function building a name table, kept per tree in a `WeakMap`; a text blanker (`stripPythonNonCode`) scans char codes and copies kept stretches by `slice`, never a per-character array.
