# src/core — Analysis pipeline & analyzers

The analysis pipeline orchestrator and all cross-file analyzers live here. Pure functions in / out — no tree-sitter parsing happens at this layer (that's delegated to extractors).

**Core is language-agnostic.** Anything per-language — extensions, parse
strategy, builtin types, complexity tables, security rules, framework hints,
external-package prefixes, AST hooks — comes from the plugin registry
([../extractors/registry.ts](../extractors/registry.ts)), which aggregates each
plugin's `meta.ts`. Don't hardcode language names, ORMs, frameworks, or file
conventions here; ask the registry. Even a **cross-file** join that needs
language knowledge stays in the plugin: core calls a generic hook (e.g.
`reconcileProjectEntities` → each entity extractor's `reconcileProject`), it
never names the language. A `schema.rb` parser or a pluralization rule in
`src/core/` is a layering bug.

## Entry point

[analyzer.ts](analyzer.ts) exports `analyze(options)` — the full pipeline. It runs:

1. File discovery + framework detection
2. Parallel per-file analysis (tree-sitter + extractors, or regex fallback)
3. Post-analysis: component graph, link graph, symbol links. A package import (`importsNameDirectories` — Go, Rust, Ruby) resolves to the ONE directory whose path ends with the longest run of its segments (a tie is no edge), narrowed to the files declaring a name the importer uses, tests excluded; dead code reads these edges as reachability, so a phantom fan-out hides real gaps in a language's own model
4. Optional LSP enhancement
5. Advanced analysis (complexity, patterns, duplicates, layer violations, blast radius, health, suggestions)
6. Write project summary + optional HTML report

Each step is gated behind the `ProgressReporter` — both verbose and non-verbose modes.

**Dependency order matters.** Health and suggestions depend on everything else. The analyzer computes the import cycles ONCE (`findCircularDeps` over the runtime graph — type-only edges and edges only a dynamic `import()` states (`dynamicImportEdges`, loaded on demand) dropped — of authored, non-test files) and hands them to refactor pressure, health and suggestions (`cycles`). A cycle group is a set: print it with `cycleChain` (a path the imports really take), never as its members joined by arrows.

## Per-file analysis & workers

- [file-analyzer.ts](file-analyzer.ts) — `analyzeFile(task)`: read + parse + run all extractors + write the per-file JSON. Pure per-file logic with no pipeline state, so it can run on any thread.
- [analyze-worker.ts](analyze-worker.ts) — worker_threads entry that wraps `analyzeFile`. Built as its own tsdown entry (`dist/analyze-worker.js`).
- [worker-pool.ts](worker-pool.ts) — `AnalysisWorkerPool`: spreads per-file analysis across cores for projects ≥200 files (override with `CLARIFYDOC_WORKERS=<n>`, `0` disables). Falls back to in-process analysis when workers can't start, and re-runs a crashed worker's task in-process.

## Discovery & IO

- [file-discovery.ts](file-discovery.ts) — a glob walk by extension. The `EXTENSION_MAP` is the source of truth for which extensions are analyzed. **Every walk goes through [glob.ts](glob.ts)** (tinyglobby — fast-glob was dropped for its `braces` advisory, GHSA-vfj7-8cjw-p6xm, which has no fixed release while `--include`/`--exclude` hand it user patterns): it never follows links — a followed link let a scanned repo read outside itself (`leak.py -> /etc/passwd`) and turned one `src/loop -> ..` into every file repeated ~32 levels deep — and keeps `deep: n` meaning "at most n-1 directories below cwd", which every spec was written against. Discovery asks for the links (`LinkedFiles`, a readdir that lists a link as a file and records it) and keeps a linked *file* only when it resolves to a regular file inside the (resolved) root; the rest land in `skippedSymlinks`. Linked directories are never descended. A new walk imports `glob.ts`, never the engine. A walk can also `prune` directories (a predicate on absolute paths, applied to each listing before the engine sees it); discovery, sub-project detection and framework detection prune what `.clarifydocignore` excludes, so an ignored tree costs one check instead of a walk — on one working tree, ignored checkouts holding 1.1M files had taken discovery from 0.3 s to 35 s.
- [clarifydoc-ignore.ts](clarifydoc-ignore.ts) — `.clarifydocignore` / `.clarifydoc/ignore` in gitignore syntax, inherited up to the nearest project root — except an inherited pattern that covers the scan root itself (a parent's `/checkouts/` while analyzing `checkouts/x` made the scan empty); `loadIgnorePatterns(root, scanRoot)` keeps such patterns for sub-roots inside the scan. Anchoring is decided in `parseIgnorePattern`, not while matching: a pattern with a `/` in it is fixed to the ignore file's directory (`/dist` leaves `src/dist/` alone), a slash-less one matches that name at any depth. Last match wins, and a file CAN be re-included under an excluded parent — a deliberate divergence from git, pinned by a test. `ignoredDirectories` is the walk-time view: a directory is pruned only by a pattern every path below inherits (an anchored prefix, an unanchored name) that no later `!` pattern follows, so pruning never changes which files come out. `fnmatch` here is the only glob engine; `project-config.ts` shares it.
- [framework-detector.ts](framework-detector.ts) — gathers `ProjectInfo` (package.json, pom.xml, build.gradle, …) per project/sub-project root and runs the plugin-contributed rules (`plugins/<lang>/frameworks.ts`, aggregated into the registry's `FRAMEWORK_RULES`). Produces `FrameworkDetection[]`, sorted by id; core knows no framework names.
- [deployment.ts](deployment.ts) — compose-manifest deployment topology (`ProjectAnalysis.deployment`): parses docker-compose/compose files with a built-in YAML-subset parser, classifies services (app vs datastore/queue/cache), matches app services to sub-projects (entrypoint dll / image tail / marker basenames), and derives service→service edges from env evidence (api-key handshake per file, connection strings literal-first, URL/issuer vars, bus/cache attachment). Powers the report's Context (C1) / Deployment (C2) architecture levels.
- [output-writer.ts](output-writer.ts) — writes per-file JSONs + `project-summary.json` (+ `lsp-enhancement.json` / `lsp-ground-truth.json` when LSP runs).
- [element-registry.ts](element-registry.ts) — the disk-I/O codec. `normalizeProject` (write) lifts repeated nodes into two registries — `elements[]` (symbol-level `file::symbol` ids) and `files[]` page_ids (a file's index, used everywhere a path was repeated); `denormalizeProject` (read) reverses it. In-memory shapes are untouched; all readers go through `denormalizeProject`. A round-trip test over every fixture is the regression gate — adding a path-bearing `ProjectAnalysis` field means adding it to `rewritePageRefs`.
- [context-docs.ts](context-docs.ts) — decision records (files under `adr/`, `decisions/`, `rfcs/` …, with their `Status:`), framing documents (ARCHITECTURE, GLOSSARY, DOMAIN …), schema dumps and the documents `.clarifydoc/config.json` `context` declares (kept inside the root); decision markers in comments (`WHY:`, `DECISION:`, `TRADEOFF:`, `RATIONALE:`, `REJECTED:`, `ADR:`); the analyzed files a document names (`governedFiles`) and which were committed after it (`judgeStaleness`, one `git log`). Read on demand by the MCP server, never during `analyze`.
- [project-config.ts](project-config.ts) — reads `<root>/.clarifydoc/config.json` (optional, never fatal): per-repository `layers` (glob → ArchLayer, first match wins), `exempt` and `generated` globs, `context` documents, and `refactorPressure` thresholds. Owners of a section resolve it (`resolveArchitectureOverrides`, `resolveRefactorPressureConfig`); unknown keys and bad values become progress warnings and defaults are kept. `matchesAnyGlob` is the one glob test (ignore-file dialect; anchoring is read off the pattern, so a slash-less pattern also matches the bare file name and one carrying a `/` does not). The analyzer loads it once, before the generated/unauthored filter, so `generated` globs reach every quality signal.
- [regex-extractor.ts](regex-extractor.ts) — thin dispatcher for regex-only languages. Real logic lives in `src/extractors/plugins/<lang>/`.

## Report

**One renderer, prebuilt.** The report viewer is a React app maintained outside this repository. `report.html` is that viewer built into a single self-contained file (react + d3 + dagre + css inlined, fully offline) with the payload JSON injected. This package carries only the built template; report features are written in the viewer, and rebuilding it refreshes `report-template.html`.

- `html-report.ts` — `generateHtmlReport` loads the prebuilt template from `html-report/viewer-assets/report-template.html` (committed; rebuilt from the viewer; mirrored into `dist/` by the root tsdown `onSuccess` hook) and swaps `__CLARIFYDOC_TITLE__` / `__CLARIFYDOC_PAYLOAD__`. The payload embeds as **gzip+base64** (`encodeReportPayload`; ~10x smaller than inline JSON, no `<` so no HTML-escaping concerns) and `standalone.tsx` inflates it in the browser via the native `DecompressionStream`. Token replace uses a replacer *function* so `$&` can't corrupt. Also writes `report-data.json` (plain JSON, for consumers that serve the payload in slices) alongside `report.html`.
- `report-payload.ts` — `buildReportPayload(summary)` reshapes a (denormalized) `ProjectAnalysis` into the `ReportPayload` the viewer consumes; `loadReportSummary(dir)` / `loadReportPayload(dir)` read it from disk (with the `lsp-enhancement.json` merge). The payload carries `deferredFields` so a consumer that slices it follows the producer's list.
- `smoke.test.ts` renders a minimal report end-to-end and round-trips hostile payload content through the encoder.

## Adding a new analyzer

1. Create `src/core/my-analyzer.ts` exporting a pure function `analyzeMyThing(input): MyResult[]`
2. Add the return type to [../types/analysis.ts](../types/analysis.ts) and add an optional field to `ProjectAnalysis`
3. Wire into `analyzer.ts` post-analysis section (step 4c)
4. Pass data to `suggestions-engine.ts` if it should drive suggestions
5. If the viewer should show it, add it to `report-payload.ts`; the tab itself is written in the viewer, which is then rebuilt into `report-template.html`
6. Add exports to [../index.ts](../index.ts) if public API

## Conventions

- **Pure functions** — no file IO except `output-writer.ts` and `html-report.ts`. Input is `FileAnalysis[]`, output is typed results.
- **Optional fields** — new fields on `ProjectAnalysis` should be optional so old `project-summary.json` files still load.
- **Progress reporting** — use the `ProgressReporter` class in `analyzer.ts`, not `console.log` directly.
- **BFS with index pointer** — never use `Array.shift()` for BFS queues (it's O(n)); use `let qi = 0; while (qi < queue.length) { ... queue[qi++]; ... }`.
