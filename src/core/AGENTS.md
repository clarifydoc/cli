# src/core — Analysis pipeline & analyzers

The analysis pipeline orchestrator and all cross-file analyzers live here. Pure functions in / out — no tree-sitter parsing happens at this layer (that's delegated to extractors).

**Core is language-agnostic.** Anything per-language — extensions, parse
strategy, builtin types, complexity tables, security rules, framework hints,
external-package prefixes, AST hooks — comes from the plugin registry
([../extractors/registry.ts](../extractors/registry.ts)), which aggregates each
plugin's `meta.ts`. Don't hardcode language names, ORMs, frameworks, or file
conventions here; ask the registry. Even a **cross-file** join that needs
language knowledge stays in the plugin: core calls a generic hook (e.g.
`reconcileProjectEntities` → each entity extractor's `reconcileProject`), it
never names the language. A `schema.rb` parser or a pluralization rule in
`src/core/` is a layering bug, and so is an import of
`extractors/plugins/<language>/` from production code here —
[core-imports.test.ts](core-imports.test.ts) fails on one (`plugins/shared/`
holds language-free helpers and is allowed).

## Entry point

[analyzer.ts](analyzer.ts) exports `analyze(options)` — the full pipeline (stages: `## The pipeline, step by step`).

Every step is gated behind the `ProgressReporter`, in both verbose and non-verbose modes.

- **Import edges of the component graph.** A package import (`importsNameDirectories`) resolves to the ONE directory the language's `packageDirectory` rule names from the repository's packages (`SubProject.packageName` + `packages`; the standard library and downloads are no directory), else to the directory whose path ends with the longest run of its segments (a tie is no edge), narrowed to the files declaring a name the importer uses, tests excluded. Dead code reads these edges as reachability, so a phantom fan-out hides real gaps. Per language: [Go](../extractors/plugins/go/AGENTS.md), [Rust](../extractors/plugins/rust/AGENTS.md), [Ruby](../extractors/plugins/ruby/AGENTS.md).
- **External imports bind nothing.** An import of a third-party package a manifest of the repository declares (`declaredPackageImports`, matched as package usage is) or of the language's standard library (`standardImport`) is no project file, and the names it binds are never matched to a project file exporting the same name.
- **Stage timings.** A stage's time (`stageTimings`, `--verbose` `Timings:`) runs from its `progress.step`/`progress.status` line to the next one, so a long span of passes carries `progress.status("…")` sub-steps at group boundaries. They emit `step` events and leave `STAGE_OF` and the stage ids alone, since consumers of `--progress json` key on those. A new pass goes under the sub-step it belongs to; a sub-step under about 50 ms is merged into its neighbour.

## Analyzers (post-analysis passes)

All take `FileAnalysis[]` and/or `componentGraph` and return typed results. Each pass lists its output, its inputs (facts plugins state) and its rules. Per-language spellings of those facts live in each plugin's `AGENTS.md` ([../extractors/plugins/](../extractors/plugins/AGENTS.md)).

**Dependency order matters.** Health and suggestions depend on everything else. The analyzer computes the import cycles ONCE (`findCircularDeps` over the runtime graph of authored, non-test files — type-only edges and edges only a dynamic `import()` states (`dynamicImportEdges`) dropped) and hands them to refactor pressure, health and suggestions (`cycles`). A cycle group is a set: print it with `cycleChain` (a path the imports really take), never as members joined by arrows.

### Linking

#### symbol-linker.ts — `SymbolLink[]`

A fallback cascade, roughly in this order:

- **Direct.** Where functions nest (`line`/`endLine`), a bare name is the function declared inside the caller, else the innermost enclosing scope's, before a top-level namesake or an import of that name; another function's inner helper only when the caller is handed it (INFERRED). Names fold case where the manifest says `caseInsensitiveNames`/`caseInsensitiveCallables`. A call into a file that only re-exports the name (`export * from`, `export { x } from`) follows the re-exports to the definition, unique-or-nothing; a named re-export stays the target only when it leads outside the project.
- **Bare `super`** — the base class's same-named method, or its constructor from a constructor; never a `super()` that only receives a member call.
- **Inheritance.** C3 order where the manifest says `multipleInheritance`. `this.foo` (and a bare `foo()` where members need no `this.`) on the enclosing class and its bases first; another class's member of the file only from a class it encloses, never from a free function, unless `bareCallsHideReceivers` (the extractor reads `p->foo()` as `foo`: then an INFERRED guess). Calls on the instance itself then reach the ONE mixed-in module/trait/interface defining it.
- **Declared-type resolution** (below).
- **Deep-qualified** never matches a chain's leaf alone on a file its head's name chose. **Factory-via** is the factory FUNCTION a library-made receiver came from; a receiver the caller constructed (`const league = new League()`) is no factory.
- **ClassName.method** — a relative namespace falls back to the ONE declared class whose name ends that way. With `classNamesByEvidence` the class binds only through the caller's own evidence (own file, an import naming it, `declaredNamespace`, a fully qualified name), never a namesake of another namespace, and the unique-global guess never re-links a refused head ([PHP](../extractors/plugins/php/AGENTS.md)). With `valuePathsNameNoType` a `receiverCut` name is refused by the guess too ([Go](../extractors/plugins/go/AGENTS.md)).
- **Constructor** — a link a call naming a class makes lands on the constructor the class declares (`constructorNames`, never a base's); a class without one stays the target, a JSX element stays on the class, a function named `new` is reached only by `new X`.
- **Package-qualified import head**; **a function by its namespace-qualified name** (`FileAnalysis.declaredNamespace`).
- **Bare call into shared scope.** A used unit (`importsShareScope`): a header's declarations are defined by the files sharing its stem (`declarationExtensions`), a `static` body (`isExported: false`) never. A wildcard import (`from m import *`: what the module exports). The caller's package directory (`directoryScope`: the one non-test sibling declaring it). A module named by its DECLARED name.
- **Unique-global-leaf** (evidenced and import-blind):
  - Imported files come from the language's `resolveImport`/`importedFile` rule, else the generic path rules; a file declaring nothing of its own (a barrel) hands on what it imports, three deep. A loader that finds files by the constants they define adds them (`autoloadedFiles`) and is never import-blind. Where imports name packages (`importsNamePackages`), an import is the files whose `FileAnalysis.packageName` it names, narrowed to those declaring the member, plus the file's own and enclosing packages. `typeNamedByReceiver` (`match_report` → `MatchReport`) is evidence too.
  - Vetoed when the receiver's type — typed local/param/field, or `CallInfo.receiverType`, builtin included — names another class. On a chain that type is what the chain resolves to (a library type vetoes; a project type lacking the member does not, an `extension … on` it may serve it; an untypable chain keeps the head's); a class head vetoes only a call on the class itself (`PlayerService.instance.x` is called on what `instance` holds). A receiver's name is evidence only as the segment right before the method (`club.league.markTable` is called on `league`).
  - Refused when a head the callable binds (typed local, parameter, `this.x`) — or, where call names spell the receiver from its head (`callPathsFromHead`), a typed field or module binding — types the receiver through its chain to a project class that, with ancestors and mixins, lacks the member (`receiverTypeRefuses`; a namesake in another namespace excepted, it may be mixed in unseen).
  - `CallInfo.receiverCut` (a name keeping only the receiver's last names: `items[0].league.markTable(` read as `league.markTable`) has no head the caller binds: `chainReceiverType`, `receiverTypeRefuses` and the guess's declared type leave it alone (`receiverCutName`).
- **Generic type-argument**, plus the route/spec/fan-out/reference producers in `buildSymbolLinks`.
  - **Abstract dispatch** (`abstractDispatchLinks`): a call landing on an abstract method (`FunctionInfo.abstract`) is re-aimed at the ONE override below the class it dispatches on; abstract methods fan out to overrides as interface methods do.
  - **Extensions.** An extension's receiver parameter makes its type's fields the body's, and a chain step the type lacks goes on through the extension of that name. An extension on a builtin collection of one element names no project class: a call on a local/parameter/field declared with that element (`collectionElementOf`) takes the one such extension, the receiver's own collection preferred (`collectionExtensionLink`).

**Declared-type resolution** (`resolveThroughDeclaredType`) types a receiver chain through field types AND declared return types (`a.getB().getC().m()`, `new X(…).m()`, a static member, fluent `$this`/`static`/`Self` returns, a local typed by its initializer call `localTypes[].from`). The receiver is, in order: a typed local; a parameter; a field of the ENCLOSING class (own ctor params, inherited fields); a typed module-level variable (`FileAnalysis.moduleBindings`: the file's own, an exported one of a unit `importsShareScope` puts in scope, or of a library an `ImportInfo.inScope` import names; a `show` list narrows it, two units typing it differently decide nothing; `typesSpanFiles` counts other parts of one type in the directory); or a member chain through declared field types, or `CallInfo.receiverType`.

Then `linkThroughPoint`: a container registration (`di-binding`, `boundImplementation`); an interface with ONE implementation and no extending interface implemented, or an abstract class (`ClassInfo.abstract`) with ONE concrete class below it (`interface-redirect`); else the declared type's own or inherited member (`injection`); else the ONE interface method the type — or one of its `ClassInfo.extension` parts, never the type's declaration — implements. A redirected/bound call also emits a `reference` link to the interface method so the interface keeps its callers. Name-classified `database`/`api-call` calls resolve ONLY through this tier.

**Module-level and local typing.**

- A module-level binding types a call where the function reads it (`moduleLocalsInScope`, [Python](../extractors/plugins/python/AGENTS.md)); a function rebinding the name lists it in `FunctionInfo.boundNames`, and `scopedName` skips the module's `<setup>` local for it.
- A bare name no local, parameter or field takes reads the file's `moduleBindings` (typed, or `from` an initializer call typed by its callee's declared result), then, where `directoryNamesShared` makes a directory one package, its siblings' and their functions. `<setup>` exists for a module that only declares typed variables.
- A local typed through an imported module (`m.Club`) takes the class that module's file declares (`moduleQualifiedType`), never a leaf-name namesake.
- A local typed by its initializer call inside a function written in place (`<watch@12>`) uses the enclosing function's call, innermost first, in that function's scope (`importedFunctionLink`).
- A held noise member called through a path from a typed head is restored (`restoreTypedReceiverCalls`, [Go](../extractors/plugins/go/AGENTS.md)). Where includes share scope, `methodBesideClass` is scoped by the caller's include closure ([C++](../extractors/plugins/cpp/AGENTS.md)).
- A call the syntax makes (`CallInfo.syntax`) links only through the receiver's declared type or the enclosing class, never a name guess, in `resolveCallToDefinitionBody` ([Ruby](../extractors/plugins/ruby/AGENTS.md)).

**Link metadata and special reads.**

- Every link carries `strategy` (`SymbolLinkStrategy` in `types/analysis.ts`) and `relation`, both set at each construction site; `relationForStrategy` derives the second.
- The per-caller-and-name dedupe keeps the highest-confidence link at the EARLIEST `sourceLine`; the target never moves.
- **Passed names.** A name handed on rather than invoked (`CallInfo.passed`) links as `relation: "passes"` (`resolvePassedName`), only to a function, method, class or default export, never through a name-only guess (`unique-global*`, `type-argument`). A factory's whole result handed on passes the factory; a name destructured from it passes what it returns under that key (`CallInfo.returnedAs`) or nothing. Reach, screens, trace and impact follow it; sequence diagrams, param-columns/param-origins and arity checks skip it.
- **Reads without parentheses** (`CallInfo.read`) link by `resolveReadName` only when they resolve without guessing to a function/method (`calls` when it returns a value, `passes` when a procedure) or a construction; a field, variable or class read draws no edge and is never a database/API call. `PropertyInfo.readAccessor` answers in the symbol index with its method.
- **Schema classes** (`declaresSchemaTypes`: contract schemas, SQL tables, Prisma models) are no strategy's target and stay out of the symbol index, exports and type catalogs.
- **Heuristic-tier guards:** same sub-project, never into test-fixture paths, the registry's `builtinMembers` stoplist (`set.add`), the caller's language's `untypedReceiverMembers` (framework methods on a receiver nothing types: `s.strip`).
- **Class-name tier.** A `FunctionInfo.explicitInterface` member never takes the class-qualified or bare name of a same-named member (`SymbolDef.explicitOnly`): a class-typed receiver reaches the public member, an interface-typed one `explicitImplementation` ([C#](../extractors/plugins/csharp/AGENTS.md)). A call through a nested type's owner path (three or more capitalized segments) resolves in `classNameMember` on the class declared inside the owner's body, never a namesake elsewhere; with `ownerPathTypes` a written TYPE resolves by `ownerPathIn`, both through `classesAtOwnerPath` ([Java/Kotlin](../extractors/plugins/java-kotlin/AGENTS.md)). `nestedTypePaths`/`lexicalConstants` name the class by its path in the class id/`typePaths` ([C++](../extractors/plugins/cpp/AGENTS.md), [Ruby](../extractors/plugins/ruby/AGENTS.md), [Perl](../extractors/plugins/perl/AGENTS.md), [Swift](../extractors/plugins/swift/AGENTS.md)).

#### reactive-triggers.ts — `SymbolLink[]`

A write to a reactive cell re-runs the callbacks watching it. Input: `FileAnalysis.reactiveCells`, each scoped `<scope line>:<name>` (plus member path) to the declaring component/class.

- Each write links the writing function to every callback on the same cell (a path leading into the other counts) as INFERRED `dispatch`, strategy `dispatch:reactive-trigger`, `callName` what the write spells. Never across files; a callback writing its own cell draws nothing.
- A trigger marked `immediate` also links from the file's `<setup>` (callName `immediate`); a component with no setup gets the pseudo-function through `ReactiveCells.component`. A statement a template runs is a write by the component's `<setup>` at its line.
- Store-state facts (`storeWatch.watchers`) and the cross-component resolvers (`dispatch:prop-flow`, `dispatch:param-type`, `dispatch:subject`, `dispatch:store-watch`, `dispatch:vuex-action`, `dispatch:vuex-state-watch`) are the JS plugin's: [JavaScript](../extractors/plugins/javascript/AGENTS.md).

#### Dispatch-side data passes (in memory, before the data-access pass)

- [channel-factories.ts](channel-factories.ts) — adds `queue-publish`/`queue-consume` rows to callers' `dataSources`. A wrapper whose publish names its own parameter (`DataSourceInfo.channelParameter`) publishes, at each resolved call handing it a literal there (`CallInfo.args`), on that channel.
- [channel-topics.ts](channel-topics.ts) — `scopeChannelTopics` retargets an event stating several topics; `resolveMqttTopicHoles` fills `${…}` holes from the file's string constants and the module-value lookup (unresolved holes stay); `joinMqttTopicFilters` repeats a publish at every covering `+`/`#` filter.
- [entity-parameters.ts](entity-parameters.ts) — `database` rows. A helper whose statement queries a model one of its parameters holds (`DataSourceInfo.entityParameter`) reads, at each call resolved by an EXTRACTED/INFERRED link handing it a project entity at that position (`CallInfo.args`, positional or by keyword), that entity — for every call of the name in the calling function. A function handing its own parameter on to such a helper is one too, three levels up; a non-entity class, a local or an unhanded parameter binds nothing ([Python](../extractors/plugins/python/AGENTS.md)).
- [mixin-self.ts](mixin-self.ts) — `captureMixinReceivers`, `bindMixinSelfAccess`: `database` rows. A mixin's access on its own receiver (`DataSourceInfo.mixinSelf`) is the table of the class the call runs on: at each EXTRACTED/INFERRED link whose receiver the linker typed (`SymbolLink.viaType`, captured before `moveInheritedCallsToSubclasses` drops it) as a project entity, a row at the call site names it (`handler` = the route for a route's own call). A call on the caller's own instance from a non-entity class hands the rows on to the caller; an untyped receiver binds nothing — the table is never guessed from the includers.
- [foreign-bindings.ts](foreign-bindings.ts) — `SymbolLink[]` across a generated language bridge. A plugin's `foreignBindings(root, read, files)` reads a generator's configuration at each sub-project root into `ForeignBindingRule`s (implementing files, the usually gitignored module path each is written to, how importers spell it, the naming rule, the generator's attribute). Each call through an import of such a module (a prefix, a name it brings in, or a module loaded in place as the call's `target`) links EXTRACTED, strategy `dispatch:foreign-binding`, to the public function the rule binds under that name; the linker's guesses for the call are dropped. A rule with `decorator.classes` also binds the classes carrying the attribute (constructor, `constructorArgument`, methods); a call joins a method through a receiver the file types, the class resolving by import, namespace or the one bound module the file loads, never a same-named class declared or imported elsewhere. A name two files of one module bind joins neither. Generators: [Rust](../extractors/plugins/rust/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Dart](../extractors/plugins/dart/AGENTS.md).
- [typed-receivers.ts](typed-receivers.ts) — per-file, before `classifyCalls`. `restoreTypedReceiverCalls` brings back member calls `extractCalls` held back as noise by leaf name (`notifier.send`) when the receiver has a declared, non-builtin type in scope or is itself a type (a static call on a capitalized head no name in scope spells — where imports bind names, only a class the file declares or imports — and `send(…)`, `this.send(…)` and `this.send()` when the enclosing class or a same-file base declares it). The linker decides whether the project declares the class; a name-classified `database`/`api-call` on a project class resolves through the class-name tier (`project-call-data-sources.ts` then drops the `db-write` it made). Also `declaredSupertypes` (extends/implements minus ORM relation targets) and `sameTypeSpace`.
- [inheritance-edges.ts](inheritance-edges.ts) — component-graph edges implementation → interface / subclass → base for supertypes no import names, resolved unambiguously (own sub-project, closest by directory, else globally unique in the type space; a qualified base through the class index). An interface's blast radius includes its implementations.
- [client-proxies.ts](client-proxies.ts) — api-call rows for calls through REST client proxies: a receiver whose declared type (through imports, or the one registered type of that name) a registration marks `proxyOf` becomes `{ contract: { type, method }, baseRef: client }`, joined by contract by the route linker. Inputs: `httpClientRegistrations`, classes/functions, imports.

#### data-flow-reach.ts — `symbolReach`, `dataFlows`

Reverse BFS per (effect, resource) from each direct DB/queue/api-call effect over the symbol links.

- **Type-parameter tables.** A read whose table is a class type parameter (`DataSourceInfo.entityTypeParameter`) is bound first: a call inside the class keeps the parameter; a link's in-memory `typeArgs` (from the receiver's written type, a subclass's closed base or a route owner) moves it to the caller's parameter or ends it at the first caller naming a type, seeding an ordinary effect at that distance. An unbound caller ends nothing.
- **Usage gate.** A walk back through a dispatch to a component's user (`SymbolLink.viaUsage`: an emit, callback-prop call or dialog close, tagged with the parent's binding site) continues only into the files binding it there. A file using the child (importing, rendering — a `dispatch:renders` `(reference)` link —, calling through a template ref, binding any event) leads out through its own bindings only (none when it binds that event nowhere). A tag spreading props or listeners into it (`dispatch:renders-open`) states no binding and keeps every one; a subclass of the child, or a file with no sign of using it, leads out through every binding. `usageGate` in [symbol-graph.ts](symbol-graph.ts) holds one level of context; the MCP trace walk and its `to=` search, `clarifydoc seq` (diagram and `--diff`/`--lock`/`--check` tree) and the screen-spec export use the same gate forward ([JavaScript](../extractors/plugins/javascript/AGENTS.md)).
  - A page rendering a shared dialog never reaches another page's handler through it. The dialog's own symbol still reaches every binding (blast radius and MCP walks are context-insensitive), but its SCREEN's data flow lists only what its own code reaches: an effect reached only through a bound emit/callback is `ReachedEffect.viaBinding`, sorted after the symbol's own effects so `EFFECTS_CAP` never drops them, and left out of the screen's flows; each parent's screen keeps the effects its binding brings in.
  - A dispatch link is no dependency: the component graph (`enrichGraphFromSymbolLinks`: cycles, dependents, communities) and component launches leave `viaUsage` links out.
- **Routes.** A route's flows are its own symbol's reach; a route whose symbol links nowhere falls back to the function around its line only when the route is declared ON it (`declaredOn` in [api-route-symbol-links.ts](api-route-symbol-links.ts)), never the function registering it. Cross-tier anchoring uses the same rule.
- **Route identity.** `RouteInfo.registrar` (the function whose body declares a route operation, [Go](../extractors/plugins/go/AGENTS.md)) is part of `routeIdentityKey` and of the route's symbol (`routeSymbolName` in [route-symbol.ts](route-symbol.ts): `route:GET /items @registerClubs`); every core site naming a route's symbol goes through it. `routeAnchor` (the call-graph symbol of a routeMap row, used by `clarifydoc_explain`, `clarifydoc_sequence`, the role reader and the flow lock) takes `registrar` too: a registrar's row anchors on its own `@registrar` symbol only.
- **Middleware reads.** What a router's middleware reads at request time is the route's: a plugin lists the functions its registration names (`RouteInfo.middlewareCalls`, the route's own group only), the linker resolves them as it does a handler (a link from the route's symbol), and a flow leaving the route through one carries `viaMiddleware`. A middleware a function-mounted route inherits from its mount site is `RouteInfo.inheritedMiddleware` (names with the file each mount is written in), resolved in THAT file and re-anchored on the route's symbol. A name the file's import binds resolves through it (`resolveMiddlewareName`), never by a leaf name across the project; a dependency's callable reads what it reads whether or not its name says it checks the caller. A bootstrap's global guards (the `nest-global-guards` fact) give every API route of the sub-project the guards as middleware/auth, `inheritedMiddleware` naming the bootstrap file. Sources: [Go](../extractors/plugins/go/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Python](../extractors/plugins/python/AGENTS.md).

#### sequence.ts, sequence-frames.ts, sequence-order.ts — Mermaid `sequenceDiagram`

Served by `clarifydoc seq` and `clarifydoc_sequence`. On demand, never stored.

- Links give what each call reaches; order and repeats are read off the function's source (`sequenceReading` → `SequenceOptions.sources`), since extractors keep one call row per callee and the linker one link per caller and callee.
- `callSitesIn` finishes a call where its parentheses close (`save(build(make()))` is make, build, save; a chain runs left to right). Every site of a name with one link is drawn; a name with several links takes the site on its own line; `await` marks the call it introduces; a link no site matches keeps its line.
- Frames come from the CFG (`Cfg.regions`: a `try` with its `catch`/`finally` as `critical` + `option`; `CfgNode.column`/`endColumn` split a one-line `if/else` into `alt`/`else`), by columns only for a function whose sites were read, else lines.

### Value resolution and service origins

#### module-values.ts — `ModuleValueLookup`, `resolveTargetRefs`, `resolveRouteTemplates`

`ModuleValueLookup` is `ProjectContext.moduleValue`: the string value a name stands for in a file, followed into the module defining it.

- Plugins report `FileAnalysis.moduleValues` and the reference as written (a `${…}` hole in a URL or route prefix, `DataSourceInfo.targetRef`). The pass resolves it in the file, through an import binding, through a package import naming a directory (`importsNameDirectories`, by `import-directories.ts`, the component graph's rule), in the caller's own package (`directoryScope`), or through a name an import puts in scope without binding it.
- A dotted `Head.member` nothing reached is filled from the ONE module of the caller's sub-project whose value table has that head (`headTable`); a head two modules declare, or only another sub-project does, fills nothing. When an import names the head, its source's last segment may match the owner's file stem case-insensitively.
- Family-scoped; test files never feed production code; two values decide nothing.
- Used for api-call URLs (`resolveSymbolicTargets`), queue targets, route paths a plugin writes as `RouteInfo.pathTemplate` (`resolveRouteTemplates`: a value nothing states is never guessed — unknown leading segments leave the tail under `prefixUnresolved: "constant:…"`, any other unknown hole stays in the path, named in `pathUnresolved`, and the route never joins a call nor counts as uncalled) and, by a plugin's route resolver, route prefixes.

#### call-origins.ts — mutates `apiCalls[].origin`

Also rebases the target and drops `baseExpr` once the base is known. The service a call reaches:

1. **Reference:** absolute/loopback URL → client registration → plugin `baseRefOf` of `baseExpr`. A hole host (`http://${IP}:5000`) is read by its port only, INFERRED.
2. **Values:** the caller's deployment `urlEnv`, then config; the code's fallback only when neither states one.
3. **Host** via the address book.

One project from every value = EXTRACTED; two = AMBIGUOUS, none chosen; none = `external` — except a base valued only by the code's fallback literal (`CallBaseRef.fallback`) whose host no address, deployment or `listen` URL names and no third party owns, which keeps the unresolved base (INFERRED; a known third-party host still marks it external).

Then **forwarding**: the project a request arrives at applies its longest matching `ProxyRule` (dev proxy, gateway), up to four hops; a rule whose target is no service here changes nothing. Inputs: `httpClientRegistrations`, `deployment`, config values, service addresses, `serviceConfigFor`.

#### config-values.ts, service-addresses.ts, route-bases.ts

- **config-values.ts** — per sub-project, the address-valued entries of every plugin's `serviceConfig.sources` and the forwarding rules of its `proxySources`. A key a config file says variables override (`ConfigEntry.envNames`) is kept even with no URL value, so call-origins' `envNamesOf` reads the caller's names. `urlValue` drops non-addresses and strips credentials (a `serviceName` entry stays as written); sensitive files are never opened. Values stay in memory, rules persist as `proxyRules`. `readRouteBases` hands every entry to the plugin's `routeBaseOf`. Inputs: `CONFIG_SOURCES`, `ROUTE_BASE_SPECS`, `isSensitive`.
- **service-addresses.ts** — `ServiceAddress[]` (`serviceAddresses` + `resolveHost`): compose/k8s service names and aliases, published host ports, `listen` URLs. A loopback host resolves by port only; several projects on one name resolve to none.
- **route-bases.ts** — mutates `analysis.routes` in memory, after router mounts, before the linker: a project's configured base in front of its complete API routes of the plugin's languages (`RouteInfo.basePath` says where it is set; a `prefixUnresolved` row keeps its tail). `stateLocalPaths`/`dropUnchangedLocalPaths` bracket the mount and base passes so a composed route carries `RouteInfo.localPath`, the path its own router wrote (never set by a plugin; the route linker's added-base tier and search's below-base alias read it before the conventional list).

#### module-search-paths.ts, compilation-database.ts

- `applyModuleSearchPaths`: a bare import two files answer to is rewritten to the file the project's build files mean — one they name for the module, else the one in the project's own directory, else the first search directory holding one. Read per sub-project root through the manifest's `moduleSearchPaths` (`pathImportsPin` says where a program pins a path); before the import index, in memory ([Pascal](../extractors/plugins/pascal/AGENTS.md)).
- `loadCompilationDatabase`: the manifest's `compilationDatabase` (paths a CI wrote matched to discovered files by their longest tail) → per translation unit its include directories and macros. `placeIncludes` rewrites an include to the file the compiler's search order finds first (before the suffix fallback; in memory); a file compiled twice with different results, and headers, keep the generic rules. `macrosOf` (the macros every unit agrees on) goes to the parser front end with the task, stamped into the incremental `resolver`, where `preprocessor-branches.ts` picks the live arm of a conditional ([C++](../extractors/plugins/cpp/AGENTS.md), [C](../extractors/plugins/c/AGENTS.md)).

### Parameters and contracts

#### param-origins.ts — `ParamOrigin[]`

For each `${slot}` that is a whole path segment or query value of an API call's URL (and each `{slot}` of a generated SDK operation whose descriptor spreads its own parameter, `DataSourceInfo.pathValues`): where its value starts — a screen's route parameter or query value, a literal, or `unknown`.

- **Walk.** Back from the call's enclosing function through its callers' `CallInfo.argOrigins`, by parameter name and, for an object argument, the property (`field: "path.id"`); eight deep, sixteen per slot; a dispatch link ends the walk. A call recorded twice is one site; a destructured parameter binds its own name.
- **Props.** A component's `prop` origin goes on to the URL value the route rendering it hands that prop (`RouteInfo.propsFromRoute`) and to the value each parent's markup binds (`FileAnalysis.propBindings`, the tag resolved among the files the parent imports, barrel re-exports followed to the declaring file, `throughBarrels`, three deep).
- **Derivations.** A value a plugin states is derived from a known one (`CallArgOrigin.derivation`/`PropBinding.derivation`) keeps that origin with the steps in `ParamOrigin.derivation`, INFERRED: a property of a record read off a keyed collection, what a function returns for it (only when its call links to a project function), or a member of what a composable returns for it (only when the linked function states how it derives from that parameter, `FunctionInfo.derivedLocals`). A record handed whole or spread stands for the property a mutation callback takes; a record in a URL slot is `unknown`. Spellings: [JavaScript](../extractors/plugins/javascript/AGENTS.md).
- Also reports the backend route parameter it binds (segments aligned from the end of the joined route). Inputs: `CallInfo.argOrigins` (`calls.argOriginsOf`), `propBindings` (`ast.propBindings`), `symbolLinks`, `apiRouteLinks`, routes, screens, `componentGraph`.

#### param-columns.ts — `ParamColumn[]`

The backend half: each API route parameter (`RouteInfo.params`, binding route/query) followed forward to the entity, field and access of the statement that filters on it. Shown in `clarifydoc_contract` ("parameters filter on") and FLOWS.md.

- **Starting points.** The route's own calls (`argOrigins` `route-param`/`query-param`); the handler's parameter of that name (`RouteParamInfo.variable` when named otherwise) or its own request read (hop `arg: -1`), including a field of a parameter whose declared type a binder fills (`PropertyInfo.boundFrom`); a callee the framework hands the route's parameters by name (`CallInfo.routeParamsByName`); any other function the route runs reading the request itself; for a handler built for a type it binds the request into (`RouteInfo.handlerTypes`), each of that type's methods the route runs.
- **Carriers.** A field slot through `receiver-field`/`param-field` origins, the receiver handed on whole (`receiver`, index -1 for a call made on it), composite literals' fields (`CallArgOrigin.field`). An object handed to a generic handler that calls a method on it goes on through the call site's `interface-redirect` link to that type's method. A `request-param` origin (path and query merged) matches either binding.
- **Through calls.** Entities a later project pass settles are filled in after it by `fillParamColumnEntities`, over the symbol links through calls that hand it on (`argOrigins` `param`). An argument given by name (`CallArgOrigin.param`) lands on the callee's parameter of that name and is the only kind followed through a dispatch link; an extension method's receiver parameter is skipped; of overloads the link's target line picks one, followed only when declared types agree.
- **Statements that filter.** `DataSourceInfo.whereFields` (a column compared to the value; a generic repository's column parameter `whereFields[].fieldParam` takes the literal the walked call hands it, and a key no call states as a literal gives no row) or `DataSourceInfo.whereObjects` (a filter on a whole object the field slot names, less the fields written first, `except`; the carried field is the column unless a `whereFields` row already names that value's column). A struct member settles to its column first — the mapper's tag found beside the statement before a same-named one elsewhere, else the mapper convention (`whereFields[].fieldOf` until the entity pass rewrites `field`; `whereObjects[].columns`). Detail: [Go](../extractors/plugins/go/AGENTS.md), [Python](../extractors/plugins/python/AGENTS.md), [JavaScript](../extractors/plugins/javascript/AGENTS.md), [C#](../extractors/plugins/csharp/AGENTS.md), [Java/Kotlin](../extractors/plugins/java-kotlin/AGENTS.md).
- Six calls deep, 32 rows per route; a call the linker did not resolve ends the walk.

#### project-dependencies.ts — `ProjectDependency[]`

Sub-project → sub-project runtime edges: `http` (cross-project `apiRouteLinks`) and `bus` (`mq` symbol links), each with its endpoints (capped, most-linked first), confidence counts, and the compose/k8s edge stating the same pair (`links: 0` = deployment only). Test callers and AMBIGUOUS links never make an edge — the same rule as the trace edges. Inputs: `apiRouteLinks` (`sourceProject`/`targetProject`), `symbolLinks`, `deployment`.

#### contract-check.ts — `ContractFinding[]`

`contractFindings`, on each EXTRACTED `apiRouteLink`, the body the call states against the route: `missing-field`/`unknown-field`/`type-mismatch` on `requestBody` vs a closed `requestSchema`; `unknown-response-field` when `responseReads` names a field a closed `responseSchema` lacks; `missing-expected-response-field` when `expectedResponseFields` (required closed members of the call's expected response type) names a field that schema lacks. Open schemas (`additionalProperties: true`) and INFERRED links stay quiet. Inputs: `apiRouteLinks`, `apiCalls`, `routeMap` schemas.

### Screens and navigation

#### rendered-views.ts, server-redirects.ts

- **rendered-views.ts** — `ScreenInfo.renderedBy` (+ `routePath` where none): the GET route whose handler (or a function it calls, two deep) renders a template screen by name — a render-named call's first string argument, a `template`/`view`/`page` field, a returned string — only when the name resolves to exactly one other-language screen by path suffix. Data flows then give the page what its route loads. Controller-template conventions come from a plugin's `templatePaths(name, fromFile)` ([Elixir](../extractors/plugins/elixir/AGENTS.md), [PHP](../extractors/plugins/php/AGENTS.md)).
- **server-redirects.ts** — `RouteInfo.redirectsTo`, the app paths an API route's handler redirects to: the literal of a redirect-named call, a `"redirect:/x"` view or a `Location` header (a concatenated tail reads `/x/{}`); or a name resolved first to the route registered under it (`RouteInfo.name`; a framework's path helper only ever by name — a stated one, else the name the framework derives, `RouteInfo.derivedName`), else to the one route whose handler has it (same file first, controller beside it). Only the handler's own body; a function holding several routes is cut at the next route. Spellings: [Ruby](../extractors/plugins/ruby/AGENTS.md), [PHP](../extractors/plugins/php/AGENTS.md), [C#](../extractors/plugins/csharp/AGENTS.md).
- Both read `symbolLinks` and raw handler source through [route-handlers.ts](route-handlers.ts).

#### screen-navigation.ts

Adds to `ScreenInfo.navigatesTo` the navigation of the components of OTHER files a screen builds, four files deep, never through another screen. Inputs: `FileAnalysis.uiComponents`, `navigationHelpers`, the component graph.

- Each name in a component's `builds` resolves to the one component another file declares under it (imported first, then the sub-project's; production never into tests). A parameter's default widget (`defaults`) counts only when the builder leaves the parameter out (`passes`).
- What a component hands a navigation helper (`navigatesVia`) is navigation when a file declares that function one (`FileAnalysis.navigationHelpers`): the imported declaration, else the sub-project's, else the analysis's one ([Dart](../extractors/plugins/dart/AGENTS.md)).
- Languages where every component file is already a screen need it not; the screen-specs export composes them.

#### screen-flow.ts — `ProjectAnalysis.screenFlow`

The navigation map: page and dialog nodes (+ `path:` nodes for client routes that only redirect), starts (main form, the screen at `/`, a redirect from `/`), edges typed `navigate`/`dialog`/`redirect`/`server-redirect`/`submit`. The Screens tab draws it. Inputs: screens, routes (`redirectTo`, `redirectsTo`), `componentLaunches`, interactive element requests, the component graph.

- **Edges.** `submit` is a form post (a post to the page's own route is a `submit` self-edge `POST /path`, the one self-edge kept) or a route's own `leadsTo`. Screens match a target by its path as written first, then by key.
- **Shells.** What no screen uses but a component rendering the language's router outlet (manifest `routerOutlet`) frames hangs off that component as a `shell` node, a start. `linksFromBase` marks languages whose bare links are app-root paths. A route's `shell`/`tab` is a shell node/edge ([Dart](../extractors/plugins/dart/AGENTS.md)). A component most pages of a sub-project include (`FRAME_PAGES`/`FRAME_SHARE`) is their frame, a `shell` node.
- **A screen is the sum of what makes it up:** components it renders (by import, or by name in its own sub-project or one it uses), its code-behind class, `codeFiles` and the `viewModel` it binds (`addViewCodeNavigation`). A component's links and dialogs count for every page and dialog that imports it, however deep, never through another screen nor two non-component modules in a row, over the import graph as it was before call edges joined it; a launcher module's own rows are skipped.
- **Scope.** A link target resolves within the screen's sub-project or one related by imports/calls (`related`); a shared library component's unresolved link resolves in the app of the page rendering it.
- **Link reading.** Comments are blanked first; every screen's own file is read. Link helpers are followed into the URL the function builds (`urlTemplate`), else its app-path literals (`resolveLinkHelpers`), a path table's member by its qualified name in the file it is imported from. A base-URL prefix before a link's path is dropped (`BASE_URL_PREFIX`). `extractNavigationTargets` (analyzer.ts) reads link elements, anchors to app paths, router/window/location calls with literals, concatenations (`"/x/" + id` → `/x/{}`), interpolations, a URL variable a navigation call takes and an item property a link binds.
- **Named routes.** A link by route name is `route:<name>`, resolved through `RouteInfo.name` — for navigation targets and interactive-element requests (GET links are navigation, other requests submit). Resolution tries the caller's own sub-project first (a name it states, then the name its framework derives), then another's, so another project stating the name never hides the caller's derived one (`canonicalNavigationTargets`). Screen-table rows keep their `name`.
- **Ambiguity.** A link to a path two screens answer opens the page, not the layout rendering the outlet, and not an empty screen. A file routing itself that a route table also routes is one screen; a template made only of the partials it includes is a page (`includedFile`). A concrete path matches the route with the most literal segments.
- Link spellings per framework: [JavaScript](../extractors/plugins/javascript/AGENTS.md), [Elixir](../extractors/plugins/elixir/AGENTS.md), [Blazor](../extractors/plugins/blazor/AGENTS.md), [templates](../extractors/plugins/templates/AGENTS.md), [XAML](../extractors/plugins/xaml/AGENTS.md).

### Tests

- **test-functions.ts** (`fileTestVerdict` basis `described`) — a spec suite describing a type (`TestFunctionRow.subject`, `FunctionInfo.testCase.subject`) in a test file holding at least one case marks the files declaring a class of exactly that name tested (framework wiring has no written call). Exact full name only, within the spec's own sub-project, never for a file a test replaces with a double; a spec without cases never counts.
- **test-navigations.ts** (`testNavigations` + `pageParts`) — the pages browser tests open by address (`FileAnalysis.browserNavigations`), joined to every screen at the path with the navigation map's matcher (`screenPathMatcher`; the test's sub-project first, else ONE sub-project; `/` never across sub-projects), each with the app start that reaches the screen by import (`FileAnalysis.appMount`, exactly one). `pagePartsOf` is what each opened screen and start uses, six uses deep over the uses graph — never into another routed page, never past the route table, a non-component module a part but a way on only to the component it loads on demand, never below a component more than 20 UI files use. A layout screen (a UI file rendering its router outlet, at a parent path of the one opened) is opened with the page below it; a file-routed app's root (`appMount.routed`) is the entry of every page of its sub-project ([JavaScript](../extractors/plugins/javascript/AGENTS.md)). The test verdict's `navigation` basis reads them; a double anywhere on a call path hides everything below it.

### Quality passes

- [blast-radius.ts](blast-radius.ts) — `BlastRadiusInfo[]`: downstream dependents, exported-symbol usage, `contextBurden` (the two-hop neighbourhood both ways with a line/token estimate). Input: reverse graph from componentGraph; `FileAnalysis.lineCount`.
- [complexity-analyzer.ts](complexity-analyzer.ts) — `FileComplexityInfo[]`: per function cyclomatic, cognitive (branch + nesting penalty, `else if` continuations exempt, callbacks deepen), nesting depth, parameter count. Input: the per-file AST; the plugin `complexity` spec (`branchNodes`, `logicalOps`, `nestingNodes`).
- [control-flow.ts](control-flow.ts) — `Cfg`: one function's control-flow graph, built **on demand**, never written to `project-summary.json` ([control-flow-file.ts](control-flow-file.ts) per-file entry, [control-flow-mermaid.ts](control-flow-mermaid.ts) renderer). Input: the complexity analyzer's `findBodyNode` plus the plugin `controlFlow` spec (node type → role).
  - Two gates in `control-flow.test.ts`: `cyclomaticFromCfg` must equal `computeComplexity`, and `undrawnStructure` must come back empty (table-independent: a complexity table can name node types its grammar lacks, so the arithmetic alone can never fail).
  - Tree-sitter languages are built exactly; a language with no grammar goes through [control-flow-regex.ts](control-flow-regex.ts), a line scanner synthesizing the same node shapes, gated by measuring it against the parser where both exist.
  - A plugin's `sourceView` may reduce the text first; the C family's is `firstBranchView` (dead blocks blanked, then only the first live arm of every conditional, since arms are alternatives of one build; [C++](../extractors/plugins/cpp/AGENTS.md)).
- [pattern-detector.ts](pattern-detector.ts) — `PatternInfo[]` from classes, functions, imports; function counts skip `synthetic` members.
- [responsibility-profile.ts](responsibility-profile.ts) — `ResponsibilityProfile[]` per file: boundaries touched (database, http, queue, auth, logging, …), workflow roles, concern count, read/write/publish/serve flags with evidence. Input: imports classified through the plugins' `knownPackages` tables + dataSources/routes/screens; core names no package.
- [security-scanner.ts](security-scanner.ts) — `SecurityIssue[]` from raw source text (regex-based).
  - A non-raw rule's match starting inside a literal the plugin says is data (`securityInLiteral`) is dropped; a private key header with no key material after it is none; `eval` never matches a method or function declared under that name, nor a test file.
  - A hardcoded-secret finding is its kind and location, its snippet masking every string literal with `********`. A value equal to its own name folded for case and separators (`API_KEY = "API_KEY"`) is no secret.
  - `isSecretConstant` is the one predicate (a known key format, or a credential-named constant whose value is no placeholder, endpoint or namespaced identifier); `dropSecretConstants`, run by `analyzeFile`'s `store`, removes such entries from `stringConstants`, `moduleValues` and class `fieldValues` before the per-file JSON is written. A value judged by name alone that is a letters-only word under 16 characters (`const TOKEN = 'pitch'`) stays.
  - A plugin whose `securityPreprocess` blanks strings states its assignment rule `raw`; a finding whose value is prose or a namespaced name (`isKeyShapedValue`) is dropped, and a linter's inline suppression comment silences hardcoded-secret only (`suppressionOf`; [Python](../extractors/plugins/python/AGENTS.md)).
- [duplication-detector.ts](duplication-detector.ts) — `DuplicateGroup[]`: structural fingerprinting; a `synthetic` function is never compared.
- [layer-analyzer.ts](layer-analyzer.ts) — `ArchLayer` map + violations from file paths + componentGraph; `.clarifydoc/config.json` `layers`/`exempt` come before the path heuristics (tests stay exempt first).
  - A file importing its neighbour in the same folder is none; into its own folder's subtree a file sits at the higher of its own and its folder's layer (`routers/api.py` mounting `routers/clubs/` is the routers folder using its parts); `router/` and `routers/` sit with `routes/` at the top.
  - `layerEvidenceAll` (declared facts — API routes, entities, queries, templates — never imports) → `fileLayerAlternates` and `fileLayerConflicts` (placed by path or name where a strong fact disagrees).
  - Team `rules` (`detectRuleViolations`): `noCycles` walks the runtime import graph. `clarifydoc rules init` ([rules-init.ts](rules-init.ts)) drafts rules from the folder dependency matrix at `--depth` (per folder "stays below its dependents", per cycle group "stays out of its cycle"), prints the diff, and with `--write` merges by rule name (never overwriting) and writes `.clarifydoc/baseline.sarif` for `analyze --baseline`, so only new drift fails.
- [refactor-pressure.ts](refactor-pressure.ts) — `RefactorPressureInfo[]` per file: 0–100 composite of complexity, size, mixed concerns, coupling and churn, band, drivers, fired gates, confidence (= share of signal available). Inputs: complexity, blastRadius, responsibilityProfiles, fileChurn, layerViolations, cycles; thresholds from `DEFAULT_REFACTOR_PRESSURE_CONFIG`, overridable in `.clarifydoc/config.json` (`project-config.ts`).
- [dead-code.ts](dead-code.ts) — `analyzeUnusedCode` → `generatedRoots` + `unusedFiles` (codegen/vendored trees nothing outside imports; a barrel is codegen only if it is no package's public entry and its tree is self-contained, <3 project files outside it); `analyzeReachability` → `deadCode` (authored files no entry point reaches, exports nothing imports). Inputs: componentGraph + symbolLinks + each plugin's `reachability` model.
  - Walks from **anchors**: manifest/convention entries, scripts a page loads, serverless/SAM handlers a descriptor routed onto (`resolvedBy: serverless-handler-anchor` or `entryPoints` with framework `sam`/`serverless`), and a file a deployment runs — a Procfile process (`procfileEntries`, [dockerfiles.ts](dockerfiles.ts)) or a compose/Dockerfile command (`DeployedService.entryFile`) — via `ReachabilityInput.deployEntries`, its reason used only where the language model gives none. Then **passive roots**: tests, fixture/example/bench dirs, ambient `.d.ts`, generated code, tool-run files, other languages' files, unreadable files' directories. A project is anchored PER LANGUAGE MODEL; one no anchor reaches is skipped, not reported whole.
  - Edges: the component graph, the model's import resolution, re-exports, path references, template tags, NAME references (models with `declaredNames`: every reachable file's text is tokenized once and any identifier a judged file declares reaches it — comments and strings included, so over-matching only keeps code alive) and compilation units (`unitOf`).
  - An export is judged only when every way into its file names what it uses — namespace/dynamic/glob imports and unexplained edges mark the whole file used — and names are followed through re-export chains.
  - Each unused-export row carries `confidence` and, when any apply, `reasons`: `own-file-only`, `re-exported` (INFERRED); `name-referenced`, `unresolved-imports` (AMBIGUOUS). `analyze --min-confidence` and `clarifydoc_health`'s `minConfidence` filter by it (`atLeastConfidence`; a row without one counts as INFERRED).
- [health-scorer.ts](health-scorer.ts) — `HealthScore`, model `rates-v2`: each dimension is a RATE over N = max(50, authored non-test files) (files in cycles, god objects, long files, files with >10 non-test importers, severity-weighted security per distinct file+category, duplicate groups, files with layer violations, files holding a function over complexity 20), deducting `cap · r/(r + rHalf)`; caps and `rHalf` live in `HEALTH_MODEL`. Penalty reasons keep the keywords the Health tab routes on. Inputs: all other analyzers + Tarjan SCC for cycles.
- [suggestions-engine.ts](suggestions-engine.ts) — `Suggestion[]` from all other analyzers.

## Per-file analysis & workers

- [file-analyzer.ts](file-analyzer.ts) — `analyzeFile(task)`: read + parse + run all extractors + write the per-file JSON. Pure per-file logic with no pipeline state, so it can run on any thread.
- [analyze-worker.ts](analyze-worker.ts) — worker_threads entry that wraps `analyzeFile`. Built as its own tsdown entry (`dist/analyze-worker.js`).
- [worker-pool.ts](worker-pool.ts) — `AnalysisWorkerPool`, generic over its task.
  - Spreads per-file analysis across cores for projects ≥200 files (override with `CLARIFYDOC_WORKERS=<n>`, `0` disables); falls back to in-process analysis when workers cannot start.
  - A worker that dies on a file (out of memory, or killed past the per-file deadline, `CLARIFYDOC_FILE_DEADLINE_MS`, default 180 s, `0` off) costs that file, never the run: it settles as `FailedFile`, lands in `ProjectAnalysis.failedFiles` with the reason, and a fresh worker takes the queue. The file is never re-run in-process, where it would end the process.
  - The query-in-loop pass hands the pool the files whose control-flow graphs it needs ([loop-shape-batch.ts](loop-shape-batch.ts), from 200 files on; fewer are built in-process).
  - **Heap bound.** While a pool runs it sets V8's `--heap-growing-percent` (`--heap-growing-percent=50`, `CLARIFYDOC_HEAP_GROWING_PERCENT`, `0` off; left alone when the process was started with one) (each worker has its own heap; V8's headroom made eight workers hold several times what they used) A run with no pool sets the same bound for the whole analysis (`boundInProcessHeapGrowth`, lifted when `analyzeProject` ends; a pool that ends restores it rather than V8's own).
  - **Shrinking.** When the files are read the analyzer stops the idle workers beyond the four that write the held output (`shrinkTo`); otherwise the pool keeps eight heaps and their grammars alive through the link passes.
  - A parser front end skips a generated file or one past 2 M characters (`frontEnd.fallback`); an ANTLR grammar's prediction cache is emptied past 10,000 states.
- [unread-code.ts](unread-code.ts) — `summarizeUnreadCode(paths)`: code files no plugin reads, by extension. The list is `extractors/shared/known-code-extensions.ts` data minus the registry's claims (`UNCLAIMED_CODE_EXTENSIONS`). Discovery matches them in its own walk and returns paths only (`DiscoveryResult.unreadCode`, `.clarifydocignore` applied); vendored roots and minified names are dropped here; nothing is opened. Surfaces: `ProjectAnalysis.unreadCode`, `analyze`'s `Not read:` line, `clarifydoc_status`. An extension that is as often data (`.cbl` reading lists, `.cue`) stays off the list.
- [ignore-suggestions.ts](ignore-suggestions.ts) — `ignoreSuggestions(files, generatedRoots)`: the generated roots and vendored roots (`vendoredRoots`) that still hold analyzed files, with counts, largest first. `analyze --verbose` prints them as `.clarifydocignore` entries and `clarifydoc_status` adds the same lines (at most 3 roots); nothing when no such root exists.
  - Performance patterns (`query-in-loop`, `blocking-in-async`) are ordered widest reach first by `rankPerformanceByReach` (finding-entries.ts: the routes `PatternInfo.entries` names plus the screens blast radius's `traceImpact` says reach the file — `PatternInfo.reach`); only the performance patterns' slots are permuted, the set never changes.
- [feature-flags.ts](feature-flags.ts) — extraction paths switched by name, each with a default (`KNOWN_FEATURES`), through `CLARIFYDOC_FEATURES` or `analyze --feature` (`no-antlr`, `antlr:go`, `-antlr:lua`; the most specific name wins).
  - What differs from the defaults joins `EXTRACTOR_VERSION` in `extractorStamp()` (manifest.ts), so a run reading files another way never reuses cached JSON. A feature ships beside the path it replaces; `scripts/ab-features.mjs <project> --feature <name>` analyzes one tree with and without it and lists every disagreement.
  - Two features, both on by default: `antlr` and `tree-sitter`. A regex language's `meta.antlr` reader, else its `meta.treeSitter` reader, supplies its functions and calls (`readWithParser` in file-analyzer.ts → `extractWithRegex(…, parsed)`); which languages have which front end is each plugin's own. A file the parser reads with syntax errors keeps the regex reading, and `FileAnalysis.frontEnd` says which reading a file got.
  - When the spec builds its own classes, `adoptParsedMembers` (regex-extractor.ts) gives a class method declared on a parsed function's line that function's calls and extent, and puts a parsed function no class pass found in the innermost class around it — refusing when several same-named classes share that extent.

## Discovery & IO

- [file-discovery.ts](file-discovery.ts) — a glob walk by extension; `EXTENSION_MAP` is the source of truth for which extensions are analyzed.
  - Every walk goes through [glob.ts](glob.ts) (tinyglobby; `--include` / `--exclude` too), which never follows links (a followed link read outside the repo — `leak.py -> /etc/passwd` — or repeated files through `src/loop -> ..`) and keeps `deep: n` meaning "at most n-1 directories below cwd". A new walk imports `glob.ts`, never the engine.
  - Discovery asks for links (`LinkedFiles`) and keeps a linked file only when it resolves to a regular file inside the resolved root; the rest land in `skippedSymlinks`. Linked directories are never descended.
  - The walks of one analysis share directory listings (`shareDirectoryEntries` in [../extractors/shared/dir-listings.ts](../extractors/shared/dir-listings.ts)), kept unfiltered (each walk prunes, ignores and records links itself); a file created mid-run is seen by the next run only. A walker of its own reads through `listEntries` / `sharedEntries`, not `readdir`. A walk may `prune` directories (a predicate on absolute paths): discovery, sub-project and framework detection prune what `.clarifydocignore` excludes.
  - No walk enters a linked git worktree of a repository below its `cwd` (a `.git` FILE saying `gitdir: …/worktrees/<name>`, as `git worktree add` makes); a submodule, a worktree of a repository elsewhere and `cwd` itself are read.
  - A `namedFiles` entry may start with `.` (only that basename is admitted); `resolveTarget` / `resolveImportSource` match such a path as written before the leading-dot relative-module rewrite.
  - Extension-less scripts are admitted by their first line: a regular, unlinked, non-dotfile in the root or a `bin/`, `script/` or `scripts/` directory, not named like a credential, whose `#!` line — through `env` and its flags — names an interpreter a manifest's `shebangInterpreter` declares (`getLanguageForShebang`). Only the first bytes are read; a file over 512 KB is skipped. A linked script lands in `skippedSymlinks` when it leaves the root, dangles or its inside target is a script (`refusedScriptLink`). A caller holding one path asks `isShebangScriptPlace` (no read) or `shebangScriptAt` (with the `#!` line or a proposed text), as freshness, `analyzeWorkingFiles` and git history do. The registry refuses two plugins declaring one `shebangInterpreterNames` entry.
  - A manifest's `pathScopedExtensions` claims an extension only below a named directory and, through `packageJsonMatches`, only where the nearest `package.json` matches (`pathScopedAdmitted`); `getLanguageForFile` answers by path alone.
- [clarifydoc-ignore.ts](clarifydoc-ignore.ts) — `.clarifydocignore` / `.clarifydoc/ignore` in gitignore syntax, applied through `globUnignored` by every reader that walks the tree for its own files (deployment manifests, CI, config and package manifests, doc drift), so an ignored folder's stack never becomes a container.
  - Inherited up to the nearest project root, except a pattern covering the scan root itself (a parent's `/checkouts/` while analyzing `checkouts/x`); `loadIgnorePatterns(root, scanRoot)` keeps such patterns for sub-roots inside the scan, read once per (root, scan root) per run through `perRunAnswer` in `dir-listings.ts`.
  - Anchoring is decided in `parseIgnorePattern`: a pattern with a `/` is fixed to the ignore file's directory, a slash-less one matches at any depth. Last match wins; a file CAN be re-included under an excluded parent (a deliberate divergence from git, pinned by a test).
  - `ignoredDirectories` is the walk-time view: a directory is pruned only by a pattern every path below inherits and no later `!` follows, so pruning never changes which files come out. `fnmatch` is the only glob engine; `project-config.ts` shares it.
- [framework-detector.ts](framework-detector.ts) — gathers `ProjectInfo` per project root and runs plugin-contributed rules (`plugins/<lang>/frameworks.ts` → `FRAMEWORK_RULES`) into `FrameworkDetection[]` sorted by id; core knows no framework names.
- [deployment.ts](deployment.ts) — compose/Kubernetes topology (`ProjectAnalysis.deployment`): classifies services, matches app services to sub-projects, derives service→service edges from env evidence. Every URL of any scheme in an env value, and every bare `host:port` item (`addressesOfEnvValue`), resolves to the service of exactly that host (compose name, k8s Service alias, `.svc` first label — `clusterServiceLabel`, shared with `resolveHost`) and is judged by its kind: a queue gets a `bus` edge, a cache a `db` edge, else none. A bare `host:port` counts only on a port the service serves (compose `ports`/`expose`, a `containerPort` and its Services' ports `K8sManifests.servicePorts`, else `DEFAULT_SERVICE_PORTS`), whatever the key is named.
- [read-text-file.ts](read-text-file.ts) — `readTextFile` / `decodeText`: the one reader of manifests, build and config files (UTF-8 with or without a mark, UTF-16 LE/BE by its mark, else UTF-8). `readSourceText` reads sources: UTF-16 by its mark, else exactly `readFile(path, "utf-8")`; a plugin's `sourceEncoding: "latin1"` keeps its own read.
- [manifest.ts](manifest.ts) — `manifest.json`, written by every run that writes (entries sorted, so equal runs write equal bytes), read only by `--incremental`. [deploy-rejects.ts](deploy-rejects.ts) — `.deploy-rejects.json` beside it: candidate files a deployment reader turned down by text alone, kept by size + mtime + extractor stamp; only rejections are kept (a Helm template and any file yielding facts are read every run).
- [output-writer.ts](output-writer.ts) — per-file JSONs + `project-summary.json` (+ LSP files when LSP runs). With a worker pool the per-file JSON is not written where it is analyzed: a task with `deferWrite` hands its bytes back (`FileResult.json`), the analyzer holds them until the sources are read (or `CLARIFYDOC_HELD_OUTPUT_MB`, default 256) and gives them to four idle workers in batches (`OutputWriteTask` → `writeOutputFilesSync`), which write while the project passes run. The run waits for them before the summary; a file not written is left out of the manifest so the next run analyzes it again.
- [element-registry.ts](element-registry.ts) — the disk codec: `normalizeProject` lifts repeated nodes into `elements[]` (`file::symbol` ids) and `files[]` page ids, `denormalizeProject` reverses it, and every reader goes through it. A round-trip test over every fixture is the gate; a new path-bearing `ProjectAnalysis` field is added to `rewritePageRefs`.
- [context-docs.ts](context-docs.ts) — decision records (`adr/`, `decisions/`, `rfcs/` …, with their `Status:`), framing documents, schema dumps, the documents `.clarifydoc/config.json` `context` declares (inside the root) and decision markers in comments (`WHY:`, `DECISION:`, `TRADEOFF:`, `RATIONALE:`, `REJECTED:`, `ADR:`); the analyzed files a document names (`governedFiles`) and which were committed after it (`judgeStaleness`, one `git log`). [stated-reasons.ts](stated-reasons.ts) — reasons written without a decision record: comment blocks stating a cause or purpose (the language's `docComments` syntax; licence headers, commented-out code and generated files left out) and the body paragraph stating one in each of a file's last 30 commits (`git log --follow`, or `-L` over one function; bots and bumps skipped), labelled as stated reasons. Both on demand only (`clarifydoc_context_docs file=`), never during `analyze`.
- [project-config.ts](project-config.ts) — `<root>/.clarifydoc/config.json` (optional, never fatal): `layers` (glob → ArchLayer, first match wins), `exempt` and `generated` globs, `context` documents, `refactorPressure` thresholds. Owners of a section resolve it (`resolveArchitectureOverrides`, `resolveRefactorPressureConfig`); unknown keys and bad values become progress warnings and defaults stay. `matchesAnyGlob` is the one glob test. The analyzer loads it once, before the generated/unauthored filter.
- [regex-extractor.ts](regex-extractor.ts) — thin dispatcher for regex-only languages; the logic lives in `src/extractors/plugins/<lang>/`.

## Report

**One renderer, prebuilt.** The report viewer is a React app maintained outside this repository. `report.html` is that viewer built into a single self-contained file (react + d3 + dagre + css inlined, fully offline) with the payload JSON injected. This package carries only the built template; report features are written in the viewer, and rebuilding it refreshes `report-template.html`.

- `html-report.ts` — `generateHtmlReport` loads the prebuilt template from `html-report/viewer-assets/report-template.html` (committed; mirrored into `dist/` by the root tsdown `onSuccess` hook) and swaps `__CLARIFYDOC_TITLE__` / `__CLARIFYDOC_PAYLOAD__`.
  - The payload embeds as **gzip+base64** (`encodeReportPayload`; ~10x smaller than inline JSON, no `<` so no HTML-escaping concerns); `standalone.tsx` inflates it in the browser via the native `DecompressionStream`.
  - Token replace uses a replacer *function* so `$&` cannot corrupt.
  - Also writes `report-data.json` (plain JSON, for consumers that serve the payload in slices) alongside `report.html`.
- `report-payload.ts` — `buildReportPayload(summary)` reshapes a (denormalized) `ProjectAnalysis` into the `ReportPayload` the viewer consumes; `loadReportSummary(dir)` / `loadReportPayload(dir)` read it from disk (with the `lsp-enhancement.json` merge). The payload carries `deferredFields` so a consumer that slices it follows the producer's list.
- `smoke.test.ts` renders a minimal report end-to-end and round-trips hostile payload content through the encoder.

## Adding a new analyzer

1. Create `src/core/my-analyzer.ts` exporting a pure function `analyzeMyThing(input): MyResult[]`.
2. Add the return type to [../types/analysis.ts](../types/analysis.ts) and an optional field to `ProjectAnalysis`.
3. Wire it into the `analyzer.ts` post-analysis section (step 4c).
4. Pass its data to `suggestions-engine.ts` if it should drive suggestions.
5. If the viewer should show it, add it to `report-payload.ts`; the tab itself is written in the viewer, which is then rebuilt into `report-template.html`.
6. Add exports to [../index.ts](../index.ts) if public API.

## Conventions

Per-language spellings of every rule below live in each plugin's AGENTS.md.

### Rules for core code

- **Language-agnostic** — core names no language, ORM, framework or file convention; it asks the registry or a plugin hook. Plugins state facts, core resolves them (never pre-resolve in a plugin).
- **Pure functions** — no file IO except `output-writer.ts` and `html-report.ts`; input is `FileAnalysis[]`, output typed results.
- **Optional fields** — new `ProjectAnalysis` / `FileAnalysis` fields are optional so old `project-summary.json` files load.
- **One import contract** — `import-index.ts` turns every specifier into a file through one helper (`resolveSpecifier`), by the name the module exports (`ImportInfo.aliases[local]`, never the local alias), for a language's own `resolveImport` and the generic path, in `localFor` and `fileForSource` alike.
- **Progress** through `ProgressReporter` in `analyzer.ts`, never `console.log`.
- **BFS** with an index pointer (`let qi = 0; while (qi < queue.length) { ... queue[qi++]; ... }`), never `Array.shift()`.
- **Link guards** — a heuristic link needs a stated basis (declared type, import, same sub-project, one candidate); the undecidable stays unlinked or AMBIGUOUS.

### Impact: changed symbols and dependents

- **`changed-symbols.ts` / `impact-diff.ts`** — `parseUnifiedHunks` keeps new-side ranges on the Map (patch coverage) and match ranges on `old` (old-side lines of deletes/edits, the line a pure insertion follows; pure deletions on `deleted`); `symbolsInHunks` matches them against the stored analysis. A deleted file (`+++ /dev/null`) is keyed by its old path with every old line on `hunks.old`; a range covering several functions names each; lines directly above a function (a decorator) belong to it.
- **Dependents are charged by the member that changed.**
  - With line ranges, `computeImpactDiff` cuts `dependents` to files that NAME what changed ([member-dependents.ts](member-dependents.ts): call and import-by-name links into a changed function; for a type touched outside its methods — `classLevel`, compared by `classChanges` — its blast-radius `typeUsages` kinds: a removed or re-typed member charges every user, an added member of an interface or abstract type only what implements, extends or builds it, `ClassChange.addedField` what builds the class) and keeps the importer count as `narrowed.importers`. Risk, tests, screens and routes read the narrowed list; `moduleOnly` edits, no line ranges, an unchanged type comparison or a type with no usage record keep every importer charged.
  - A removed or re-typed function is `breaking` only for callers the change leaves alone (`signatureChanges` `edited`); an edit inside a re-exporting file's import block (`HunkSpans.reexports`, `ImpactDiff` `forwarded`) charges only importers of a forwarded name (`filesImportingNames`).
  - A file handing a charged module on whole (`starForwarders`, from the `exports` `*` rows) is charged up the chain only when the change takes a name away; targets come from `ProjectAnalysis.starReexports` (`starReexportTargets` via `ImportIndex.fileForModule`, no path-word guess), an older summary reports `StarForwarders.stale` (`STAR_REEXPORTS_STALE_NOTE`). `narrowed.members[].lost` marks a lost name; `clarifydoc_blast_radius` takes `change` (removed/renamed/moved/retyped/body) and cascades only for a lost name. The CLI `impact` and the MCP tools build `symbols` with `symbolsOfChange` (also `impactOfContents`, a proposed edit).
  - A hunk wholly inside a module-level name (`FileAnalysis.moduleNames`) is an edit of it (`symbolsInHunks` `bound`, judged before the import block); `boundReaders` charges the importers (`componentGraph`) whose imports list the name, take the module whole or star-import it, following re-exports four hops deep; an importer with no per-file record stays charged, as does every importer for a hunk no name covers.

### Lint and caret assertions

- **`analysis-lint.ts`** — `lintAnalysis(project, files?)` checks one analysis against itself (dangling links, relations, `apiRouteLinks`; lines past a file's end; two routes with one `dedupeRoutes` key); `clarifydoc lint <outputDir>` prints it (exit 1), `analysis-lint.test.ts` gates every `test-output/` summary with a commented allow-list. A new rule must be clean on a fresh fixture set, or fix the extractor.
- **`caret-assertions.ts`** — a comment line under a source line, in the language's line-comment prefix (`manifest.docComments.line`, last entry), whose `^^^` marks a span and names the fact: `def <name>`, `call [-> <file>::<symbol> | -> unresolved]` (`unresolved` fails when any call in the span carries a link), `route [METHOD] <path>`, `api-call [METHOD] <url> [-> METHOD <routePath>]`, `table <name> [read|write]`.
  - `checkCaretAssertions(project, files)` (pure) judges each `passed` / `failed` / `unmatched` by line and span text; `renderCarets` prints the grammar. `caret-testkit.ts` (`expectCarets({path: source})`) is the vitest helper, never imported by the product; `clarifydoc lint <dir> --carets [file]`; `caret-fixture.test.ts` walks `CARET_FIXTURES`.

### Graph notes

- `entity-graph.ts` `EntityGraphNode.origin: "contract"` marks a schema an API-contract language declares (carried through `element-registry.ts`): shown apart, never covering a same-named table (`synthesizeReferencedTableEntities` seeds its dedup set without them, `nodeKeyIndex` ranks their keys last).
- `data-access-graph.ts` queue nodes are `queue::<broker>::<address>` (`DataSourceInfo.broker`, else read from the label by `extractors/shared/message-brokers.ts`, else the address's other rows, else `?`); only equal broker + address pair (`synthesizeQueueSymbolLinks`, `SymbolDataAccess.broker`); an unresolved destination is `queue::<broker>::?<file>:<line>`, never paired.
- `queue-env-targets.ts` retargets a queue row whose target is an env var name to the queue the deployment gives it (a bus edge with `DeployedService.destination` from a service running the row's project; disagreeing services refuse).

### Receiver typing and URL targets

- **Values the source chooses between stay AMBIGUOUS.** `DataSourceInfo.targetChoice` (and `PathArgCall.argAlternatives`) marks `targetAlternatives` that are the values one local takes: the route linker links EVERY route a value reaches, AMBIGUOUS (one of several INFERRED at most), where a helper's `urlTemplateAlternatives` stay first-hit. `CallInfo.alternative` marks one of several calls a descriptor key holds (`task.api.subscribe()`): its links cap at AMBIGUOUS.
  - A hole reading a member of a typed local (nested path, `this.field.kind`, a loop element, a closed `const` array, `FileAnalysis.templateLoops`) is expanded by `typed-member-holes.ts` when the declared type is a closed set of strings (an enum or literal union, read through `requestSchema.describeType`).
  - A URL helper called through a module binding (`urls.club_url(id)`) is looked up in the imported module's file only where the head is the module itself — a namespace import, a binding named like the module's file, or like its directory when the file is the index module (`directoryIndexStems`) — and the module does not export it as a member; `api.club_url(id)` with no such binding keeps its own URL, while a class-method helper may match by bare name through a receiver (`configService.APIUrl(…)`).
- A bare type name in a package-scoped language (`importsDeclaredPackages`) is the class its own package declares before any namesake (`typeFileFor`).
- **Wrapper index** ([wrapper-index.ts](wrapper-index.ts)) — one import-resolved index behind `expandRequestFactories` and the JS plugin's `resolveUrlBuilders`. A name resolves lexically, through its import (`importedFrom`), then to the ONE top-level declaration in the caller's sub-project (`declarationsInProject`); else unknown. A member wrapper (`receiver.callee`) counts only when EVERY same-named definition the receiver can be (`memberDefinitions`) forwards the URL.
- **Bare-call locals and star chains.** A local initialised by a bare call states `localTypes[].from` as `name()`; the linker types it by the enclosing class's own method return type, else through `importedFunctionLink` (which reads a bare call an import puts in scope, `ImportInfo.inScope`, as cross-file). A bare call through a wildcard import whose module declares nothing follows that module's wildcard imports up to three hops (`starChainDefinition`, Strategy 6b), linking only when exactly one file defines the name.
- **Receivers with several candidate types.** A type a run-time choice makes — `localTypes` entries sharing one `choice` (a conditional initializer, or an if/else or `switch` chain right after the declaration) or a declared `Club | Player` / `Club & Named` (`receiverTypeCandidates` in `extractors/shared/type-parser.ts`, where the manifest sets `candidateTypeUnions`) — is typed per candidate: `scopedName` hands them to its caller in `branches`, and the call links through each (`resolveCallToDefinition`). A candidate without the member is skipped; different methods link each, AMBIGUOUS (`injection`); a lone declaring candidate is INFERRED; a non-project candidate leaves the receiver untyped; `Club | null` / `Club | undefined` stay `Club` (`receiverTypeName`'s absent types).

### Value flow

- **Value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass in `buildSymbolLinks`, after `handedParameterLinks`/`handedClientLinks`, before `abstractDispatchLinks`) follows a function value from where it is named to the call that runs it, through locals, parameters, fields, lists and returns.
  - Facts are neutral and plugin-stated (`FunctionInfo.valueFlow`, `FileAnalysis.moduleValueFlow`: `seed` / `copy` / `arg` / `result` / `return` / `invoke` over `ValueCell`s — a name and optionally a member; `this`/`self` is the receiver, a list or map element the member `[]`). Plugins resolve nothing; the pass costs nothing when no file states any.
  - Core names the cells: a formal when `params` list it, a local when its facts or `localTypes` bind it, the file's module cell (`ValueCell.module`; a global written from a function is `{ name: X, module: true }`) or the exporting file's when imported; a member is the class's field (own, then bases) for `this`/a typed local, the module holder's otherwise. A project class name names its own members; a dotted name walks property types first; sibling scopes of one member declaring one local are two cells (`h@<first line of the scope>`); a name another file of the package declares is a `ValueCell.package` cell joined to the one sibling binding it (`ValueFlowHost.sharedModuleFiles`).
  - Seeds resolve through `resolvePassedName` (never a name guess); one held lambda's seeds and copies share a `lambda` id standing for at most four project functions. Arguments bind to formals by written index (a leading `self`/`this`/`cls` skipped) or by `name` against `ParamInfo.argumentLabel ?? name` (`**kwargs` or an unknown name binds nothing), through the callees ordinary links found plus what the solver finds, to an inclusion-based, flow- and context-insensitive fixpoint.
  - Every invoke site links to each function its cell holds: `value-flow`, relation `calls`, INFERRED for 1 to 4 targets, AMBIGUOUS for 5 to 32, nothing above 32 (the overflow poisons the cell), never EXTRACTED, never production to test file, never a function written in place to itself (`const old = x.f; x.f = () => old()`; real recursion keeps its link); a spent work budget emits nothing.
  - Name tiers: a call with an `invoke` fact skips them (`LinkContext.invokeSites`, `valueFlowInvokeSites`) when its cell is a parameter or a seed/copy writes it; a name only a call's result writes (`const reload = debounce(load)`, `useCallback(…)`) keeps a link into its own file only; a member nothing writes (`this.model.apply()`) and a dotted path rooted at an imported name (`kit.Bench.label()`) keep ordinary resolution; `boundLocally` counts as an invoke of its cell; `CallInfo.via` still runs them.
  - **`ifFnType`** — an `invoke` (or a C `copy` of a parameter into a field) may carry a type name the file cannot judge; `scopesOf` drops it unless the host says it runs a function (`ValueFlowHost.isFunctionType(file, type)`; `isCallableMember({ file, symbol, receiver, member })` for `fieldInvokes`). The linker answers (`functionTypeQuestion`) from `FileAnalysis.functionTypeAliases` (`ast.functionTypeAliases`) and the class index through the nearest scope declaring the name: the file, its imports, the packages it imports by name, its sub-project, the sub-projects it imports, those its build references (`SubProject.references`), or a shared include closure — an alias alone is a function type, a class (alone or beside an alias) is not, names are never pooled across sub-projects. A dropped invoke neither links nor keeps the name tiers off the call.
  - `fieldInvokes` derives an `invoke` for `x.m()` through a field a class declares callable (`PropertyInfo.callable`, names in `CallableQuestions.callableFieldNames`) when no plugin invoke is stated at the line and `isCallableMember` (`callableMemberQuestion`) says yes: receiver typed by `receiverDeclaredType`, class by `locateClass` from the caller's file, then its bases (`parentClassOf`, three hops).

### Field writes and thrown types

- **Field writes and thrown types** ([member-effects.ts](member-effects.ts), `ProjectAnalysis.fieldWrites` / `thrownTypes`): who assigns a field and who throws an exception class, resolved to project classes by declared types only and within the writer's language family. Surfaces: `clarifydoc_trace direction=writers` (`Class.field`, or an exception's throwers) and `clarifydoc_explain`'s "Writes and throws" (`mcp/tools/member-effects.ts`). Rows hold names and `path:line`, skip tests and generated files, exist only where something is stated.
  - Plugin facts: what a function assigns (`FunctionInfo.fieldWrites`: `member`, `receiver` as written — `this`, `this.<field>`, a typed parameter or local, "" for a bare field — and line; never from an untyped receiver) and throws (`FunctionInfo.throws`: the type with its qualifier, the site, `declared` for a signature or docblock). A constructor states no writes; a member a type's body declares unwritten is an `init` declaration, never listed as a writer.
  - Core decides the class from declared types only: `this` and a bare field are the enclosing class or the `extends`-chain base declaring the field; `this.<field>` goes through the field's declared type; a name through its parameter type or its one stated local type; a class name binds only where exactly one class of that name is in reach (own file, sub-project, project).
  - A qualified name binds by its last segment only through a qualifier the project backs (`qualifierBacksClass`: a namespace/package the class is declared in — `ClassInfo.namespace`, `FileAnalysis.packageName`/`declaredNamespace` —, directories or a file stem on its path, a class its own file declares, or an import of it); `writtenTypeName` keeps the qualifier `receiverTypeName` drops; `relativeTypeQualifiers` name no module; `wholeTypeNames` stops the fallback.
  - Lookup scope: `typesBeyondDirectory` looks a type up past its directory (the directory first; a qualified name or several real declarations the writing file does not own refuse); `classNamesByEvidence` binds through the writing file's `use`/namespace ([class-evidence.ts](class-evidence.ts), shared with the symbol linker; `ParamInfo.typePath`/`PropertyInfo.typePath`); `typesSpanFiles` makes a directory's parts one type (`ClassRef.parts`); a bare package-variable assignment (`fieldWrites[].package`) becomes a `via: "package"` row only when exactly one file declares it (`FileAnalysis.packageVariables`, `moduleVariableHome`).

### Config keys, config files, spec join, vulnerable-function reach

- **Config key → consumer** ([config-keys.ts](config-keys.ts), `ProjectAnalysis.configKeys`): `serviceConfig.sources` states the keys config files set (`keysOnly: true`: no call origin may read it); code states a read as an `env` data source with `DataSourceInfo.configRead` (`key`, or `prefix`) or `FileAnalysis.configKeyReads` (`variable`). Joined per sub-project (a namesake key elsewhere is another setting); relaxed binding (`match-day` = `matchDay` = `match_day`) and `envNamesFor` match a key; a key only a test profile sets (`ConfigEntry.test`) is read by test code only. Rows exist only for read keys, hold names and locations, never values, cap at 50 consumers; a key whose `envNamesFor` name a deployed service sets joins that variable's reads (`env-vars.ts`).
- **Config file → consumer** ([config-files.ts](config-files.ts), `ProjectAnalysis.configFiles`): `ast.filePathReads` states a path of plain literals (`anchor: "file"` for a file-relative anchor); `joinConfigFiles` resolves beside the reader, then at its sub-project root, then at the analysis root, never by file name alone; a `..` leaving the root, an absolute, `~` or URL path, a test reader and a code target join nothing.
- **Spec join beside a code twin** — a contract row (OpenAPI, …) with exactly one production code route of its method and normalized path joins by operation id only, never by a name derived from its path (`spec-join`, `codeServes` in [symbol-linker.ts](symbol-linker.ts); `pairContractTwins`), and even then only a function in the twin's file; no twin or two keeps the full name join. Both deciders count twins by ONE rule, `codeTwinsIndex` ([route-linker.ts](route-linker.ts)): method, normalized path, narrowed by the API version the contract path names (the symbol linker also asks `loose`), each over its own code set.
- **Vulnerable-function reach** — `analyze --osv` reads the functions an advisory names (`affected[].ecosystem_specific.imports` → `ExternalPackage.advisories[].functions`) through the ecosystem's `PackageManagerSpec.advisoryFunctions`; other ecosystems stay package-level with no `reach`.
  - [vuln-reach.ts](vuln-reach.ts) `attachVulnerableReach`: a call `head.Symbol(…)` on a name the file imports from that exact path is a hit; symbol links walked backwards (depth 8, never across AMBIGUOUS) to a handler or entry point give `reach.status` `reachable` (with `calls[].from` and the shortest `path`), else `called`; no hit is `not-called`, except an advisory also naming a method (`Type.Method`): `not-judged`. Tests are skipped.
  - A route's root is [`routeHandlerKey`](api-route-symbol-links.ts), shared with `computeDataFlows` (a route registered inside another function: `handlerKeyByName`, `registeredElsewhere`, which also resolves an entry point's), plus the middleware it names. The OSV fetch is injectable (`AnalyzeOptions.osvFetch`).

## The pipeline, step by step

The ordered overview. Each pass has its rules in the section that owns it ("Analyzers (post-analysis passes)", "Discovery & IO", "Conventions"); per-language rules live in the plugin folders' `AGENTS.md` files under [../extractors/plugins/](../extractors/plugins/).

1. **Discover files** — [file-discovery.ts](file-discovery.ts) (rules in "Discovery & IO").
   - A glob walk by extension through `core/glob.ts`, which never follows links; it skips credential-looking files and a linked git worktree inside the root (a `.git` FILE naming `…/worktrees/…`; a submodule stays).
   - A manifest's `packageRoots` re-admits build-output-looking directories below it as packages; a generated file past 4 MB is skipped with its reason.
   - A folder `.clarifydocignore` names is out of every reader that walks the tree itself — deployment manifests, CI pipelines, config and package files, Markdown (`globUnignored`); `.gitignore` is not read.
   - Files under a vendored root (`third_party/`, `vendored/`, `public/**/plugins|lib`) or carrying a copied single-file library's banner (the manifest's `vendoredBanners`, `FileAnalysis.vendoredLibrary`) stay analyzed but contribute no routes, screens, calls or data (`dropVendoredFacts`).
   - **Code no plugin reads** — a known code extension (`extractors/shared/known-code-extensions.ts`: `.sol`, `.elm`, `.tcl`, `.nix`, `.gd`, `.robot`…) minus every extension a plugin claims (`UNCLAIMED_CODE_EXTENSIONS`) is matched by the same walk and only counted ([unread-code.ts](unread-code.ts)): `ProjectAnalysis.unreadCode`, the `Not read:` line of `analyze`, a `not read:` line of `clarifydoc_status`.
2. **Detect frameworks** — [framework-detector.ts](framework-detector.ts). Manifests, build files and config files are read through `readTextFile` ([read-text-file.ts](read-text-file.ts): UTF-8 with or without a mark, UTF-16 by its mark); a UTF-16 source file is read by its mark (`readSourceText`).
3. **Detect sub-projects** — [project-detector.ts](project-detector.ts); every file gets a `projectId` (innermost enclosing project).
   - The marker files that make a directory a project are each plugin's `projectMarkers` on the static manifest (`ProjectMarkerSpec`: glob, `kind`, `priority` — the lowest wins a directory holding several kinds —, optional `isProjectRoot`). The registry builds `PROJECT_MARKERS` and `PROJECT_KIND_PRIORITY` (a kind stated with two priorities throws); core keeps only innermost-wins and the pick; `SubProjectKind` is an open string.
   - A manifest's `declaredProjects` hook makes the directories a build file names sub-projects too, with `dependsOn`/`aggregate` read as `SubProject.references`.
4. **Per-file analysis** — see "Per-file analysis & workers". Parallel; worker threads from 200 files. Extracts imports/exports, functions/classes, routes, data sources, ORM entities + relations, data mutations, events, interactive elements, template tree, type references, complexity, security. With `--incremental`, unchanged files reuse cached JSON.
5. **Post-analysis** — one bullet per pass.
   - **Component graph** — imports, plus implements/extends edges no import states ([inheritance-edges.ts](inheritance-edges.ts)); an import of a declared package or of the standard library never binds a project file by the names it imports.
   - **Link graph** (proximity-weighted).
   - **Symbol links** ([symbol-linker.ts](symbol-linker.ts)) — call→def traces, dependency-injection aware: through `FileAnalysis.diBindings` a call on an injected/typed receiver reaches the implementation the container builds ("Teach a plugin a DI container").
   - **Route resolvers** (plugin-contributed, cross-file route facts) — joined before router mounts compose and before the symbol linker anchors routes: mounts and includes, routes registered by a function on the router it is handed (`owner: "fn:<name>"` rows + `router-call` facts, composed by [plugins/shared/router-functions.ts](../extractors/plugins/shared/router-functions.ts)), security-configuration rules, guards a route inherits from where its router or controller is declared ([plugins/shared/class-guards.ts](../extractors/plugins/shared/class-guards.ts)).
     - Guards a route inherits through its mount, and registrar-declared routes, are stated once in "Analyzers (post-analysis passes)". A filter or dependency is a guard only when its name says it checks the caller ([plugins/shared/guard-words.ts](../extractors/plugins/shared/guard-words.ts)).
   - **Dispatch resolvers** (plugin-contributed): links the text has no call for — a call landing on an abstract method → the one override below the class it dispatches on (`abstractDispatchLinks`; `ClassInfo.abstract`/`FunctionInfo.abstract`), a framework's own dispatch (mediators, advice, assembly scans, template handlers, emitted events, template refs), and a manifest's `foreignImportTarget` (`foreignImportMember`), the one link that crosses language families (a bare call only, one declaring file only).
   - **Stated local path** (`RouteInfo.localPath`, set by [route-bases.ts](route-bases.ts), never by a plugin, omitted when equal to `path`): the route linker's added-base tier meets a call that leaves the mount out through it first — INFERRED, `base-prefix:<mount>`, only where one sub-project states that path.
   - **Route identity** (`dedupeRoutes` keys a route on sub-project + method + path + declared API-version set).
   - **Client resolution** — a plugin's `resolveProject` hook on its data-source extractor substitutes a project URL-builder's `urlTemplate` (`urlTemplateAlternatives` → `targetAlternatives`); generated clients (`FileAnalysis.generatedClients`) and framework hooks become api-calls at the spec's method and path; a fact map is read by own property only (`ownValue`, [extractors/shared/own-value.ts](../extractors/shared/own-value.ts)); reactive-trigger joins are in [reactive-triggers.ts](reactive-triggers.ts).
   - **Scheme-hole URLs** (`finalizeApiTargets`): leading holes spelling `${protocol}://${host}[:${port}]` are an absolute URL of unknown origin, the path after it the target.
   - **Request wrappers** — a project method that hands its path parameter to a client and picks the verb from another is joined by `expandRequestFactories` from each call site's `FileAnalysis.pathArgCalls` (regex plugins emit them through `RegexLangSpec.extractPathArgCalls`).
   - **Client-proxy calls** ([client-proxies.ts](client-proxies.ts)) — a call on a receiver whose declared type a registration says is a REST client proxy (`HttpClientRegistration.proxyOf`) becomes an api-call carrying its `contract`, the interface operation `a.b.PersonApi#getPerson`.
   - **gRPC client stubs** ([grpc-clients.ts](grpc-clients.ts)) — a plugin's `grpcStubService` reads the generator's stub naming; a call on a stub becomes an api-call at the rpc row's own path when the `.proto` is in the analysis, else with its `contract`.
   - **Call origins** ([call-origins.ts](call-origins.ts)) — the service each call reaches, followed through stated facts: an absolute or loopback URL, the client it is made through (`FileAnalysis.httpClientRegistrations`), or a base expression the plugin reads (`serviceConfig.baseRefOf`), valued from the caller's deployment env (`DeployedService.urlEnv`) and config files ([config-values.ts](config-values.ts)) and the host resolved through the address book ([service-addresses.ts](service-addresses.ts); `ConfigEntry.serviceName`). A project is named only when every value agrees; a base valued only by the code's fallback literal whose host nothing names keeps its unresolved-base link (INFERRED).
     - **Forwarding** — a request arriving at a project with a matching `ProxyRule` (`meta.ast.proxyRules`, `serviceConfig.proxySources`, a gateway's routes) goes on to the rule's target, path rewritten, up to four hops → `apiCalls[].origin`, `proxyRules`.
   - **Route linking** ([route-linker.ts](route-linker.ts), `apiRouteLinks`) — api-call URL ↔ route by method + normalized path across three tiers (as written, a conventional base stripped, one added): code > contract > prefix-unknown, literal tier first, same sub-project; a route serving another method is REFUSED. A contract row yields to the code row implementing it (`pairContractTwins`; "Spec join beside a code twin" in "Conventions"); a call with a `contract` joins the route declaring that operation first (`matchedVia: "contract"`); an EXTRACTED origin joins only the routes that project serves (`projectServesClosure`, miss = `refused.originMismatch`), an INFERRED one only ranks them; the version the client names (`/api/v5/`) wins, `matchedVia: "version-mismatch"` when none does. Links from tests and generated code carry `sourceRole`; `apiRouteLinkStats` counts links, refusals and unmatched calls.
   - **Handler params + request schemas** ([request-schemas.ts](request-schemas.ts)) — `params` from the handler's signature (`bindParam` hook) and body reads (`FunctionInfo.requestAccess`); a body-bound class flattened through `extends` and mapped by the plugin's `requestSchema` hooks → `routeMap[].requestSchema`.
   - **Server redirects + navigation map** ([server-redirects.ts](server-redirects.ts): `RouteInfo.redirectsTo`; [screen-flow.ts](screen-flow.ts): `ProjectAnalysis.screenFlow`) — screens and dialogs joined by typed edges (navigate, dialog, router redirect, server redirect, form submit — a post to the page's own route is a `submit` self-edge, the one self-edge kept), from the main form or `/`.
   - **Webhook routes** ([webhook-routes.ts](webhook-routes.ts)) — `RouteInfo.webhook` (`provider`, `verified`; `verified: false` only when every call in reach is known); the `webhook-unverified` finding (CWE-345) only when every call in reach is known; a webhook route is never "no call reaches".
   - **Click→data trace edges** ([api-route-symbol-links.ts](api-route-symbol-links.ts)) — an api-call joining a route whose handler is an action a mixin defines for several includers lands on that includer's own `route:` symbol.
   - **Value flow** ([value-flow.ts](value-flow.ts), the `valueFlowLinks` pass after `handedClientLinks`) — rules in "Conventions" → "Value flow".
6. **LSP enhancement** (optional) — resolve unresolved calls; writes `lsp-enhancement.json` + `lsp-ground-truth.json`. The Docker probe (`isDockerAvailable`: `DOCKER_HOST`, else the current context's `meta.json`, else the platform sockets, pinged with `GET /_ping`; a `tcp://`, `ssh://` or unreadable endpoint gets `docker info` bounded to 1.5 s) starts before cross-file linking and is awaited here; a run where no language has a configured server never probes. Containers run with `--network none` (`LspDockerConfig.network`, `dockerRunArgs`) except servers that restore packages to type-check, which say `"bridge"`; `cli/SECURITY.md` states it.
7. **Advanced analysis** — one bullet per pass.
   - **Quality and topology** — patterns, duplicates, layer violations, blast radius, communities/topology, class graph.
   - **Data-access graph** — message-queue publish/consume nodes (scoped by topic where the framework scopes them — `core/channel-topics.ts`) and the rest of the data stores. **Entity (ER) graph** — a schema an API contract declares is `origin: "contract"`, listed apart by `clarifydoc_data_model` and the viewer, and never covers a same-named table.
   - **External-package inventory** — with `--osv`, an advisory naming vulnerable functions carries `functions` and `reach` (`routeHandlerKey`; [vuln-reach.ts](vuln-reach.ts)).
   - **Deployment topology** ([deployment.ts](deployment.ts), [dockerfiles.ts](dockerfiles.ts): a compose `build:` reads the `CMD`/`ENV`, `entryFile` is the source file the command starts; [deployment-terraform.ts](deployment-terraform.ts); [deployment-cloudformation.ts](deployment-cloudformation.ts): env `Ref`/`GetAtt`/`Sub`; [deploy-rejects.ts](deploy-rejects.ts)'s `.deploy-rejects.json`; `RawService.servedPorts`, `DEFAULT_SERVICE_PORTS`, `clusterServiceLabel`), **config keys** ([config-keys.ts](config-keys.ts), `configKeys`, `configRead`, `configKeyReads`, `serviceConfig.normalizeKey`), **config files** ([config-files.ts](config-files.ts), `configFiles`, `FileAnalysis.filePathReads` through `meta.ast.filePathReads`), **environment variables** ([env-vars.ts](env-vars.ts)), **CI deploys** ([ci-pipelines.ts](ci-pipelines.ts)).
   - **Cross-file taint** ([cross-file-taint.ts](cross-file-taint.ts)) — a handler's request input passed into a function another file declares, joined through the symbol links from each file's `taintFacts`.
   - **Dead code** ([dead-code.ts](dead-code.ts), `analyzeReachability`) — judged only for languages whose plugin declares a `reachability` model; a process or container command is an entry; each unused export carries `confidence` and `reasons` (`own-file-only`, `re-exported`: INFERRED; `name-referenced`, `unresolved-imports`: AMBIGUOUS), filtered by `analyze --min-confidence` and `clarifydoc_health`'s `minConfidence`; generator-written classes are generated, so their calls' links carry `sourceRole: generated`.
   - **Health** and **suggestions**; **test coverage** (`--coverage` or the usual report paths → `testCoverage` per file and function, by path suffix — [test-coverage.ts](test-coverage.ts)); **doc drift** ([doc-drift.ts](doc-drift.ts), guarded by git).
   - **Performance patterns** — `query-in-loop`, `blocking-in-async` (`blockingCalls`; [query-in-loop.ts](query-in-loop.ts)), ordered by `rankPerformanceByReach`; a manifest's `blockingOnReceiver` flags `x.Wait()` / `x.Result` only when `x`'s declared type is that type.
   - **Ignore suggestions** ([ignore-suggestions.ts](ignore-suggestions.ts)), **type-only import edges** (`typeOnlyEdges`: cycles are judged without them — [import-kinds.ts](import-kinds.ts)), **named communities** ([community-names.ts](community-names.ts)), **entry points** that are not routes (`entryPoints`, `command` data flows), **external API specs** (`--spec`, read as `@spec/<name>`) and the third-party service an external call reaches (`CallOrigin.service`, `externalServices`).
8. **Write output** — per-file JSON + `project-summary.json` + `report-data.json` (viewer payload, written unconditionally) (+ `manifest.json`, + optional `report.html`). The JSON artifacts are streamed in slices ([json-stream.ts](json-stream.ts): the top levels walked, members through native `JSON.stringify` in batches), byte-identical to `JSON.stringify(v, null, 2)`, never one whole-file string (about −0.9 GB peak on a 6,000-file repository), written to `<name>.partial` and renamed; large text such as `report.html` goes out through `writeTextFile` in 8 M-character slices.

## Data structures in detail

- `RouteInfo` — the attribute layer is kept, not just the path: `middleware` (guard strings), `auth` (policies/roles/schemes/anonymous, structured), `versions`/`deprecatedVersions`, `params` (each handler parameter with its binding: body/query/route/header/form/services, `inferred` when derived from framework defaults).
  - A page route carries `renderMode` (`ssr`/`ssg`/`isr`/`csr`, copied to `ScreenInfo.renderMode` and shown by `clarifydoc_screens`) only where the framework's own settings state it.
  - Field names are language-agnostic; any plugin can fill them.
  - Decorators (`FunctionInfo`/`ClassInfo`/`PropertyInfo.decorators`) carry their **arguments** in every language — never reduce an attribute to its bare name.
- `ProjectAnalysis` — aggregated: `subProjects`/`fileProjects`, `componentGraph`, `linkGraph` (weighted), `symbolLinks` (call→def, `resolvedBy`, `confidence`), `routeMap` (rows carry `filePath` + `projectId`, optional `requestSchema`), `apiCalls`, `apiRouteLinks` (each with its `sourceProject`/`targetProject`), `projectDependencies` (sub-project → sub-project HTTP/bus edges with their endpoints and the deployment edge that agrees — `clarifydoc_services`, the Architecture Containers view), `screens`, `entityGraph`, `dataAccessGraph`, `classGraph`, `migrations`, `externalPackages`, `deployment`, `deadCode` (unreachable files + unused exports, with what was judged and what was skipped), `fieldWrites`/`thrownTypes` (rules in "Conventions" → "Field writes and thrown types"), plus all quality/topology results.

## How to extend the core

Plugins state facts, core decides; every hook below lives on the plugin's static manifest or `meta.ts` ([../types/language-plugin.ts](../types/language-plugin.ts)) and is leaf code that keeps no module state. Per-language spellings are in the plugin folders' `AGENTS.md`.

- **Teach a plugin a DI container** — plugins only report facts; core resolves. Never pre-resolve in a plugin.
  - Fill `ParamInfo`/`PropertyInfo.type` as written (core normalizes with `receiverTypeName`, unwrapping `meta.transparentTypeWrappers`), `qualifier` for a token/key on an injection point, constructor params, `FunctionInfo.localTypes` for typed locals and container lookups, `CallInfo.receiverType` for a lookup chained into a call (`meta.calls.receiverTypeOf`, or a regex `callPatterns` entry), `ClassInfo.kind: "interface"` (+ `structural: true`), and registrations as `FileAnalysis.diBindings` (`meta.ast.diBindings` / `RegexLangSpec.extractDiBindings`).
  - A local initialized by a call that states no type is stated as that call in `localTypes[].from` (spelled by `callChainText`, `awaited` when awaited; one entry per distinct initializer, a stated type always wins). Core types it through declared return types (`FunctionInfo.returnType`; `asyncResultTypes` unwraps the async wrapper), and only when every initializer agrees.
  - The arms of one conditional initializer are marked with a shared `localTypes[].choice`; arms are all-or-nothing — one initializer core cannot type leaves the local untyped, so plugins emit every arm and never pre-filter. Separate declarations of one name in different blocks carry no `choice`.
  - A union type (manifest `candidateTypeUnions`) links once per candidate that declares the member: AMBIGUOUS when the targets differ, INFERRED when one declares it, untyped when any candidate is no project class.
  - A type read off one assignment is `localTypes[].inferred`; core drops it when another assignment of the name is a call it cannot type or one typing another class.
  - A `DiBinding` says asking for `service` (type or token) yields `implementation`, with `qualifier`/`keyedOnly`, `primary`, `matchesMemberName`, `consumer` (contextual), `ifAbsent`, `conditional` (active only under a profile or condition, yielding to an unconditional binding).
  - Core picks: test containers never apply to production code; contextual beats general; the consumer's own sub-project beats others (which must agree); a default yields to a real registration; then ONE implementation, or one primary, or one named like the member — otherwise it refuses to choose and the call stays on the interface.
- **Teach a plugin where services are** — a leaf `plugins/<lang>/service-config.ts` exporting a `ServiceConfigSpec` on the manifest's `serviceConfig`:
  - `sources`: config files at each project root and a parser returning `ConfigEntry`s — mark `profile`/`test`, `env` for variables a profile sets, `listen` for URLs the project binds; core keeps only URL-shaped values; `ConfigEntry.envNames` carries the variables that override an entry.
  - `baseRefOf`: a base expression as written → `env`/`config`/`literal` `CallBaseRef`, with `fallback` for a default literal (`?? "…"`). `envNamesFor`: config key → overriding env vars. `normalizeKey`: a key's relaxed spelling.
  - `routeBaseOf`: every entry → the base the project serves its routes under, profiles never; [route-bases.ts](route-bases.ts) prefixes the complete API routes (`RouteInfo.basePath`).
  - `proxySources`: config files declaring forwarding rules → `ProxyRule`s ([plugins/shared/proxy-kit.ts](../extractors/plugins/shared/proxy-kit.ts)); a code file's proxies go through `meta.ast.proxyRules`.
  - Clients go through `meta.ast.httpClientRegistrations` / `RegexLangSpec.extractHttpClientRegistrations` (keyed the way a call names the client) and the call row's `baseRef: { kind: "client" }` or `client`; a generated proxy of an API interface sets `proxyOf` to its fully qualified name, and core turns every call on a receiver of that type into a contract call. Routes declared on a typed API set `RouteInfo.contract`.
  - Never resolve a host in the plugin — core's call-origin pass does. `.env` files are never read (discovery treats them as secrets).
  - Labelled fixture: `test-fixtures/sample-microservices` + [cross-project-fixture.test.ts](cross-project-fixture.test.ts).
- **Add a package manager** — a `PackageManagerSpec` in `plugins/<lang>/package-manifests.ts`, listed in the manifest's `packageManagers`:
  - The manifest files to read at each root (exact names or bounded globs, `firstOnly`, `readSibling` for a lockfile) and a parser per format; `selfName` for the package the project publishes; `registry` when its names are another ecosystem's.
  - How an import names a package: `importKey`, `packageKey`, `prefixMatch`, `assertsUnused` only where EVERY import of a package is visible, `installedOwners`, `installedApi` (read on demand by `clarifydoc_extract package=`, never during analysis).
  - Each language lists the ecosystems it imports from in `packageEcosystems`. It lives on the static manifest because the inventory reads every manifest whether or not the language was discovered.
  - [dependency-inventory.ts](dependency-inventory.ts) only walks the roots, dedupes, classifies and counts — it names no ecosystem but `.gitmodules`.
- **Judge a language for dead code** — give its meta a `reachability` hook (`ReachabilityHooks`): `load()` returns a model that says which files START the program (`entryReason` — these anchor a project), which are merely RUN BY A TOOL (`passiveReason`: kept alive, never reported, anchor nothing), resolves an import specifier to the files it loads (`resolve`: `[]` = external, `null` = local but unknown) and resolves `pathReferences`/template tags.
  - `judgeExports: false` when imports don't name what they use. A language that reaches by NAME declares `declaredNames` (core reaches a file when any reachable file's text mentions one); `configMentions` anchor what the framework instantiates by name; `unitOf` makes a directory one unit; `foldNames` for case-insensitive names.
  - Declarative specs are built by [plugins/shared/reachability-kit.ts](../extractors/plugins/shared/reachability-kit.ts); extension-less `#!` scripts are read through [plugins/shared/shebang-scripts.ts](../extractors/plugins/shared/shebang-scripts.ts). Markup and schema formats are never judged but are read as mention sources; a published library's modules are its API, not dead.
  - Only declare it for a language whose imports NAME files — an import graph cannot prove namespace- or autoload-found files unreachable. Measure precision on a real repo first: every finding is an accusation. `test-fixtures/sample-dead-code` + [dead-code-fixture.test.ts](dead-code-fixture.test.ts) are labelled by hand.
- **Explain a complexity number** — `clarifydoc cfg <file> --function <name>` renders one function's control-flow graph as Mermaid ([control-flow.ts](control-flow.ts)); `--slice <line>` prints the backward slice instead, by reaching definitions and control dependence ([control-flow-slice.ts](control-flow-slice.ts); defs/uses read off node text, so approximate). On demand only: it reads one file and never reaches `project-summary.json`.
  - Node roles come from `meta.controlFlow` ([control-flow-defaults.ts](../extractors/shared/control-flow-defaults.ts), the shared C-family table; `extendControlFlow` adds a plugin's spellings).
  - A language with no grammar gets a second front end, not a second builder: [control-flow-regex.ts](control-flow-regex.ts) reads the text, blanks comments/strings, infers nesting from block delimiters and synthesizes nodes of the SAME canonical types (`FlowNode` in [../types/control-flow.ts](../types/control-flow.ts) is the seam) through `meta.regexControlFlow`, marked `approximate` everywhere it shows. Keyword-delimited languages add `blockDelta` (what a line opens) beside `blockClose`, plus `armBlocks` and `inlineGuard`.
  - The regex tier is gated against the parser: ≥90% of TypeScript and Java functions and ≥85% of C# ones must come out the same shape ([control-flow-regex.test.ts](control-flow-regex.test.ts)). `clarifydoc cfg --capabilities` lists covered languages; the VS Code `$(flame) complexity N` CodeLens falls back to the Complexity report for the rest.
  - Two gates in `control-flow.test.ts`: `cyclomaticFromCfg` must equal `computeComplexity`, and `undrawnStructure` must find nothing.
- **Tell the impact report how to run tests** — a manifest's `testCommand(tests, ctx)` returns the runner's command for test files and the test functions a change reaches; `projectCommands(root)` reads how a project is built, tested and started (`ProjectAnalysis.projectCommands`, shown in `clarifydoc_status` and the `install` guidance block); `TestCommandContext.projectTests` hands a plugin the project's own test commands.
  - A command needing a stated fact reads it from `TestTarget.suites` (`FileAnalysis.testSuites`) or `TestCommandContext.testTargets`. `testSetupRuns(root, files)` names the files a test run executes while setting up, which the test-reach verdict counts as tested (`ProjectAnalysis.testSetupRuns`); a spec suite describing a type the file declares is test-verdict basis `described`. `blockingCalls` names the calls that block inside async code; `docComments` is the comment syntax tools read on demand.
- **Teach a plugin a taint reader** — a regex language states its `TaintSpec` through `meta.regexTaint` (`{ gate, taint }`): a file whose source matches the gate is parsed once more with the one tree-sitter grammar variant the manifest registers (in `dist/grammars`; the `taint` feature switches it off) for the shared `handlerTaint` walk — never a test or generated file or a tree with syntax errors. The walk reads expression values from `valueParts`, guards through one `condition(ifNode)` text hook, and treats a redirect or outbound-URL sink, by its category, as one a fixed host does not reach; `TaintSpec.binds` follows a request body bound into a struct, `stringReads` string captures.
- **Draft architecture rules** — `clarifydoc rules init` ([rules-init.ts](rules-init.ts)) writes `.clarifydoc/config.json` `rules` from the folder dependency matrix (per folder "stays below its dependents", per cycle group "stays out of its cycle"; never an `allowOnly`), shows the diff, and with `--write` merges by rule name and writes the baseline SARIF `analyze --baseline` takes. `clarifydoc install --remove` ([../agents/remove.ts](../agents/remove.ts)) reverses every install writer; `mcp --print-config --pin` prints `npx -y clarifydoc@<version>`.

## Performance rules

- **Profiling:** `CLARIFYDOC_WORKERS=0 node --cpu-prof --cpu-prof-dir=<dir> dist/cli.js analyze …` (workers=0 keeps per-file work in the profile), then aggregate the profile per function. Self-time is too flat to act on — aggregate **inclusive** time per function.
- **Thermal-resistant metric:** wall clock swings up to 3× on laptops. Track the nonParse/parse ratio instead — `(inclusive analyzeFile − inclusive parseSource) / parseSource`; parseSource is fixed WASM work, so the ratio isolates extraction efficiency.
- **Correctness gates for any perf change:** (1) byte-identical per-file JSON on a real corpus (diff ignoring `analyzedAt`); (2) regenerate fixtures and diff `test-output/`; (3) vitest.
- **Worker pool:** the cap of 8 workers is empirically optimal (more measured slower). Each worker's young generation is capped at 16 MB (`CLARIFYDOC_WORKER_YOUNG_MB`, `0` = V8's default, which scales with machine memory): cold-run peak RSS −20 to −27 % on three 4,000–6,500-file repositories, output identical.
- **V8 hidden-class trap:** `Node.type` is cached on instances via a patched prototype getter (parser-manager.ts). Do **not** add more lazily-created cache properties to nodes — it forks hidden classes and makes all node property access megamorphic (measured 3.5× slowdown in route extraction). Cache per-file data in `Map<node.id, value>` memos instead. `id`/`startIndex`/`startPosition`/`tree` are free fields; `endPosition`/`endIndex`/`text`/`childForFieldName` cross into WASM per call.
- **Walk fusion:** full-tree walks dominate non-parse time; fuse N extractor walks into one traversal with per-extractor buckets.
  - Stateful extractors keep per-file state — fused walks must call the base-class `beginFile`/`endFile` hooks around the traversal or state silently goes stale.
  - `extractCalls` does not enter a childless node whose type no step of its walk reads (not a scope, binding site or call type) when the plugin states no per-node hook (`readNames`, `collectExtraCalls`, `destructuredFromCall`, `heldFunction`) and no `skip` is given (`READ_TYPES_BY_LANGUAGE`, [call-graph.ts](../extractors/shared/call-graph.ts)); a hook that only acts on some node types is gated on them before it reads text.
- **Memos per link run:** the linker's per-run caches are the `memos` object of `LinkContext` (`LinkMemos`: `typeFileFor` per (type, file, project), callable members, include closures …), never module-level `WeakMap`s; never spread a context; anything a memo reads from the context must be built before linking starts.
  - A dotted call of an internal name whose last name no file of the run declares (`namesNothingDeclared`, `declaredLeafNames`: every function, method, class, property, event, alias, export, import, mixin rename, returned-member key, constructor name and `constructorCalls` entry, lower-cased; a name with `<` never) is refused after the dispatch-map and record questions and before the receiver is walked — a bare name is not.
  - `namespaceHeadMember` is memoized per (file, written path), a directory's package files per language family (`packageFilesOf`); `familyHoldsMaps` lets a one-key `x.y` call skip the imported-map lookup where no file of the family holds a dispatch map.
- **Flat trees:** `parseSource` of a language in `FLAT_TREE_LANGUAGES` copies the tree once into typed arrays and returns `FlatNode`s ([parsers/flat-tree.ts](../parsers/flat-tree.ts)) — a 4,000-file repository's cold CPU 67.7 s → 43.5 s, output identical. A language joins the set only when its corpus output is byte-identical on the flat copy and the real tree (`--stable-output`); `flat-tree.test.ts` holds every member equal to the real node, quirks included; `descendantForIndex` is not copied (its edge answers differ by grammar), so callers descend through `children`. A file whose real root says `hasError` while the copy does not reads the flag from the real nodes (`readErrorFlags`).
- **Scaling gate:** `cli/scripts/check-scaling.mjs` (CI `verify` job, about 20 s) analyzes generated TS/Python/Go sub-projects at N and 4N single-threaded and fails when (t(4N) − t(1 project)) / (t(N) − t(1)) / 4 exceeds 2.5 — a quadratic pass shows there, fixtures are too small; it prints both runs' stage timings on failure. Never spread a six-figure array into `splice`/`push`/`Math.max` (stack overflow) and never scan a file's whole text per call or per name (cache the answer per file, `httpResourceFile`, `mutatesCollection`).
- **Cheap gates:** substring-gate expensive subtree walks (`sourceText.includes("import(")` before walking for dynamic imports); whole-text regex gate before per-line rule loops, and a whole-text gate asked per call site is computed once per file; a pattern built from a name is built only after a substring test on that name passes; a per-line rule loop over a whole file first tests one alternation of the words every rule names and skips the line otherwise; index a body's identifiers once instead of testing every declared name against every line. A per-argument walk of the enclosing function is one walk per function building a name table, kept per tree in a `WeakMap`; a text blanker scans char codes and copies kept stretches by `slice`, never a per-character array.
